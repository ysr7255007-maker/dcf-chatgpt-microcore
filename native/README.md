# DCF Native

`native/` 是当前 DCF 新原生实现的唯一默认施工根目录。

它不是：

```text
Chrome 扩展的新版本目录
Electron 桌面端的新版本目录
userscript 的迁移目录
旧 engine/ 的重命名
```

它表示：

> **从当前 `docs/spec/` 与正式功能包络出发重新生长的 DCF 实现世界。**

## 施工前提

新功能进入本目录前，必须先有设计层冻结的功能包络，至少明确：

```text
输入契约
输出契约
错误契约
允许 / 禁止状态变化
完整功能需求
质量 / 性能要求
真实依赖关系
最小功能通路验证
完整验收步骤与 PASS / FAIL 条件
```

执行层可以选择内部实现方式，但不得修改这些契约来降低本节点施工难度。

如果合法输入下既定设计无法成立：

```text
DESIGN_BLOCKED
+
可重复失败证据
```

返回设计层。

## 最小功能通路验证

每个功能包络自己的最小通路验证属于该功能本身，不是独立能力节点。

默认使用：

```text
最小合成夹具（Minimal Synthetic Fixture）
或
真实样本切片（Real Sample Slice）
```

因此通路验证默认不需要等待真实上游实现完成；只要设计层已经冻结本功能的输入 / 输出契约，就应该尽早验证最短底层逻辑路径能否产生最小有效输出。

通路验证通过不等于完整功能 `PASSED`。

完整能力成立仍要求：

```text
必要上游真实能力已经成立
+
本功能完整实现完成
+
本包络全部正式验收通过
```

## 旧代码复用

允许从旧实现复制、抽取或直接调用已经证明满足新功能包络的零件。

复用判断方向必须是：

```text
新功能包络
↓
旧代码是否满足
```

禁止反向：

```text
旧代码已经存在
↓
改变新功能定义来迁就它
```

默认历史实现包括但不限于：

```text
chrome-extension/
dcf-chatgpt-microcore.user.js
engine/
packages/desktop-electron/
packages/target-adapter-chrome/
旧控制平面 / Surface / Companion / seed
```

它们不作为 `native/` 的目录结构模板。

## 分支边界

正式功能包络应在独立 branch / worktree 中施工。

推荐命名：

```text
feature/<功能编号>-<简短名称>
```

一个功能分支默认只修改：

```text
native/ 内本功能实现
本功能包络与验收资产
必要的 current-state 状态记录
```

除非既定功能包络明确要求兼容 / 复用旧实现，否则禁止顺手重构历史代码。

## 当前状态

当前目录只是新的施工边界声明。

> **目录存在不代表任何新原生功能已经实现或通过验收。**

第一个正式功能包络开始施工前，仍需先把功能包络元格式和该节点的机器可验证契约定死。
