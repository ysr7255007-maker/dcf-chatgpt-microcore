## A. 任务理解

真正要回答的问题：macOS 已长期维护哪些公共事实 / 索引 / 生命周期 / 动作面，让 DCF 可以少维护一整层自有 watcher、connector、index、daemon 和状态机。

衡量标准不是 API 数量或 demo 成功，而是复杂度吸收率与长期残差最小化。

边界：

> **系统拥有现实，DCF 拥有认知关系。**

Plan 阶段本机勘探已完成，全部只读。任务书关键事实与机器状态一致，无阻塞项，按任务书直接进入执行。

## C. 候选池

### 已知种子

- FSEvents + Spotlight
- NSWorkspace
- InputMethodKit + Unified Logging
- Endpoint Security / eslogger
- launchd + XPC
- App Intents / Shortcuts / Apple Events
- Accessibility
- ScreenCaptureKit / OCR（末端兜底）

### Plan 新发现

**CoreDuet / KnowledgeC**  
可能已经维护前台 App 起止、屏幕亮灭、媒体播放、通知使用等活动历史。与 NSWorkspace 组合后可能吸收大量 session detector，但私有数据库 / schema 厚度是主要风险。

**Spotlight 使用型元数据**  
`kMDItemLastUsedDate`、`kMDItemContentModificationDate`、`kMDItemWhereFroms` 等可作为“什么被用过 / 从哪来”的免费辅助事实。

**eslogger 作为零代码探针**  
优先用 Apple 签名工具验证 Endpoint Security 的公共动作面，再判断正式 DCF 客户端是否值得承担 entitlement 与分发依赖。

## D. 实验计划

### E1 — 用户表达事实面：IMK 成本与覆盖

当前第一道“明文可得”门已经有成功证据。

继续：

- 增量统计 IMK 事件数、可提纯文本字节、Unified Log store 增长；
- 覆盖 TextEdit、Chrome、ChatGPT、VS Code/Qoder、QQ/微信、语音输入；
- 区分 composition / marked text 与最终 commit / insertText；
- 验证 profile 撤销路径；
- 记录 CPU / I/O 与掉线补读。

长窗口采样启动后不阻塞其他 E2～E7。

裁决：

- 日增量可控、常用路径覆盖高、语义纯 → 保留 A 候选；
- 每 1 MB 有价值输入导致数百 MB 额外长期数据或字段极脆 → 降 B/C；
- 一次明文 demo 不构成最终晋级。

### E2 — 文件世界：FSEvents + Spotlight

- 最小 Swift 探针，以持久 event ID 从 Data 卷补读 + 实时流；
- 验证 DCF 停止后重启补读；
- 用 `mdfind` / `NSMetadataQuery` 回答“现在存在什么”；
- 统计与自建 watcher / 普通索引相比可以删除多少状态。

裁决：补读与查询组合成立则保留 A 候选；Spotlight 有语义缺口可以单独降 B，不影响 FSEvents 自身定级。

### E3 — 活动时间骨架：CoreDuet / KnowledgeC + NSWorkspace

- 只读观察 `/app/usage`、`/display/isBacklit` 等分段；
- 与 NSWorkspace 实时前台通知对比；
- 测最旧记录、保留窗口、轮询成本、休眠 / 唤醒；
- **额外必须测：数据库位置、schema、字段与 macOS build 的耦合程度。**

裁决：功能成立但私有 schema 厚则降 B/C；不能只因为数据丰富就授予 A。

### E4 — Agent 行动收据：Endpoint Security / eslogger

- 短窗口同时运行 shell、Agent、普通进程；
- 用 eslogger 观察 exec / create / rename / open / mmap / exit 等；
- 测 pid / ppid / path / 签名等身份字段；
- 判断 Resource / ReadSet / WriteSet / EffectKind 能抽取到什么程度；
- 记录事件速率、CPU、JSON 稳定性。

形成两个独立裁决：

```text
ES 系统现实面能力
→ A/B/C

DCF 长期 ES 接入路径
→ A/B/C/unverified
```

不得用 eslogger 的 Apple entitlement 替 DCF 自建客户端证明 entitlement 可得。

### E5 — 生命周期：launchd + XPC

建立最小 LaunchAgent / XPC 探针验证：

- 按需唤醒；
- 崩溃拉起；
- 空闲退出；
- IPC；
- 状态所有权切分。

目标：

```text
launchd → 进程存在
XPC → 通信
DCF 持久层 → Job / Result / Receipt
Becsy → 当前语义活动
```

不得出现双重权威。

### E6 — 跨 App 行动面

轻量验证：

- `shortcuts list/run`；
- AppleScript / scripting 对少量代表性 App；
- `sdef` 等能力发现；
- 参数结构、稳定身份、错误表达。

不做全 App 普查。

### E7 — Unified Log 矿藏普查

低强度统计默认脱敏状态下的：

```text
subsystem
category
process
事件频率
<private> 比例
```

只产生少量高价值 subsystem 候选，不全量同步、不为“发现更多日志”扩大范围。

## E. 裁决规则

候选晋级 A 至少要求：

```text
runtime_verified
+
能够吸收多个 DCF 岗位或一个关键高残差岗位
+
长期成本可控
+
恢复语义明确
+
组合后不制造更厚的状态同步
```

`吸收 ≥2 个岗位` 是强加分项而不是机械门槛：如果某能力只解决一个岗位，但它从源头消除一个高复杂度、不可替代边界，也允许成为 A。

成本近似随开机时间高速增长、依赖版本私有细节过厚、失败不能诚实退化或只是把 connector 换成 hook 的候选必须降级。
