# ADR — 可编辑叙事与 Surface Runtime 边界收口

日期：2026-08-09  
状态：Accepted，具体 Surface 技术选型待各 Capability 设计时验证

本文记录在 `2026-08-08-game-derived-cognitive-interaction.md` 之后，DCF 对“游戏级认知交互”继续深入讨论后形成的第二次收口。

上一条 ADR 仍然成立：DCF 应从游戏工业学习高带宽认知交互，并保留剧本替换测试。

本 ADR 不否定它，而是解决继续推演后暴露出来的边界问题：

```text
哪些东西真的需要做成游戏？
真实材料与推理游戏的差异是什么？
用户到底在修改什么？
SillyTavern 能否先作为现成交互实验场？
Godot 的价值是否只存在于“以后做完整游戏”？
```

---

# 1. 背景：进一步推演暴露了几个错误方向

讨论过程中先后否定了以下方向：

```text
把长期价值直接当成当下乐趣
把纠正 AI 错误当成核心玩法
假定现实天然存在足够强的谜题与悬疑
把现实问题简单改名为 Boss / 武器 / 奖励
把关系图、证据板直接当成游戏本身
假定系统一开始就知道现实真正的问题和结构
为了保持游戏潜力而要求所有 Capability 优先游戏化
```

这些方向的共同问题是：

> **把 DCF 真正需要完成的认知工作，与玩家愿意玩的主观目标混在了一起。**

游戏级交互仍然有价值，但不能因此给所有功能增加不必要的游戏设计负担。

---

# 2. 决策一：剧本替换测试保留，但不要求日常材料天然好玩

剧本替换测试继续是全景沉浸交互的产品上限判据。

它回答的是：

> **如果内容足够优秀，DCF 的交互层有没有能力承载它？**

它不回答：

> **普通日常生活本身能否自动成为一个好游戏？**

因此当前不再为难系统提前解决“把所有日常生活讲得有趣”这一未成熟问题。

讲述质量以后可以由不同叙事编译器、模型、Renderer 或交互实现继续优化。

---

# 3. 决策二：真实事实是 Canon，玩家拥有解释权

DCF 的真实数据类似剧情中的不可修改节点：

> **到了那个时间，那个事情确实发生过。**

这些事实不能因为当前叙事需要而被改写。

真正开放的是：

```text
这些事实为什么重要
彼此是什么关系
谁是这一段的主角
什么是导火索 / 转折 / 背景
某次失败后来应该如何理解
几件事究竟属于一条故事还是多条故事
```

因此形成正式模型：

```text
Reality Canon
→ 硬，不可篡改

Interpretation / Narrative
→ 软，可追加、可修改当前版本、可形成分支
```

用户可以在任何时刻修改当前故事，而不是等待系统预先设置的“选择点”。

修改产生新的叙事世界线；旧解释继续保留为当时的认知历史。

---

# 4. 决策三：前台是故事，图结构退回后台

《The Roottrees Are Dead》证明了：

> 固定事实 + 玩家认知参与可以形成优秀交互。

但它的核心玩法建立在“关系尚未知、玩家负责重建”之上。

DCF 大量现实关系已经可以从真实数据中得到；真正没有唯一答案的是意义与故事结构。

因此不复制 Roottrees 的核心玩法。

正式原则：

> **后台可以是图，前台应该是戏。**

关系图、时间线、证据板可以作为辅助认知工具，但不得因为底层数据结构存在，就把用户主要工作退化成知识图谱维护。

---

# 5. 决策四：SillyTavern 作为近期活体原型候选

SillyTavern 已经提供：

```text
Edit
Swipe
Regenerate
Continue
Branch
Checkpoint
Persona
Scenario / Author's Note
World Info / Lorebook
Extensions
```

它证明一种用户体验已经成立：

> **用户可以消费 AI 叙事，同时不断编辑、分支和重生成，而不必把自己理解成在维护数据库。**

DCF 与它的关键差别是：

```text
SillyTavern 可以改虚构世界事实
DCF 不允许改 Reality Canon
DCF 只允许改变事实之上的当前解释与叙事
```

因此当前允许优先在 SillyTavern 上验证交互语法，甚至研究直接嵌入 / 扩展桥接，而不急着重新实现完整叙事 UI。

是否最终保留 SillyTavern、部分移植或完全重做，留给真实使用决定。

---

# 6. 决策五：Godot 的价值不依赖“必须做成游戏”

继续研究 Godot 后发现，它即使只作为软件前端，也有独立结构性价值：

```text
位置关系是显式场景结构
UI、2D、3D、动画和自定义绘制处于统一 Runtime
适合空间界面和连续状态变化
编辑器可以直接观察和修改场景
独立 Scene 可以单独运行验证
无需每次正式部署整个应用
适合“描述 → AI 修改 → 视觉验收 → 再修改”的高频循环
开源，AI 可以从 GDScript 下钻到插件、GDExtension 甚至引擎源码
```

因此当前对 Godot 的定义从：

> “以后做完整游戏时可能用到的引擎”

修正为：

> **高表现力实时 Surface Runtime 的强候选，同时保留未来继续升级成完整游戏级表现的潜力。**

但本 ADR 仍然不决定正式采用 Godot。

---

# 7. 决策六：Godot / Web / SillyTavern 都必须服从同一个业务边界

DCF 现有 Replaceable UI 与 Surface Contract 架构不需要因为 Godot 而改变。

正式边界继续是：

```text
DCF Core
Capability / State / Action / Workflow / Evidence
        ↓
Surface Contract
        ↓
Replaceable Surface Runtime
Web / Godot / SillyTavern / 其他
```

Surface 可以负责：

```text
视觉
空间
动画
焦点
镜头
临时选择
拖拽
局部交互状态
```

DCF Core 继续负责：

```text
真实事实
长期状态
证据
当前与历史解释
Workflow
AI 结果来源
用户确认形成的业务状态
```

因此：

> **Surface 可以决定世界如何被看见，不能决定世界实际上是什么。**

具体通信方式当前不冻结。

---

# 8. 决策七：停止继续泛化游戏设计，进入 Capability 逐项定稿阶段

经过本轮讨论，跨 Capability 的交互方向已经足够清楚。

继续泛化“DCF 应该像什么游戏”已经开始产生边际收益递减。

下一阶段改为：

```text
Capability Registry v1 的 15 项能力
↓
逐项明确真实用户目的
逐项明确输入 / 输出 / 状态 / Action
逐项明确与其他 Capability 的边界
逐项明确哪些过程需要 Workflow
逐项明确需要什么 Surface / 交互带宽
逐项明确证据与验收
↓
15 项能力完成定稿
↓
再编写整体 DCF 项目设计书
```

`现实闭环行动` 继续保持 `DISCOVERY_DEFERRED`，不因为进入设计书阶段而解冻。

---

# 9. 结果

本次收口没有增加 Capability，也没有改变当前 Go + DBOS + PostgreSQL + Replaceable UI 架构。

它完成的是三层边界的硬化：

```text
事实层
→ Reality Canon 不可篡改

认知层
→ 当前解释可以变化，历史解释追加保留

表现层
→ Web / SillyTavern / Godot 等都只是可替换 Surface
```

同时明确下一阶段不再继续无边界扩展交互研究，而是回到 Capability Registry v1，逐项把功能敲定，然后再形成整体项目设计书。
