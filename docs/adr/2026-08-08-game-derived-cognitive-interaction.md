# ADR — 沉浸式交互转向游戏工业认知交互谱系

日期：2026-08-08  
状态：Accepted，实施验证待完成

本文记录 DCF 为什么不再把“专业软件 UI”作为全景沉浸交互的默认参照，并引入游戏工业作为主要交互技术来源。

当前专项要求见：

`docs/spec/2026-08-08-DCF-沉浸式认知交互与游戏设计谱系规范.md`

---

# 1. 背景

DCF 已经形成三种交互 Capability：

```text
全景沉浸交互
嵌入式交互
环境微交互
```

此前设计曾进一步冻结叙事日历、三列布局、论坛回复式后续认知等具体 UI 形态。

随后整体架构已经明确：

> **Function Hard, UI Soft。**

即 Capability、业务状态、Action、Workflow 与 Surface Contract 稳定；Shell、Panel、Layout、Canvas、DOM、视觉和具体交互方式允许整体推翻。

最近继续讨论全景沉浸交互时，发现问题不只是“具体 UI 不应该冻结”，而是此前默认参考系本身过窄。

传统专业软件通常把大量内部结构直接暴露给用户，并默认用户负责学习系统；而优秀剧情、文字、推理游戏长期处在相反压力下：

> 玩家不欠系统学习成本。设计者必须主动让复杂人物、事件、关系、规则和意义以人能承受的方式进入理解，否则玩家会直接离开。

这与 DCF 的长期价值目标高度一致：

> **系统内部复杂性不应转嫁给用户。**

---

# 2. 新观察：游戏不是视觉参考，而是交互技术谱系

剧情、文字和推理游戏长期解决的问题包括：

```text
复杂信息如何渐进出现
大量人物和关系如何被记住
怎样把工作记忆外置而不替玩家推理
怎样突出真正值得注意的矛盾
怎样让玩家表达自己的推断
怎样在不读说明书的情况下理解规则
怎样用反馈帮助建立正确心智模型
怎样让状态变化直接可感知
```

这些问题与 DCF 的个人叙事、项目叙事、证据、关系、Researcher、ADR 和长期认知变化高度重合。

因此游戏工业对 DCF 的价值，不是“让 DCF 更像游戏”，而是提供一套已经经过大量真实用户验证的高带宽认知交互方法。

---

# 3. 决策一：全景沉浸交互优先从游戏工业学习

DCF 不再默认从传统知识管理、Dashboard、后台管理和专业工具 UI 中寻找全景沉浸交互的上限。

新的参考优先级为：

```text
成熟成品游戏真实体验
↓
GDC / Postmortem / 设计师复盘与经典案例教程
↓
游戏设计、叙事设计、认知设计、无障碍等理论
```

成品游戏优先于理论，因为真正需要验证的是：

> 用户面对复杂度上升以后，是否仍然愿意理解、操作并持续使用。

参考重点是交互语法，不是美术模仿。

---

# 4. 决策二：建立“剧本替换测试”

形成新的产品方向判据：

> **如果把 DCF 底层采集到的真实生活材料替换成优秀剧情 / 推理游戏作者精心设计的剧本数据，那么 DCF 上层应具备把它呈现为一款真正成立的好游戏的能力。**

该判据用于区分：

```text
真正的认知交互系统
vs
把复杂数据放进漂亮 Dashboard 的专业软件
```

如果剧本原料已经具有完整的人物、事件、证据、冲突、转折与关系结构，而系统最终仍只能呈现为 Wiki、搜索框、静态关系图和 AI 摘要，则说明交互层仍未承担“帮助用户理解”的责任。

剧本替换测试是方向性产品验收，不是自动化 benchmark。

---

# 5. 决策三：DCF 相比游戏多承担“现实叙事编译”

游戏的剧情结构由编剧主动设计；用户日常生活没有编剧。

真实材料包含大量：

```text
普通事件
重复
噪声
长期未完成事件
当时无关、后来才显现意义的旧材料
需要数周或数月才能看出的关系变化
```

因此 DCF 必须从真实材料中恢复当前值得注意的：

```text
人物 / 项目
事件
关系
问题
矛盾
判断
转折
未解决线索
```

这一过程可以理解为 Narrative Compiler（叙事编译）。

但它不是故事创作器。

正式边界：

> **可以重新组织意义，不能伪造事实。**

> **可以追加新的解释，不能静默覆写旧解释。**

> **重要投影必须能够穿透回原始材料、证据层级和形成时间。**

---

# 6. 决策四：交互规范从“控件清单”改为“认知动作 + 成熟模式”

后续不再优先写：

```text
左侧栏是什么
右侧 Panel 是什么
页面有几个 Card
某个字段如何编辑
```

而是先描述：

```text
用户现在在理解什么
什么信息当前最重要
哪些信息应该暂时隐藏
用户要执行什么认知动作
系统必须保留哪部分用户判断权
成熟游戏如何解决同类问题
```

再决定具体 Surface。

后续逐步形成 DCF Interaction Pattern Library（DCF 交互模式库），按认知问题组织，而不是按 UI 组件组织。

---

# 7. 对 Godot / 游戏引擎的处理

游戏引擎因此进入全景沉浸交互的 P0 候选研究范围。

Godot 当前具有明显研究价值，因为它提供：

```text
持续交互世界
Scene / Node
事件与信号
脚本
2D / 3D
动画
输入
可编程 UI
命令行 / headless 闭环
开放源码与扩展能力
```

但本 ADR **没有决定**：

```text
DCF 使用 Godot
DCF 所有 UI 使用游戏引擎
Godot SceneTree 成为 DCF 业务事实源
```

游戏引擎只能是 Replaceable UI / Surface Runtime 的候选。

事实与认知权威仍属于 DCF 业务层。

---

# 8. 对旧叙事 UI 冻结的处理

`docs/spec/2026-08-05-DCF-叙事日历与三Surface交互规范.md` 中关于以下产品语义继续有效：

```text
草稿可编辑
正式叙事形成后不可静默覆写
后续理解只能追加
来源需要可穿透
```

但其中曾冻结的具体表现：

```text
三列布局
固定日历视觉
固定论坛回复式结构
固定侧边栏 / 悬浮球表现
```

不再是当前 UI 权威。

它们保留为当时的设计候选和历史记录。

---

# 9. 结果

本次变化没有新增 Capability，也没有改变三种交互 Capability 的身份。

它改变的是全景沉浸交互的设计上限与方法：

```text
过去：
专业认知软件
→ 尽量易用

现在：
游戏级认知交互
→ 系统主动承担帮助用户理解复杂世界的责任
```

最终目标不是“DCF 像游戏”。

而是：

> **如果游戏已经证明一种复杂认知可以被人自然理解和操作，DCF 不应退回到要求用户学习内部结构的专业软件范式。**
