# ADR：Capability Discovery 收口、产品主权与三条复杂度切线

日期：2026-08-07  
状态：**Accepted**

---

# 1. 背景

DCF 在 2026-08-07 之前已经完成两组关键架构验证：

```text
Capability × Bun+Becsy World 组合实验
公共设施消歧实验 E0–E5
```

这些实验已经证明：

```text
Capability 可以在 Standalone World 独立证明
多个 Capability 可以进入同一个 Composite World
Shared Semantic Component 可以替代大量私有调用接缝
Becsy 可以根据组件访问关系形成执行先后
外部异步执行可以统一进入 ExternalOperation 生命周期
AI / Agent / Cognition Data / Evidence Intake 可以形成薄公共设施
```

但继续 Capability Discovery 时出现了一个新问题：

旧判断方式容易把“独立能力”错误理解为：

> **剥掉公共设施、配方、界面以后，还剩多少独占实现。**

这会错误否定 Wiki、知识卡、语言弹药、个人叙事、项目叙事和工作台这类由公共基础能力组合后形成的稳定产品。

同时，沿 ECS、Becsy World 与 Bun 三个结构性切面重新观察 DCF 后，发现大量过去看起来像“功能模块”的东西其实是：

```text
关系接缝
运行接缝
宿主工程接缝
```

因此需要同时修正：

```text
Capability 身份标准
Capability Discovery 门禁
界面能力定义
下一阶段施工入口
```

---

# 2. 决策一：Capability 按产品主权判断

接受：

> **Capability 身份由产品主权决定，不由独占代码量、独占算法量或实现厚度决定。**

产品主权要求候选能够独立回答：

```text
服务什么稳定用户目的？
管理什么对象 / 状态 / 交互关系？
用户执行什么独特行为？
什么叫产品成功？
```

“去 DCF 测试”继续保留，但重新解释为：

> **抹掉 DCF 品牌后，这个用户目的是否仍然是一项可以命名、使用和验收的软件能力？**

而不是：

> “去掉所有公共设施以后还能不能自己实现全部机制。”

---

# 3. 决策二：原生能力与涌现能力地位相同

接受两种 Capability 形成方式：

```text
原生能力
→ 直接对应一个独立问题闭环

涌现能力
→ 多个基础构件组合后形成新的稳定用户目的、交互节奏与产品身份
```

两者在运行时和 Registry 中地位相同。

“原生 / 涌现”只解释形成原因，不表示成熟度、优先级或等级。

由此明确：

> **公共设施 + 配方 + 查询策略 + 专门交互可以涌现出真正 Capability。**

---

# 4. 决策三：采用三条架构切线解释复杂度吸收

## 4.1 ECS 切线

ECS（实体组件系统）主要吸收：

```text
生产者 → 消费者路由
订阅 / 回调
一对多 / 多对一分发
状态交接
UI 贡献发现
权限 / 审核结果交接
诊断共享
恢复需求发现
```

正式方向：

> **上游不指定消费者；下游不指定生产者；双方围绕共同理解的世界状态和产物语义发生关系。**

ECS 不取代专业机制。

---

## 4.2 World 切线

Becsy World（运行世界）主要吸收：

```text
系统生命周期
系统启停
运行身份
大量执行先后关系
坏组合启动前拒绝
活动 Provider 解析后的统一运行权威
外部操作的 World 内生命周期身份
```

接受：

> **DCF 是一个 World；Capability 是共同参与并推进这个 World 的系统，而不是很多孤立软件先各自运行再人工协调。**

World 不替代长期权威数据库与历史存储。

---

## 4.3 Bun 切线

Bun 主要吸收宿主层通用工程复杂度。

采用 Bun-first Host（Bun 优先宿主）原则：

> **Bun 已经稳定原生提供的宿主能力，默认先直接使用；只有出现明确不足证据才新增替代层。**

优先覆盖：

```text
子进程
HTTP
WebSocket
IPC / PTY
SQLite 驱动
测试
构建
单文件部署
常规文件 / 定时机制
```

Bun 不获得业务语义与世界定义权。

---

# 5. 决策四：四刀法用于净化，而不是消灭 Capability

四刀：

```text
ECS
World
Bun
Public Facility
```

它们回答的是：

> **哪些责任不应该由这个 Capability 自己承担？**

而不是：

> “砍完以后还有没有足够多独有代码？”

因此允许非常薄的 Capability：

```text
独特用户目的
+ 产品状态
+ 语义声明
+ 少量业务规则
+ 专门交互
```

---

# 6. 决策五：两条新的独立性证据

## 6.1 跨 Capability 保持同一身份

若一种业务对象可以由多个 Capability 产生 / 消费 / 引用，并且跨这些场景后仍保持同一产品身份，则这是强独立性证据。

因此 Wiki 与知识卡不因为可以成为个人叙事、项目叙事、AI 任务执行等能力的附属产物而降级；恰恰因为它们跨多个来源仍保持自身身份，更倾向独立存在。

## 6.2 产品重力

高频、稳定、独特的使用方式可以形成产品重力。

语言弹药虽然大量复用认知数据、查询与界面基础设施，但其：

```text
高频收录
高频寻找
高频调用
高频复制 / 插入
最近使用
收藏 / 分类
```

形成稳定用户中心，因此承认独立 Capability 身份。

---

# 7. 决策六：三种界面形态升级为三种交互能力

废止把 Capability 名称绑定为：

```text
能力主页
上下文侧边栏
环境悬浮球
```

这些名称降级为当前 Surface（界面载体）。

接受三种稳定交互生态位：

```text
全景沉浸交互
嵌入式交互
环境微交互
```

其中：

### 全景沉浸交互

主动发现、收集、归纳 DCF 整体 Capability / 状态 / 产物 / 操作，形成统一“能力交互投影”，并提供最高信息与操作带宽的完整交互空间。

### 嵌入式交互

把 DCF 的部分信息和操作嵌入其他宿主工作空间，与原工作并存。

“上下文相关”只是一种筛选策略，不是能力定义。

### 环境微交互

在不占据工作空间的情况下，用极低信息量与极短操作路径长期存在于环境中。

三者的区别来自交互空间与注意力带宽，而不是某个固定 UI 控件。

# 8. 决策七：Capability Registry v1 收口

接受 15 项进入 Capability Registry v1：

```text
证据源采集管理
多源证据编译
AI 协作审阅编辑器
个人叙事
项目叙事
Wiki
知识卡
语言弹药
AI 工作台
认知数据工作台
AI 任务执行台
约束决策助手
全景沉浸交互
嵌入式交互
环境微交互
```

这些能力的产品身份正式承认，但不等于 Envelope 已关闭。

---

# 9. 决策八：现实闭环行动暂缓

“现实闭环行动”保留为问题方向，但不进入当前 Registry 定型队列。

原因：它同时触及执行、权限、风险、副作用、现实观察、验收、因果、补偿、部分成功与人工介入等大量尚未充分讨论的问题。

当前只保留 E5 已验证不变量：

> **Agent 执行状态 ≠ 现实效果。Agent 负责劳动；现实负责验收。**

状态：

```text
DISCOVERY_DEFERRED
```

未来只有出现足够真实需求与行为证据时重新打开。

---

# 10. 决策九：开放式 Capability Discovery 关闭

本轮 Discovery 不再继续以“还能想到什么能力”为任务。

未来新增 Capability 必须由新的真实产品目的触发，并重新通过产品主权门禁与四刀净化。

下一阶段转为：

```text
Capability Registry v1
↓
Capability Envelope
↓
Standalone World
↓
Composite World
↓
实现与行为验收
```

Capability DAG 继续只作为从真实声明派生的视图。

---

# 11. 后果

正面后果：

```text
允许底层机制极度复用而上层产品持续增长
减少为了“独立”而复制数据库 / AI / Agent / 路由 / 生命周期
避免把 UI 控件名称写死为产品能力
让跨产品业务对象获得自然独立位置
让高频交互产品得到正式架构身份
减少开放式架构讨论持续拖延施工
```

风险：

```text
“涌现能力”概念可能被滥用，导致所有界面 / 配方都升级成 Capability
“能力交互投影”可能膨胀成新的中央业务大对象
ECS / World 可能被误用成数据库或全能工作流引擎
Bun-first 可能被误解成禁止使用成熟第三方轮子
```

控制方式：

```text
始终要求产品主权四问与独立验收
新增能力必须有稳定用户目的，不以代码包装命名
共享语义只表达真实共同世界状态
World 不拥有长期权威历史
Bun 只吸收宿主工程，不定义业务世界
公共设施只吸收重复专业机制，不拥有上层产品意义
```

---

# 12. 被替代的判断

以下旧判断不再拥有当前权威：

```text
“底层主要由公共设施 + 配方 + 界面组成，所以不算 Capability”
“主页 / 侧边栏 / 悬浮球就是三个 Capability 名称”
“嵌入式交互必须与当前上下文相关”
“Capability Discovery 继续开放寻找更多候选”
“现实闭环行动现在就应关闭完整边界并进入施工”
```

它们作为历史推演保留，但当前实施以本 ADR 与对应 Registry v1 规范为准。
