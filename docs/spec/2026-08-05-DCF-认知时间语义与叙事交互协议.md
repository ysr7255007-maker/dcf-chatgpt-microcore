# DCF 认知时间语义与叙事交互协议

日期：2026-08-05  
状态：**正式子规范 v1；当前实施依据**

关联文档：

- `docs/spec/2026-08-05-DCF-总设计说明书.md`
- `docs/spec/2026-08-04-DCF-当前实施规范.md`
- `docs/spec/2026-08-05-DCF-P0-功能舱-窄腰-不可变代际协议.md`

本文负责冻结 DCF 中“人如何阅读叙事、校准叙事、沿来源回看历史、形成新的理解，以及这些理解怎样进入当天叙事与派生知识”的时间语义与产品交互模型。

若本文与旧文档中“修改过去叙事”“延迟复盘”“当天只做快速审核”“新增理解形成新版本”等表述冲突，以本文为准。

---

# 1. 总裁决

## 1.1 认知只发生在当前时点【已冻结】

DCF 中，用户所有：

```text
认同
不满意
否认
修正
补充
改写
评论
新增理解
证据质疑
重要性判断
```

本质上都是：

> **当前时间点新产生的一条认知材料。**

它可以指向过去的任意对象，但不能修改过去本身。

正式原则：

> **认知永远记录在它产生的时间点；它可以引用任意过去，但永远不回写过去。**

因此：

```text
2026-05-18
用户看到 2026-01-14 的个人叙事
↓
写下“这里更准确的理解应该是……”
```

DCF 记录的是：

```text
形成时间 = 2026-05-18
指向对象 = 2026-01-14 的叙事节点
内容 = “这里更准确的理解应该是……”
```

而不是修改 1 月 14 日的历史内容。

---

## 1.2 “校准”和“新增理解”底层同义【已冻结】

从用户界面看，可以存在不同操作方式：

```text
👍 认同
👎 不满意
✕ 明确否认
直接修正文字
补充一段背景
新增一条理解
评论
请求重新生成
```

这些 UI 动作有不同交互用途，但底层不应被建模成多套互相竞争的“历史修改系统”。

它们统一产生**当前认知事件**。

最小语义可以表示为：

```text
当前认知事件
├─ cognition_id
├─ formed_at
├─ author
├─ content / signal
├─ refers_to[]
├─ source_context[]
├─ interaction_kind
└─ causal_context（若存在显式操作链）
```

其中：

```text
formed_at
→ 这份理解现在何时形成

refers_to
→ 它在谈什么历史对象 / 知识对象 / 项目对象

interaction_kind
→ 用户通过何种交互表达它，例如 👎、修正、补充、自由文本
```

`interaction_kind` 仅保留交互语境，不赋予“修改旧对象”的语义。

---

## 1.3 理解改变本身就是叙事【已冻结】

同一个历史节点可以在不同时间得到不同理解：

```text
2026-01-14 · 当时的理解
“……”

2026-05-18 · 后来形成的理解
“……”

2026-08-05 · 又一次形成的新理解
“……”
```

三者都是真实发生过的认知。

后来的理解不能自动：

```text
覆盖旧理解
隐藏旧理解
把旧理解降级为不存在
把旧理解改写成后来版本
```

因此：

> **DCF 不维护“当前唯一正确理解”；DCF 保存理解怎样产生、变化、被重新解释和继续生长。**

理解的变化本身就是 DCF 要保存的叙事内容。

# 2. 双时间关系：发生时间与指向关系

## 2.1 两个概念必须分开【已冻结】

DCF 至少必须区分：

```text
认知形成时间
≠
认知指向的历史对象时间
```

例如：

```text
认知事件 C-0518
formed_at = 2026-05-18 21:32
refers_to = 2026-01-14 的个人叙事节点 N-0114
content = “现在回头看，这里更像是后来某条路线的早期萌芽。”
```

C-0518 属于 5 月 18 日发生的认知活动。

它只是在内容关系上指向 1 月 14 日。

## 2.2 历史节点显示后来理解只是关系投影【已冻结】

打开 1 月 14 日历史节点时，可以显示：

```text
2026-01-14 · 当时的叙事
……

后续相关理解
├─ 2026-05-18 ……
└─ 2026-08-05 ……
```

这只是把后来形成、且 `refers_to` 当前节点的认知事件投影在旁边。

禁止把这些后来认知重新写进 1 月记录，或改变 1 月记录的形成时间和原始身份。

# 3. 当天叙事编制：消费“今天形成的认知”

## 3.1 当前认知进入当前日期材料池【已冻结】

无论用户今天评论的是：

```text
今天的 AI 关系叙事
昨天的项目叙事
三个月前的个人叙事
一年前的知识来源
旧 Git commit
旧知识卡
```

只要这条理解今天形成，它就属于今天的认知材料。

当天项目 / 个人叙事编制应看到：

```text
今天发生的现实
+
今天形成的 AI 交互
+
今天发生的工程变化
+
今天形成的用户认知事件
```

其中用户认知事件可以引用任意过去。

## 3.2 示例【已冻结】

```text
2026-05-18
↓
用户发现一张知识卡不准确
↓
沿来源回到 2026-01-14 的个人叙事
↓
新增一条理解：
“这里并不是一直如此，而是后来经过某件事才发生转变。”
```

这条理解应进入：

```text
2026-05-18 当天材料池
```

因此当天项目叙事可以描述：

> 今天在检查某个知识结论时，用户回溯到一月份的一段个人叙事，并重新形成了对当时变化过程的理解。

禁止把这条五月理解回写成：

> 一月份当时已经知道后来才形成的结论。

# 4. 派生知识重新生成：显式因果优先于时间猜测

## 4.1 典型链路【已冻结】

```text
用户看到知识卡 K17
↓
觉得不对
↓
查看来源
↓
沿 provenance 向下穿透
↓
找到旧个人 / 项目 / 关系叙事节点 N12
↓
写下当前认知 C91
↓
返回知识卡
↓
点击“重新生成”
```

重新生成时，不允许先修改 N12 再生成 K17。

应直接使用：

```text
旧来源材料
+
历史上已有相关理解
+
刚产生的当前认知 C91
+
其他当前相关材料
↓
重新生成知识卡
```

## 4.2 相关性优先级【已冻结】

当重新生成动作与刚产生的新认知存在明确操作链时，应优先使用**显式因果上下文**，而不是仅依赖“时间很近所以大概相关”。

例如重新生成请求可以携带：

```text
originating_artifact = K17
newly_created_cognition = C91
traversed_provenance = [...]
```

于是：

```text
显式因果相关认知
>
当前时间窗口内的相关认知
>
普通历史相关材料
```

时间接近仍然可以作为相关性信号，但不是唯一依据。

## 4.3 当前表示允许重算，历史认知不被重算【已冻结】

知识卡、摘要、当前项目视图等派生物可以重新生成。

但其上游历史认知节点不可因为重新生成而被修改。

因此：

> **投影可以重算；形成过的认知不可被重算成从未发生。**

# 5. UI 总体形态

## 5.1 主界面：完整阅读、理解与编辑工作台【已冻结】

叙事审核 / 阅读不是“当天快速审批”功能。

用户审核深度取决于：

```text
用户当前状态
AI 叙事质量
问题复杂度
是否需要查看证据
是否需要补充大量背景
```

而不取决于这条叙事是不是今天产生。

因此叙事阅读、修正、补充、新增理解必须是**完整形态主界面的一等工作模式**。

主界面至少支持：

```text
连续阅读叙事
快速 👍 / 👎 / ✕
直接编辑 / 修正表达
新增独立理解
补充背景
查看来源 / 证据
沿来源继续穿透
重新生成派生结果
查看同一节点后来形成的其他理解
```

用户可以在同一篇叙事里：

```text
一部分只快速点击
一部分仔细阅读
一部分直接改写
一部分补充长文本
```

系统不得人为拆成“快速模式”和“深度模式”两套业务语义。

---

## 5.2 “新增理解 / 修正”的视觉原则【已冻结】

新增理解、修正、补充都不得覆盖旧理解。

UI 至少可以使用两种合法形式：

### 形式 A：正文向下生长

```text
原叙事……

2026-05-18 · 我的理解
这里更准确的理解是……

2026-08-05 · 我的理解
后来我发现……

＋ 添加现在的理解
```

### 形式 B：独立后续理解栏

```text
原叙事正文                后续理解
                          2026-05-18 ……
                          2026-08-05 ……
                          ＋ 添加理解
```

两种形式语义完全相同：

```text
旧节点保持原样
+
新认知另起一条记录
```

不得设计成：

```text
旧版本 → 新版本
旧理解被折叠为“历史版本”而默认消失
修正后只显示最新内容
```

# 6. 侧边栏：快速显现、调用与溯源入口

## 6.1 侧边栏职责【已冻结】

侧边栏不是叙事完整审核工作台。

它主要承担：

```text
快速阅读当前高频对象
快速调用功能
快速查看来源
沿来源关系穿透
在上下文足够时直接新增一条当前理解
必要时跳转完整主界面
```

因此侧边栏和主界面的区别是**承载容量与注意力预算**，不是“允许什么认知动作”的业务分裂。

同一个“新增当前理解”动作可以在两处存在。

## 6.2 历史回看的自然入口【已冻结】

DCF 不把历史回看默认设计成：

```text
用户主动选择某年某月
↓
专门浏览一批历史
```

更自然的入口是现实工作中的**来源穿透**。

典型路径：

```text
侧边栏出现知识卡 / 项目摘要 / 当前判断
↓
用户觉得有问题或想知道来源
↓
点击来源
↓
项目叙事
↓
关系叙事
↓
个人叙事 / 原始交互 / 工程事实
↓
在某个历史节点产生当前理解
```

因此：

> **历史不是一个独立档案馆模式；任何当前认知对象都应能够沿 provenance 向过去穿透。**

## 6.3 侧边栏局部完成与主界面展开【已冻结】

如果用户只需要补一句：

```text
“这里我现在有一个新的理解……”
```

侧边栏可以直接完成并形成当前认知事件。

如果需要：

```text
查看完整上下文
比较多份证据
大段编辑
重新组织叙事
查看完整历史关系
```

则进入完整形态，并继续使用同一功能身份和同一动作语义。

# 7. 功能划分

## 7.1 不拆“当天校准”和“延迟复盘”两个功能【已冻结】

以下拆法禁止：

```text
当天叙事校准
vs
延迟叙事复盘
```

原因：

- 审核深浅不由时间远近决定；
- 对旧历史的修正 / 新理解本质仍是当前认知；
- 用户回看历史通常由当前对象和来源链触发，而不是定时浏览旧月份；
- 两者最终都进入当前日期认知材料池。

## 7.2 核心功能块建议【已冻结业务边界，名称可调整】

当前业务上应存在一个统一的：

> **叙事阅读与认知追加功能块**

其职责包括：

```text
读取任意当前 / 历史叙事节点
展示原有内容
展示相关来源
展示后来形成的相关理解
产生新的当前认知事件
沿 provenance 穿透
把显式因果上下文交给派生物重新生成
```

它不拥有：

```text
原始来源事实
Git/GitHub 工程真相
旧叙事的可变“最新版”
知识卡长期生成算法
项目叙事生成算法
```

它只负责让用户面对已有认知对象继续产生当前认知。

# 8. 与知识卡 / 项目叙事 / 个人叙事的关系

## 8.1 知识卡【已冻结】

知识卡是可重算派生物。

用户从知识卡溯源后产生的新认知，不修改知识卡来源历史。

重新生成知识卡时，新的当前认知可以因为显式因果关系获得高优先级。

## 8.2 项目叙事【已冻结】

当天用户对旧项目 / 个人 / 关系叙事形成的新理解，应作为当天材料进入当天项目叙事编制。

它指向过去，但属于今天。

## 8.3 个人叙事【已冻结】

同理，今天形成的对旧个人历史的新理解可以进入今天的个人叙事。

个人叙事不通过回写旧日期来“修正历史”，而是保留：

```text
当时怎样理解
后来怎样理解
理解如何继续变化
```

# 9. 数据与行为验收

## 9.1 必须通过的行为验收

### 验收 A：旧内容不被覆盖

```text
1 月存在节点 N1
5 月用户针对 N1 新增理解 C5
8 月再次新增理解 C8
```

必须能够同时看到：

```text
N1
C5
C8
```

且三者各自形成时间不变。

### 验收 B：五月认知进入五月叙事

五月用户针对一月节点形成 C5 后，当天项目叙事编制必须能够消费 C5。

不得把 C5 归入一月材料池。

### 验收 C：知识卡重生不改历史

从知识卡 K1 溯源到 N1，产生 C5，再重新生成 K1。

必须：

```text
新知识卡优先获得 C5
+
N1 保持不变
+
C5 保持独立
```

### 验收 D：同一动作跨 Surface 同义

侧边栏新增一条当前理解后，完整主界面必须立即看到同一个认知事件；不得生成第二份业务事实。

### 验收 E：相反认知允许共存

用户五月对 N1 表达 👎，六月又表达 👍。

两条当前认知事件都必须保留，不能相互覆盖。

# 10. 明确禁止

```text
禁止把后来理解回写进过去日期
禁止维护“历史节点最新版”并默认隐藏旧理解
禁止把“修正”实现成物理修改旧叙事
禁止把“新增理解”实现成替换旧理解
禁止按“当天 / 多日后”拆成两套认知业务系统
禁止把侧边栏定义成只能快速审核、主界面定义成只能深度审核
禁止让知识卡重新生成先修改上游历史
禁止只靠时间接近猜测显式存在的因果关系
禁止把历史回看主要设计成孤立年月档案浏览
```

# 11. 当前仍需通过 UI 继续闭合的细节

本文已经冻结时间语义与功能边界，但以下产品细节应继续通过真实 UI 设计确定：

```text
主界面叙事正文与“后续理解”采用内联还是双栏为主
选中一段文本后，新增理解怎样自动绑定 refers_to 范围
👍 / 👎 / ✕ 的最小视觉反馈怎样显示而不打断阅读
直接编辑一段文字时，UI 怎样让用户感觉自然，同时底层仍形成独立当前认知事件
来源链在主界面与侧边栏分别怎样展开
知识卡 → 来源 → 历史节点 → 新认知 → 重新生成的完整交互路径
同一历史节点拥有很多后续理解时，默认怎样排序、折叠与展开
如何把显式因果上下文传给重新生成动作而不增加用户操作负担
```

这些不是底层时间语义缺口，而是下一轮 UI 设计应主动逼出的产品细节。

---

# 12. 一句话冻结

> **DCF 中所有校准、修正、补充和新增理解都只是当前时点新形成的认知；它们可以指向过去，但绝不改变过去。旧理解与后来理解并列存在，理解变化本身就是叙事。主界面负责完整阅读与编辑，侧边栏负责快速显现、调用与来源穿透；两者共享同一认知动作。今天对过去形成的新理解进入今天的叙事材料，派生知识重新生成时优先消费与本次操作存在显式因果关系的当前认知，而不是先改写历史。**
