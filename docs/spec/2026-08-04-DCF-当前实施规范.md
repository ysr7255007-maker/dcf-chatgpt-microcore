# DCF 当前架构与实施要求

Date: 2026-08-04  
状态：当前汇总实施规范；仍包含显式实施门禁

> 本文只保存当前仍成立的设计结论。历史推演、被推翻路线和阶段性候选保存在 ADR，不再作为实现依据。

> **AI 编程实施原则：在把工作交给 AI 之前，不必把实现设计完，但必须把所有“做错了仍然可以声称做对”的关键空间尽可能消掉。**

---

# 0. 文档权威与阅读规则

本文是当前 DCF 架构与需求的实现权威。

规则：

1. 历史 ADR 负责解释“为什么”；本文负责回答“现在必须是什么”。
2. 本文中的 `MUST / MUST NOT` 是实现硬约束。
3. `Current` 表示当前实现切片必须做到；`Invariant` 表示现在可以不实现完整能力，但当前结构不得堵死；`Future` 只表示未来方向，不得被实现 AI 擅自提前扩建成大平台。
4. 若某个问题被列入“Implementation Gate / 未闭合点”，在该问题影响的正式功能开工前必须先闭合；不得由实现 AI自行选择一个方便答案并把它冒充正式决定。
5. 局部工程细节——函数拆分、内部类型名、目录细分、局部库选择、具体优化算法——只要不违反本文硬约束，保留给实现 AI 决定。

## 0.1 中文优先的可理解性原则

DCF 的实现表面首先服务于用户能够直接参与设计、实现和验收全过程。

MUST：

- DCF 自己拥有的文件名、目录名、变量名、函数名、类型名、组件名、系统名、状态名、任务说明、日志、测试名称、验收证据和内部架构术语，默认使用中文；
- 新专业概念第一次出现时，可以用“中文名称（业界原名）”建立对应关系，后续在 DCF 内部默认只使用中文名称；
- 外部协议、第三方 API 字段、包名、方法名、环境变量和其他由外部生态定义的标识保持原名，不为了中文化而额外制造包装层；
- 外部概念一旦进入 DCF 自有领域，应尽量映射成稳定的中文内部语义，而不是让外部命名向内部结构扩散；
- 如果未来某类外部接口频繁进入用户的设计或审核视野，再基于真实使用建立接口术语字典；当前不得为了可能的未来阅读需求提前建立大而全的翻译层；
- 本规则生效前已经存在的历史英文命名不要求为了形式统一一次性大规模迁移；从现在开始新建或实质修改的 DCF 自有命名应遵循中文优先，并在真实触及时逐步收敛。

核心原则：

> **英语和外部协议停在边界；DCF 自己拥有的世界，优先用用户可以直接理解的中文表达。**

本原则的目的不是追求形式上的“全中文”，而是减少用户在需求、架构、任务、代码、日志和验收之间来回翻译概念的认知损耗。

# 1. DCF 是什么

DCF 是长期个人认知基础设施。

它最先从 AI 交互历史开始，但基础模型不得把 DCF 锁死为 ChatGPT 存档工具。

DCF 的核心分工：

```text
机器负责历史不乱
AI 负责意义生长
```

进一步拆开：

```text
Reality / Observable Records
→ 保存真实发生过、可观察到的材料

Deterministic Structure
→ 用规则建立可重放的时间、来源、关系骨架

AI Projection
→ 从材料中生成叙事、需求、项目理解、知识等可重算解释

Human Calibration
→ 用户只在真正需要价值判断与语义校准的地方介入
```

DCF 不允许派生解释冒充原始事实。

---

# 2. 核心不可变量

## 2.1 原件与投影分离

MUST：

```text
原始可观察记录
≠
确定性结构
≠
AI 叙事 / 需求 / 知识投影
```

派生物可以重算、修订、替换；原始观察不得因为新解释出现而被静默改写。

## 2.2 长期事实与活动运行状态分离

当前物理边界：

```text
facts.db
→ 稳定、追加式的可观察事实

dcf.db
→ 可变的认知投影与业务对象

ops.db
→ Job / Run / 结果 / 进度 / 恢复相关运行收据

logs/
→ 诊断日志，不冒充事实库或业务库
```

Becsy World 只承载“当前正在发生什么”的活动计算状态，不成为长期事实唯一来源。

## 2.3 单写者 / 明确权威

每一类重要事实 MUST 有明确权威写入者。

观察、缓存、UI、外部程序状态不得静默冒充 DCF 的已承诺事实。

## 2.4 可恢复优先于持续存活

正式工作可以失败、卡住、被取消、被重启；DCF 的控制能力不能随某一正式工作一起丢失。

## 2.5 能力增长不能要求用户管理内部结构

用户面对的是一个完整 DCF，而不是插件、Worker、Agent、证据链或恢复状态的人工管理员。

---

# 3. 可观察事实模型

## 3.1 最小事件骨架

基础观察统一拥有一个小的公共外壳：

```text
When
Who
Through What
Did What
+
Raw Payload / Source Ref
```

人话：

> 在什么时间，谁，通过什么交互载体，进行了什么可观察动作。

这个公共外壳只负责跨来源最小同构，不强迫不同来源失去原生语义。

## 3.2 Observable Record Source

记录源是可插拔“传感器”。

Current：只有交互 / 对话来源必须工作。

Future：Git、文件、测试、浏览器、IDE、AI Agent、运行时等都可成为新来源。

MUST：

- 新来源保留自己的原始 payload 结构；
- 接入新来源不改变基础事实模型；
- 新来源只能增加观察能力，不能回写篡改旧观察；
- 每个来源拥有自己的关联策略，不预设一套全局相关性规则。

## 3.3 可重放采集

Invariant：同一个现实 observation 被重复看到，不应因为 append-only 而自动生成多份重复事实。

Source Adapter 必须存在稳定的重放 / 去重依据，例如 source-native event id、source cursor 或稳定 fingerprint；具体机制由来源决定。

> 可重放采集必须幂等。

## 3.4 Event Link

跨来源关系通过显式关系边连接，不用统一时间窗强行推断。

关系至少区分：

```text
确定关系
可能关系
```

关联器只统一承载关系，不负责统一发明所有来源的关联规则。

# 4. 认知投影

## 4.1 第一层不是 AI 叙事

原始交互首先生成确定性的交互轨迹骨架。

规则层只回答：

```text
发生了什么
顺序是什么
来自哪里
```

不负责猜测用户意图。

## 4.2 Human Narrative

人物叙事是第一层真正的 AI 语义叙事。

它从真实交互轨迹生成，对行为意图允许高度概然推断，但必须保留不确定性强度；证据不足时降低叙事强度，而不是补造解释。

用户可按自己的节奏校准人物叙事。

界面天然采用时间 / 日历形状，重点是：

> 这一天我经历了什么、想了什么、后来长出了什么。

## 4.3 Project Narrative

项目叙事不是实时状态机。

它在需要回看项目历史时，从选定时间范围、人物叙事和其他事实来源重新构造。

它天然采用 GitHub 式项目历史形状：变化、理由、来源、实现、回滚、后续影响。

人物叙事与项目叙事不是上下级事实，而是同一材料的不同投影。

## 4.4 来源关系

所有有价值的派生物 MUST 保留 lineage / 来源关系，使系统能够回答：

```text
这个项目变化来自哪些历史材料？
这一天后来长出了哪些项目、需求或知识？
```

# 5. 运行时总结构

当前优先路线：

```text
Bun
+
Becsy
+
DCF 自研最小 AI 执行核
+
成熟 Agent Runtime
+
SQLite / Files / Git / Blob 等长期载体
```

这不是要求所有事情都塞进同一 Runtime。

## 5.1 主线程是最小存在核 / 控制平面

硬规则：

> **任何可以定义为独立 Job 的正式工作，无论预期长短，都默认脱离主线程执行。**

主线程只承担：

```text
维持 Becsy World
创建 / 派发 Job
接收 Progress / Result / Failure
原子状态推进
恢复游标
取消 / 超时 / 重试控制
健康检查
保持 UI / API / 诊断可响应
```

判断标准不是“这段代码快不快”，而是：

> 如果它意外变慢或失败，DCF 是否仍应保持控制能力？

如果答案是“应”，它不属于主线程正式执行路径。

## 5.2 Bun 单进程只意味着共享世界

```text
Bun Process
├─ Main Thread: survival / control
├─ Workers: deterministic / CPU work
├─ AI executors
└─ External Processes: Browser / Coding Agent / Local LLM / etc.
```

单进程共享类型、世界和能力入口，不等于所有正式工作共享一个执行线程。

## 5.3 Job / Result 边界

所有正式功能优先通过：

```text
Job
→ Executor
→ Progress / Result / Failure
→ World state transition
```

进入执行平面。

MUST：执行器崩溃不等于业务主体或语义进度消失。

---

# 6. Becsy World：DCF 的活动计算状态层

Becsy 在 DCF 中不是业务数据库，而是当前活动世界。

专业结构：

```text
Entity
→ 当前世界里存在的一个活动对象

Component
→ 这个对象当前的一小块状态数据

System
→ 专门处理某类状态的功能机器

Query
→ 这台机器的接活条件

World
→ 当前活动对象与状态的总表
```

核心原则：

```text
身份 ≠ 数据 ≠ 处理逻辑
```

以及：

> 功能之间优先通过共同 World 中的数据状态发生关系，而不是形成互相深度调用的控制网。

## 6.1 热 / 冷数据分离

Becsy 只保存调度和状态推进真正需要频繁访问的小数据：

```text
State
Role / PolicyRef
Priority
ContextRef
ContinuationRef
WaitingOn
ResultRef
```

巨大上下文、长文档、Tool payload、模型历史、Browser snapshot 等放在冷存储，只在需要时按引用取得。

---

# 7. AI 执行：不是自研或第三方二选一

DCF 同时保留两种 AI 执行区域。

## 7.1 前沿探索区：成熟 Agent Runtime

负责：

```text
路线未知的问题
高认知规划
开放世界探索
新工具 / 新模型能力
异常诊断
尚未形成稳定范式的任务
```

成熟生态可以直接提供 Agent、MCP、Browser、Coding、Memory、Subagent 等能力。

DCF 不为追赶生态而复制一套通用 Agent Framework。

## 7.2 结构化执行区：DCF AI Kernel + Becsy

负责已经理解、可大量重复、可重组的 AI 工作。

DCF 自研最小 AI Kernel 只需要掌握：

```text
活动语义执行状态
↓
发起一次 Model Turn
↓
取得 Reasoning / Continuation + 0..N Action Intents
↓
在真实执行前暴露 Intent
↓
等待外部执行 Result
↓
重新注入
↓
继续语义状态推进
```

自研 Kernel 不默认承担通用开放世界规划、全套 Browser Agent、Coding Agent 或所有 MCP Tool 的兼容层。

## 7.3 自由度梯度

```text
高自由度
Planner / Architect / Resolver
“应该怎么做？”

↓

中自由度
Investigator
“这个局部未知怎么解？”

↓

低自由度
Semantic FSM
“在已知路线和合法动作里下一步是什么？”

↓

确定性
System / Effect
```

> 自由智能负责吸收剩余不确定性，不重复承担已经被理解的问题。

---

# 8. Semantic FSM：高认知计划与机器执行之间的 IR

高级语义状态机不是纯确定性 FSM，也不是自由 Agent。

它表达：

```text
当前语义阶段
已有证据 / 结果
还缺什么
合法下一步集合
什么时候必须调用 AI 判断
什么时候可以确定性推进
什么时候必须 Escalate
完成条件
```

例如：

```text
ResearchCase #37
State = NeedSecondIndependentSource
CandidateRef = ...
EvidenceRef = ...
AllowedActions = Search | Read | Reject | Accept | Escalate
```

AI 可以做复杂语义判断，但不再重新发明整个研究方法。

## 8.1 Residual / Escalation

当执行模板遇到自己不能解释的现实：

```text
证据冲突
未知格式
计划假设失效
合法动作无法推进
工具行为超出模型
```

MUST 产生：

```text
Residual
+
NeedsEscalation
```

再交给更高自由度 AI。

不得让低自由度执行器为了“继续跑”而自行扩张自由度、猜测路线或假装成功。

---

# 9. 能力下沉：第三方探索，DCF 收割成熟结构

新 AI 能力的默认生命周期：

```text
成熟 Agent Runtime 黑盒运行
↓
真实使用产生 trajectory
↓
发现高频、稳定、有效的执行模式
↓
抽取 Execution Template
↓
形成 Semantic FSM
↓
下沉到 DCF AI Kernel
↓
Becsy / ECS 规模执行
↓
出现 Residual
↓
重新升级给高自由度 Runtime
```

这类似 JIT：成熟 Runtime 是通用解释执行器，DCF Runtime 是热路径编译后端。

MUST：DCF 学习的是稳定工作方法，不复制第三方 Runtime 内部实现和快速变化 API。

能力可以只下沉一部分：稳定段进入 DCF，高认知节点仍临时调用成熟 Runtime。

# 10. Agent 与执行实例在 World 中的表示

未来主要负载不是“500 个自由 Agent”，而更可能是：

```text
少量 High-Cognition Agent
+
大量 Semantic Execution Instance
+
更多 Operation / Effect
```

Agent / Semantic Execution Instance 在 Becsy 中优先表示为活动数据，而不是常驻 while loop / async stack。

示意：

```text
Entity #42
├─ Agent / SemanticExecution
├─ State
├─ PolicyRef
├─ ContextRef
├─ ContinuationRef
├─ Priority
└─ WaitingOn
```

状态推进：

```text
NeedsInference
→ AI System
→ WaitingForEffects
→ Effect Systems
→ ResultReady
→ Resume / AI System
```

语义上的 Agent loop 仍然存在，但它被展开成 World 状态转换，而不是每个 Agent 一套隐藏执行循环。

# 11. Operation 与 Effect

## 11.1 Action Intent 必须先成为数据

Model Turn 可以一次产生多个 Action Intent。

```text
Model Turn
→ Read(A), Read(B), Search(X), ...
→ 在真实执行前交给 World
```

Agent 负责产生意图；ECS 负责把大量意图转化成更高效的现实执行。

## 11.2 Logical Operation 与 Physical Execution 分离

MUST 区分：

```text
Logical Operation
→ 某个调用者真正等待的因果身份

Physical Execution
→ 为满足一个或多个逻辑 Operation 实际进行的物理工作
```

例如：

```text
Read(A) × 320 logical operations
↓
1 physical read
↓
fan-out
↓
320 logical results
```

ECS 可以压缩物理工作量，不能压掉调用者身份、call id、continuation、取消语义、trace 或 lineage。

## 11.3 Effect Projection

DCF 不重新包装所有 Tool Schema。

原始 Tool / MCP payload 可以保持 opaque，只在存在可靠信息时投影一个薄的效果足迹：

```text
Resource / Scope
ReadSet
WriteSet
EffectKind
Ordering Constraint
PayloadRef
ContinuationRef
```

人话：

> 不需要完全理解工具，只抽取“它会碰什么、会改变什么、可能和谁冲突”。

## 11.4 保守退化

MUST：

```text
Effect 明确
→ 可以利用确定性性质优化

Effect 未知 / 不完整
→ 仍可执行
→ 默认不可去重、不可合并、不可越过未知因果边界重排
```

Effect Projection 是优化权限，不是外部 Tool 接入门槛。

---

# 12. ECS 优化的两类收益

## 12.1 工作消除 / 合并

高度同质工作可能产生：

```text
重复 Read → 共享结果
相同请求 → cache / dedup
显式可结合操作 → merge
可批量调用 → batch
```

目标是：

```text
Logical Work >> Physical Work
```

## 12.2 机器执行优化

即使工作不能合并，仍可通过：

```text
热 / 冷数据分离
紧凑 Component 布局
按资源分组
时序重排
减少锁竞争
减少上下文切换
提高缓存局部性
```

获得收益。

> 同质化决定 ECS 收益上限；数据导向和时序局部性决定异构负载下限。

## 12.3 不支付昂贵“优化税”

优化层优先级：

```text
Level 0
纯机器级数据组织

Level 1
确定性 Effect 规律
相同 key / 显式冲突 / 已声明幂等、交换、结合性质

Level 2
只有真实高频价值出现后才增加领域专属优化
```

不得为了寻找可能不存在的优化机会，让每个请求先经过昂贵 AI 语义判断。

---

# 13. 因果与重排

ECS 只能在证明不会改变语义的范围内改变执行顺序。

Invariant：

> **存在 happens-before / 数据依赖 / 明确 Ordering Constraint 的 Logical Operation，不能被优化器跨越。**

默认原则是保守的：

```text
能证明顺序可交换
→ 可以重排

不知道顺序是否重要
→ 不重排
```

不得用简单 `sortBy(resource)` 之类的物理优化静默改变逻辑结果。

---

# 14. 资源边界

DCF 追求的不是“所有动作都必须由自己控制”，而是：

> **最大可重组性。**

如果某项 Provider 内部动作：

```text
不占用 DCF 稀缺共享资源
不会与其他实例形成明显共享 / 冲突
Provider 自己处理更成熟
集中调度没有明显结构收益
```

可以保持黑盒。

但成熟 Agent Runtime 一旦触碰 DCF 共享现实资源，例如：

```text
共享 Git Workspace
共享 Browser Context
共享文件
共享本地 GPU
共享数据库
```

必须满足二选一：

```text
A. 获得隔离世界
   独立 worktree / sandbox / browser context / resource partition

或

B. 进入 DCF Resource / Effect 边界
```

高认知过程可以黑盒，共享现实资源不能在冲突模型之外偷偷修改。

---

# 15. 两套 AI Runtime 的合流对象

成熟 Agent Runtime 与 DCF Semantic Runtime 可以有不同内部执行方式，但交接时 MUST 落成同一个 DCF 工作世界：

```text
Plan
Task
ExecutionTemplate
SemanticState
LogicalOperation
Effect
PhysicalExecution
Result
Finding
Residual
```

执行方式可以多套；工作事实、结果、来源与可迁移结构不能裂成多个权威世界。

# 16. Template 版本

Invariant：Semantic Execution Instance 一旦实例化，必须知道自己基于哪个 Execution Template Version。

新 Template 不得静默重新解释已经存在或正在运行的实例。

是否允许显式迁移、如何迁移可以后续定义，但迁移必须是可见的状态变化，而不是文件覆盖后自动改变历史语义。

# 17. 能力下沉必须经过行为等价验证

发现稳定模式不等于证明已经可以替代成熟 Runtime。

能力下沉应复用 DCF 已有 Candidate / Shadow / Reality Replay 思路：

```text
Mature Runtime Path
= 当前参考行为

Execution Template Candidate
↓
Shadow / Replay
↓
比较：
结果质量
失败边界
成本 / 延迟
Residual 率
↓
满足验收
↓
Promote
```

不能因为“看起来重复了几次”就直接将自由 Agent 路径替换为固定状态机。

---

# 18. AI Coding 与自动验收

核心原则：

> **锁定“做成什么才算对”，不要锁死“代码必须怎么写”。**

每项进入 Current Implementation Slice 的重要需求，至少应能回答一个反例问题：

> 出现什么运行现象，就能证明这条需求实际上没有实现？

例如：

```text
主线程隔离
→ 故意卡死正式 Job，DCF 仍必须可查询、取消、诊断

Read dedup
→ logical=100, physical=1, delivered=100

Residual
→ 给模板未定义输入，不得猜一个合法动作继续，必须升级
```

代码存在、测试 mock 通过、README 宣称支持，都不能单独构成现实行为证据。

# 20. Implementation Gates：正式实施前仍需闭合的问题

以下不是允许实现 AI 自由选择的工程细节，而是尚待设计层决定的语义接缝。

## Gate A — Job / Result 的崩溃边界与副作用幂等

必须明确进程可能死在：

```text
记录 Job
派发
真实副作用发生
记录 Result
```

任意两步之间时，重启后如何判断“已经真实发生 / 尚未发生 / 未知”，以及重试如何避免静默重复不可逆副作用。

## Gate B — Becsy World 的进程级恢复边界

必须明确哪些 Component 是纯瞬态，哪些语义进度在整个 DCF 进程崩溃后必须从 ops.db / durable state 恢复或确定处置。

不要求持久化整个 World，但不能让“Worker 可恢复”被误写成“DCF 进程重启后所有活动语义任务直接丢失也算恢复”。

## Gate C — 当前实施切片

必须冻结第一轮到底交付什么，否则本文仍是完整架构规范而不是可验收的单次 Coding Task。
