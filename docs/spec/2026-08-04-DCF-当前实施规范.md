# DCF 当前架构与实施要求

日期：2026-08-05  
状态：当前汇总实施规范；按 DCF 概念完整性分层

> 本文只保存当前仍成立的设计结论。历史推演、被推翻路线和阶段性候选保存在 ADR，不再作为实现依据。

> **AI 编程实施原则：在把工作交给 AI 之前，不必把实现设计完，但必须把所有“做错了仍然可以声称做对”的关键空间尽可能消掉。**

---

# 0. 文档权威与分层规则

本文是当前 DCF 架构与需求的实现权威。

历史 ADR 负责解释“为什么”；本文负责回答“现在认为什么是 DCF，以及各能力处在哪一层”。

本文的层级不是施工顺序，而是**概念完整性层级**。

判断一个能力属于“基础 DCF”还是“扩展能力”，只问一个问题：

> **把这个能力拿掉以后，剩下的系统还配不配叫 DCF？**

因此：

```text
基础 DCF
→ 少了其中任一关键环节，系统就不再完整表达 DCF 的核心概念

扩展能力
→ 拿掉以后，DCF 仍然是 DCF，只是观察范围、认知能力、行动能力或执行效率下降

实现机制
→ Bun、Becsy、SQLite、Worker 等技术可以从第一天就使用，
  但“什么时候开始使用”不决定它属于基础概念还是扩展概念
```

## 0.1 规范用语

- **必须**：违反即不满足当前规范。
- **禁止**：出现即判定为错误实现。
- **基础 DCF**：构成 DCF 概念完整性所必需的能力。
- **扩展**：建立在基础 DCF 之上的新增能力。
- **实施门禁**：设计层尚未闭合、不得由实现 AI 自行选择方便答案的问题。

局部工程细节——函数拆分、内部类型细节、目录细分、局部库选择、具体优化算法——只要不违反本文硬约束，保留给实现 AI 决定。

## 0.2 中文优先的可理解性原则

DCF 的实现表面首先服务于用户能够直接参与设计、实现和验收全过程。

必须：

- DCF 自己拥有的文件名、目录名、变量名、函数名、类型名、组件名、系统名、状态名、任务说明、日志、测试名称、验收证据和内部架构术语，默认使用中文；
- 新专业概念第一次出现时，可以用“中文名称（业界原名）”建立对应关系，后续在 DCF 内部默认只使用中文名称；
- 外部协议、第三方接口字段、包名、方法名、环境变量和其他由外部生态定义的标识保持原名，不为了中文化而额外制造包装层；
- 外部概念一旦进入 DCF 自有领域，应尽量映射成稳定的中文内部语义，而不是让外部命名向内部结构扩散；
- 如果未来某类外部接口频繁进入用户的设计或审核视野，再基于真实使用建立接口术语字典；当前不得为了可能的未来阅读需求提前建立大而全的翻译层；
- 本规则生效前已经存在的历史英文命名不要求一次性迁移；从现在开始新建或实质修改的 DCF 自有命名遵循中文优先。

核心原则：

> **英语和外部协议停在边界；DCF 自己拥有的世界，优先用用户可以直接理解的中文表达。**

# 1. DCF 的完整概念

DCF 是长期个人认知基础设施。

它最先从 AI 交互历史开始，但基础模型不得把 DCF 锁死为 ChatGPT 存档工具。

DCF 的核心不是永久保存一份精确过去，而是让真实交互经过机器编制、AI 叙事和人的重新参与，持续长成个人与项目的认知历史，并进一步产生知识、工程和新的现实。

最简分工更新为：

```text
机器编制
→ 让 AI 能重新读懂过去

AI 叙事
→ 让人能重新想起过去

用户校准
→ 让过去重新进入人的当前认知

时间
→ 不断提供新的现实、新的回看机会和新的变化材料
```

基础主链：

```text
真实交互
↓
机器编制
↓
交互记录
↓
AI 关系叙事
↓
人的回忆被唤醒
↓
用户复盘 / 校准
↓
新认知
```

这里存在一个重要消费者分界：

```text
交互记录
→ 主要给 AI 使用

AI 关系叙事
→ 主要给人使用
```

不是所有真实交互都天然带有“理解”。

DCF 允许大量历史只进入交互记录，不被强行解释，也不被强行提炼成知识。

真正需要长期保护的是：

```text
发生过什么
AI 当时怎样叙述
人后来怎样回忆、补充和重新理解
这些理解后来怎样继续影响个人与项目
```

已经形成过的认知不能因为后来出现更好的解释就被偷偷改写。

只有记录而没有人的重新进入，系统更接近档案工具。

只有 AI 解释而没有用户校准，系统更接近普通摘要或记忆工具。

只有个人认知而不能继续进入项目、知识和现实，系统则还没有发挥 DCF 作为长期认知基础设施的扩展潜力。

# 2. 基础 DCF：最小但完整的认知闭环

基础 DCF 至少必须形成：

```text
一个真实 AI 交互来源
↓
确定性机器编制
↓
形成面向 AI 的交互记录
↓
AI 从相关记录中形成关系叙事
↓
叙事把用户重新带回过去
↓
用户复盘、补充、纠正
↓
产生新的认知材料
↓
后续理解只追加，不覆盖
```

如果这条闭环成立，即使还没有项目叙事、GitHub、知识卡、任务系统、多智能体、Becsy 或自研执行底座，它仍然已经可以被称为基础 DCF。

---

## 2.1 基础能力一：接住真实交互

基础 DCF 至少拥有一个真实记录来源，第一种来源是 AI 交互 / 对话。

真实交互只回答：

> **发生了什么。**

它不负责回答：

> **这意味着什么。**

记录源必须：

- 接入真实发生的交互，而不是只接收事后人工编造的总结；
- 保留发生时间、参与者、交互载体和必要内容；
- 重复采集同一个现实事件时不得静默制造第二份现实；
- 采集失败、缺口和未知必须诚实保留，不能用推测补齐。

初始阶段允许高保真保存原件，但基础 DCF 不承诺所有原始 token、工具输出和低层细节永久存在。

---

## 2.2 基础能力二：机器编制交互记录

第二阶段是机器编制阶段，不是理解阶段。

它把原始交互中的格式差异、工具调用、重复内容和低价值噪声，编成稳定、规则化、可搜索、可组合的交互记录。

示意：

```text
原始对话 / 工具调用 / 输出
↓
确定性编制
↓
时间 + 对象 + 动作 + 结果 + 必要来源定位
```

这层首先服务 AI，不首先服务人。

目标是：

- 体积可控；
- 结构稳定；
- 可检索、可组合；
- 可重新计算；
- 必要时能定位原始来源；
- 让 AI 重新理解当时发生了什么；
- 不强迫每条交互都产生意义解释。

因此：

> **机器编制 ≠ 理解。**

禁止在这一层因为后续可能需要叙事，就提前把 AI 推断伪装成事实。

---

## 2.3 基础能力三：AI 形成关系叙事

AI 从一批相关交互记录中组织出关系、阶段、变化和可能意义，形成面向人的关系叙事。

理解可能产生在多条记录之间的关系中，而不一定存在于任意单条记录内部。

例如若机器记录中长期出现：

```text
多次否定不同架构
反复讨论复杂度
提出黑洞架构
开始存储实验
```

AI 可以形成：

> 这一阶段架构选择标准逐渐从“功能是否完整”转向“结构能否吸收复杂度”，随后这种判断开始进入工程实验。

这一层允许：

- 粗糙；
- 不完整；
- 暂时理解错；
- 只抓到表层原因；
- 留下未解决问题。

禁止：

- 把 AI 草稿冒充最终事实；
- 为了故事完整而伪造不存在的经历；
- 后来纠正时直接覆盖旧叙事。

AI 关系叙事的首要作用是：

> **把人重新带回过去。**

因此“回忆锚点”主要是叙事对人的作用，而不是机器编制记录本身的定义。

人通常通过关系、情境和连续故事被唤醒，而不是通过阅读第二阶段的机器记录回忆过去。

---

## 2.4 基础能力四：用户复盘与校准产生新认知

用户面对 AI 关系叙事时，不是在做普通质检。

叙事唤醒真实回忆以后，用户可能：

```text
认同
补充
纠正
重新解释
想起 AI 无法知道的背景
形成今天才有的新理解
```

这些内容必须作为新的认知材料进入 DCF。

禁止：

```text
用户纠正
→ 直接修改旧 AI 文本
→ 只保留最新版
```

正确结构至少保留：

```text
AI 当时的叙事
+
用户后来补充 / 纠正
+
两者之间发生了什么变化
```

因此：

> **用户校准不是把 AI 草稿变成真相，而是人重新进入历史以后继续生产认知。**

---

## 2.5 基础能力五：事情发生时间与理解形成时间必须分开

必须区分：

```text
事情发生在什么时候
≠
这份理解形成在什么时候
```

例如：

```text
2026 年 3 月
→ 当时只是觉得“状态机挺有意思”

2026 年 8 月
→ 回看后认为：
  3 月那次关注可能是后来一条长期路线的早期萌芽
```

禁止把 8 月的理解回写成：

```text
2026 年 3 月
→ 当时已经明确知道这是长期路线
```

新的理解可以重新连接旧经历，但不能让过去的自己突然拥有今天的认知。

---

## 2.6 基础能力六：原件可以代谢，认知变化不能被静默抹除

必须始终区分：

```text
原始交互
≠
机器编制记录
≠
AI 关系叙事
≠
用户后来形成的新理解
```

原件和机器编制材料可以随着认知代谢逐步简化，例如：

```text
完整原件
↓
压缩记录
↓
代表性片段
↓
来源标记
```

具体何时降级、降级到什么程度属于后续实现策略。

但：

> **已经进入认知历史的意义与变化关系不能被伪装成从未发生。**

核心原则仍是：

> **原件可以变轻，认知变化必须变长。**

---

## 2.7 基础能力七：后续现实提供自然纠错与补漏机会

时间不是一个独立流水线步骤，也不是自动真理机器。

它持续带来：

```text
新的真实交互
新的选择
新的失败与成功
新的回看机会
新的用户理解
```

真正长期重要的问题、倾向和未解决矛盾通常会在后续现实里以不同形式反复出现。

例如：

```text
“代码为什么这么乱？”
↓
“为什么每加一个功能都要改五个地方？”
↓
“我想找能吸收复杂度的架构。”
```

表面是不同问题，跨时间后可能逐渐被理解成同一条长期驱动力。

新的现实允许强化、补漏、削弱、纠正和重新解释旧理解，但禁止覆盖旧理解。

---

## 2.8 基础能力八：长期连续性跨重启成立

必须保证在：

```text
程序退出
机器重启
短暂离线
采集端重连
```

之后：

- 机器编制记录仍可继续使用；
- 已经形成的 AI 叙事不会凭空消失；
- 用户后来形成的新认知不会覆盖旧理解；
- 事情发生时间与理解形成时间仍可区分；
- 原件若已简化，其来源与代谢状态不会被伪装成“从来不存在”。

长期真正不可丢的是：

```text
发生过的现实痕迹
+
曾经形成的叙事 / 认知
+
后续认知变化
+
必要来源定位
```

而不是永久保存每一份低层原始载荷。

---

## 2.9 基础 DCF 的概念验收

一个系统只有在以下问题都回答“是”时，才算基础 DCF 概念闭合：

```text
1. 是否真的接住了一段现实 AI 交互？
2. 是否把原始交互编成稳定、机器可用的交互记录？
3. 机器编制是否保持“记录”身份，而没有强迫每条记录产生理解？
4. AI 是否能从相关记录形成面向人的关系叙事？
5. 叙事是否真的能把人重新带回过去，而不是只生成机器摘要？
6. 用户复盘、纠正和新理解是否成为新的认知材料？
7. 后来的理解是否通过追加而不是覆盖进入历史？
8. 系统能否区分事情发生时间与理解形成时间？
9. 重启以后，这条认知连续性是否仍然存在？
```

# 3. 第一类扩展：观察范围与现实证据扩展

这一层扩大：

> **DCF 能看见多少现实，以及这些现实分别由谁来证明。**

拿掉这一层，基础 DCF 仍然成立；只是它目前只理解已经接入的 AI 交互历史。

本层的总原则不是“DCF 自己监控更多”，而是：

> **优先消费现实世界已经存在的事实面；来源自己的高语义事实优先，macOS 公共事实负责跨 App 的最低公共现实，DCF 只保存游标、提纯事实、来源关系与认知意义。**

因此现实证据的优先级是：

```text
来源自己的结构化事实
>
macOS 已经维护的公共现实事实
>
机会主义语义面
>
高频原始传感流 / OCR
```

这不是“越靠前越真实”的价值等级，而是优先选择**语义更直接、依赖更薄、增量更自然、恢复成本更低**的事实源。

---

## 3.1 现实所有权边界

当前宿主实验形成的正式架构边界是：

```text
macOS
→ 维护跨 App 的现实事实、时间骨架、文件世界、生命周期与系统行动接缝

来源适配器
→ 读取某个具体软件已经拥有的高语义事实

Git / GitHub
→ 维护确定性的工程事实

DCF
→ 保存消费游标、提纯事实、来源关系、认知关系与叙事意义
```

核心原则：

> **系统需要某项能力，不等于这项能力应该由 DCF 自己实现。**

如果宿主操作系统或来源软件已经为整个世界维护了一个更强、更稳定的事实面，DCF 不应复制一个局部版本。

因此以下方向默认淘汰为 DCF 自有基础设施：

```text
自建全局文件 watcher
自建全局文件索引
自建前台 App 活动历史
自建进程 supervisor
自建 IPC 总线
自建跨 Agent 全量副作用观察器
屏幕 / OCR 作为常规基础事实源
```

只有当宿主能力不能满足真实需求，并有行为证据证明缺口存在时，才重新考虑自建。

---

## 3.2 来源原生事实：单个来源的最高语义入口

当某个来源自己已经维护完整、高语义、可增量读取的现实记录时，应优先使用来源适配器，而不是退回系统级观察面。

典型例子：

```text
ChatGPT 网页
→ 浏览器插件 / 页面适配器
→ 会话身份、用户消息、AI 回复、页面事件

Codex
→ thread / rollout JSONL / SQLite / app-server 等来源事实
→ 用户消息、AI 回复、tool call、任务与线程身份

其他 AI IDE / Agent
→ 其稳定本地数据库、日志、事件流或官方接口
```

这些适配器允许比系统底层拿到更完整的上下文。

但它们是**来源专用能力**，不能冒充跨 App 的最低公共保证。

原则：

> **公共底座追求跨来源通用；来源适配器追求单个来源的信息密度。两者互补，不互相替代。**

---

## 3.3 macOS 公共现实面一：KnowledgeC + NSWorkspace 提供活动时间骨架

当前宿主实机已经验证：KnowledgeC（CoreDuet）维护前台 App 等活动分段，NSWorkspace 提供实时活动变化通知；二者可以形成低成本的个人活动时间骨架。

它主要回答：

> **某个时间段，人主要处在哪个 App / 工作上下文中。**

示意：

```text
09:10–11:30  Qoder
11:31–12:04  Chrome
13:20–16:40  Codex
```

DCF 不需要自己持续轮询前台窗口来制造另一份活动历史。

这一时间骨架可作为其他事实的对齐轴：

```text
                     个人时间线
                         │
              KnowledgeC / NSWorkspace
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
    用户表达         AI 来源适配器      Git / 文件变化
```

当前宿主证据包括：

- KnowledgeC 存在约 29 天分段保留；
- 与 NSWorkspace 实时通知在实验窗口内秒级一致；
- 增量查询成本很低。

这些数值是当前宿主的运行事实，不应被写成跨 macOS 版本永久契约。

---

## 3.4 macOS 公共现实面二：IMK + Unified Logging 提供用户表达事实

当前宿主已经验证，豆包作为活动输入法时，InputMethodKit 相关 Unified Logging 可以观察 `setMarkedText` / `insertText`，并在受控 private-data 配置下读到真实提交文本与目标 App 归因。

它主要回答：

> **用户在什么时候，向哪个 App 提交了什么文本表达。**

数据流是：

```text
用户键盘 / Fn 语音
↓
活动输入法
↓
InputMethodKit
↓
setMarkedText / insertText
↓
目标 App
```

这条事实面已经在 TextEdit、Chrome、ChatGPT、Cursor/VS Code 类编辑器、微信、QQ 等场景得到本机运行验证；后续黑洞实验又验证了持久化补读和成本边界。

这一能力的意义不是替代来源适配器。

例如：

```text
IMK
→ 可以证明“用户向 Codex 提交了这句话”

Codex 来源适配器
→ 可以进一步知道这句话属于哪个 thread、AI 回了什么、调用了什么工具
```

二者语义层级不同。

必须明确：

> **IMK 解决的是“用户向电脑表达了什么”，不解决“App / AI 向用户展示了什么”。**

AI 回复等输出内容优先由对应来源适配器读取，不追求使用 IMK、AX 或 OCR 建立一个系统级万能回答读取器。

---

## 3.5 macOS 公共现实面三：FSEvents + Spotlight 提供文件世界

文件世界由两种宿主能力互补承担：

```text
FSEvents
→ 什么发生了变化

Spotlight
→ 当前相关文件在哪里、如何定位
```

DCF 不应自建全局 watcher 和全局文件索引来复制这一事实。

当前宿主已经验证 FSEvents 可以从历史游标补读 Data 卷中的文件事件，系统自身负责日志轮转；Spotlight 负责当前索引与定位。

在工程项目中还应继续分工：

```text
FSEvents
→ 文件发生过变化

Spotlight
→ 找到当前文件

Git / GitHub
→ 工程内容究竟怎样变化

DCF
→ 这次变化为什么重要、属于哪个项目阶段、改变了什么理解
```

因此文件事件不应被 DCF 直接解释成工程意义。

---

## 3.6 macOS 公共现实面四：EndpointSecurity / eslogger 提供 Agent 行动收据

EndpointSecurity 的当前最佳用途不是“监控电脑的一切”，而是为自动执行者提供现实副作用收据。

它主要回答：

> **哪个进程 / Agent 实际碰了哪些现实资源。**

当前宿主已经验证：

- eslogger NOTIFY 面可按 pid / ppid 链对多个 Agent 的文件副作用进行独立归因；
- 精简事件管道远低于全量 ES 事件流；
- 自建 ES 客户端受 entitlement 约束，当前宿主存在 SIP-off 的 ad-hoc 例外，但该例外不作为通用正式底座前提。

典型用途：

```text
AI 声称“我已经修改文件”
≠
现实证明已经发生

ES / eslogger 收据
→ 证明某个 Agent 进程确实触碰了对应资源

Git diff / 测试 / 其他事实源
→ 再判断具体改了什么、结果是否正确
```

因此 ES 是**行动归因证据**，不是长期知识真源。

---

## 3.7 Git / GitHub：确定性工程事实源

项目一旦进入工程世界，Git / GitHub 继续作为确定性工程事实的权威来源。

它负责：

```text
Repository 身份
Branch 历史
Commit
Diff
Merge
PR
Issue（在采用时）
文件版本
```

DCF 不复制并维护另一套 Commit / Branch 真相。

DCF 保存的是：

> **为什么这些工程事实发生、它们怎样改变项目叙事、又怎样影响个人认知。**

Git / GitHub 同时可以与 KnowledgeC、IMK、来源适配器、FSEvents 和 ES 共同构成一次工程活动的多层现实证据，但不同来源必须保持各自直接能够证明的边界。

---

## 3.8 launchd + XPC：生存与控制底座，不是认知证据源

当前宿主已经验证 launchd + XPC 可以承担 DCF 本地服务的生命周期与稳定 IPC：服务进程被杀后由系统拉起，稳定 mach 名不随具体进程实例改变。

它们的职责是：

```text
launchd
→ 进程生命周期权威

XPC
→ 稳定本地通信接缝
```

DCF 不应再自建一套与 launchd 竞争的 supervisor，也不应让 IPC 层同时拥有第二套生命周期权威。

但必须明确：

> **launchd + XPC 是让事实消费与认知系统长期活着的基础设施，不是“用户做了什么”的证据源。**

---

## 3.9 Apple Events / ScriptingBridge / Shortcuts：结构化行动面

当 DCF 需要主动改变其他 App 的现实状态时，优先使用系统已经提供的结构化自动化面：

```text
Apple Events
ScriptingBridge
Shortcuts
```

其价值在于：

- 命令结构明确；
- 目标 App 明确；
- 错误码机器可读；
- 不需要退回鼠标坐标与 OCR 猜测。

它们属于**行动能力的系统接缝**，不是主要观察证据源。

行动发生以后，仍应由来源事实、ES、Git、文件变化等重新观察现实结果，而不是因为 Apple Event 返回成功就直接宣布认知结论成立。

---

## 3.10 机会主义语义面与最后兜底

Accessibility（AX）仍然可以作为低成本、高语义的机会主义来源，但不承担“所有 App 必须可读”的基础保证。

必须区分：

```text
AX 不保证跨 App 完整覆盖
≠
某个具体 App 的内容一定不可读取
```

具体 App 已有更强来源适配器时，优先适配器。

屏幕 / OCR 继续保持最后兜底或研究工具定位，不进入常规基础事实面。

原因仍是：

- 高频像素变化与有意义事实量不成比例；
- 页面正文、按钮、历史消息、广告等事实边界混杂；
- 需要二次推断“哪些是用户自己的表达”；
- 常驻成本由屏幕变化驱动，而不是由真实有价值事件驱动。

---

## 3.11 证据层次与机器编制的关系

同一现实活动可以同时留下多个层次的事实，但 DCF 不应把它们粗暴去重成一条“唯一真相”。

例如用户在 Codex 中提出一个架构判断：

```text
IMK
→ 证明用户在某时向 Codex 提交了这句话

KnowledgeC
→ 证明当时主要工作上下文处于 Codex

Codex 来源适配器
→ 证明这句话属于哪个 thread，AI 如何回应、调用了什么工具

ES
→ 证明后续哪个 Agent 进程实际触碰了哪些资源

FSEvents
→ 证明哪些文件发生变化

Git
→ 证明工程内容具体怎样变化
```

这些仍然只是现实材料。

随后才进入：

```text
多源事实
↓
确定性机器编制
↓
稳定交互 / 项目记录
↓
AI 关系叙事
↓
用户复盘 / 校准
↓
认知历史
```

因此新增系统事实源不改变基础纪律：

> **证据源负责证明现实发生了什么；机器编制负责把事实变成稳定材料；AI 和人负责理解这些事实意味着什么。**

---

## 3.12 跨来源关系

多个来源出现以后，需要真正的跨来源关系能力。

关系至少区分：

```text
确定关系
可能关系
```

禁止用一个统一时间窗口强行把所有来源关联起来。

例如：

```text
同一个 Codex thread_id
→ 可以形成强来源关系

同一个 Git commit / 文件身份
→ 可以形成强工程关系

只是发生在相近时间
→ 最多是弱候选关系，不能自动宣称因果
```

关联能力统一的是：

> **关系如何被保存和表达。**

而不是：

> **所有现实都必须使用同一种关联规则。**

---

# 4. 第二类扩展：叙事、知识与项目工程化

这一层扩大的是：

> **DCF 如何把已经形成的新认知继续编织成人与项目的长期结构，并进一步提炼知识、发现缺口和产生工程。**

基础 DCF 只要求关系叙事与用户校准闭环。

在此之上，长期认知开始沿两个对象展开：

```text
个人叙事
项目叙事
```

它们不是上下级，也不是谁天然更真实。

---

## 4.1 个人叙事

个人叙事回答：

> **这个人怎样成为今天这个人。**

它以人的长期时间线组织：

- 反复出现的关注；
- 价值判断变化；
- 新形成的概念与区分；
- 被工程经历改变的思想；
- 长期持续的驱动力；
- 对过去自己的重新解释。

个人叙事本身可以直接提炼：

```text
个人知识卡
语言弹药
判断原则
认知构件
当前自我理解
```

不要求先建立“个人工程”，才能从个人叙事中生成知识。

---

## 4.2 项目发现：明示成项与涌现成项

新认知进入项目叙事主要有两种路径。

### 明示成项

用户明确表达：

```text
这是一个新项目
这个以后单独做
我们把它叫作 X
这是新的工程 / 实验方向
```

此时项目边界由人给出，DCF 建立项目身份与初始叙事。

### 涌现成项

用户没有明确宣布成项，但一段时间内不同交互持续受到同一个驱动力牵引。

项目识别不能只靠主题相似度。

重点观察：

```text
是否反复服务同一个持续目标 / 问题 / 欲望 / 探索方向
后一次交互是否承接前一次留下的问题
是否逐渐形成“以前怎样、后来怎样、下一步怎样”的内部历史
```

项目暂定定义：

> **一组被同一个持续驱动力牵引、并在时间中不断产生新行动和新认知的历史。**

项目边界本身也允许以后重新理解。禁止因为后来发现“两个项目其实是一个更大项目”，就静默改写过去曾经怎样分类。

---

## 4.3 项目叙事

项目叙事回答：

> **这个项目怎样成为今天这个项目。**

它关注：

```text
项目为什么出现
经历了哪些阶段
哪些想法进入实现
哪些路线被推翻
现实实验证明了什么
项目目标如何变化
当前仍有哪些未闭合问题
```

项目叙事与第三阶段“AI 关系叙事”不同。

```text
AI 关系叙事
→ 主要负责把人带回某段过去

项目叙事
→ 负责把经过人重新参与后的认知，编织成项目自己的持续历史
```

---

## 4.4 从项目叙事开始明确对接 GitHub

成项是 DCF 中一个重要相变点。

成项之前，主要依靠交互记录、AI 关系叙事与人的认知组织历史。

成项之后，应尽量把确定性的工程事实交给 Git / GitHub。

原则：

> **项目一旦成项，工程事实尽量落入 GitHub 的确定性结构；DCF 在其上保存项目叙事、认知变化与工程事实之间的意义关系。**

典型映射：

```text
DCF 项目身份
↔ GitHub Repository

当前主工程状态
↔ 默认分支

不同实验路线 / 局部现实
↔ Branch

设计理解与决策变化
↔ ADR

工程状态推进
↔ Commit

候选改变与合流
↔ PR / Merge

任务与待解决问题
↔ Issue 或 DCF 自身任务对象
```

这不是要求所有概念机械映射成 Git 对象。

职责边界是：

```text
Git / GitHub
→ 文件、提交、分支、合流、版本等确定性工程事实

DCF
→ 这些事实为什么发生、怎样改变项目理解、又怎样影响人的认知
```

Branch 适合表达同一个项目的不同现实状态或实验路线，不应用作普通分类树。

---

## 4.5 个人叙事与项目叙事必须可以交叉引用

两条叙事独立存在，但必须能够互相穿透。

### 从个人时间线找到项目

个人叙事按时间查看时，应能够看到同一时期有哪些项目正在推进，以及这些项目如何共同塑造个人认知。

例如：

```text
某段个人叙事：
开始重视“复杂度吸收”

同期项目：
DCF 黑洞架构探索
存储内核实验
P0 技术池研究
```

### 从项目概念找到个人思想源头

项目叙事中的关键概念、设计原则或方向，应能够反向找到个人叙事中相关思想在什么时间出现、怎样演化。

例如：

```text
项目概念：复杂度黑洞
↓
个人叙事：功能完整 ≠ 架构强
↓
个人叙事：开始把复杂度吸收当成主要判断尺度
↓
项目实验：存储黑洞实验进一步强化该认识
```

### 反馈方向

项目实践也可以反过来：

```text
促成新的个人认识
暴露新的区分缺口
强化已有判断原则
推翻旧个人认识
```

因此元工程真正关注的是：

```text
个人思想
↓
进入项目
↓
工程实践
↓
现实反馈
↓
改变个人思想
↓
影响下一批项目
```

---

## 4.6 普通关系型数据库足以承载双叙事交叉引用

现阶段不需要因为“关系很多”就引入图数据库。

最小结构可以是：

```text
叙事实体
叙事节点
叙事关系
现实锚点
```

个人叙事节点与项目叙事节点共享稳定节点身份，通过关系表建立显式关系。

例如：

```text
个人认知节点
──启发──→ 项目设计节点

项目实验节点
──修正──→ 个人认知节点
```

时间重叠等弱关系不要求全部预先存边，可以在查询时计算。

Git commit、Branch、ADR、Issue、文件、对话等保持为外部现实锚点，不强行复制 GitHub 已经拥有的工程事实。

原则：

> **底层用关系数据库保存节点和显式关系；上层需要“图”的时候动态投影成图。数据呈图状，不等于必须使用图数据库。**

---

## 4.7 叙事可以直接提炼知识，不必先工程化

个人叙事和项目叙事都可以直接长出可复用知识。

```text
个人叙事
├→ 个人知识卡
├→ 语言弹药
├→ 判断原则
└→ 认知构件

项目叙事
├→ 项目知识卡
├→ ADR
├→ 当前架构知识
└→ Ripple Wiki / 人类可读项目知识
```

因此：

> **知识化和工程化是叙事的两个并列出口。**

知识负责提炼“现在有什么可以复用”。

工程负责处理“现在还有什么缺口值得主动改变”。

---

## 4.8 两类核心缺口：能力缺口与区分缺口

DCF 不需要建立两套项目系统。

所有项目都可以工程化，真正需要区分的是项目主要试图缩小什么缺口。

### 能力缺口

```text
世界里还缺一个应该存在的能力 / 结构
↓
构造能力
↓
改变外部世界
```

典型问题：

> “我觉得系统应该能这样，但现实还做不到。”

成熟结果是：

> **原来不存在的能力，现在真实存在并能工作。**

### 区分缺口

```text
人的认知里还缺一个应该存在的边界 / 区分
↓
建立区分
↓
提高认知分辨率
```

典型问题：

> “这两个东西不应该继续混在一起，但我现在还分不清。”

例如：

```text
功能丰富
≠
架构结构性优势
```

成熟结果不是多背一条知识，而是：

> **原来分不出来的东西，现在能够稳定区分，并在下一次真实判断中据此行动。**

---

## 4.9 个人工程与工程项目共享同一套工程框架

“个人工程”不需要单独发明项目管理体系。

它完全可以：

```text
建 Repository
写 ADR
形成知识卡
建立任务
做实验
有版本
有分支
做验收
```

区别只在主要缺口类型和现实反馈来源。

```text
围绕工程本身
→ 主要缩小能力缺口
→ 构造现实能力

围绕个人提升
→ 主要缩小区分缺口
→ 构造稳定认知边界
```

个人工程的主要历史材料是个人叙事。

工程项目的主要历史材料是项目叙事。

但两种叙事都可以直接生成知识，两种工程也都可以同时包含能力缺口与区分缺口。

---

## 4.10 元工程：工程“如何建立工程”本身

当工程实践与个人认知提升形成闭环时，出现元工程。

```text
做工程
↓
暴露能力缺口
+
暴露区分缺口
↓
同时改造系统和工程者
↓
形成更强的工程方法
↓
进入下一轮工程实践
```

普通工程可以理解为：

```text
输入：想法
输出：现实能力
```

元工程则更接近：

```text
输入：过去做工程的全过程
输出：更强的“从想法到现实”的转换机制
```

因此项目叙事、个人叙事、ADR、知识卡、语言弹药、任务和 Better Loop 类评估框架，可以在元工程层汇合。

元工程不是某个固定软件模块，而是 DCF 能够长期观察：

```text
我做了什么
为什么这样做
哪里失败
工程结果暴露了什么认知缺口
我因此学会了什么新的区分
新的区分又怎样改变下一次工程
```

---

## 4.11 Qoder 类知识与项目工作路线的适用位置

从个人叙事或项目叙事形成稳定项目世界以后，可以借鉴 Qoder 类系统的结构思想：

```text
叙事
↓
当前知识 / 知识卡
↓
面向人或 Agent 的知识投影
↓
缺口发现
↓
任务
↓
AI 工作 Harness
↓
现实行动
↓
新现实重新进入 DCF
```

但 DCF 不复制 Qoder 的历史模型。

DCF 必须保留：

- 个人叙事与项目叙事的交叉引用；
- 用户校准产生的新认知；
- 项目边界与理解变化的历史；
- 当前知识能够回到其叙事与现实来源；
- 当前表示可以更新，但历史变化不能被伪装成从未发生。

---

# 5. 第三类扩展：行动能力扩展

这一层让 DCF 从：

> **保存、理解并组织现实**

进一步变成：

> **能够持续推动现实工作。**

这时开始出现：

```text
任务
执行者
运行
进度
结果
失败
恢复
外部工具
成熟智能体运行时
浏览器
编码智能体
本地模型
```

没有行动层，DCF 仍可以是完整的认知基础设施。

有了行动层，DCF 才进一步成为持续工作的认知与执行系统。

## 5.1 任务来源必须能回到缺口

任务不能只是孤立 Todo。

至少应能够回答：

> **为什么会有这个任务？它正在缩小什么缺口？**

来源可能是：

```text
能力缺口
区分缺口
用户明确目标
项目未闭合问题
知识缺口
现实失败
个人叙事中反复出现的问题
```

任务最终可以由人、规则或 AI 提议，但自动生成的任务不天然等于已经获得执行授权。

## 5.2 正式工作与控制平面

任何可以定义为独立正式工作的任务，无论预期长短，都默认脱离最小控制平面执行。

控制平面只承担：

```text
维护当前活动状态
创建 / 派发任务
接收进度 / 结果 / 失败
原子状态推进
取消 / 超时 / 重试控制
恢复位置
健康检查
保持界面 / 接口 / 诊断可响应
```

判断标准：

> 如果某项工作意外变慢或失败，DCF 是否仍应保持控制能力？

如果答案是“应该”，它就不应把 DCF 本体一起卡死。

## 5.3 成熟智能体运行时

路线未知、高认知、开放世界探索的工作，可以直接使用成熟智能体运行时。

它们负责：

```text
高认知规划
开放探索
新工具
新模型能力
异常诊断
尚未形成稳定方法的任务
```

DCF 不为了“完全自研”而复制整个智能体生态。

## 5.4 行动结果不能直接宣布知识为真

必须坚持：

```text
Agent 执行成功
≠
某项长期判断已经为真
```

正确闭环是：

```text
任务
↓
行动
↓
现实发生变化
↓
DCF 重新观察
↓
新的交互记录 / 项目事实 / 用户理解
↓
重新进入叙事与认知循环
```

执行系统制造现实；认知系统解释现实意味着什么。

## 5.5 行动扩展当前实施门禁

必须明确程序可能死在：

```text
记录任务
派发
真实副作用发生
记录结果
```

任意两步之间时：

- 如何判断真实副作用是否已经发生；
- 如何判断是否应该重试；
- 如何避免静默重复不可逆副作用；
- 如何诚实表达“未知”。

这个问题阻塞行动能力扩展，不阻塞基础 DCF 的认知闭环。

# 6. 第四类扩展：规模化 AI 执行与 ECS 工业化

这一层解决的不是：

> “DCF 有没有 AI？”

而是：

> **当 AI 工作已经大量重复时，怎样把它从很多分散控制流变成机器容易批量处理的数据。**

当前候选结构：

```text
Bun
+
Becsy
+
DCF 自研智能执行核
+
外部执行器
```

Becsy 是 DCF 的活动计算状态层，不是长期业务数据库。

## 6.1 活动世界

Becsy 中：

```text
实体
→ 当前世界里存在的活动对象

组件
→ 对象当前的一小块状态数据

系统
→ 专门处理某类状态的功能机器

查询
→ 系统的接活条件

世界
→ 当前活动对象与状态总表
```

核心原则：

```text
身份 ≠ 数据 ≠ 处理逻辑
```

长期事实继续存在于持久层。

活动世界只保存当前正在发生什么。

## 6.2 高级语义状态机

高级语义状态机是高认知计划与机器执行之间的中间表示。

它表达：

```text
当前语义阶段
已有证据 / 结果
还缺什么
合法下一步
什么时候调用 AI 判断
什么时候确定性推进
什么时候必须升级
完成条件
```

AI 仍然可以做复杂语义判断，但不再重新发明整个研究方法。

当现有结构吃不掉现实情况时，必须显式产生：

```text
残差
+
需要升级
```

再交给更高自由度 AI。

禁止低自由度执行器为了“继续跑”而自行扩大自由度或假装成功。

## 6.3 自研智能执行核

DCF 自研智能执行核不追求成为通用智能体框架。

它只需要掌握结构化执行边界：

```text
活动语义状态
↓
发起一次模型推理
↓
取得 0..N 个动作意图
↓
在真实执行前把动作意图暴露成数据
↓
等待外部执行结果
↓
把结果重新注入
↓
继续状态推进
```

模型一次提出多个动作是允许的。

DCF 追求的不是最大控制权，而是最大可重组性。

## 6.4 逻辑动作与物理执行

必须区分：

```text
逻辑动作
→ 某个调用者真正等待的因果身份

物理执行
→ 为满足一个或多个逻辑动作实际进行的现实工作
```

可以压缩物理工作量，不能压掉：

```text
调用者身份
继续位置
取消语义
证据来源
追踪关系
```

## 6.5 效果投影

DCF 不重新包装所有第三方工具协议。

只在存在可靠信息时，抽取一个薄的效果投影：

```text
资源 / 范围
读取集合
写入集合
效果类型
顺序约束
载荷引用
继续位置引用
```

效果投影是优化权限，不是外部工具接入门槛。

```text
效果明确
→ 可以利用确定性性质优化

效果未知 / 不完整
→ 仍然允许执行
→ 默认不可去重
→ 默认不可合并
→ 默认不可跨越未知因果边界重排
```

## 6.6 ECS 优化

高度同质工作可以产生：

```text
重复读取 → 共享结果
相同请求 → 缓存 / 去重
显式可结合操作 → 合并
可批量调用 → 批处理
```

即使工作不能合并，也可以通过热 / 冷数据分离、紧凑状态布局、按资源分组、时序重排、减少锁竞争与上下文切换等方式获得机器执行收益。

不得为了寻找可能不存在的优化机会，让所有请求先支付昂贵 AI 语义判断成本。

## 6.7 因果边界

只能在证明不会改变语义的范围内改变执行顺序。

```text
能证明顺序可以交换
→ 可以重排

不知道顺序是否重要
→ 不重排
```

存在明确先后因果、数据依赖或顺序约束的逻辑动作，禁止被优化器跨越。

## 6.8 共享现实资源边界

成熟智能体运行时一旦碰触 DCF 共享现实资源，例如：

```text
共享 Git 工作区
共享浏览器上下文
共享文件
共享本地 GPU
共享数据库
```

必须二选一：

```text
A. 获得隔离世界

或

B. 进入 DCF 的资源 / 效果边界
```

不能让一个黑盒智能体绕过资源模型偷偷修改共享现实。

## 6.9 规模化执行当前实施门禁

必须明确：

- 哪些组件只是可以丢弃的瞬态；
- 哪些语义进度在整个 DCF 进程崩溃后必须恢复；
- 哪些可以确定地标记失败并重新开始；
- 哪些状态必须写入持久运行收据。

不要求持久化整个 Becsy 世界。

# 7. 第五类扩展：能力成熟与下沉

这一层解决：

> **怎样把成熟智能体生态里已经被我们真正理解的高频工作，逐渐收回到 DCF 自己的高效执行结构。**

默认生命周期：

```text
成熟智能体运行时自由探索
↓
真实运行留下轨迹
↓
发现稳定、高频、有效模式
↓
抽取执行模板
↓
形成高级语义状态机
↓
下沉到 DCF 智能执行核
↓
Becsy / ECS 规模运行
↓
出现残差
↓
重新升级给高自由度智能体
```

成熟智能体运行时是前沿探索区。

DCF 自研执行层是成熟能力收割区。

## 7.1 执行模板版本

一个语义执行实例一旦创建，就必须知道自己基于哪个执行模板版本。

新模板禁止静默重新解释已经存在或正在运行的实例。

是否允许显式迁移、如何迁移可以以后定义，但迁移必须是可见状态变化。

## 7.2 下沉必须经过行为等价验证

能力下沉必须经过候选 / 影子运行 / 现实重放式验证：

```text
成熟路径
= 当前参考行为

执行模板候选
↓
影子运行 / 现实重放
↓
比较结果质量、失败边界、成本 / 延迟、残差率
↓
满足验收
↓
正式提升
```

DCF 学习的是稳定工作方法，不复制第三方运行时内部实现和快速变化接口。

# 9. 当前盲点按概念层级归位

## 9.1 基础 DCF 的盲点

### 机器编制的稳定句式 / 编码合同

已经确定第二阶段是面向 AI 的确定性机器编制层，但正式实现前仍需压实：

```text
哪些原始字段必须进入编制记录
工具调用如何编码
重复与失败如何表示
来源定位最小保留什么
怎样验证编制规则可重放且不会偷偷加入解释
```

### 认知变化的最小结构

“旧理解禁止覆盖、新理解必须追加”已经确定。

仍需要最小结构足以表达：

```text
理解形成时间
主要指向的历史时期 / 对象
理解内容
它在补充 / 修正 / 重新解释哪个旧理解
形成主体
必要来源定位
```

目标不是建立庞大知识图谱，而是确保未来真的能展示认知变化。

## 9.2 观察与证据层的盲点

公共能力黑洞已经完成本机行为验证，但正式长期使用仍需持续验证以下边界：

```text
KnowledgeC 的跨 macOS 版本 schema / 保留行为
IMK + Unified Logging 配置跨重启、跨版本稳定性
IMK 对非输入法文本路径（粘贴、ABC 直键等）的覆盖边界
FSEvents MUST_SCAN_SUBDIRS 等恢复路径
EndpointSecurity / eslogger 的离线缺口与 entitlement 边界
LaunchAgent / launchd 的跨整机重启行为复查
来源适配器升级后的 schema / 路径变化
```

这些盲点的默认处理不是预先自建替代系统，而是：

```text
版本 / 启动探针
↓
行为仍成立 → 继续消费系统事实
行为不成立 → 明确降级 / 标记缺口
↓
只有真实缺口反复成立，才考虑替代实现
```

同时不同来源仍需逐步定义：

```text
稳定事件身份
消费游标
关联策略
确定关系 / 可能关系的标准
```

不需要现在提前统一所有来源的数据 schema。

## 9.3 叙事与项目层的盲点

当前最需要实验的包括：

```text
明示成项的识别规则
涌现成项怎样避免把普通主题聚类误判成项目
个人叙事与项目叙事的最小节点粒度
哪些跨叙事关系值得显式保存
哪些时间关系应查询时动态计算
项目叙事与 GitHub Repository 的绑定 / 拆分 / 合并语义
知识卡从叙事提炼后的来源回链
区分缺口怎样验证已经真正进入人的稳定判断
元工程如何避免变成空泛总结
```

## 9.4 行动扩展的盲点

当前最重要的是：

> **任务 / 结果崩溃边界与不可逆副作用幂等。**

同时任务生成需要继续闭合：

```text
如何把缺口变成候选任务
候选任务何时需要用户裁决
不同项目如何定义自己的验收方式
```

## 9.5 规模化执行扩展的盲点

当前最重要的是 Becsy 活动世界在整个 DCF 进程死亡后的语义恢复边界。

# 10. 自动验收原则

> **锁定“做成什么才算对”，不要锁死“代码必须怎么写”。**

每一项进入正式实现的能力，都至少应回答一个反例问题：

> 出现什么现实运行现象，就能证明这项能力实际上没有实现？

例如：

```text
机器编制
→ 编制输出夹带 AI 对用户动机的猜测，并被当成事实字段
→ 立即判失败

现实事实所有权
→ macOS / 来源已经维护确定事实，DCF 又建立第二套权威并发生漂移
→ 判失败

用户表达事实
→ 系统声称捕获用户提交，但无法区分最终 insertText 与中间 composition
→ 判失败

来源适配器
→ 明明能直接读取 Codex thread，却改用 OCR 猜测 AI 回复
→ 判失败

AI 关系叙事
→ 只能生成逐条摘要，无法把相关记录组织成能唤醒人的关系与情境
→ 判失败

用户校准
→ 用户后来纠正 AI 后，旧 AI 叙事被直接改成新版本
→ 立即判失败

个人 / 项目交叉引用
→ 项目中的关键概念无法反查个人思想来源，个人时间线也看不到同期项目进展
→ 判失败

GitHub 对接
→ DCF 自己复制并维护一套 Commit / Branch 真相，且与 GitHub 发生漂移
→ 判失败

任务来源
→ 系统生成大量任务，却无法回答各自在缩小什么缺口
→ 判失败

控制平面隔离
→ 一个正式任务卡死后，DCF 无法查询或取消其他任务
→ 立即判失败

读取去重
→ 宣称去重，但 100 个相同逻辑读取仍发生 100 次物理读取
→ 立即判失败

残差升级
→ 给语义状态机一个未定义情况，它自行猜测路线继续
→ 立即判失败
```

代码存在、模拟测试通过、文档宣称支持，都不能单独构成现实行为证据。

# 11. 当前明确不提前锁死的内容

以下继续保留给实现与实验：

```text

是否未来需要图数据库
叙事节点的最终粒度
跨叙事关系类型全集
机器编制句式的最终语法

来源适配器数量与具体 App 覆盖顺序
具体组件内存布局
具体运行数据库结构
具体数据库事务实现
具体工作线程 / 外部进程技术
具体调度器 / 求解器算法
具体批处理算法

外部接口术语字典
```

只要这些选择不违反对应概念层的不变量，就不应为了“实现闭合”而提前规定。

# 12. 一句话总结

> **DCF 先从来源自己的高语义事实和 macOS 已经维护的公共现实面中取得真实材料——KnowledgeC 管活动时间骨架，IMK 管用户表达，FSEvents / Spotlight 管文件世界，ES 管 Agent 行动收据，Git / GitHub 管确定性工程事实，来源适配器负责各软件自己的完整语义；DCF 不重新拥有这些现实，只把它们确定性地编成 AI 可重新读取的记录。随后 AI 把相关历史编织成人能重新进入过去的关系叙事，人被叙事唤醒后进行复盘与校准，新的认知继续长成个人叙事与项目叙事。项目成项后尽量借用 GitHub 保存确定性工程现实，两种叙事通过时间与思想来源彼此穿透，并分别提炼知识、发现能力缺口与区分缺口。对能力缺口的工程改变世界，对区分缺口的工程提高人的认知分辨率；两者互相反馈时，DCF 开始形成“如何把想法变成现实”的元工程能力。**
