# DCF 项目叙事机制与 UI 规范

**状态：讨论稿 v0.3**  
**日期：2026-08-05**  
**用途：项目叙事、项目识别、立项、项目成熟度、项目形态图及相关 Surface 的当前讨论基线。**

---

# 1. 核心定义

项目叙事不是日记，不是 Git Log，也不是项目 Wiki。

它回答的是：

> **这个项目是什么，它怎样一路长成今天这个样子，过程中哪些重要理解、方向和结构发生过改变。**

因此：

> **项目组织叙事，时间定位叙事。**

时间必须保存并显示，但不是项目叙事的主组织轴。

个人叙事天然可以按日期形成；项目叙事则围绕持续存在的“项目身份”形成。

---

# 2. 项目叙事不是每日流水账

个人叙事是项目叙事的重要材料源，但不存在：

```text
每日个人叙事
↓
每日项目叙事
```

这种一一映射。

很多个人叙事当天可能：

- 看不出属于哪个项目；
- 证据不足；
- 只是零散念头；
- 同时涉及多个方向；
- 最终根本不会形成项目。

这些都允许暂时不进入任何项目叙事。

更自然的过程是：

```text
个人叙事
GitHub / 系统事实
AI 交互
实验结果
后续几天的新理解
        ↓
材料与证据逐渐聚集
        ↓
形成项目判断
        ↓
编入某个项目的项目叙事
```

因此，一段项目叙事可以覆盖数天甚至更长时间。

---

# 3. 项目识别的主要证据

项目结构允许 AI 推断，但不能无依据分类。

当前主要证据来源分为三类。

## 3.1 GitHub / 原生工程事实

GitHub 最适合证明：

- repo 存在；
- branch 存在；
- commit 连续发展；
- 独立实现持续存在；
- 某次工程结构变化确实发生；
- 一个工程方向已经形成持续活动。

GitHub 是**工程现实的强证据**。

但 GitHub 不能独立决定“这个变化在人类意义上是不是一个新项目”。

## 3.2 用户在个人叙事中的明确表达

例如：

> “这个方向现在应该独立成项目。”

或者：

> “这不是新项目，它只是 DCF 的内部实验。”

这种表达是项目意义上的高权重证据。

因此：

```text
GitHub / 原生系统
→ 工程事实强

用户明确表达
→ 项目意义强
```

两者分别在自己擅长的事实类型上拥有高权重。

## 3.3 AI 的高度概然判断

如果连续材料里长期出现：

- 相同的问题空间；
- 独立的问题边界；
- 一系列相关实验；
- 自己的结论；
- 自己的后续问题；

即使用户从未明确说“创建项目”，AI 也可以判断：

> **这里似乎正在长出一个独立项目。**

但这种判断首先形成的不是正式项目，而是**推荐项目**。

---

# 4. 推荐项目：项目身份之前的萌芽

低成熟度、证据尚不足的项目假说，可以作为“推荐项目”存在。

推荐项目的作用不是管理，而是：

> **向用户指出：这里好像正在形成一个值得注意的持续方向。**

推荐项目允许：

- 消失；
- 改名；
- 合并；
- 并入已有项目；
- 长期保持观察；
- 最终什么都不成为。

所以：

> **推荐项目可以大胆，正式项目必须有门槛。**

项目首页应把推荐项目作为洞察区域展示，而不是和正式项目混为一类。

---

# 5. 立项与成熟度彻底解耦

**项目成熟度和“能不能立项”是两个不同问题。**

立项回答：

> **这个方向凭什么获得一个正式项目身份？**

成熟度回答：

> **这个已经存在的项目，已经在多大程度上被整理成 AI 容易正确理解、自然接手、可靠继续推进的形态？**

因此：

- 正式项目可以成熟度仍然很低；
- 推荐项目可能已经积累很多材料，但仍然不满足立项条件；
- 不能用一个简单的“成熟度超过 60 分”替代立项门禁；
- 成熟度不承担项目身份裁决；
- 成熟度主要用于指引项目怎样变得更适合 AI 持续推进。

一句话：

> **立项判断项目有没有继续生长的资格；成熟度判断项目自身已经为后续 AI 准备好了多少。**

---

# 6. 三种合法立项路径

正式项目可以通过三条不同路径获得项目身份。

## 6.1 现实立项

如果现实系统已经明确创建了一个独立项目，例如 GitHub 中已经存在明确独立 repo / project，并出现持续工程事实，则 DCF 应承认项目已经存在。

流程：

```text
GitHub / 现实系统明确项目
↓
DCF 承认项目身份
↓
AI 补齐《立项说明》
↓
形成 ADR-000
```

这里《立项说明》不是审批材料，而是把现实中已经存在的项目纳入 DCF 的认知系统。

## 6.2 用户立项

如果用户明确表达：

> “这个单独开一个项目。”

则项目身份直接成立。

AI 不能用“成熟度不足”“证据不足”阻止用户立项。

流程：

```text
用户明确立项
↓
项目身份成立
↓
AI 根据现有材料生成《立项说明》
↓
形成 ADR-000
```

项目是否值得用户亲自立项，本来就属于用户判断权。

## 6.3 涌现立项

没有 GitHub 明确项目，也没有用户明确要求立项时，AI 可以在后台静默观察材料的持续聚集。

最初只是：

```text
零散材料
↓
项目假说
↓
推荐项目
```

随着证据增加，如果材料已经形成一套能够驱动未来持续发展的结构，AI 才有资格完成**涌现立项**。

这是最适合后台静默推进的立项路径。

---

# 7. 涌现立项的硬门槛：可持续推进结构

涌现立项不能只因为“有一个契机”或“材料很多”。

真正的门槛是：

> **现有材料必须已经形成一套足以指导项目继续自然生长的结构。**

它至少必须可靠回答四个问题。

## 7.1 为什么做？——需求

必须存在一个值得持续解决的问题、目标或缺口。

可能来自：

- 用户个人叙事；
- 重复出现的问题；
- 已有项目无法吸收的新问题；
- 现实世界中的持续需求。

## 7.2 凭什么认为它真实存在？——事实基础

必须有足够材料证明这不是 AI 临时幻想出来的主题。

可能包括：

- Git / GitHub；
- 实验；
- 交互记录；
- 个人叙事；
- 现实行为；
- 系统事实。

## 7.3 靠什么继续做？——推进能力

必须已经存在能够继续推进该方向的能力基础。

可能包括：

- 现有工具；
- Skill；
- 代码；
- 外部系统；
- 方法论；
- 已积累的项目能力。

## 7.4 接下来怎样自然继续？——推进路径

这是涌现立项最关键的条件。

项目不能只是“这个主题很有意思”，而必须已经能够产生后续行动。

可能的证据包括：

- 下一轮明确问题；
- 可执行实验路线；
- 知识卡；
- 相关技能；
- 设计框架；
- 方法论；
- 可验证假说；
- 已知下一阶段实现路径。

如果 AI 无法回答：

> **“然后呢？这个项目下一步自然做什么？”**

则它仍然更像一个主题、兴趣或知识聚类，不应因为材料丰富就自动立项。

---

# 8. 立项门槛约束结构，而不是固定工件

涌现立项不应死板规定：

```text
必须有 GitHub
必须有知识卡
必须有 Skill
必须有某一种文档
```

不同项目需要不同证据组合。

例如研究项目可能依靠：

```text
明确需求
+
现实证据
+
实验方法
+
知识卡
+
下一轮实验问题
```

软件项目可能依靠：

```text
明确需求
+
GitHub 原型
+
技术能力
+
可执行 Skill
+
架构方案
+
下一阶段实现路径
```

个人型项目可能依靠：

```text
长期稳定目标
+
连续个人叙事
+
已经形成的方法
+
能够持续产生行动的路径
```

所以硬门槛检查的是：

> **结构是否已经完整到可以持续推进。**

而不是某一种固定文件是否存在。

---

# 9. 《立项说明》与 ADR-000

任何正式项目都必须形成一份最小《立项说明》。

它不是长篇商业计划书，而是项目身份的根锚点。

最低应说明：

- 项目名称；
- 为什么存在；
- 准备解决什么；
- 不准备解决什么；
- 从哪里长出来；
- 当前有哪些事实与证据；
- 当前具备哪些推进能力；
- 接下来怎样继续；
- 与父项目 / 其他项目是什么关系。

正式立项本身形成该项目第一个 ADR 级节点：

```text
ADR-000
项目立项
```

因此，正式项目从出生开始就天然拥有：

- 身份；
- 来路；
- 边界；
- 第一批证据；
- 推进能力；
- 后续方向；
- 第一段正式项目叙事。

不存在一个只有名字的空项目。

# 10. 后台涌现立项流程

涌现立项特别适合交给 AI 后台静默推进。

推荐流程：

```text
新材料不断进入
        ↓
尝试匹配现有项目
        ↓
无法稳定匹配
        ↓
形成项目假说
        ↓
显示为推荐项目
        ↓
后台继续积累与归并材料
        ↓
需求        ✓
事实基础    ✓
推进能力    ✓
推进路径    ✓
        ↓
生成《立项说明》
        ↓
形成 ADR-000
        ↓
涌现项目正式成立
```

对于涌现立项，当前设计倾向于：

> **只要硬门槛已经满足，不需要再额外弹窗要求用户确认。**

原因：

- 正式立项前已经保留了较高门槛；
- 推荐项目阶段可以长时间观察；
- DCF 允许后续证据重新组织项目当前表示；
- 用户仍然能在项目总览的“最近形成”中看见新项目；
- 如果后续发现误判，可并回、拆分或重新解释，而旧判断仍保留在认知历史中。

这使 AI 可以真正承担后台整理与洞察工作，而不是每次发现结构都把判断重新丢回用户。

# 11. 项目成熟度：AI 可推进成熟度

项目成熟度不是“项目完成百分比”，也不是“项目有多重要”，更不是立项门槛。

它是一个**指引性质的诊断指标**。

正式定义：

> **项目成熟度衡量项目已经在多大程度上把隐含上下文、判断依据、推进方法和验证方式外显化，使 AI 能够低猜测、低重新理解成本地持续推进项目。**

内部可以继续简称 `Project Maturity`，但其真正语义更接近：

> **AI 可推进成熟度。**

成熟度的核心问题不是：

> “这个项目做了多少？”

而是：

> **“一个新的 AI 现在接手它，还需要猜多少？”**

成熟度越高，项目越接近成为一个 AI 可以自然进入、理解、执行、验证并继续积累的工作环境。

## 11.1 Better Harness 只借核心思想，不做 1:1 复刻

Better Harness 的具体评分维度属于编码 Agent 外层工作循环，不直接复制到 DCF 项目成熟度。

DCF 借用的是它更深的一层思想：

```text
发现隐含理解 / 临场猜测 / 人工兜底
        ↓
找出它为什么仍然存在
        ↓
给出最小、owner-aligned 的修复
        ↓
让下一次执行更容易理解、更可靠
```

因此成熟度不是奖杯，也不是一次性评级。

它的真正用途是：

> **不断寻找“AI 下一次还需要猜什么”，然后把这些猜测逐步变成项目自身已经拥有的能力。**

## 11.2 五个主要观察面

当前先采用五个诊断观察面。它们用于帮助 AI 判断缺口，不是硬门禁，也暂不要求固定等权计算。

### 11.2.1 项目可理解性

AI 能否快速回答：

- 为什么有这个项目；
- 它解决什么；
- 不解决什么；
- 核心原则是什么；
- 与其他项目什么关系。

如果每个新 AI 都需要重新阅读大量原始聊天才能理解项目，说明这一项较低。

常见改善来源：

- 《立项说明》；
- 项目叙事；
- ADR；
- 清楚的项目边界；
- 关键概念的项目知识。

### 11.2.2 当前状态可理解性

AI 能否知道：

> **“项目现在到底走到哪里了？”**

至少包括：

- 当前主线；
- 最近的重要 ADR；
- 已经确定的事实与判断；
- 仍是候选的内容；
- 当前未决问题；
- 哪些历史方向已经被替代、封存或分叉。

项目形态图和当前项目叙事主要服务这一观察面。

### 11.2.3 可继续推进性

AI 看懂项目以后，能不能自然回答：

> **“然后呢？”**

可能依靠：

- 当前阶段目标；
- 下一问题；
- 方法论；
- Skill；
- 可调用工具和外部能力；
- 项目知识；
- 实验路线；
- 设计框架；
- 待验证假说。

只有文档很多但不知道下一步怎么走的项目，仍然不是高成熟项目。

### 11.2.4 可验证性

AI 做完一项工作后，能否回答：

> **“我怎么知道这次真的推进了项目，而不是看起来完成了？”**

可能依靠：

- 自动测试；
- 行为验收；
- 实验指标；
- 用户明确判断；
- GitHub / 系统事实；
- 运行时证据；
- 对照实验；
- 后续真实结果。

不能只依赖 AI 自报完成。

### 11.2.5 可积累性

这次工作做完后，是否会让下一次 AI 更容易？

理想的积累路径例如：

```text
一次重要判断
↓
形成 ADR

一次踩坑
↓
形成规则 / Skill / 可复用方法

一次实验
↓
形成知识卡或可复用证据

一次用户纠正
↓
进入认知历史 / 项目叙事

一次稳定能力
↓
成为后续 AI 可直接调用的项目能力
```

如果不同 AI 每次都需要重新理解、重新踩坑、重新设计，即使项目存在很多年，它的 AI 可推进成熟度仍然可能很低。

这一观察面最终关心的是：

> **项目能否把过去的工作转化成未来 AI 的能力。**

## 11.3 项目年龄与成熟度无关

成熟项目不等于存在时间长。

一个刚建立的项目，如果已经具有：

- 清楚的立项说明；
- 明确边界；
- 完整方法；
- 可执行 Skill；
- 验证方式；
- 清晰下一步；

它完全可以拥有较高的 AI 可推进成熟度。

反过来，一个维护十年的项目如果：

- 没有项目叙事；
- 没有 ADR；
- 核心原因只存在于人脑；
- 验证路径不清楚；
- AI 每次都需要重新考古；

它的成熟度仍然可以很低。

## 11.4 成熟度评分是方向提示，不是硬性裁决

成熟度可以有分数，也可以在项目总览用于排序，但分数不是主要产品。

用户更需要看到：

```text
DCF                          成熟度 82

✓ 项目身份清晰
✓ ADR 演化完整
✓ 当前架构可理解
✓ 验收能力较强

△ 下一阶段推进路径分散
  AI 仍需从多个规范中自行拼接下一步。

推荐修复：
  增加一个当前阶段的“继续推进入口”，
  把阶段目标、可用 Skill、未决问题连接起来。
```

因此成熟度输出至少应包含：

1. 当前整体成熟度或成熟区间；
2. 主要强项；
3. 当前仍迫使 AI 猜测的缺口；
4. 一个或少量高杠杆推荐修复；
5. 推荐修复完成后应改善哪个观察面。

## 11.5 推荐修复的原则

推荐修复不追求“大而全治理”。

优先寻找：

> **最小、owner-aligned、能够明显降低下一次 AI 猜测成本的改变。**

例如：

- 缺项目边界 → 补一段边界说明，而不是重写整个仓库文档；
- 缺当前状态 → 生成当前项目状态页，而不是重新整理全部历史；
- 缺验证 → 为关键行为补行为验收，而不是先增加更多设计文档；
- 缺继续路径 → 连接当前问题、Skill 与下一步，而不是增加一个新的管理系统。

成熟度诊断应推动项目变得更可执行，而不是推动文档数量增长。

## 11.6 证据仍然约束成熟度判断，但不必机械复刻 Better Harness ceiling

成熟度是指引性质，但仍不能完全依靠 AI 主观印象。

应保持 Better Harness 的认识论纪律：

- “没有观察到”不能自动等于“不存在”；
- “存在”不能自动等于“已经有效使用”；
- “刚刚补上”不能自动等于“长期有效”；
- 效果性判断需要更强的实际结果支持。

未来可以为不同观察面定义适合项目语义的证据状态与可信区间。

但当前不冻结：

- 固定的五维权重；
- 固定的 59 / 74 / 84 / 94 / 100 ceiling；
- 一套跨所有项目类型完全相同的公式。

原因是成熟度首先服务诊断和推荐修复，而不是制造一个看似精确的统一分数。

# 12. 项目当前结构允许被重新解释

项目识别允许犯错。

可能发生：

- AI 创建错项目；
- 把一个内部阶段误判成独立项目；
- 把两个项目错误合并；
- 选择了错误的分叉点；
- ADR 节点组织不合理。

随着后续证据变厚，当前项目表示允许重新组织：

- 合并误判项目；
- 拆开误合并项目；
- 项目降为项目内部阶段；
- 内部方向升格成独立项目；
- 调整项目出生节点；
- 调整分叉关系；
- 重新组织 ADR 节点；
- 封存；
- 重新激活。

但必须区分：

```text
现实材料
不可覆写

过去形成过的认知
不可偷偷删除

当前项目图 / 当前项目叙事投影
可以重新编译
```

因此：

> **现实不可重写，地图可以重画；重画地图本身也属于认知历史。**

---

# 13. 项目图节点：ADR 级变化

项目形态图不是事件流，也不是 Git commit 图。

图上的正式节点表示：

> **ADR 级项目认知变化。**

只有当项目的：

- 目标；
- 方向；
- 边界；
- 架构；
- 核心理解；
- 项目状态；

发生足以留下“为什么改变”的变化时，才形成新节点。

普通 bug 修复、文案修改、连续实现、一般测试、没有核心认识变化的讨论，不必形成独立形态节点。

一个 ADR 节点至少应讲清：

```text
之前是什么？
↓
为什么不能继续？
↓
现在变成什么？
↓
这次改变影响了什么？
```

项目图展示的不是“发生过多少事”，而是项目怎样一步步变成今天这样。

---

# 14. 项目分叉与跨项目关系

## 14.1 同项目内部探索

如果不同路线仍属于同一项目的问题空间，可以继续作为同项目内部探索存在。

## 14.2 分叉为独立项目

一旦某个方向正式获得独立项目身份，父项目不继续展开它的所有后续节点。

父项目只留下一个**虚框项目入口**：

```text
● 本项目 ADR
│
├──────┐
│      ┌ ─ ─ ─ ─ ─ ─ ┐
│        新独立项目
│      └ ─ ─ ─ ─ ─ ─ ┘
│
● 本项目后续 ADR
```

虚框表示：

> **这里从当前项目里长出了另一个独立项目。**

点击虚框直接切换到对方项目页面。

## 14.3 成果回流

独立项目的成果可以回流其他项目，但成果回流不意味着来源项目身份消失。

因此：

> **同项目内部路线可以合流；独立项目之间更常见的是成果流动。**

---

# 15. 项目状态

项目至少允许：

```text
推荐
正式
活跃
长期不活跃
阶段完成
封存
重新激活
```

“不活跃”和“封存”不同。

长期不活跃只是最近没有继续推进。

封存表示当前明确不再作为活跃项目推进，但历史身份仍然存在，未来仍可重新激活。

# 16. 项目叙事三级 UI

项目叙事采用三级展开。

---

## UI 第一层：项目总览

回答：

> **“我现在有哪些项目？”**

项目以卡片为基础形态。

排序优先考虑：

```text
高成熟度项目
+
最近形成项目
+
最近重新活跃项目
```

长期不活跃与封存项目自然沉到底部。

成熟度在这里主要作为**阅读优先级与可推进程度提示**，不是项目资格标识。

推荐项目单独作为“可能正在形成 / 洞察”区域展示，并与正式项目视觉区分。

正式项目是实体卡。

推荐项目应呈现“尚未完全成为一个东西”的视觉感觉，例如更轻、半透明或雾化，但不要和项目形态图中的跨项目虚框入口使用完全相同的视觉语义。

---

## UI 第二层：项目形态图

点击项目以后，不立刻进入长篇叙事。

首先回答：

> **“这个项目现在长成什么样了？”**

核心规则：

### 倒叙

当前永远优先：

```text
现在
↓
最近 ADR
↓
更早 ADR
↓
……
↓
ADR-000 立项
```

用户不需要从项目出生开始读到今天。

### 实心节点

表示本项目 ADR 级认知变化。

### 实线

表示本项目自身连续演化。

### 虚框项目入口

表示这里从当前项目中诞生了另一个独立项目。

点击后直接切换项目。

### 时间

每个节点保留时间戳 / 时间范围。

但：

> **时间是坐标，不是组织框架。**

---

## UI 第三层：正式项目叙事

点击一个 ADR 节点以后，进入完整项目叙事。

它回答：

> **“这个节点到底意味着什么？”**

正文采用自然可读叙事，而不是 ADR 表格。

主要解释：

- 此前我们怎样理解；
- 后来发现了什么；
- 为什么改变；
- 现在怎样理解；
- 对项目造成了什么影响。

正文中可以自然下钻到：

- 概念 / 项目知识；
- 其他项目；
- 规范；
- GitHub；
- 实验；
- 个人叙事；
- 原始证据；
- 认知历史。

这些都是穿透入口，不与项目叙事争夺主阅读位置。

---

# 17. 项目叙事是项目域面向人的主要阅读界面

项目叙事是项目域中人类理解项目的主要终点。

其他能力围绕它继续生长：

```text
项目叙事
├─ 概念 → 项目知识
├─ 为什么这样判断 → 证据
├─ 现实发生什么 → Git / 系统事实
├─ 我们以前怎样理解 → 认知谱系
├─ 项目从哪里来 → 来源项目
└─ 接下来做什么 → 任务 / 行动
```

项目知识、Memory、经验与规则原则上主要服务项目自身及 AI。

用户需要时仍然必须拥有优秀的维护 UI，以重新理解和掌控系统，但这些维护 UI 不应制造第二套与项目叙事竞争的人类主阅读产品。

# 19. 当前已冻结的核心原则

> **项目组织叙事，时间定位叙事。**

> **不是所有个人叙事都必须立刻进入项目叙事。**

> **推荐项目是洞察，不是正式身份。**

> **项目成熟度与是否立项无关。**

> **项目可以由现实创建、由用户创建，也可以从证据中涌现。**

> **用户明确立项拥有最高项目意义判断权，不能被 AI 以成熟度不足阻止。**

> **AI 只有在材料已经形成“可持续推进结构”时，才有权完成涌现立项。**

> **涌现立项的硬门槛不是固定工件清单，而是需求、事实基础、推进能力和推进路径共同形成的结构完整性。**

> **正式项目从 ADR-000 开始，不允许只有名字的空项目。**

> **立项判断项目有没有继续生长的资格；成熟度判断项目自身已经为后续 AI 准备好了多少。**

> **项目成熟度是指引性质的 AI 可推进成熟度，不是完成率、项目价值或项目资格评分。**

> **成熟度的核心问题是“一个新的 AI 接手项目时，还需要猜多少”。**

> **成熟度诊断不是为了增加文档，而是为了把隐含理解、判断依据、推进方法和验证方式逐步变成项目自身能力。**

> **成熟度输出应优先给出高杠杆推荐修复，而不是只给一个分数。**

> **Better Harness 在这里提供认识论和修复思想，不做业务维度与评分公式的 1:1 复刻。**

> **项目形态节点代表 ADR 级认知变化，而不是普通事件。**

> **AI 可以识别错项目、错分叉、错节点；当前项目地图允许随着证据增厚重新组织。**

> **现实不可重写，地图可以重画；重画地图本身也属于认知历史。**

> **独立项目可以分叉出去；父项目只保留跨项目入口。**

> **成果可以跨项目回流，但来源项目的历史身份不因此消失。**

> **项目叙事是项目域面向人的主要阅读界面。**

---

# 20. 尚未冻结的问题

后续继续讨论：

1. 五个成熟度观察面是否足够，是否需要合并或增加；
2. 成熟度是否需要单一总分，还是以成熟区间 + 观察面诊断为主；
3. 各观察面的证据状态如何定义，怎样保留 Better Harness“没有观察到 ≠ 不存在”的纪律；
4. 推荐修复怎样排序，如何识别真正的高杠杆最小修复；
5. 怎样验证某项成熟度修复确实降低了后续 AI 的理解和执行成本；
6. 涌现立项的四项硬门槛如何形式化为可执行判断，而不退化成死 checklist；
7. AI 静默涌现立项后，用户侧采用什么最低打扰的通知方式；
8. ADR 级变化如何自动识别；
9. 一个方向何时是“同项目内部探索”，何时足以独立成项目；
10. 跨项目成果回流采用什么一等关系；
11. 当前项目图重组后，旧项目图怎样作为历史投影保存；
12. 项目叙事是否复用个人叙事已经确定的“AI 草稿 → 用户审阅 → 正式历史”机制；
13. 三级 Surface 最终视觉与交互细节。
