# DCF 项目叙事机制与 UI 规范

**状态：讨论稿 v0.2**  
**日期：2026-08-05**  
**用途：项目叙事、项目识别、立项、项目形态图及相关 Surface 的当前讨论基线。**

---

# 1. 核心定义

项目叙事不是日记，不是 Git Log，也不是项目 Wiki。

它回答的是：

> **这个项目是什么，它怎样一路长成今天这个样子，过程中哪些重要理解、方向和结构发生过改变。**

因此：

> **项目组织叙事，时间定位叙事。**

时间必须保存并显示，但不是项目叙事的主组织轴。

个人叙事天然可以按日期形成；项目叙事则围绕持续存在的“项目身份”形成。

---

# 2. 项目叙事不是每日流水账

个人叙事是项目叙事的重要材料源，但不存在：

```text
每日个人叙事
↓
每日项目叙事
```

这种一一映射。

很多个人叙事当天可能：

- 看不出属于哪个项目；
- 证据不足；
- 只是零散念头；
- 同时涉及多个方向；
- 最终根本不会形成项目。

这些都允许暂时不进入任何项目叙事。

更自然的过程是：

```text
个人叙事
GitHub / 系统事实
AI 交互
实验结果
后续几天的新理解
        ↓
材料与证据逐渐聚集
        ↓
形成项目判断
        ↓
编入某个项目的项目叙事
```

因此，一段项目叙事可以覆盖数天甚至更长时间。

---

# 3. 项目识别的主要证据

项目结构允许 AI 推断，但不能无依据分类。

当前主要证据来源分为三类。

## 3.1 GitHub / 原生工程事实

GitHub 最适合证明：

- repo 存在；
- branch 存在；
- commit 连续发展；
- 独立实现持续存在；
- 某次工程结构变化确实发生；
- 一个工程方向已经形成持续活动。

GitHub 是**工程现实的强证据**。

但 GitHub 不能独立决定“这个变化在人类意义上是不是一个新项目”。

## 3.2 用户在个人叙事中的明确表达

例如：

> “这个方向现在应该独立成项目。”

或者：

> “这不是新项目，它只是 DCF 的内部实验。”

这种表达是项目意义上的高权重证据。

因此：

```text
GitHub / 原生系统
→ 工程事实强

用户明确表达
→ 项目意义强
```

两者分别在自己擅长的事实类型上拥有高权重。

## 3.3 AI 的高度概然判断

如果连续材料里长期出现：

- 相同的问题空间；
- 独立的问题边界；
- 一系列相关实验；
- 自己的结论；
- 自己的后续问题；

即使用户从未明确说“创建项目”，AI 也可以判断：

> **这里似乎正在长出一个独立项目。**

但这种判断首先形成的不是正式项目，而是**推荐项目**。

---

# 4. 推荐项目：项目身份之前的萌芽

低成熟度、证据尚不足的项目假说，可以作为“推荐项目”存在。

推荐项目的作用不是管理，而是：

> **向用户指出：这里好像正在形成一个值得注意的持续方向。**

推荐项目允许：

- 消失；
- 改名；
- 合并；
- 并入已有项目；
- 长期保持观察；
- 最终什么都不成为。

所以：

> **推荐项目可以大胆，正式项目必须有门槛。**

项目首页应把推荐项目作为洞察区域展示，而不是和正式项目混为一类。

---

# 5. 立项与成熟度彻底解耦

**项目成熟度和“能不能立项”是两个不同问题。**

成熟度回答：

> **这个已经存在的项目，后来发展得有多稳定、多完整、多经验证？**

立项回答：

> **这个方向凭什么获得一个正式项目身份？**

因此：

- 正式项目可以成熟度仍然很低；
- 推荐项目可能已经积累很多材料，但仍然不满足立项条件；
- 不能用一个简单的“成熟度超过 60 分”替代立项门禁；
- 成熟度未来可以借鉴 Better Harness 的“证据限制评分上限”机制，但不承担项目身份裁决。

一句话：

> **立项判断项目有没有继续生长的资格；成熟度判断它后来究竟长得怎么样。**

---

# 6. 三种合法立项路径

正式项目可以通过三条不同路径获得项目身份。

## 6.1 现实立项

如果现实系统已经明确创建了一个独立项目，例如 GitHub 中已经存在明确独立 repo / project，并出现持续工程事实，则 DCF 应承认项目已经存在。

流程：

```text
GitHub / 现实系统明确项目
↓
DCF 承认项目身份
↓
AI 补齐《立项说明》
↓
形成 ADR-000
```

这里《立项说明》不是审批材料，而是把现实中已经存在的项目纳入 DCF 的认知系统。

## 6.2 用户立项

如果用户明确表达：

> “这个单独开一个项目。”

则项目身份直接成立。

AI 不能用“成熟度不足”“证据不足”阻止用户立项。

流程：

```text
用户明确立项
↓
项目身份成立
↓
AI 根据现有材料生成《立项说明》
↓
形成 ADR-000
```

项目是否值得用户亲自立项，本来就属于用户判断权。

## 6.3 涌现立项

没有 GitHub 明确项目，也没有用户明确要求立项时，AI 可以在后台静默观察材料的持续聚集。

最初只是：

```text
零散材料
↓
项目假说
↓
推荐项目
```

随着证据增加，如果材料已经形成一套能够驱动未来持续发展的结构，AI 才有资格完成**涌现立项**。

这是最适合后台静默推进的立项路径。

---

# 7. 涌现立项的硬门槛：可持续推进结构

涌现立项不能只因为“有一个契机”或“材料很多”。

真正的门槛是：

> **现有材料必须已经形成一套足以指导项目继续自然生长的结构。**

它至少必须可靠回答四个问题。

## 7.1 为什么做？——需求

必须存在一个值得持续解决的问题、目标或缺口。

可能来自：

- 用户个人叙事；
- 重复出现的问题；
- 已有项目无法吸收的新问题；
- 现实世界中的持续需求。

## 7.2 凭什么认为它真实存在？——事实基础

必须有足够材料证明这不是 AI 临时幻想出来的主题。

可能包括：

- Git / GitHub；
- 实验；
- 交互记录；
- 个人叙事；
- 现实行为；
- 系统事实。

## 7.3 靠什么继续做？——推进能力

必须已经存在能够继续推进该方向的能力基础。

可能包括：

- 现有工具；
- Skill；
- 代码；
- 外部系统；
- 方法论；
- 已积累的项目能力。

## 7.4 接下来怎样自然继续？——推进路径

这是涌现立项最关键的条件。

项目不能只是“这个主题很有意思”，而必须已经能够产生后续行动。

可能的证据包括：

- 下一轮明确问题；
- 可执行实验路线；
- 知识卡；
- 相关技能；
- 设计框架；
- 方法论；
- 可验证假说；
- 已知下一阶段实现路径。

如果 AI 无法回答：

> **“然后呢？这个项目下一步自然做什么？”**

则它仍然更像一个主题、兴趣或知识聚类，不应因为材料丰富就自动立项。

# 8. 立项门槛约束结构，而不是固定工件

涌现立项不应死板规定：

```text
必须有 GitHub
必须有知识卡
必须有 Skill
必须有某一种文档
```

不同项目需要不同证据组合。

例如研究项目可能依靠：

```text
明确需求
+
现实证据
+
实验方法
+
知识卡
+
下一轮实验问题
```

软件项目可能依靠：

```text
明确需求
+
GitHub 原型
+
技术能力
+
可执行 Skill
+
架构方案
+
下一阶段实现路径
```

个人型项目可能依靠：

```text
长期稳定目标
+
连续个人叙事
+
已经形成的方法
+
能够持续产生行动的路径
```

所以硬门槛检查的是：

> **结构是否已经完整到可以持续推进。**

而不是某一种固定文件是否存在。

---

# 9. 《立项说明》与 ADR-000

任何正式项目都必须形成一份最小《立项说明》。

它不是长篇商业计划书，而是项目身份的根锚点。

最低应说明：

- 项目名称；
- 为什么存在；
- 准备解决什么；
- 不准备解决什么；
- 从哪里长出来；
- 当前有哪些事实与证据；
- 当前具备哪些推进能力；
- 接下来怎样继续；
- 与父项目 / 其他项目是什么关系。

正式立项本身形成该项目第一个 ADR 级节点：

```text
ADR-000
项目立项
```

因此，正式项目从出生开始就天然拥有：

- 身份；
- 来路；
- 边界；
- 第一批证据；
- 推进能力；
- 后续方向；
- 第一段正式项目叙事。

不存在一个只有名字的空项目。

# 10. 后台涌现立项流程

涌现立项特别适合交给 AI 后台静默推进。

推荐流程：

```text
新材料不断进入
        ↓
尝试匹配现有项目
        ↓
无法稳定匹配
        ↓
形成项目假说
        ↓
显示为推荐项目
        ↓
后台继续积累与归并材料
        ↓
需求        ✓
事实基础    ✓
推进能力    ✓
推进路径    ✓
        ↓
生成《立项说明》
        ↓
形成 ADR-000
        ↓
涌现项目正式成立
```

对于涌现立项，当前设计倾向于：

> **只要硬门槛已经满足，不需要再额外弹窗要求用户确认。**

原因：

- 正式立项前已经保留了较高门槛；
- 推荐项目阶段可以长时间观察；
- DCF 允许后续证据重新组织项目当前表示；
- 用户仍然能在项目总览的“最近形成”中看见新项目；
- 如果后续发现误判，可并回、拆分或重新解释，而旧判断仍保留在认知历史中。

这使 AI 可以真正承担后台整理与洞察工作，而不是每次发现结构都把判断重新丢回用户。

# 11. 项目成熟度

项目成熟度不是“项目完成百分比”。

它描述的是一个已经存在项目的稳定与发展程度。

可能反映：

- 项目身份是否稳定；
- 问题边界是否清楚；
- 是否形成持续 ADR；
- 方法是否实际使用；
- 是否出现独立成果；
- 后续结果是否支持已有判断；
- 项目是否持续产生新的有效行动。

成熟度以后应参考 Better Harness 的认识论结构：

> **AI 可以判断分数，但证据强度对分数设置硬上限。**

不能因为 AI “觉得很成熟”就突破证据能够支持的上限。

但具体项目成熟度维度、证据等级和 ceiling 数值尚未冻结，后续单独讨论。

---

# 12. 项目当前结构允许被重新解释

项目识别允许犯错。

可能发生：

- AI 创建错项目；
- 把一个内部阶段误判成独立项目；
- 把两个项目错误合并；
- 选择了错误的分叉点；
- ADR 节点组织不合理。

随着后续证据变厚，当前项目表示允许重新组织：

- 合并误判项目；
- 拆开误合并项目；
- 项目降为项目内部阶段；
- 内部方向升格成独立项目；
- 调整项目出生节点；
- 调整分叉关系；
- 重新组织 ADR 节点；
- 封存；
- 重新激活。

但必须区分：

```text
现实材料
不可覆写

过去形成过的认知
不可偷偷删除

当前项目图 / 当前项目叙事投影
可以重新编译
```

因此：

> **现实不可重写，地图可以重画；重画地图本身也属于认知历史。**

---

# 13. 项目图节点：ADR 级变化

项目形态图不是事件流，也不是 Git commit 图。

图上的正式节点表示：

> **ADR 级项目认知变化。**

只有当项目的：

- 目标；
- 方向；
- 边界；
- 架构；
- 核心理解；
- 项目状态；

发生足以留下“为什么改变”的变化时，才形成新节点。

普通 bug 修复、文案修改、连续实现、一般测试、没有核心认识变化的讨论，不必形成独立形态节点。

一个 ADR 节点至少应讲清：

```text
之前是什么？
↓
为什么不能继续？
↓
现在变成什么？
↓
这次改变影响了什么？
```

项目图展示的不是“发生过多少事”，而是项目怎样一步步变成今天这样。

# 14. 项目分叉与跨项目关系

## 14.1 同项目内部探索

如果不同路线仍属于同一项目的问题空间，可以继续作为同项目内部探索存在。

## 14.2 分叉为独立项目

一旦某个方向正式获得独立项目身份，父项目不继续展开它的所有后续节点。

父项目只留下一个**虚框项目入口**：

```text
● 本项目 ADR
│
├──────┐
│      ┌ ─ ─ ─ ─ ─ ─ ┐
│        新独立项目
│      └ ─ ─ ─ ─ ─ ─ ┘
│
● 本项目后续 ADR
```

虚框表示：

> **这里从当前项目里长出了另一个独立项目。**

点击虚框直接切换到对方项目页面。

## 14.3 成果回流

独立项目的成果可以回流其他项目，但成果回流不意味着来源项目身份消失。

因此：

> **同项目内部路线可以合流；独立项目之间更常见的是成果流动。**

---

# 15. 项目状态

项目至少允许：

```text
推荐
正式
活跃
长期不活跃
阶段完成
封存
重新激活
```

“不活跃”和“封存”不同。

长期不活跃只是最近没有继续推进。

封存表示当前明确不再作为活跃项目推进，但历史身份仍然存在，未来仍可重新激活。

# 16. 项目叙事三级 UI

项目叙事采用三级展开。

---

## UI 第一层：项目总览

回答：

> **“我现在有哪些项目？”**

项目以卡片为基础形态。

排序优先考虑：

```text
高成熟度项目
+
最近形成项目
+
最近重新活跃项目
```

长期不活跃与封存项目自然沉到底部。

推荐项目单独作为“可能正在形成 / 洞察”区域展示，并与正式项目视觉区分。

正式项目是实体卡。

推荐项目应呈现“尚未完全成为一个东西”的视觉感觉，例如更轻、半透明或雾化，但不要和项目形态图中的跨项目虚框入口使用完全相同的视觉语义。

---

## UI 第二层：项目形态图

点击项目以后，不立刻进入长篇叙事。

首先回答：

> **“这个项目现在长成什么样了？”**

核心规则：

### 倒叙

当前永远优先：

```text
现在
↓
最近 ADR
↓
更早 ADR
↓
……
↓
ADR-000 立项
```

用户不需要从项目出生开始读到今天。

### 实心节点

表示本项目 ADR 级认知变化。

### 实线

表示本项目自身连续演化。

### 虚框项目入口

表示这里从当前项目中诞生了另一个独立项目。

点击后直接切换项目。

### 时间

每个节点保留时间戳 / 时间范围。

但：

> **时间是坐标，不是组织框架。**

---

## UI 第三层：正式项目叙事

点击一个 ADR 节点以后，进入完整项目叙事。

它回答：

> **“这个节点到底意味着什么？”**

正文采用自然可读叙事，而不是 ADR 表格。

主要解释：

- 此前我们怎样理解；
- 后来发现了什么；
- 为什么改变；
- 现在怎样理解；
- 对项目造成了什么影响。

正文中可以自然下钻到：

- 概念 / 项目知识；
- 其他项目；
- 规范；
- GitHub；
- 实验；
- 个人叙事；
- 原始证据；
- 认知历史。

这些都是穿透入口，不与项目叙事争夺主阅读位置。

---

# 17. 项目叙事是项目域面向人的主要阅读界面

项目叙事是项目域中人类理解项目的主要终点。

其他能力围绕它继续生长：

```text
项目叙事
├─ 概念 → 项目知识
├─ 为什么这样判断 → 证据
├─ 现实发生什么 → Git / 系统事实
├─ 我们以前怎样理解 → 认知谱系
├─ 项目从哪里来 → 来源项目
└─ 接下来做什么 → 任务 / 行动
```

项目知识、Memory、经验与规则原则上主要服务项目自身及 AI。

用户需要时仍然必须拥有优秀的维护 UI，以重新理解和掌控系统，但这些维护 UI 不应制造第二套与项目叙事竞争的人类主阅读产品。

# 18. 当前完整生长链

```text
现实事实
GitHub / 系统事实
+
个人叙事
+
AI 交互与其他材料
        ↓

材料持续积累
        ↓

AI 尝试匹配已有项目
        ↓

无法稳定匹配
        ↓

项目假说
        ↓

推荐项目
        ↓

三种可能：
├─ GitHub / 现实明确建项 → 现实立项
├─ 用户明确要求建项     → 用户立项
└─ 形成可持续推进结构   → 涌现立项
        ↓

《立项说明》
        ↓

ADR-000
        ↓

正式项目
        ↓

持续吸收现实与个人认知
        ↓

形成 ADR 级变化
        ↓

继续主线 / 内部探索 / 分叉新项目 /
吸收其他项目成果 / 停滞 / 封存 / 再激活
```

# 19. 当前已冻结的核心原则

> **项目组织叙事，时间定位叙事。**

> **不是所有个人叙事都必须立刻进入项目叙事。**

> **推荐项目是洞察，不是正式身份。**

> **项目成熟度与是否立项无关。**

> **项目可以由现实创建、由用户创建，也可以从证据中涌现。**

> **用户明确立项拥有最高项目意义判断权，不能被 AI 以成熟度不足阻止。**

> **AI 只有在材料已经形成“可持续推进结构”时，才有权完成涌现立项。**

> **涌现立项的硬门槛不是固定工件清单，而是需求、事实基础、推进能力和推进路径共同形成的结构完整性。**

> **正式项目从 ADR-000 开始，不允许只有名字的空项目。**

> **立项判断项目有没有继续生长的资格；成熟度判断它后来究竟长得怎么样。**

> **项目形态节点代表 ADR 级认知变化，而不是普通事件。**

> **AI 可以识别错项目、错分叉、错节点；当前项目地图允许随着证据增厚重新组织。**

> **现实不可重写，地图可以重画；重画地图本身也属于认知历史。**

> **独立项目可以分叉出去；父项目只保留跨项目入口。**

> **成果可以跨项目回流，但来源项目的历史身份不因此消失。**

> **项目叙事是项目域面向人的主要阅读界面。**
