# 0. 阅读规则与状态标记

## 0.1 本文回答什么

一个实现 AI 在读完本文后，至少必须能够回答：

```text
DCF 最终要形成什么产品？
为什么选择当前架构？
哪些事实由谁拥有？
一个新功能怎样进入系统？
Bun、Becsy、Swift/macOS、SQLite、launchd/XPC 分别负责什么？
功能、World、Surface 怎样咬合？
哪些工作必须脱离控制平面？
系统崩溃后哪些东西必须恢复？
P0、P1、P2……为什么按这个顺序施工？
哪一个阶段第一次形成完整 DCF 体验？
当前哪些依赖链仍然缺失？
哪些缺口阻塞哪个阶段？
```

如果回答不了，不应直接开始拆实现任务。

## 0.2 状态标记

本文使用以下状态：

- **【已冻结】**：当前正式架构结论；实现不得自行改义。
- **【已验证】**：除已冻结外，已经有独立现实行为证据。
- **【候选】**：当前优先路线，但允许通过实验推翻。
- **【未决】**：实现前必须补齐；存在多个合理答案。
- **【禁止】**：已经确认不采用的路线；不得因为实现方便重新捡回。

状态变化必须显式修改本文，不允许只在代码里偷偷改变架构。

## 0.3 实施 AI 的缺口审计义务

在拆任何阶段任务之前，实施 AI 必须先做一次缺口审计：

```text
读取本阶段目标

↓

↓
列出故障与恢复边界
↓
列出行为验收
↓
```

发现缺口后，应输出：

```text

推荐依据
需要新增哪条规范
```

禁止：

> “规范没写，所以我选一个最方便的实现。”

# 1. DCF 的产品目标

## 1.1 核心目标【已冻结】

DCF 是长期个人认知基础设施。

它不是聊天存档器，也不是普通 Agent 平台。它要形成以下长期循环：

```text
现实发生
↓
确定性记录
↓
AI 关系叙事
↓
人重新进入过去
↓
用户低成本校准 / 补充 / 重新理解
↓
形成新的认知历史
↓
认知进入个人 / 项目 / 知识 / 工程
↓
行动改变现实
↓
新现实再次进入 DCF
```

最重要的历史原则：

> **原件可以变轻，认知变化必须变长。**

> **事情发生时间 ≠ 理解形成时间。**

> **后来出现更好的理解，不允许把过去曾经形成的理解静默改写成从未发生。**

## 1.2 第一版产品形态【已冻结】

DCF 主产品为独立 macOS App，同时拥有三种 Surface：

```text
完整形态
→ 完整世界、复盘、管理、配置、诊断

侧边栏
→ 用户可组装的高频工作面

悬浮球
→ 极简、低打扰的常驻状态与入口
```

三种 Surface 不是三个产品，使用同一功能身份、同一事实和同一动作语义。

# 3. 核心程序架构

## 3.1 功能块是最小产品增长单位【已冻结】

DCF 的增长单位不是“后端模块”，也不是“一个页面”，而是完整功能块。

每个正式功能块必须同时定义：

```text
1. 功能身份
2. 业务目的
3. 上游输入
4. 长期状态所有权 / 引用
5. 允许的 Actions
6. World / 运行域
7. 公共资源依赖
8. 完整形态 Surface
9. 侧边栏 Surface，或明确不提供
10. 悬浮球 Surface，或明确不提供
11. 设置贡献（若需要）
12. 故障 / 恢复语义
13. 现实行为验收
```

原则：

> **新增功能 = 能力增长 + 运行增长 + 产品表面增长。**

禁止出现：

```text
后端已经支持新功能
但主页面、侧边栏和设置页仍需要下一轮单独硬编码
```

## 3.2 World 是隔离单位，公共能力是复用单位【已冻结】

Becsy 对 DCF 最重要的价值首先是 World，不是要求整个 DCF 信奉 ECS。

World 负责：

```text
功能活动状态的归属
功能运行生命周期
功能内部状态变化边界
与其他功能之间的依赖边界
```

公共能力负责跨 World 复用：

```text
持久层访问
AI Runtime
Job / Executor
Cache
Scheduler
来源查询
日志 / 诊断
公共资源协调
```

核心原则：

> **World 是隔离单位，公共能力是复用单位，ECS 是优化手段，不是领域建模宗教。**

> **World 规定所有权与依赖边界，不规定内部实现方式。**

> **限制关系，不限制能力。**

因此功能块内部可自由使用：

```text
普通 TypeScript
Becsy ECS
状态机
Swift / SwiftUI / AppKit
WKWebView
BlockNote
Metal
第三方库
其他局部结构
```

是否违反 World 隔离，看的是依赖关系和状态所有权是否越界，而不是使用了什么语言或 UI 技术。

## 3.3 ECS 的正式位置【已冻结】

ECS 优势只在真正适合的地方使用：

```text
大量同质活动对象
Query 批量命中
热 / 冷数据分离
紧凑状态布局
共享读取
缓存 / 去重
资源分组
批处理
可证明安全的重排
减少锁竞争和上下文切换
```

领域对象不得为了“贯彻 ECS”被强行 Component 化。

长期正文和冷数据例如：

```text
完整对话
叙事正文
知识正文
工具大 payload
Git 历史
```

留在持久层，World 中只保存必要引用和活动元数据。

## 3.4 Bun 的正式位置【已冻结】

Bun 承担两类价值：

### A. 成熟生态复用

允许 DCF 直接借用 JS / TS / npm 生态中已经成熟的能力，而不是重写一遍。

### B. 功能块伪热更新

目标不是复杂的进程内 HMR，而是：

```text
功能块新增 / 修改
↓
检测变化
↓
保存必要恢复位置
↓
快速、干净地结束当前活动运行实例
↓
重新扫描功能块
↓
重新注册 World / Actions / Surface
↓
恢复长期状态与必要活动
↓
用户体感接近热更新
```

核心原则：

> **DCF 的热更新目标不是让旧进程永远不死，而是让一次确定、极快、状态可恢复的重载在体验上接近热更新。**

## 3.5 macOS 原生宿主的正式位置【已冻结】

macOS App 不只是窗口容器。

它拥有：

```text
功能注册接缝
Surface 注册表
导航 / 布局编排
完整形态 Host
侧边栏 Host
悬浮球 Host
设置与用户编排
重新连接 / 注册表刷新
原生系统能力接缝
```

功能块拥有展示能力；宿主拥有展示秩序。

宿主不得硬编码未来所有功能名单。

## 3.6 原生 Swift 功能扩展【已冻结】

受信任功能块原则上允许携带任意 Swift / SwiftUI / AppKit 原生实现。

禁止为了动态 UI 自建一个劣化版万能 JSON UI DSL。

功能块可直接使用最适合自己的原生技术；DCF 只要求它遵守功能身份、状态所有权、Actions、World、公共资源和生命周期边界。

【未决】Swift 功能块的具体编译、签名、产物形式、原子替换和重新装载合同尚未闭合，见缺口 G-001。

## 3.7 launchd + XPC【已验证 / 已冻结】

```text
launchd
→ 进程生命周期权威

XPC
→ 稳定本地通信接缝
```

已经验证 launchd 可在服务进程死亡后拉起新实例，稳定 mach 名不随 PID 改变。

DCF 不自建第二套 supervisor，也不让 IPC 层拥有第二套生命周期权威。

这为伪热更新提供宿主级恢复基础。

# 4. 动态功能注册与 Surface 编排协议

## 4.1 功能注册的目标【已冻结】

一个功能块成功加载，不能只表示 `module import` 成功。

它至少必须完成：

```text
功能身份注册
动作注册
World / 运行域建立
公共资源依赖确认
完整形态贡献注册
侧边栏贡献或“不提供”注册
悬浮球贡献或“不提供”注册
设置贡献注册（若存在）
诊断信息可见
```

## 4.2 Surface 贡献模型【已冻结原则，合同细节未决】

功能块可以提供：

```text
完整页面
首页 / Dashboard 贡献
侧边栏组件
悬浮球状态 / 动作
设置入口
专用原生交互
```

三种 Surface 读取同一功能状态并调用同一 Actions。

例如：

```text
功能：叙事复盘

完整形态
→ 全文 + 证据 + 深度校准

侧边栏
→ 当前待复盘摘要 + 少量快速动作

悬浮球
→ 可选：存在高价值待复盘事项
```

【未决】最小 Surface 注册合同、原生 View / Bundle 如何被宿主发现、功能更新后 Registry diff 如何传播，见 G-002。

## 4.3 用户编排【已冻结】

完整形态负责：

```text
选择哪些注册组件进入侧边栏
排序
折叠 / 展开
场景组合
选择哪些贡献进入悬浮球
悬浮球动作
```

设置页根据当前注册功能动态形成，不提前硬编码功能名。

# 5. 长期持久世界与活动世界

## 5.1 长期事实【已冻结】

必须长期保存或能够稳定恢复的内容包括：

```text
现实来源定位与消费游标
机器编制记录
AI 关系叙事
用户校准事件
认知变化关系
个人 / 项目叙事
知识 / 缺口 / 任务的长期事实
功能配置
必要运行收据
```

当前关系数据库路线可满足主结构，不因为存在关系就提前引入图数据库。

## 5.2 活动状态【已冻结】

World 中适合保存：

```text
当前阶段
等待什么
正在处理什么
优先级
资源身份
继续位置
小型状态标志
长期对象引用
少量结果元信息
```

## 5.3 崩溃恢复原则【已冻结原则，细节未决】

任何正式工作都必须先判断：

```text
进程死在动作前
动作过程中
现实副作用已经发生但结果未记录
结果已记录但状态未推进
```

分别怎样恢复。

不要求持久化整个 Becsy World；只持久化真正不可从长期事实确定重建的语义进度。

【未决】P0 需要定义最小恢复快照 / checkpoint 合同，见 G-003。

# 6. 业务核心：基础 DCF 认知闭环

## 6.1 机器编制【已冻结】

```text
原始对话 / 工具调用 / 来源事实
↓
确定性机器编制
↓
AI 可重新读取的稳定交互记录
```

机器编制不负责理解，不允许把 AI 对用户动机的猜测伪装成事实字段。

## 6.2 AI 关系叙事【已冻结】

AI 可以跨多条记录形成关系、阶段、变化与可能意义。

首要目的不是“压缩文本”，而是：

> **把人重新带回过去。**

## 6.3 校准动作【已冻结】

用户审核不是质检，而是认知生产。

DCF 应尽量让用户的判断直接成为低成本表达。

第一组核心动作包括：

```text
👍 认同
👎 不满意
✕ 明确否认
直接修改 / 修正表达
＋ 补充遗漏
↻ 请求重写
🔗✕ 证据无关
🔗? 证据不足
🔗↻ 请求重新关联
⭐ 重要
淡化 / 降低注意权重
```

特别冻结：

> **👎 不满意 ≠ ✕ 明确否认。**

用户不需要先解释为什么不满意，弱负反馈本身就是有效认知材料。

所有校准都形成追加式认知事件；原 AI 叙事不得因为校准被静默改写。

## 6.4 叙事复盘 Surface【候选】

当前首选产品思想：

> 用户看到一篇自然文章；DCF 得到结构化动作流。

候选编辑器底座：BlockNote，用于解决选区、块菜单、编辑表面等富文本复杂度；DCF 自己拥有校准动作语义和认知历史。

BlockNote 不得成为 DCF 长期认知真源。

# 7. 正式工作与控制平面

## 7.1 Job 边界【已冻结】

任何能够定义为独立正式工作的工作，无论预期长短，默认脱离最小控制平面执行。

判断问题：

> 如果这项工作意外变慢或失败，DCF 是否仍然必须能查看状态、取消工作、处理其他任务和保持 UI 响应？

若是，则该工作必须脱离控制平面。

## 7.2 控制平面只保留【已冻结】

```text
当前活动状态
Job 创建 / 派发
进度 / 结果 / 失败接收
原子状态推进
取消 / 超时 / 重试控制
恢复位置
健康检查
UI / 接口 / 诊断持续可响应
```

## 7.3 逻辑动作与物理执行【已冻结】

逻辑动作保持调用者身份、因果关系、继续位置、取消语义和证据来源。

物理执行允许共享、缓存、去重或批处理，只要能够证明不改变语义。

# 8. 构建时间线与阶段门禁

> 概念层级与施工顺序是两个不同维度。以下是当前正式施工主线。

```text
P0 动态产品骨架
↓
P1 第一份真实材料闭环
↓
P2 基础 DCF 最小完整认知体验 ★
↓
P3 多来源现实 + 个人 / 项目长期叙事
↓
P4 缺口 → 任务 → 行动 → 再观察
↓
P5 ECS 工业化 + 成熟能力持续下沉
```

三种 Surface Host、动态注册与编排能力从 P0 就存在，不是后期 UI 阶段。

---

## 8.1 P0 — 动态产品骨架

### 阶段目标

证明：

> **DCF 能通过增加一个完整功能块，同时增加运行能力和原生产品表面，并且不要求修改既有功能。**

### 前置条件

无真实 DCF 业务依赖。

### 必须交付

```text
独立 macOS App
完整形态 Host
侧边栏 Host
悬浮球 Host
Bun Core
功能扫描 / 注册
World 创建 / 销毁
公共资源注入
Surface Registry
设置动态编排
launchd / XPC 生存与重新连接
伪热更新
最小长期状态恢复
诊断入口
```

### 试验功能

至少使用 A / B 两个极简功能块，再在运行中加入 C。

每个试验功能都必须有：

```text
业务状态
World
完整页面
侧边栏贡献
悬浮球贡献或明确不提供
可验证的持久状态
```

### P0 通过条件

```text
A / B 已运行
↓
加入 C
↓
Bun 检测变化
↓
活动运行层快速重载
↓
C World 建立
↓
完整形态自动出现 C
↓
侧边栏设置自动出现 C
↓
悬浮球配置自动出现 C（若声明）
↓
A / B 无需修改且旧长期状态不丢
```

同时必须证明：

- 一个 World 内部状态变化不要求其他 World 了解其私有实现；
- 两个 World 可以复用同一公共资源；
- 正式工作卡死时宿主和控制面仍可响应；
- UI 在运行实例切换后能重新取得注册表和状态。

### P0 失败反例

以下任一出现即 P0 未通过：

```text
新增 C 还需要手改 MainView / Sidebar / FloatingBall 的功能名单
新增 C 必须修改 A / B 的内部代码
功能代码更新了但产品表面没有同步更新
重载后长期状态丢失
Bun 重启后 macOS App 无法自动重新连接
World 被当成长期业务数据库
```

---

## 8.2 P1 — 第一份真实材料闭环

### 阶段目标

证明真实来源可以稳定、幂等、可恢复地进入 DCF，并形成确定性机器记录。

### 当前优先来源

选择一个高语义来源：ChatGPT 或 Codex。

### 必须交付

```text
来源适配器
稳定来源身份
事件身份 / 去重
消费游标
断线恢复
确定性机器编制
来源定位
完整形态中的诊断 / 检查页面
```

### P1 通过条件

- 同一来源重放多次不制造多份现实；
- 来源中断后可以从游标继续；
- 相同原始事实确定性编制得到稳定结果；
- AI 推断不进入事实字段；
- 用户可从完整形态定位到机器编制记录和来源。

P1 结束时，DCF 可以像一个可靠档案系统，但还没有完成核心认知价值。

---

## 8.3 P2 — 基础 DCF 最小完整认知体验 ★

### 阶段目标

第一次形成真正完整的 DCF：

```text
真实交互
↓
机器编制
↓
AI 关系叙事
↓
用户在可操作叙事中复盘
↓
低成本校准动作
↓
追加式新认知
↓
重启后历史变化仍然存在
↓
后续 AI 能读懂这些校准
```

### 必须交付

```text
关系叙事生成
叙事稳定身份
叙事段落 / 范围稳定定位
叙事复盘 World
校准动作事件模型
叙事复盘完整形态
必要侧边栏投影
悬浮球贡献决策
AI 重写 Job
证据查看 / 校准的第一版
重启恢复
```

### 最小体验验收

真实运行一次：

```text
用户产生真实 ChatGPT / Codex 交互
↓
自动进入 DCF
↓
AI 生成关系叙事
↓
用户在完整 App 中看到叙事
↓
对一段点 👎
↓
退出并重启 DCF
↓
原叙事仍在
↓
👎 作为独立校准事件仍在
↓
下一次 AI 处理该历史时知道：
“用户当时对这段理解不满意，但没有明确否认”
```

做到这里，基础 DCF 才第一次真正存在。

```text

↓
```

# 10. 功能块规格模板

任何真实功能拆任务前，先按以下模板补齐。

## F-XXX 功能名称

### 1. 目的

它解决什么真实问题？若拿掉会失去什么？

### 2. 上游依赖

需要哪些功能、事实、身份、接口已经存在？

### 3. 不依赖什么

明确哪些后续系统不应阻塞本功能。

### 4. 本功能拥有

列长期事实、配置、活动状态。

### 5. 本功能不拥有

列外部事实和其他 World 的状态边界。

### 6. 输入

来源、格式、身份、幂等要求。

### 7. Actions

每个动作精确定义业务语义与失败语义。

### 8. World

当前活动实体、状态、等待条件、退出条件。

### 9. 公共资源

AI、数据库、Cache、Executor、来源、Git 等。

### 10. 完整形态

完整功能怎样被用户理解和操作。

### 11. 侧边栏

高频投影，或明确不提供。

### 12. 悬浮球

极简投影，或明确不提供。

### 13. 持久化

什么必须持久；什么可以重建；什么仅是 UI 瞬态。

### 14. 故障 / 恢复

列举进程可能死亡的关键缝隙和恢复结果。

### 15. 行为验收

正向验收 + 至少一个能够证明“其实没做对”的反例。

### 16. 未决项

所有仍有多个合理答案的设计问题。

# 11. 当前缺口审计

> 本节不是缺陷列表，而是下一轮设计讨论的入口。只有当上游缺口闭合后，才允许把对应阶段拆成确定实施任务。

## G-001 Swift 原生功能块的构建与装载合同【未决，阻塞 P0】

需要明确：

```text
功能块 Swift 源码由谁编译
产物是什么（bundle / framework / 其他）
如何签名
如何版本化
如何原子替换
宿主如何发现
旧版本什么时候退出
失败后如何回退
功能块与宿主之间的 ABI / API 稳定边界是什么
```

当前原则已经冻结：允许任意受信任 Swift 原生实现；未闭合的是工程装载机制。

## G-002 Surface 注册协议最小合同【未决，阻塞 P0】

需要明确功能块至少怎样声明：

```text
功能身份
完整形态入口
侧边栏入口
悬浮球入口
设置入口
状态订阅
Action 发送
可用 / 不可用状态
版本
```

还需明确注册表更新后 macOS Host 如何获得 diff / snapshot。

## G-003 World 重建与最小恢复点【未决，阻塞 P0】

需要明确：

```text
哪些 World 状态可直接丢弃重建
哪些语义进度必须 checkpoint
功能块重载时怎样判断旧 Job 是否仍在运行
World 创建失败如何表示
部分 World 恢复失败是否阻塞其他 World
```

## G-004 功能依赖声明与加载顺序【未决，阻塞 P0】

功能块之间应尽量低耦合，但真实系统仍会出现依赖，例如：

```text
叙事复盘依赖关系叙事生成
关系叙事生成依赖机器编制查询
```

需要明确：

```text
依赖是声明能力还是声明具体功能 ID
循环依赖怎样阻止
依赖缺失时功能怎样降级
功能更新时兼容性怎样判断
```

## G-005 功能状态 / Action 跨 Bun 与 Swift 的协议【未决，阻塞 P0】

需要明确：

```text
状态查询是 pull、订阅还是事件流
Action 身份如何稳定
动作成功 / 失败 / 未知如何表达
Swift UI 是否允许直接同步调用 Bun
断线期间动作如何处理
重新连接后如何恢复最新状态
```

## G-006 持久层最小权威模型【未决，阻塞 P0/P1】

当前已冻结“长期事实在持久层，World 只是活动世界”，但仍需明确第一版最小结构：

```text
功能身份 / 版本
来源身份 / 游标
长期对象 ID
事件 / 追加历史
配置
Job / receipt 最小字段
```

不要求现在把个人叙事、项目叙事最终表结构一次性设计完。

## G-007 伪热更新完整生命周期【未决，阻塞 P0】

需要把以下过程写成逐步协议：

```text
检测到功能变化
↓
停止接收哪些新工作
↓
哪些状态先持久化
↓
哪些 Job 继续 / 取消 / 交给外部 Executor
↓
Bun 运行实例退出
↓
launchd 拉起
↓
功能扫描
↓
World 建立
↓
Surface Registry 恢复
↓
macOS Host 重连
↓
用户当前页面 / 输入草稿怎样处理
```

## G-008 P0 试验功能选择【未决，轻度阻塞 P0】

需要选择足够简单、但能真实验证：

```text
持久状态
World 隔离
公共资源复用
完整态
侧边栏
悬浮球
动态加入 C
```

计数器 / 便签只是示意，并未冻结。

## G-009 叙事稳定定位模型【未决，阻塞 P2】

校准动作需要稳定指向：

```text
整篇叙事
段落
句子 / 文本范围
证据关系
```

但用户直接修改、AI 重写以后，旧定位如何保持历史可解释，需要专门设计。

## G-010 BlockNote 与 DCF 认知事件的映射【候选待实验，阻塞 P2 UI】

必须证明：

```text
编辑器负责输入 / 编辑体验
DCF 校准事件负责认知真相
```

不能因为编辑器内部 document 更新就丢失历史认知动作。

# 12. 后续讨论与文档回填方式

后续每轮讨论优先从第 11 节的缺口进入。

每闭合一个缺口，必须完成三件事：

```text
1. 把决定写成【已冻结】或【候选】
2. 更新依赖矩阵和受影响阶段
3. 如果足够具体，补进对应功能块规格 / 协议
```

如果新决定推翻旧决定：

- 当前总设计说明书更新为最新实施依据；
- 历史转变如有长期解释价值，另写 ADR，不在总说明书里保留互相矛盾的当前路线。

# 13. 拆任务前最终门禁

任何阶段只有在以下条件同时成立后，才进入正式任务拆分：

```text
阶段目标明确
上游依赖明确
功能所有权明确
World 边界明确
公共资源明确
持久化边界明确
Actions 明确
三种 Surface 决策明确
故障 / 恢复明确
行为验收明确
阻塞级未决项已清零
```

随后任务拆分应尽量沿**完整纵向功能块**进行，而不是先拆“所有后端任务”、再拆“所有 UI 任务”。

核心施工原则：

> **先让实现者理解整个系统，再让它负责一个局部；先闭合依赖链，再拆代码任务；先定义什么现实行为才算成功，再决定代码怎样写。**
