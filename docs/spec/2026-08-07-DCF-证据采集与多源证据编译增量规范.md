# DCF 证据采集与多源证据编译增量规范

日期：2026-08-07  
状态：**当前 Capability Discovery 增量裁决**  
适用范围：证据源采集管理、多源证据编译、证据来源输出、ECS（实体组件系统）公共语义组件、采集侧与编译侧职责边界。

> 本规范建立在 `2026-08-07-DCF-Capability与公共设施当前规范.md` 之上，只细化本轮已经讨论收敛的前两个 Capability 候选。
>
> 本规范不冻结最终组件字段、最终文件格式或最终第三方轮子选型；它冻结的是职责边界和组合方向。

---

# 0. 当前总裁决

本轮 Capability Discovery 已经把证据链前两项收敛为两个强候选：

```text
能力一：证据源采集管理
能力二：多源证据编译
```

两者不是一条大流水线内部的人为节点，而是两个可以独立成立的软件问题：

```text
证据源采集管理
→ 解决“现实怎样可靠地进入 DCF”

多源证据编译
→ 解决“已经进入 DCF 的证据怎样按确定规则变成不同消费环节需要的产物”
```

核心边界：

> **采集能力负责输入侧复杂度；编译能力负责输出侧复杂度。**

以及：

> **编译器不关心证据是怎样被采到的；采集器也不关心下游最后怎样理解这些证据。**

两者之间优先不建立传统的 Source Output（来源输出）私有接口，也不建立 callback（回调）订阅网。

当前优先模型是：

```text
外部来源
↓
证据源采集管理 + Evidence Intake Facility（证据接入公共设施）
↓
把“新证据已经存在”表达成 World 中可组合的 ECS 公共语义组件
↓
多源证据编译通过 ECS 查询自己关心的组件组合
↓
产生一个或多个可追溯编译产物
```

---

# 1. 能力一：证据源采集管理

## 1.1 独立软件目的

即使删除 DCF 语境，仍然存在一个完整软件需求：

> **统一发现、接入、配置、授权、运行、监控、恢复和管理各种值得持续或按需观察的信息与现实来源，并稳定产出可消费的原始证据。**

当前 DCF 已经使用的人物活动与电脑运行活动只是第一批来源，不构成这个 Capability 的边界。

未来允许接入：

```text
人物与电脑活动
Git / 文件系统 / IDE / Agent
RSS / 新闻源
网页 / API
论文 / PDF / 探索文档
邮件
公开数据源
行动验收所需的现实来源
未来其他用户关心的证据来源
```

因此它管理的不是“电脑活动”，而是：

> **所有被用户明确接入、未来可能被认知、研究、查询、判断或现实验收使用的可追溯来源。**

---

## 1.2 每个来源拥有自己的采集配置

不同证据源的新鲜度、可靠性、事件能力和成本完全不同，因此禁止强迫所有来源使用同一采集策略。

每个来源应允许独立配置：

```text
来源身份
连接 / 获取方式
权限
启停
事件触发
轮询
定时获取
手动获取
允许的新鲜度
并发
限流
失败重试
可重放能力
游标 / 检查点
缓冲 / 积压处理
去重
健康状态
恢复方式
来源自己的输出方式
```

其中：

```text
事件驱动来源
→ 可以在事件出现时立即产生证据

轮询来源
→ 可以按自己的新鲜度要求决定轮询频率

静态来源
→ 没变化时不需要反复获取

不可重放来源
→ 可以采用更强的缓冲保护

可重放来源
→ 优先依赖游标 / 检查点恢复
```

并发、限流、重试、缓冲、游标、来源生命周期等属于采集侧复杂度，不应下推给多源证据编译。

---

## 1.3 证据接入公共设施仍然成立

`Evidence Intake Facility`（证据接入公共设施）继续负责多个来源反复需要的低业务语义机制，例如：

```text
来源生命周期
确认 / ack
游标 / 检查点
健康
缓冲 / 背压
重试 / 恢复
去重基础机制
```

证据源采集管理 Capability 使用同一正式公共设施配置和管理这些机制，不走测试后门，也不自己复制一套采集运行时。

因此：

```text
证据源采集管理
= 用户面对来源的完整产品能力

证据接入公共设施
= 多种来源共享的可靠采集机制
```

# 2. 来源输出：优先采用 ECS 小组件自由组合

## 2.1 不采用“万能 RawEvidence 大对象”作为优先设计

当前不优先把所有证据都塞进一个不断膨胀的：

```text
RawEvidence {
  type
  source
  metadata
  payload
  ...
}
```

因为能力一已经为每个来源拥有独立配置，那么来源输出天然也可以按该来源真实拥有的语义自由组合。

当前优先设计是：

```text
一个证据实体
+
若干公共 / 来源语义组件
```

示意：

```text
原始证据标记
来源身份
证据类型
内容引用
时间信息
来源特有语义
可选的工程 / 会话 / 操作 / 文档等身份
```

最终字段与拆分粒度尚未冻结；本轮只冻结“小组件组合优先于万能大对象”。

---

## 2.2 不同来源可以自然输出不同组件组合

例如 RSS 新闻：

```text
原始证据标记
+ 来源身份
+ RSS 文章语义
+ 发布时间
+ 内容引用
```

Git 提交：

```text
原始证据标记
+ 来源身份
+ Git 提交语义
+ 仓库身份
+ 提交身份
+ 内容引用
```

Agent 活动：

```text
原始证据标记
+ 来源身份
+ Agent 活动语义
+ 会话身份
+ 操作身份
+ 时间信息
```

论文 / PDF：

```text
原始证据标记
+ 来源身份
+ 文档语义
+ 文档身份
+ 内容引用
+ 时间信息（若来源拥有）
```

新增来源时，优先复用已有公共语义组件；只有真实新语义无法表达时才增加新组件。

---

## 2.3 大正文不要求进入 ECS

ECS（实体组件系统）负责表达：

> **这条证据存在、它属于什么语义、怎样找到它。**

它不应被当成大正文数据库。

大正文、PDF、网页、长日志或批量原始数据可以保存在适合的持久层中，World 只持有稳定引用，例如：

```text
内容引用
内容哈希
来源锚点
稳定证据身份
```

因此：

```text
World / ECS
→ 管证据存在性与公共语义

持久证据存储
→ 管实际内容与可回源原件
```

# 3. 能力二：多源证据编译

## 3.1 独立软件目的

多源证据编译解决：

> **把已经到达 DCF 的一个或多个来源证据，依据显式、版本化、可重放的规则，转换成一个或多个面向不同消费方式的可追溯证据产物。**

它不负责：

```text
连接 RSS
监听文件
申请权限
决定抓取频率
控制 HTTP 并发
来源限流
来源重试
恢复 Probe
维护来源游标
```

这些全部属于能力一与证据接入公共设施。

对于多源证据编译器而言：

> **证据已经来了。**

它只处理“来了以后怎么办”。

---

## 3.2 编译规则允许不同强度

不同来源不需要强行被转换成同一种内容形态。

允许的确定性规则包括：

```text
原样直通
字段规范化
格式转换
替换 / 翻译
去噪
排序
分组
确定关系闭合
有事实依据的少量关联补充
拆分成多个产物
合并成一个产物
```

例如：

```text
RSS 正文
→ 基本直通 + 来源 / 时间 / URL 规范化

FSEvents
→ 底层事件翻译为可读文件变化事实

Git
→ commit / diff 编译成工程变化事实

PDF
→ 提取正文 / 结构，同时保留原 PDF 锚点
```

编译器的硬边界不是“只能少做事”，而是：

> **凡是能够由来源事实 + 显式确定规则推出的，都可以编译；需要开放理解才能成立的，不属于编译。**

因此：

```text
时间相邻
≠
因果

同一时间段出现
≠
属于同一项目

Agent 声称成功
≠
现实成功
```

这些开放意义留给后续 AI、叙事、查询或验收 Capability。

---

# 4. 多源不是单一输出：一个编译目标可以产生多个产物

多源证据编译不要求所有输入收敛为一个统一文件，也不要求所有消费环节吃同一种 EvidenceMaterial（证据材料）。

允许：

```text
一批输入
↓
按目标选择 / 分组
↓
使用对应规则
↓
多个输出产物
```

例如人物活动材料可以产生：

```text
时间线.md
对话材料.md
代码活动.json
来源映射.json
```

行动验收可以产生：

```text
结构化现实事实.json
来源证明.json
```

新闻研究可以产生：

```text
文章原文集合
来源索引
时间线
专题材料包
```

同一条原始证据可以进入多个派生产物，但这些产物不得反向冒充来源原件。

---

# 5. 编译输出时间也属于能力二，但采集时间不属于

能力一决定：

> **什么时候把现实拿进来。**

能力二决定：

> **已经拿到的材料什么时候形成某种编译产物。**

因此多源证据编译允许：

```text
证据到达立即编译
事件触发编译
定时编译
累计到一定数量后编译
时间窗口结束后编译
手动触发编译
消费端明确请求时编译
```

例如：

```text
电脑活动
→ 持续采集
→ 每日编译人物材料

RSS
→ 每 10 分钟采集
→ 新文章到达后立即形成新闻条目
→ 每天再编译一次日报材料

行动验证
→ 行动期间持续采集
→ 验收请求出现时立即编译验证事实
```

禁止为了满足某个编译目标，让编译器自己再起一套采集器。

如果编译所需证据尚未进入 World，编译器只能等待、失败或显式报告材料不足，不能越权去抓取来源。

---

# 6. 能力一与能力二通过 ECS 查询式订阅连接

## 6.1 不订阅具体 Provider

多源证据编译不应写成：

```text
订阅 Codex Provider
订阅 RSS Provider
订阅 Git Provider
```

否则新增来源时会不断修改消费端。

它应查询自己真正需要的公共语义组件组合。

例如人物活动编译：

```text
原始证据
+
时间信息
+
（用户表达 / Agent 活动 / 前台活动 / Git 变化）
```

项目证据编译：

```text
原始证据
+
工程 / 仓库身份
+
（Git 提交 / Agent 活动 / 文档变化）
```

行动验证编译：

```text
原始证据
+
操作身份
+
（测试结果 / 文件变化 / Git 状态 / 系统状态）
```

---

## 6.2 新来源只要提供已有语义，下游可以零修改接入

例如未来增加一个新的 AI 编程工具，只要能力一将其输出表达为：

```text
来源身份
+ Agent 活动
+ 会话身份
+ 操作身份
```

原来查询 `Agent 活动` 的编译规则原则上不需要知道这个新工具品牌存在。

因此正式原则是：

> **来源差异停留在来源侧；能够共享的意义通过 ECS 公共语义组件自然汇合。**

以及：

> **新增实现，不新增接缝。**

---

# 7. 本轮不新增统一触发 / 工作流基础设施

本轮讨论中一度考虑引入统一 Trigger Runtime（触发运行时）或完整工作流平台。

当前裁决：**不需要。**

原因是大部分复杂度已经有清晰所有者：

```text
来源事件 / 轮询 / 新鲜度 / 并发 / 限流 / 重试 / 恢复
→ 能力一 + 证据接入公共设施

编译时机 / 编译分组 / 输出频率 / 输出事件
→ 能力二

外部长任务生命周期
→ ExternalOperation（外部操作）
```

在没有真实重复复杂度证据以前，不新增横跨三者的第二工作流权威。

若以后能力一内部的来源调度机制本身变复杂，应优先寻找成熟轮子承载，但轮子只能吸收采集工程复杂度，不能取得 DCF World 的业务语义定义权。

# 8. 当前 Capability Discovery 结果

当前先记录为：

```text
证据源采集管理
→ 强 Capability 候选
→ 独立目的与输入侧边界已收敛
→ 尚未冻结正式编号与 Capability Envelope

多源证据编译
→ 强 Capability 候选
→ 独立目的与输出侧边界已收敛
→ 尚未冻结正式编号与 Capability Envelope
```

两者当前最小接缝不是私有 API，而是：

> **World 中由 ECS 小组件组合表达的公共证据状态。**

下一步 Capability Discovery 可以在此基础上继续审查后续候选，不需要重新打开本轮已经收敛的采集 / 编译职责，除非出现新的行为证据与之冲突。

# 9. 声明匹配继续向下游延伸：产物也是 World 中的公共语义状态

本轮进一步收敛：

> **多源证据编译与后续认知类 Capability 之间，也优先使用“声明自己需要什么状态”的匹配方式，而不是建立生产者指向消费者的私有调用关系。**

核心原则：

> **上游不指定消费者；下游不指定生产者。双方只围绕共同理解的产物语义发生关系。**

因此，多源证据编译完成以后，不需要调用：

```text
个人叙事接口
项目叙事接口
Wiki 接口
行动验证接口
```

而是把编译结果表达成 World 中的“产物实体”，由小组件自由组合描述，例如：

```text
产物标记
+ 产物用途
+ 产物类型
+ 状态
+ 时间范围
+ 内容引用
+ 来源映射引用
+ 可选的项目 / 人物 / 操作 / 主题身份
```

“产物”是业务语义，不等于必须是一个物理文件。实际内容可以是：

```text
Markdown 文件
JSON 文件
文件集合
数据库对象
大型材料包引用
其他持久对象
```

World 只需要表达“这个产物已经存在、它是什么、怎样找到它”。

---

## 9.1 个人叙事只匹配自己的材料，不认识编译器

个人叙事 Capability 可以声明：

```text
需要：
产物用途 = 个人叙事材料
+
状态 = 编译完成
+
符合当前时间范围 / 人物范围
```

匹配成功后沿内容引用取得材料即可。

它不需要知道：

```text
由哪一个编译器生成
来自哪些具体采集 Provider
采用了哪种物理文件布局
```

因此，多源证据编译器增加新的来源或调整内部规则，只要继续满足同一产物语义契约，个人叙事无需修改。

---

## 9.2 AI 协作审阅编辑器也保持通用，不认识“个人叙事”业务意义

AI 协作审阅编辑器当前仍属于待继续 Discovery 的 Capability 候选，因此本节只冻结**优先交互方向**，不提前冻结其最终边界。

它不应拥有：

```text
if 个人叙事
if 项目叙事
if Wiki
```

更自然的方式是让需要 AI + 人协作审阅的业务 Capability 产生类似：

```text
待审阅标记
+ 材料引用
+ 审阅规则 / 配方引用
+ 目标产物类型
+ 业务对象身份
```

AI 协作审阅编辑器声明匹配“待审阅”状态，完成后再产生：

```text
草稿
修订
审阅结果
已接受 / 已拒绝 / 待再审
```

等公共语义状态。

这样个人叙事、项目叙事、Wiki 等能力可以复用同一个协作审阅能力，而协作审阅能力不需要知道它们各自的业务意义。

# 10. 声明匹配能够继续吸收的接缝复杂度

以下是沿当前架构原则得到的**架构推论**。其中部分已经被 Capability × Becsy World 组合实验间接支持，但尚未逐项完成真实业务行为验收，因此不得写成“全部已验证”。

声明匹配优先可以吸收的是：

> **谁通知谁、谁调用谁、谁等谁、结果交给谁。**

而不是把所有专业机制塞进 ECS。

---

## 10.1 生产者 → 消费者路由

传统：

```text
A 调 B
A 发布 B 专用消息
B 注册 A 的回调
```

优先：

```text
A 把世界推进成某种公共语义状态
↓
B 声明匹配这种状态
```

可减少：

```text
私有回调
消费者注册表
消息主题路由
一对一适配器
生产者对消费者品牌的认知
```

---

## 10.2 一对多与多对一的扇入 / 扇出

同一条 Git 证据可以同时被：

```text
个人材料编译
项目材料编译
行动验证
工程研究
```

匹配；反过来，一个编译目标也可以同时匹配：

```text
用户表达
AI 活动
Git 活动
前台活动
```

因此消费者数量和来源数量增加时，不应要求接缝数量同比增长。

> **扇入、扇出应该主要增加声明，不增加连接代码。**

---

## 10.3 显式工作流编排

传统工作流可能写成：

```text
采集完成
→ 调用编译
→ 调用叙事
→ 调用审阅
→ 调用保存
```

优先模型是：

```text
[原始证据]
↓ 声明匹配
[编译产物]
↓ 声明匹配
[待形成认知]
↓ 声明匹配
[待审阅]
↓ 声明匹配
[正式认知]
```

因此相当一部分人工维护的流程图、调用链和能力 DAG（有向依赖图）应当退化为**从输入 / 输出语义声明派生出的视图**，而不是第一事实。

这不意味着所有流程控制都消失；需要事务、资源锁、明确顺序、人工批准或外部长任务生命周期时，仍由对应专业机制负责。

---

## 10.4 用户确认与权限请求的来回接缝

对于“需要用户决定”的状态，可以优先表达为：

```text
权限请求 / 审核请求 / 决策请求
+
待决定
+
业务身份
```

任何承担对应交互的界面只声明匹配“待决定”状态。

用户决定后写入：

```text
决定结果
+
对应业务身份
```

原执行能力再匹配自己的决定结果继续推进。

因此未来可以减少：

```text
执行器 → 权限管理器 → UI → 执行器
```

这种往返回调链。

这里的“如何等待、超时、恢复、保证权限安全”仍由 Agent Execution Facility（智能体执行公共设施）等专业机制负责，ECS 只吸收状态交接接缝。

---

## 10.5 UI（用户界面）贡献接缝

未来若 Capability 需要向能力主页、上下文侧边栏、环境悬浮球等 Surface（界面载体）贡献内容，可以优先表达为：

```text
界面贡献
+ 目标位置 / 展示类别
+ 显示条件
+ 内容引用
+ 行为引用
```

界面 Capability 声明匹配自己负责的位置，而不是每个业务 Capability 分别调用：

```text
registerHome()
registerSidebar()
registerOrb()
```

这可以减少插件式 UI 中常见的注册钩子森林。

此项目前是架构推论，尚未行为冻结最终组件语义。

---

## 10.6 诊断状态与管理工作台

来源健康、外部操作状态、认知派生状态等如果已经作为真实 World 状态存在，则：

```text
证据源管理器
诊断工具
能力主页
环境悬浮球
```

可以分别声明自己关心的状态，而不要求每个底层设施重复提供：

```text
getHealthForManager()
getHealthForDiagnostics()
getHealthForSidebar()
```

核心原则：

> **共享现实，不共享为某个消费者特制的 API。**

---

## 10.7 恢复需求的发现

例如 World 中出现：

```text
外部操作状态 = 运行中
+
有效执行者不存在
```

恢复系统可以声明匹配这个组合，并把它推进为：

```text
需要恢复
```

真正怎样重连、重放或重新启动，仍属于对应公共设施。

因此 ECS 可以吸收：

> **谁需要恢复的发现与交接。**

但不负责：

> **恢复算法本身。**

---

## 10.8 执行与现实验收之间的危险接缝

行动能力产生：

```text
期望效果
+ 操作身份
```

证据系统产生：

```text
现实证据
+ 同一操作身份 / 可证明关联
```

现实验证能力声明匹配两者，并产生：

```text
现实验证结果
```

因此执行者不需要直接调用验收者，验收者也不需要知道执行者是 Codex、Claude、人类还是其他工具。

这进一步强化 E5 已验证原则：

> **Agent 负责劳动；现实负责验收。**

---

# 11. 组合器可以从声明中派生关系，而不是人工维护关系

如果一个 Capability 最终主要声明：

```text
我需要哪些公共语义组件组合
我会产生哪些公共语义组件组合
```

那么 Composer（组合器）可以机械派生：

```text
哪些能力能够互相形成闭环
哪些要求没有生产者
哪些 Provider 缺失
哪些语义契约不兼容
哪里出现多个 active provider（运行中提供者）
能力之间的派生 DAG
```

Composer 仍然禁止：

```text
解释正文
转换业务字段
修复业务意义
替 Capability 决定“这个材料到底意味着什么”
```

因此新的方向不是“让 Composer 变聪明”，而是：

> **让 Capability 的输入 / 输出语义声明足够真实，使组合关系可以被机械推出。**

---

# 12. ECS 的红线：吃掉接缝，不吞掉专业机制

这条路线最容易出现的误区是：

> “既然声明匹配很好用，那什么都塞进 ECS。”

当前明确禁止这样扩张。

ECS 优先吸收的是：

```text
路由
订阅
分发
等待关系
状态交接
扇入 / 扇出
运行顺序的部分推导
能力发现
UI 贡献发现
权限 / 审核请求的状态交接
诊断状态共享
恢复需求发现
现实验收材料交接
```

ECS 不取代：

```text
大型正文 / 原件持久存储
数据库权威
证据采集可靠性
网络并发 / 限流
文件监听
AI 推理
向量 / 全文检索
Solver（求解器）
Agent（智能体）真实执行
大型数据传输
具体恢复算法
```

正式边界：

> **ECS 吃掉“谁等谁、谁通知谁、结果交给谁”；专业设施继续负责“困难的事情本身到底怎么做”。**

---

# 13. 当前更高层的组合洞察

沿当前路线，DCF 的 Capability 关系应逐渐从：

```text
谁调用谁
谁订阅谁
谁给谁发消息
```

转向：

```text
谁理解哪些世界状态
谁能够把世界推进成哪些新状态
```

因此当前架构公式进一步补充为：

> **Capability 不主要通过彼此调用构成系统；它们通过声明自己理解哪些世界状态、并能把世界推进成哪些新状态，在同一个 World 中自然组合。**

以及：

> **关系不是“谁订阅谁”，而是“谁认识同一种现实”。**

若这条原则在后续真实 Capability 中持续通过行为验收，则 Becsy + Shared Semantic Component（共享语义组件）的主要价值将不仅是执行框架，而是：

> **成为 DCF 的接缝复杂度吸收结构。**

当前仍需用后续 Capability Discovery 与 Standalone / Composite World 行为实验逐项证明哪些接缝可以安全被吸收，不能仅凭架构美感扩大适用范围。
