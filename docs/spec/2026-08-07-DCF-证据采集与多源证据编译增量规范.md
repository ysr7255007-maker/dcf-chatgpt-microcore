# DCF 证据采集与多源证据编译增量规范

日期：2026-08-07  
状态：**当前 Capability Discovery 增量裁决**  
适用范围：证据源采集管理、多源证据编译、证据来源输出、ECS（实体组件系统）公共语义组件、采集侧与编译侧职责边界。

> 本规范建立在 `2026-08-07-DCF-Capability与公共设施当前规范.md` 之上，只细化本轮已经讨论收敛的前两个 Capability 候选。
>
> 本规范不冻结最终组件字段、最终文件格式或最终第三方轮子选型；它冻结的是职责边界和组合方向。

---

# 0. 当前总裁决

本轮 Capability Discovery 已经把证据链前两项收敛为两个强候选：

```text
能力一：证据源采集管理
能力二：多源证据编译
```

两者不是一条大流水线内部的人为节点，而是两个可以独立成立的软件问题：

```text
证据源采集管理
→ 解决“现实怎样可靠地进入 DCF”

多源证据编译
→ 解决“已经进入 DCF 的证据怎样按确定规则变成不同消费环节需要的产物”
```

核心边界：

> **采集能力负责输入侧复杂度；编译能力负责输出侧复杂度。**

以及：

> **编译器不关心证据是怎样被采到的；采集器也不关心下游最后怎样理解这些证据。**

两者之间优先不建立传统的 Source Output（来源输出）私有接口，也不建立 callback（回调）订阅网。

当前优先模型是：

```text
外部来源
↓
证据源采集管理 + Evidence Intake Facility（证据接入公共设施）
↓
把“新证据已经存在”表达成 World 中可组合的 ECS 公共语义组件
↓
多源证据编译通过 ECS 查询自己关心的组件组合
↓
产生一个或多个可追溯编译产物
```

---

# 1. 能力一：证据源采集管理

## 1.1 独立软件目的

即使删除 DCF 语境，仍然存在一个完整软件需求：

> **统一发现、接入、配置、授权、运行、监控、恢复和管理各种值得持续或按需观察的信息与现实来源，并稳定产出可消费的原始证据。**

当前 DCF 已经使用的人物活动与电脑运行活动只是第一批来源，不构成这个 Capability 的边界。

未来允许接入：

```text
人物与电脑活动
Git / 文件系统 / IDE / Agent
RSS / 新闻源
网页 / API
论文 / PDF / 探索文档
邮件
公开数据源
行动验收所需的现实来源
未来其他用户关心的证据来源
```

因此它管理的不是“电脑活动”，而是：

> **所有被用户明确接入、未来可能被认知、研究、查询、判断或现实验收使用的可追溯来源。**

---

## 1.2 每个来源拥有自己的采集配置

不同证据源的新鲜度、可靠性、事件能力和成本完全不同，因此禁止强迫所有来源使用同一采集策略。

每个来源应允许独立配置：

```text
来源身份
连接 / 获取方式
权限
启停
事件触发
轮询
定时获取
手动获取
允许的新鲜度
并发
限流
失败重试
可重放能力
游标 / 检查点
缓冲 / 积压处理
去重
健康状态
恢复方式
来源自己的输出方式
```

其中：

```text
事件驱动来源
→ 可以在事件出现时立即产生证据

轮询来源
→ 可以按自己的新鲜度要求决定轮询频率

静态来源
→ 没变化时不需要反复获取

不可重放来源
→ 可以采用更强的缓冲保护

可重放来源
→ 优先依赖游标 / 检查点恢复
```

并发、限流、重试、缓冲、游标、来源生命周期等属于采集侧复杂度，不应下推给多源证据编译。

---

## 1.3 证据接入公共设施仍然成立

`Evidence Intake Facility`（证据接入公共设施）继续负责多个来源反复需要的低业务语义机制，例如：

```text
来源生命周期
确认 / ack
游标 / 检查点
健康
缓冲 / 背压
重试 / 恢复
去重基础机制
```

证据源采集管理 Capability 使用同一正式公共设施配置和管理这些机制，不走测试后门，也不自己复制一套采集运行时。

因此：

```text
证据源采集管理
= 用户面对来源的完整产品能力

证据接入公共设施
= 多种来源共享的可靠采集机制
```

# 2. 来源输出：优先采用 ECS 小组件自由组合

## 2.1 不采用“万能 RawEvidence 大对象”作为优先设计

当前不优先把所有证据都塞进一个不断膨胀的：

```text
RawEvidence {
  type
  source
  metadata
  payload
  ...
}
```

因为能力一已经为每个来源拥有独立配置，那么来源输出天然也可以按该来源真实拥有的语义自由组合。

当前优先设计是：

```text
一个证据实体
+
若干公共 / 来源语义组件
```

示意：

```text
原始证据标记
来源身份
证据类型
内容引用
时间信息
来源特有语义
可选的工程 / 会话 / 操作 / 文档等身份
```

最终字段与拆分粒度尚未冻结；本轮只冻结“小组件组合优先于万能大对象”。

---

## 2.2 不同来源可以自然输出不同组件组合

例如 RSS 新闻：

```text
原始证据标记
+ 来源身份
+ RSS 文章语义
+ 发布时间
+ 内容引用
```

Git 提交：

```text
原始证据标记
+ 来源身份
+ Git 提交语义
+ 仓库身份
+ 提交身份
+ 内容引用
```

Agent 活动：

```text
原始证据标记
+ 来源身份
+ Agent 活动语义
+ 会话身份
+ 操作身份
+ 时间信息
```

论文 / PDF：

```text
原始证据标记
+ 来源身份
+ 文档语义
+ 文档身份
+ 内容引用
+ 时间信息（若来源拥有）
```

新增来源时，优先复用已有公共语义组件；只有真实新语义无法表达时才增加新组件。

---

## 2.3 大正文不要求进入 ECS

ECS（实体组件系统）负责表达：

> **这条证据存在、它属于什么语义、怎样找到它。**

它不应被当成大正文数据库。

大正文、PDF、网页、长日志或批量原始数据可以保存在适合的持久层中，World 只持有稳定引用，例如：

```text
内容引用
内容哈希
来源锚点
稳定证据身份
```

因此：

```text
World / ECS
→ 管证据存在性与公共语义

持久证据存储
→ 管实际内容与可回源原件
```

# 3. 能力二：多源证据编译

## 3.1 独立软件目的

多源证据编译解决：

> **把已经到达 DCF 的一个或多个来源证据，依据显式、版本化、可重放的规则，转换成一个或多个面向不同消费方式的可追溯证据产物。**

它不负责：

```text
连接 RSS
监听文件
申请权限
决定抓取频率
控制 HTTP 并发
来源限流
来源重试
恢复 Probe
维护来源游标
```

这些全部属于能力一与证据接入公共设施。

对于多源证据编译器而言：

> **证据已经来了。**

它只处理“来了以后怎么办”。

---

## 3.2 编译规则允许不同强度

不同来源不需要强行被转换成同一种内容形态。

允许的确定性规则包括：

```text
原样直通
字段规范化
格式转换
替换 / 翻译
去噪
排序
分组
确定关系闭合
有事实依据的少量关联补充
拆分成多个产物
合并成一个产物
```

例如：

```text
RSS 正文
→ 基本直通 + 来源 / 时间 / URL 规范化

FSEvents
→ 底层事件翻译为可读文件变化事实

Git
→ commit / diff 编译成工程变化事实

PDF
→ 提取正文 / 结构，同时保留原 PDF 锚点
```

编译器的硬边界不是“只能少做事”，而是：

> **凡是能够由来源事实 + 显式确定规则推出的，都可以编译；需要开放理解才能成立的，不属于编译。**

因此：

```text
时间相邻
≠
因果

同一时间段出现
≠
属于同一项目

Agent 声称成功
≠
现实成功
```

这些开放意义留给后续 AI、叙事、查询或验收 Capability。

---

# 4. 多源不是单一输出：一个编译目标可以产生多个产物

多源证据编译不要求所有输入收敛为一个统一文件，也不要求所有消费环节吃同一种 EvidenceMaterial（证据材料）。

允许：

```text
一批输入
↓
按目标选择 / 分组
↓
使用对应规则
↓
多个输出产物
```

例如人物活动材料可以产生：

```text
时间线.md
对话材料.md
代码活动.json
来源映射.json
```

行动验收可以产生：

```text
结构化现实事实.json
来源证明.json
```

新闻研究可以产生：

```text
文章原文集合
来源索引
时间线
专题材料包
```

同一条原始证据可以进入多个派生产物，但这些产物不得反向冒充来源原件。

---

# 5. 编译输出时间也属于能力二，但采集时间不属于

能力一决定：

> **什么时候把现实拿进来。**

能力二决定：

> **已经拿到的材料什么时候形成某种编译产物。**

因此多源证据编译允许：

```text
证据到达立即编译
事件触发编译
定时编译
累计到一定数量后编译
时间窗口结束后编译
手动触发编译
消费端明确请求时编译
```

例如：

```text
电脑活动
→ 持续采集
→ 每日编译人物材料

RSS
→ 每 10 分钟采集
→ 新文章到达后立即形成新闻条目
→ 每天再编译一次日报材料

行动验证
→ 行动期间持续采集
→ 验收请求出现时立即编译验证事实
```

禁止为了满足某个编译目标，让编译器自己再起一套采集器。

如果编译所需证据尚未进入 World，编译器只能等待、失败或显式报告材料不足，不能越权去抓取来源。

---

# 6. 能力一与能力二通过 ECS 查询式订阅连接

## 6.1 不订阅具体 Provider

多源证据编译不应写成：

```text
订阅 Codex Provider
订阅 RSS Provider
订阅 Git Provider
```

否则新增来源时会不断修改消费端。

它应查询自己真正需要的公共语义组件组合。

例如人物活动编译：

```text
原始证据
+
时间信息
+
（用户表达 / Agent 活动 / 前台活动 / Git 变化）
```

项目证据编译：

```text
原始证据
+
工程 / 仓库身份
+
（Git 提交 / Agent 活动 / 文档变化）
```

行动验证编译：

```text
原始证据
+
操作身份
+
（测试结果 / 文件变化 / Git 状态 / 系统状态）
```

---

## 6.2 新来源只要提供已有语义，下游可以零修改接入

例如未来增加一个新的 AI 编程工具，只要能力一将其输出表达为：

```text
来源身份
+ Agent 活动
+ 会话身份
+ 操作身份
```

原来查询 `Agent 活动` 的编译规则原则上不需要知道这个新工具品牌存在。

因此正式原则是：

> **来源差异停留在来源侧；能够共享的意义通过 ECS 公共语义组件自然汇合。**

以及：

> **新增实现，不新增接缝。**

---

# 7. 本轮不新增统一触发 / 工作流基础设施

本轮讨论中一度考虑引入统一 Trigger Runtime（触发运行时）或完整工作流平台。

当前裁决：**不需要。**

原因是大部分复杂度已经有清晰所有者：

```text
来源事件 / 轮询 / 新鲜度 / 并发 / 限流 / 重试 / 恢复
→ 能力一 + 证据接入公共设施

编译时机 / 编译分组 / 输出频率 / 输出事件
→ 能力二

外部长任务生命周期
→ ExternalOperation（外部操作）
```

在没有真实重复复杂度证据以前，不新增横跨三者的第二工作流权威。

若以后能力一内部的来源调度机制本身变复杂，应优先寻找成熟轮子承载，但轮子只能吸收采集工程复杂度，不能取得 DCF World 的业务语义定义权。

当前先记录为：

```text
证据源采集管理
→ 强 Capability 候选

→ 尚未冻结正式编号与 Capability Envelope

多源证据编译
```

> **World 中由 ECS 小组件组合表达的公共证据状态。**

下一步 Capability Discovery 可以在此基础上继续审查后续候选，不需要重新打开本轮已经收敛的采集 / 编译职责，除非出现新的行为证据与之冲突。
