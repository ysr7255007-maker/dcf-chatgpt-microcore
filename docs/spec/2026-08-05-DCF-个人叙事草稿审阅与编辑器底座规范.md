# DCF 个人叙事草稿审阅与编辑器底座规范

日期：2026-08-05  
状态：**正式子规范 v1；当前产品/UI 实施依据**

关联文档：

- `docs/spec/2026-08-05-DCF-总设计说明书.md`
- `docs/spec/2026-08-05-DCF-认知时间语义与叙事交互协议.md`

- `docs/spec/2026-08-05-DCF-P0-功能舱-窄腰-不可变代际协议.md`

本文负责冻结 DCF 中“AI 个人叙事草稿怎样被用户审阅、怎样调用 AI 二次修订、怎样提交为正式个人叙事，以及编辑器本底由谁负责”的第一版实现关系。

若本文与旧文档中“DCF 自己实现富文本编辑器”“AI 修订时重新查询全部事实源”“任何草稿修改都必须经过 AI”“审阅意见必须逐条接受/拒绝”等表述冲突，以本文为准。

---

# 1. 总裁决

## 1.1 DCF 不自建文本编辑器【已冻结】

DCF 不把以下问题作为自己的主要工程责任：

```text
contenteditable
光标与选区
跨段选择
中文输入法兼容
段落 / 标题 / 列表
撤销 / 重做
复制 / 粘贴
键盘导航
格式工具栏
块拖拽
基础文档 JSON
阅读态渲染
基础主题与样式
```

这些能力优先由 Bun / npm 生态中的成熟编辑器承担。

正式原则：

> **DCF 不做编辑器；DCF 只做叙事审阅语义。**

> **借完整编辑器世界，只定义认知接缝。**

这条原则属于“借完整世界，只定义薄接缝”在 UI / 文档编辑领域的直接应用。

---

## 1.2 第一版编辑器本底：BlockNote【候选首选，P2 默认实施路线】

第一版个人叙事草稿编辑与正式叙事展示，默认采用 BlockNote 作为 Web 编辑器本底。

选择它的原因不是“DCF 需要块编辑器”本身，而是 BlockNote 已经把大量成熟文本编辑能力打包成接近产品级的完整世界：

```text
BlockNote
↓
内建块编辑体验
内建 Selection / Formatting Toolbar
内建菜单与工具栏 UI
内建文档结构
可直接主题化
可扩展 custom style / inline content / block
可加入 ProseMirror plugin / Tiptap extension
```

BlockNote 本身建立在 ProseMirror 与 Tiptap 之上，因此 DCF 默认不直接从更底层的 Tiptap / ProseMirror 开始搭编辑 UI。

当前优先级：

```text
BlockNote 公共能力足够
→ 直接使用 BlockNote

BlockNote 缺少局部能力，但可通过其 extension / custom schema 扩展
→ 在 BlockNote 内扩展

只有 BlockNote 无法提供必要能力
→ 才允许下探 Tiptap / ProseMirror
```

禁止因为“自己写更自由”而绕过成熟本底重新实现通用文本编辑器。

---

## 1.3 DCF 自研范围必须极薄【已冻结】

第一版 DCF 在编辑器之上只拥有：

```text
DCF Review Extension
│
├─ 选中文字后的 DCF 审阅动作
│  ├─ 不满意
│  ├─ 否认
│  ├─ 补充
│  └─ 批注 / 修改意图
│
├─ 审阅意见与文本范围的稳定关联
├─ 本轮审阅侧栏
├─ AI 修订动作
├─ 查看本轮修改
└─ 完成审阅并提交
```

DCF 不拥有：

```text
通用文本格式系统
通用多人评论平台
通用 suggestion / track changes 平台
多人 presence
通用协同编辑服务
编辑器文档内核
```

# 2. 草稿生命周期

## 2.1 三种业务状态【已冻结】

个人叙事的第一版生命周期只有三个核心阶段：

```text
① AI 初稿
↓
② 用户修订中的草稿
↓
③ 正式个人叙事
```

### ① AI 初稿

来源：当日事实、交互记录、当前认知等材料经过首次 AI 编制。

此阶段 AI 的任务是：

> **根据事实材料形成第一份可供用户审阅的个人叙事草稿。**

### ② 用户修订中的草稿

用户可以：

```text
直接改字
改句
删段
补段
调整顺序
选择文字添加审阅意见
给整篇增加修改要求
调用 AI 修订
再次手改
再次调用 AI 修订
```

只要尚未“完成审阅并提交”，它仍是一份工作草稿。

### ③ 正式个人叙事

用户明确提交后，草稿取得正式历史身份。

从此：

```text
正文不可被覆盖
形成时间不可回写
后续修正 / 补充 / 新理解只能形成新的当前认知
```

正式原则：

> **首次生成负责从事实到草稿；AI 修订负责从用户修订意图到更好的草稿；提交负责从草稿到历史。**

---

# 3. 两条合法修订路径

## 3.1 路径 A：手工小改后直接提交【已冻结】

适用情况：AI 草稿整体已经足够准确，仅需要少量修改。

流程：

```text
AI 初稿
↓
用户直接修改正文
↓
完成审阅并提交
↓
正式个人叙事
```

系统不得强制用户在提交前再调用一次 AI。

典型修改：

```text
改两个词
删一句
补一句背景
调整一小段
修改标题
```

如果用户认为手工修改已经足够，最短路径必须成立。

---

## 3.2 路径 B：留下大量修订意图后调用 AI 修订【已冻结】

适用情况：

```text
用户知道哪里不对
但不想亲自重写整篇
```

流程：

```text
AI 初稿
↓
用户直接编辑部分正文
+
对局部留下不满意 / 否认 / 补充 / 批注
+
可选全局修改要求
↓
AI 修订
↓
新草稿
↓
用户继续阅读 / 手改 / 再次 AI 修订
↓
完成审阅并提交
↓
正式个人叙事
```

两条路径可以在同一篇草稿中任意混用。

禁止设计成“手工模式”和“AI 模式”两套不同编辑器。

---

# 4. AI 修订的职责边界

## 4.1 AI 修订不是重新调查事实【已冻结】

首次 AI 编制与二次 AI 修订是两个不同任务。

### 首次编制

```text
事实 / 交互 / 当前认知材料
↓
AI 理解
↓
个人叙事草稿
```

### AI 修订

```text
当前草稿
+
用户已经直接修改后的正文
+
用户局部审阅意见
+
用户补充内容
+
用户全局修改要求
↓
理解用户修订意图
↓
修正 / 整理 / 润色
↓
新草稿
```

默认情况下，AI 修订阶段：

- **不得重新主动搜索原始事实源**；
- **不得重新启动一次完整事实调查**；
- **不得因为旧证据与用户修订存在张力，就偷偷把用户刚改掉的表达重新写回来**。

正式原则：

> **AI 修订时，用户修订意图是当前工作的最高优先级输入。**

---

## 4.2 如果用户想重新核对事实，必须显式进入来源查看【已冻结】

当用户怀疑：

```text
“是不是我自己记错了？”
“AI 最初为什么这么写？”
“原始事实到底是什么？”
```

应由用户显式触发：

```text
查看事实来源
```

然后用户自行决定是否修改当前草稿 / 审阅意见。

禁止 AI 在“帮我润色修订”任务里擅自兼职成为事实裁判。

---

## 4.3 AI 修订后的结果仍是草稿【已冻结】

AI 修订完成不等于提交。

流程必须允许：

```text
AI 修订 v2
↓
用户再次阅读
↓
再手改两句
↓
再 AI 修订 v3
↓
用户提交
```

AI 无权自行把草稿晋升为正式个人叙事。

---

# 5. 草稿编辑 UI：借成熟审阅语法

## 5.1 总体原则【已冻结】

DCF 第一版审阅交互不自己发明新的文本审阅范式。

采用三类成熟产品交互思想的组合：

```text
Notion
→ 选中文字后就地出现轻量操作

Google Docs
→ 文本范围与批注意图建立关联

Microsoft Word Simple Markup
→ 默认正文保持干净，审阅密度按需展开
```

但不照搬这些产品的多人协作业务模型。

---

## 5.2 直接编辑优先【已冻结】

正文始终保持普通文档编辑体验。

如果用户已经知道正确文本是什么：

> **直接改。**

不要要求用户先创建一条“修改建议”，再接受自己的修改。

DCF 是“用户把 AI 草稿变成自己的叙事”，不是多人协作文档审批。

因此第一版不引入：

```text
接受自己的修改
拒绝自己的修改
每次键入都形成 suggestion
```

---

## 5.3 选中文字后的审阅浮条【已冻结】

当用户选中一句或一段文字时，BlockNote 默认 Formatting Toolbar 允许被替换 / 扩展为 DCF 审阅动作。

第一版核心动作保持极少：

```text
[不满意] [否认] [补充] [批注]
```

含义：

### 不满意

用户知道这里“不太对”，但当前不需要说明完整理由。

### 否认

用户明确认为所选表达不成立。

### 补充

用户认为所选内容缺少背景、条件、过程或重要材料。

### 批注

用户用自由文本说明：

```text
真正想表达什么
为什么有问题
希望 AI 怎样改
```

这些动作属于本轮草稿制作过程，不直接成为正式长期认知历史。

---

# 6. 本轮修订栏

## 6.1 草稿态右栏职责【已冻结】

完整形态进入草稿修订态后，右侧栏不显示“后续认知”，而显示：

> **本轮修订**

概念结构：

```text
本轮修订

第 2 段
不满意
“这里把我的动机理解反了。”

第 4 段
补充
“在这之前其实还发生了……”

第 6 段
批注
“不要说已经明确决定，当时还只是倾向。”
```

正文保持连续阅读能力；侧栏集中承载需要 AI 理解的修订意图。

---

## 6.2 正式态右栏职责【已冻结】

提交为正式个人叙事以后，同一右侧空间切换为：

> **后续认知**

因此页面骨架不变：

```text
草稿态右栏
= 本轮修订

提交
↓

正式态右栏
= 后续认知
```

正式原则：

> **同一视觉空间随叙事生命周期切换职责，不制造两套页面。**

---

# 7. 审阅意见与文本的关联

## 7.1 DCF 不自建通用文本定位内核【已冻结】

审阅意见必须能稳定对应草稿中的文字范围，但 DCF 不应从字符 offset 开始自己制造富文本选区系统。

第一版优先利用 BlockNote / ProseMirror 已存在的文档结构、选区与 extension 能力建立关联。

概念上每条本轮修订至少拥有：

```text
review_id
selection_anchor
review_kind
review_content
created_at
status
```

其中 `selection_anchor` 的具体内部格式由所选编辑器本底能力决定，不要求 DCF 发明跨编辑器通用标准。

---

## 7.2 优先使用编辑器原生扩展能力【已冻结】

BlockNote 当前允许：

- 自定义选中文字时的 Formatting Toolbar；
- 自定义 text style / inline content / schema；
- 插入 ProseMirror plugins；
- 插入 Tiptap extensions。

因此第一版应优先通过这些官方扩展接缝实现 DCF Review Extension。

只有在验证 BlockNote 官方公共能力确实不足时，才允许下探更底层结构。

---

# 8. 不直接采用 BlockNote / Tiptap 完整评论世界

## 8.1 BlockNote Comments 不作为第一版默认依赖【已冻结】

BlockNote 已经提供 Comments / Thread / Reply / Emoji 等协作评论能力，但其正式评论体系面向多人协作，并需要 ThreadStore、用户解析以及实时协作能力。

DCF 第一版需求只是：

```text
用户本人
审阅 AI 草稿
```

因此默认不为几个审阅批注引入完整多人评论世界。

若未来出现真实多人协作需求，再重新评估。

---

## 8.2 Tiptap Tracked Changes 不作为第一版默认依赖【已冻结】

Tiptap 当前提供接近 Word / Google Docs 的 Tracked Changes：

```text
insert
remove
overwrite
accept
reject
comments integration
```

但当前官方状态仍属于付费 add-on / Alpha，Comments 也属于额外商业协作能力。

更重要的是，DCF 第一版并不需要完整的多人 suggestion workflow。

因此：

```text
不采用完整 Tracked Changes
不实现逐条接受 / 拒绝用户自己的编辑
```

只借成熟产品的交互思想。

---

# 9. AI 修订输入合同

## 9.1 AI 修订最小输入【已冻结】

一次 AI 修订至少接收：

```text
draft_document
manual_edits_applied
review_items[]
global_instruction（可选）
```

每条 `review_item` 至少表达：

```text
review_id
anchored_content / anchor
review_kind
user_content
```

AI 修订必须优先理解：

```text
用户明确修改后的正文
>
用户明确批注 / 补充 / 否认
>
尚未处理的原草稿表达
```

---

## 9.2 AI 修订输出【已冻结】

AI 修订输出：

```text
新的完整草稿正文
+
本轮哪些 review_item 已被消化的映射
+
可选的修改摘要
```

默认不要求 AI 输出永久 diff 历史。

用户需要检查时可以进入：

```text
查看本轮修改
```

该功能属于草稿制作辅助，而不是正式认知历史。

---

# 10. 草稿历史与防丢失

## 10.1 草稿迭代不是长期认知历史【已冻结】

例如：

```text
AI 初稿 v1
↓
用户修改
↓
AI 修订 v2
↓
用户修改
↓
AI 修订 v3
```

这些版本属于同一正式个人叙事“出生前”的制作过程。

第一版允许保存：

```text
undo / redo
自动保存
防崩溃快照
短期草稿版本
```

但默认不得把每一轮草稿都升格成永久认知叙事节点。

正式原则：

> **不要把编辑器噪声冒充认知历史。**

---

# 11. 完成审阅并提交

## 11.1 提交是业务动作，不是普通 Save【已冻结】

`保存草稿` 与 `完成审阅并提交` 必须是不同语义。

### 保存草稿

```text
保存当前工作状态
保持可编辑
仍然显示日历待审阅提示
```

### 完成审阅并提交

```text
用户确认当前内容可以代表自己的当时叙事
↓
草稿取得正式个人叙事身份
↓
进入只增不改历史
↓
日历待审阅提示消失
↓
页面从修订态切换为展示态
↓
出现轻量“已审阅”印记
↓
右栏从“本轮修订”切换到“后续认知”
```

这是一条必须经过 DCF Action 的正式业务状态跃迁。

# 12. 三 Surface 关系

## 12.1 完整形态【已冻结】

完整形态承担完整草稿修订能力：

```text
BlockNote 正文编辑
选区审阅浮条
本轮修订栏
来源查看
AI 修订
查看本轮修改
完成审阅并提交
```

---

## 12.2 侧边栏【已冻结】

侧边栏不承担完整富文本编辑器全部能力。

它继续保持：

```text
上：日期选择
中：当天草稿 / 正式个人叙事的快速阅读
下：后续认知 / 轻量追加
```

若当天仍是待审阅草稿：

- 可以显示待审阅状态；
- 可以提供“打开完整审阅”入口；
- 不要求在窄侧边栏中复制整套 BlockNote 审阅工作台。

---

## 12.3 悬浮球【已冻结】

悬浮球只显示：

```text
今天已收集证据数量
+
书写 / 审阅图标
```

状态：

```text
白色图标
→ 当天个人叙事尚未完成审阅

绿色图标
→ 当天个人叙事已经完成审阅
```

不增加草稿具体修改数量、批注数量等编辑器内部状态。

---

```text
编辑操作
撤销重做
```

```text
每次文字编辑永久写入认知历史
```

# 14. 行为验收

## 14.1 小改直接提交

```text
AI 生成草稿
↓
用户改两个词
↓
直接完成审阅并提交
```

必须：

- 不强制调用 AI；
- 生成正式个人叙事；
- 页面进入展示态；
- 待审阅日历状态消失。

---

## 14.2 大量批注后 AI 修订

```text
用户给 5 处内容留下不同意见
+
直接修改一部分正文
↓
AI 修订
```

必须：

- AI 读取当前草稿与本轮修订；
- 默认不重新查询原始事实源；
- 用户明确否认的表达不得被旧证据偷偷恢复；
- 输出仍是草稿；
- 用户可以再次手改后才提交。

## 14.3 编辑器故障不改变业务语义

如果未来 BlockNote 被替换：

```text
BlockNote
→ 其他成熟编辑器
```

以下语义必须保持：

```text
AI 初稿
用户手改
局部审阅意见
AI 修订
完成审阅并提交
正式个人叙事
```

因此编辑器是可替换能力本底，不是 DCF 业务真源。

# 16. 一句话冻结

> **DCF 的个人叙事编辑不从文本编辑器开始造轮子。第一版借 BlockNote 这一成熟编辑器世界承载正文、选区和编辑体验，只在其上增加极薄的 DCF Review Extension。用户可以直接手改后提交，也可以留下不满意、否认、补充和批注意图后调用 AI 修订；AI 修订只消化当前草稿与用户修订意图，默认不重新调查事实。只有用户执行“完成审阅并提交”时，草稿才晋升为正式个人叙事，并从此进入只增不改的认知历史。**
