# DCF × Qoder 认知机制移植与认知引擎规范

**状态：讨论基线 v0.1**  
**日期：2026-08-05**  
**用途：把 Qoder Better Harness、Knowledge Engine、Repo Wiki、Memory 中已经证明有价值的机制移植到 DCF；不是复刻 Qoder 产品与实现。**

---

# 0. 总原则：移植机制，不移植产品形态

Qoder 的四个子系统分别回答四个问题：

```text
Better Harness   → 一个判断凭什么成立、哪里值得修
Knowledge Engine → 当前知识怎样组织
Repo Wiki        → 当前理解怎样面向人组织和叙述
Memory           → 经验怎样随时间使用、衰减、冲突和演化
```

DCF 不照搬 Qoder 的目录、数据库 schema、评分维度、UI 或 Agent 实现。

DCF 只继承其中已经暴露出结构性价值的机制，并按 DCF 自己的核心原则重新解释：

> **系统拥有现实，Git/GitHub 拥有工程事实，DCF 拥有意义与认知历史。**

> **现实不可重写，当前地图可以重画；重画地图本身也留下认知历史。**

> **人的正式审阅止步于个人叙事。个人叙事以后，项目叙事、知识、Memory、成熟度诊断和推荐修复均进入自动认知编译链。**

> **主动推进不等于 DCF 自己执行；DCF 主动把工作委派给最适合的完整执行世界。**

# 1. 统一认知骨架

移植完成后，DCF 项目域采用四层结构：

```text
长期历史层
现实记录
+ 正式个人叙事
+ 项目认知事件 / ADR
+ 认知转变关系
+ 执行结果与来源锚点
        ↓ 自动编译

当前状态层
├─ 当前项目叙事
├─ 当前项目知识
└─ 当前项目 Memory
        ↓ 规划 / 诊断

未来意图层
├─ 推荐项目
├─ 推荐修复
├─ 任务候选
└─ 正式委派任务
        ↓ 执行世界

现实层
Codex / GitHub / Bun Job / 其他完整执行世界
        ↓
新事实、新结果、新证据
        └────────────→ 回到长期历史层
```

核心不是建立四套互相复制的数据，而是：

> **一个长期历史根，编译出多个面向不同消费者的当前状态。**

当前状态允许被重新生成；历史认知不静默覆写。

# 2. Better Harness → AI 可推进成熟度与推荐修复

Better Harness 不做 1:1 复刻。

DCF 继承其核心思想：

```text
发现仍依赖隐含理解 / 临场猜测 / 人工兜底的地方
        ↓
区分 Fact / Lead / Judgment
        ↓
判断证据够不够支持当前结论
        ↓
找出最小、高杠杆、owner-aligned 修复
        ↓
规定完成条件与验证路径
        ↓
把修复交给合适执行世界
        ↓
以后用新现实重新评价
```

## 2.1 成熟度不是门禁

项目成熟度与是否立项无关。

成熟度定义为：

> **项目已经在多大程度上把隐含上下文、判断依据、推进方法和验证方式外显化，使新的 AI 能低猜测、低重新理解成本地持续推进。**

当前主要观察面：

1. 项目可理解性；
2. 当前状态可理解性；
3. 可继续推进性；
4. 可验证性；
5. 可积累性。

成熟度首先是指引，不是 KPI。

## 2.2 推荐修复是一等对象

每个成熟度缺口应尽量形成一个可以进入下一轮工作的推荐修复：

```text
为什么成立
+ 当前缺口影响什么
+ 最小推荐改变
+ 预期结果
+ 应留下的工件 / 证据
+ 验证路径
+ 推荐执行世界
```

推荐修复不是 ADR；它属于未来意图层。

只有修复执行后真正改变项目认知、方向、边界或结构时，才可能形成新的 ADR。

## 2.3 证据纪律

保留 Better Harness 的认识论纪律：

- Fact、Lead、Judgment 分离；
- Missing / Unobserved / N/A 不坍缩；
- 证据强度与“好坏判断”分离；
- 同一窗口内修好，只证明当前修复状态，不自动证明长期有效；
- 判断标准一个观察窗口内固定，标准变化必须显式版本化；
- 声明类型不同，所需证据门槛不同。

但不固定复刻 Better Harness 的五维权重、15 check 或 59/74/84/94/100 ceiling。

# 3. Knowledge Engine → 项目当前知识系统

Qoder Knowledge Engine 最值得继承的不是 Markdown 卡片长相，而是四个机制：

1. **本体与投影分离**；
2. **现实范围隔离**；
3. **多切面并存**；
4. **当前知识可自动重生**。

DCF 在此基础上补上 Qoder 没有一等化的认知历史与认知转变关系。

## 3.1 当前项目知识的定位

项目知识主要服务项目自身与 AI，不是用户日常阅读主界面。

它回答：

> **为了继续推进这个项目，现在最好让 AI 知道什么？**

它可以吸收：

- Git / 系统确定性事实；
- 正式项目叙事中的稳定理解；
- 项目 Memory 中反复有效的经验；
- 实验结论；
- 架构边界；
- 方法论；
- 关键概念；
- 已验证规则；
- 可复用能力与 Skill。

用户需要理解某个概念时，可以从项目叙事中的链接穿透到知识卡，但知识卡本身不是项目域第二套主要阅读产品。

## 3.2 本体与投影分离

DCF 不把某个 Markdown 文件当成知识本体。

推荐结构：

```text
当前项目知识状态（权威当前态）
        ↓
├─ AI 注入导航投影
├─ 人类维护 UI 投影
├─ Markdown / Git 导出投影
└─ 特定任务上下文投影
```

投影允许自动重生。

内容 hash 只说明“这是不是同一份内容”，不证明权威或正确：

> **身份 ≠ 权威 ≠ 正确性。**

## 3.3 局部隔离 + 全局连续

不同现实范围可以同时拥有互相冲突但都正确的当前状态。

例如：

```text
main 当前知识
实验分支当前知识
旧版本当前知识
另一个设备 / 工作区当前知识
```

不能为了“统一知识”把它们强行混成一个当前态。

因此：

```text
各现实范围
→ 当前知识局部隔离

跨范围同一问题 / 概念 / 项目身份
→ 通过全局认知谱系保持连续
```

这意味着“当前态隔离”和“历史连续”同时成立。

## 3.4 多切面并存，不压成一棵树

Qoder 同时维护模块切面与主题切面，而且互不要求谁成为唯一真树。

DCF 继承这一点。

一个项目的当前知识可以同时拥有：

```text
模块切面    → 这个模块是什么
主题切面    → 项目横向有哪些共同知识
任务切面    → 当前任务需要什么知识
概念切面    → 关键概念如何连接
能力切面    → 当前有哪些可复用能力 / Skill
```

不要求所有知识先进入一个统一目录层级，再从那一棵树解释全部世界。

## 3.5 关系：结构关系与语义关系分层

值得确定性维护的一等关系进入结构层，例如：

- 父子 / 包含；
- 来源 / 引用；
- 现实范围；
- 由哪条 Memory / ADR / 实验晋升而来；
- 跨范围身份；
- 认知转变关系。

偏解释性的“依赖 / 相关 / 为什么相似”可以留在语义内容中，除非真实使用证明它值得升格成一等关系。

> **不因为图数据库能建边，就把所有语义都结构化。**

## 3.6 知识晋升必须保留反向来源

Memory、实验或项目叙事中的内容如果晋升成项目知识，必须保留：

```text
当前知识卡
↓ provenance
来自哪条 Memory / ADR / 事实 / 实验
```

不能只做“Memory → Knowledge”而断掉反向链路。

# 4. Repo Wiki → 当前项目叙事的规划与生成机制

Qoder Repo Wiki 最值得继承的是：

> **先决定怎样理解和组织，再生成面向人的当前叙述。**

在 DCF 中，Repo Wiki 不单独形成第二套人类主产品，而是被吸收到“当前项目叙事 / 项目首页 / 项目说明”的自动生成机制里。

## 4.1 区分两类项目叙事

DCF 项目域必须同时区分：

### A. 历史项目叙事

与 ADR 节点绑定，回答：

> **当时项目为什么发生这次重要变化？**

它属于认知历史，不静默覆写。

### B. 当前项目叙事投影

回答：

> **站在现在，这个项目整体是什么、现在到哪里、主要结构和问题是什么？**

它是当前态，可以随着历史和知识变化自动重生。

Repo Wiki 的机制主要移植到 B，而不是把历史 ADR 覆盖成“最新版 Wiki”。

## 4.2 叙事规划层

生成当前项目叙事之前，先形成一个轻量叙事规划：

```text
当前最需要回答哪些问题
哪些 ADR 是主骨架
哪些项目知识需要解释
哪些现实事实必须引用
哪些历史分叉必须显示
哪些内容属于细节，不应占主阅读位置
```

可以理解成 Qoder catalog/index 的 DCF 版本。

它不是最终正文，而是：

> **“现在准备怎样讲这个项目”的生成计划。**

规划可以随当前现实自动调整。

## 4.3 用户审阅边界

用户正式审阅只发生在个人叙事。

```text
现实 / AI 交互
↓
个人叙事草稿
↓
用户审阅
↓
正式个人叙事
========================
后续项目域全部自动编译
```

因此：

- 项目叙事不要求逐条用户审批；
- 当前项目叙事可以自动重生；
- ADR 级项目认知由系统根据已形成的正式个人叙事、Git/现实事实和后续证据自动形成；
- 如果后来证明组织错误，重新组织当前项目图和当前叙事，同时保留过去曾经形成过的机器认知历史。

用户如果主动纠正项目理解，这个纠正发生在当前时间，并作为新的认知事件进入历史，而不是回写过去。

# 5. Memory → 项目经验的生命周期系统

Qoder Memory 最值得继承的是：

1. 当前记忆状态与操作演化分离；
2. 召回本身也是事件；
3. 来源锚点与演化历史分离；
4. 软遗忘与当前检索地位可变化；
5. Memory 可以被整理、评估和晋升。

DCF 不继承 Qoder 的“冲突败者从当前层物理删除”做法。

## 5.1 DCF 项目 Memory 是什么

Memory 不是正式历史叙事，也不是稳定知识卡。

它更像：

> **项目在持续工作中暂时值得记住、以后可能再次有用的经验单元。**

例如：

- 某种故障常见原因；
- 某个工具在当前环境里的特殊用法；
- 某个方案曾踩过的坑；
- 某类用户偏好在本项目中的具体表现；
- 某个尚未升格成正式知识的工作经验；
- 某次 Codex 执行暴露出的重复模式。

## 5.2 当前态 + 演化账本 + 认知谱系

DCF 采用三层：

```text
当前 Memory 状态
→ 现在是否活跃、常用、值得召回

机械操作账本
→ create / retrieve / evaluate / organize / deactivate ...

认知谱系
→ 延续 / 补充 / 修正 / 重新解释 / 取代 / 合流
```

机械账本回答“发生了什么操作”。

认知谱系回答“为什么这算同一条经验的新理解”。

二者不混在一起。

## 5.3 召回即事件

每次 Memory 被真正用于 AI 上下文或任务时，都应留下召回事件。

召回可以改变：

- 使用频率；
- 当前重要性；
- 保留优先级；
- 下一次复审时间；
- 是否值得晋升为知识 / Skill / 规则。

所以：

> **Memory 内容可以不变，但它在项目中的认知地位可以变化。**

## 5.4 来源锚点与演化历史分离

必须分别回答：

```text
这条 Memory 最初来自哪里？

它后来怎样被使用、修改、修正、降级或晋升？
```

来源可以指向：

- 会话 / Codex 线程；
- ADR；
- Git 事实；
- 实验；
- 个人叙事；
- 其他项目结果。

来源不是完整演化历史；演化历史也不是来源。

## 5.5 遗忘只作用于当前可用层，不删除认知历史

DCF 继承软遗忘：

```text
高优先召回
↓
普通
↓
低优先
↓
当前层 inactive / forgotten
```

但是：

> **检索层可以忘，认知历史不能因为“现在不想召回”而被物理删除。**

如果确实存在隐私删除、法律删除或用户明确要求销毁，则属于另一套数据删除语义，不与“Memory 遗忘”混用。

## 5.6 冲突：保留双方 + 转变关系

Qoder 可以 modify 覆盖或 delete 败者。

DCF 不采用这一点。

例如：

```text
A：此前认为 X 是主要原因
B：后来发现 Y 才是主要原因
```

正确表示是：

```text
A ──修正 / 重新解释──→ B
```

当前 Memory 可以只优先召回 B，但 A 仍留在历史中。

## 5.7 Memory 晋升

一条经验如果反复被召回、跨任务仍然有效，可能晋升为：

```text
项目知识卡
Skill
方法论
行为验收
规则
推荐修复模板
```

晋升以后必须保留反向来源。

如果只对某个现实范围有效，则保持项目 / 分支局部，不自动晋升为跨项目通用知识。

# 6. 三种规划层：叙事、知识、行动

从 Qoder catalog 机制可以抽出一个更通用的结构：

> **生成之前先规划“现在需要什么表示”。**

DCF 因此采用三个互相独立的规划层：

```text
叙事规划
→ 现在怎样把项目讲给人理解
→ 生成当前项目叙事 / 项目首页

知识规划
→ 现在为了继续推进需要知道什么
→ 生成 / 更新项目知识

行动规划
→ 现在什么最值得改变
→ 形成推荐修复 / 任务候选
```

三者消费同一个长期历史根，但服务不同消费者，禁止坍缩成同一个“大一统规划”。

# 7. 主动推进：DCF 不自研通用 Harness

成熟度诊断和行动规划会自然产生推荐修复。

DCF 的职责到这里为止：

```text
发现缺口
↓
形成推荐修复
↓
明确任务上下文
↓
明确权限 / 资源边界
↓
明确完成条件
↓
明确证据要求
↓
选择执行世界
```

真正执行交给完整世界。

## 7.1 软件工程默认执行世界：Codex APP 独立任务线程

软件工程类推荐修复优先：

```text
DCF 推荐修复
↓
生成任务书
↓
通过 Codex 子线程 / 新任务能力
在 Codex APP 中创建独立任务会话
↓
Codex 自己规划、修改、测试、授权、交互
↓
DCF 通过线程观察接缝读取状态和结果
↓
记录结果 / 证据 / 来源线程
```

DCF 不复制 Codex 的：

- Agent UI；
- 对话；
- Shell 输出；
- 权限交互；
- 工具循环；
- 任务内部规划。

> **Codex 拥有执行事实，DCF 拥有“这次执行对项目意味着什么”。**

## 7.2 执行线程天然作为来源收据

DCF 至少保存：

```text
repair_id
execution_world
thread_id / task_id
started_at
current_status
final_result_summary
key_evidence_refs
```

详细过程需要追究时，直接穿透回原始执行世界。

## 7.3 执行结果不等于 ADR

```text
推荐修复
↓
执行结果
↓
验证结果
```

这些首先是现实结果。

只有当结果造成项目的重要认知、方向、边界或结构变化时，才形成 ADR。

# 8. UI：Qoder 机制在 DCF 中如何出现

这些机制不能把项目首页变成工程后台。

主阅读顺序保持：

```text
项目总览
↓
项目首页：现在怎么样
↓
项目形态图：为什么变成这样
↓
ADR 项目叙事：这次变化意味着什么
↓
知识 / Memory / 证据 / Git / Codex 原始线程
```

## 8.1 项目首页

第一屏只显示：

```text
项目身份
当前一句话状态
AI 可推进成熟度
当前最值得改善的问题
正在执行的主动改善
最近重要变化
```

示意：

```text
DCF
个人认知基础设施

成熟度 82                         ● 活跃

现在
项目叙事、立项与成熟度机制已经形成基本闭环。

当前最值得改善
△ 当前阶段入口仍然分散
  [查看推荐修复]

正在自动改善
● Codex：建立统一当前阶段入口
  [在 Codex 中查看 ↗]
```

## 8.2 当前项目叙事

项目首页及项目说明属于 Repo Wiki 机制迁移后的“当前人类叙事投影”。

它自动重生，不需要用户审批。

用户若想知道“现在为什么这样讲”，可以展开：

```text
叙事依据
→ 主要 ADR
→ 关键知识
→ Git / 系统事实
→ 个人叙事来源
```

默认不展示 catalog / prompt / 内部规划结构。

## 8.3 项目知识 UI

知识不是主导航首页的高频入口。

主要进入方式：

- 项目叙事里的概念链接；
- 推荐修复中引用的能力 / 方法；
- 维护页“项目知识”；
- AI 任务上下文。

人类维护 UI 应能回答：

```text
这个知识是什么？
现在在哪些现实范围有效？
为什么我们现在相信它？
它来自哪里？
最近什么时候被使用？
有没有冲突 / 更晚理解？
```

## 8.4 Memory UI

Memory 不做成聊天记忆列表。

维护 UI 主要展示：


# 10. 当前冻结的移植原则

> **Better Harness 移植为“AI 可推进成熟度 + 推荐修复”，不复制其业务评分模型。**

> **Knowledge Engine 移植“本体/投影分离、局部隔离、多切面、自动重生”，并补上 DCF 的认知历史。**

> **Repo Wiki 移植“先规划怎样理解，再生成当前人类叙事”，但不制造第二套与项目叙事竞争的主阅读产品。**

> **Memory 移植“当前态 + 操作账本、召回即事件、来源与演化分离、软遗忘、经验晋升”，但不采用冲突败者物理删除。**

> **当前检索层可以忘，认知历史不能因为‘不再常用’而消失。**

> **Memory 晋升为 Knowledge / Skill / Rule 后必须保留反向来源。**

> **多维知识不强行压成一棵树；现实范围局部隔离，跨范围认知全局连续。**

> **用户正式审阅止步于个人叙事；项目域后续认知产物自动生成并允许后续重新解释。**

> **主动推进由 DCF 发起，但执行交给完整执行世界；软件工程优先使用 Codex APP 独立任务线程。**

> **执行结果不是 ADR；只有重要认知变化才进入项目形态图。**
