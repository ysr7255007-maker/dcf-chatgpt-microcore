# DCF 叙事日历与三 Surface 交互规范

日期：2026-08-05  
状态：**正式子规范 v1；当前产品/UI 实施依据**

关联文档：

- `docs/spec/2026-08-05-DCF-总设计说明书.md`
- `docs/spec/2026-08-05-DCF-认知时间语义与叙事交互协议.md`
- `docs/spec/2026-08-05-DCF-P0-功能舱-窄腰-不可变代际协议.md`

本文负责冻结 DCF “个人叙事”功能在完整形态、侧边栏与悬浮球中的第一版产品形态，并补齐 AI 叙事草稿、人工审阅、正式个人叙事、后续认知追加之间的生命周期关系。

---

# 1. 总裁决

## 1.1 AI 首先生成的是“个人叙事草稿”，不是正式个人叙事【已冻结】

当某日材料已经足够形成叙事时，AI 首先产生：

```text
当日事实 / 交互 / 当前认知材料
↓
AI 编制
↓
个人叙事草稿
```

个人叙事草稿是**待人工审阅的工作副本**。

在用户完成审阅之前，它允许：

```text
直接改字
改句
改段落
删除 AI 草稿中的错误表达
增加遗漏背景
调整叙事顺序
进行长文本重写
使用快速认同 / 不满意 / 否认等辅助动作
```

原因不是历史允许修改，而是：

> **此时它还没有取得“正式个人叙事”的历史身份。**

因此正式原则是：

> **草稿可编辑；历史不可覆写。**

---

## 1.2 审阅完成是一次身份晋升【已冻结】

用户明确完成当日叙事审阅后：

```text
个人叙事草稿
↓ 用户确认完成审阅
正式个人叙事
```

从这一刻开始：

- 正式个人叙事成为该时点真实存在过的认知叙事；
- 不再通过直接覆盖正文的方式修改；
- 后续任何“修正、补充、新增理解、否认、评论”均产生当前时点的新认知记录；
- 后续认知可以指向这条个人叙事，但不能改变其原始正文与形成时间。

这使两条原则同时成立：

```text
审阅阶段
→ 用户拥有自然、完整的编辑器体验

审阅完成以后
→ 认知历史只增不改
```

---

## 1.3 界面必须显式区分“修订态”和“展示态”【已冻结】

同一个日期页面有两个主要视觉状态。

### 修订态

对象：个人叙事草稿。

界面重点：

```text
AI 草稿正文
直接编辑工具
快速反馈动作
来源检查
事实核对
完成审阅
```

视觉上应明确让用户知道：

> 这是 AI 交给我的草稿，我正在把它变成自己的叙事。

### 展示态

对象：已经审阅完成的正式个人叙事。

界面重点：

```text
安静阅读
来源穿透
后续认知追加
查看后来理解
```

修订工具退出主视觉；页面转为稳定的阅读态。

正式个人叙事应带一个**轻量、低压、可识别的“已审阅”视觉印记**。

首选方向：

- 类似浅色印章 / 验讫章；
- 不遮挡正文；
- 不采用强烈成功提示；
- 作用是告诉用户“这已经从 AI 草稿晋升为我的个人叙事”。

具体印章图形、文字与颜色可在视觉设计阶段微调。

---

# 2. 完整形态：叙事日历 + 阅读/修订 + 后续认知

## 2.1 总布局【已冻结】

第一版完整形态采用三列信息架构：

```text
左：日期导航 / 叙事日历
中：该日个人叙事草稿或正式个人叙事
右：后续认知追加
```

核心布局参考：

```text
┌────────────┬──────────────────────────┬────────────────────┐
│ 叙事日历   │ 个人叙事                 │ 后续认知            │
│            │                          │                    │
│ 年/月/日   │ 修订态：AI 草稿          │ 2026-05-18 ……      │
│ 日期状态   │ 展示态：正式个人叙事     │ 2026-08-05 ……      │
│            │                          │                    │
│            │                          │ ＋ 添加现在的理解   │
└────────────┴──────────────────────────┴────────────────────┘
```

这不是三个独立事实源：

- 左侧是日期与状态投影；
- 中间是当前选中日期的主叙事对象；
- 右侧是后来形成且指向当前叙事的认知事件投影。

---

# 3. 左侧叙事日历

## 3.1 日历的显示原则【已冻结】

日历不是“把所有发生过的事情都编码成状态灯”。

日历主要显示两类信息：

```text
A. 需要用户注意 / 处理的事情
B. 软件已经自动生成、且值得快速知道的少量派生产物
```

因此默认**不显示**以下状态标记：

```text
“有原叙事”
“有新增理解”
“有修正表达”
```

这些都属于打开日期后自然可见的信息，不值得占用日历注意力预算。

---

## 3.2 待审阅 / 待处理【已冻结】

如果某日存在 AI 个人叙事草稿，但用户尚未完成审阅：

- 日期需要有明显但低压的待处理提示；
- 首选为日期周围的细圈 / 轻量描边；
- 可以使用偏红或暖色，但不得把整个格子染成强烈警报色；
- 目的只是让用户扫日历时立即知道“这里还有我需要完成的认知工作”。

概念示意：

```text
   ╭───╮
   │ 18│   ← 待审阅细圈
   ╰───╯
```

颜色、线宽和动画不在当前规范锁死。

---

## 3.3 原始事实 / 来源数据缺失【已冻结】

如果某日应当存在的原始事实数据、来源记录或关键证据找不到，这不是普通待办，而是**数据链故障**。

它的严重性高于“叙事还没审阅”，但视觉仍然不得制造持续焦虑。

第一版建议：

- 日期角落显示一个小型感叹号角标；
- 使用与普通待审阅不同的暖橙 / 琥珀 / 暗红警示色；
- 允许日期格有极轻微底色提示，但不得整格高饱和红色；
- 悬停 / 点击后明确说明故障：缺什么来源、最后一次正常时间、是否可以恢复。

概念示意：

```text
  18  !
```

正式语义：

> **来源链故障必须可见，但不能让整个叙事日历变成报警面板。**

---

## 3.4 自动派生产物的小标记【已冻结】

日历允许显示少量“软件已经为这一天产出了什么”的小型角标。

第一批允许的方向：

```text
知识卡已生成
项目叙事 / 项目关联已形成
```

表现方式优先使用微型图标，而不是状态文字或强颜色：

```text
18  ▣   ← 微型知识卡片图标
21  ◆   ← 微型项目关联 / 项目叙事图标
```

这些图标：

- 只表达“存在”；
- 不承担待处理提醒；
- 数量多时不得在单日期格无限叠加；
- 若未来派生产物种类增长，应通过聚合或详情弹层处理，而不是把日历变成图标墙。

---

# 4. 中间主叙事区

## 4.1 修订态：AI 个人叙事草稿【已冻结】

当日期处于待审阅状态，中间区域显示 AI 生成的个人叙事草稿。

必须支持自然混合操作：

```text
一部分直接快速通过
一部分仔细读
一部分直接改字改句
一部分重写整段
一部分补大量遗漏背景
一部分查看原始事实
```

因此不建立“快速审核模式 / 深度审核模式”两个业务模式。

修订态 UI 应提供：

- 正文级直接编辑；
- 选区级操作；
- 来源 / 证据查看；
- 快速认同、不满意、否认等低成本表达；
- 完成审阅动作。

其中快速动作服务于用户表达，不决定最终文本如何自动覆盖。

---

## 4.2 完成审阅【已冻结】

“完成审阅”不是普通保存按钮。

它意味着：

```text
AI 草稿工作副本
↓
用户认可当前正文代表此时自己的个人叙事
↓
冻结正文与形成时间
↓
取得正式个人叙事身份
↓
界面进入展示态
```

行为验收必须证明：

- 完成前允许自然修改草稿；
- 完成后普通编辑器不再直接覆盖该正式叙事；
- 完成后再次产生的修正，进入新的当前认知事件；
- 旧正文仍保持审阅完成时的样子。

---

## 4.3 展示态：正式个人叙事【已冻结】

审阅完成后，中间区域切换到以阅读为主的展示态。

要求：

- 去除大部分修订态工具噪声；
- 显示轻量“已审阅 / 已成为个人叙事”的印记；
- 保留来源穿透入口；
- 保留“添加现在的理解”入口；
- 允许跳转相关知识卡、项目叙事等派生物，但不在此处执行它们的专属重算工作流。

特别冻结：

> **知识卡重新生成不属于个人叙事页面的主要操作。**

知识卡重新生成应发生在知识卡专门界面；个人叙事页面只作为其来源和认知追加入口。

---

# 5. 右侧后续认知区

## 5.1 视觉隐喻【已冻结】

正式个人叙事相当于“主帖 / 布告板底稿”；后续认知相当于围绕它持续增加的“回复 / 评论 / 标签纸”。

第一版产品结构采用更稳定的**纵向卡片 / 论坛回复式信息结构**，而不是依赖真实软木板、图钉、自由拖拽等强拟物交互。

原因：

- 纵向结构可读性更稳定；
- 更适合长文本与大量后续理解；
- 更容易保持时间顺序；
- 不牺牲“主叙事 + 后续层层长出”的视觉语义。

可以借用轻度便签 / 标签纸的视觉语言，但不得让装饰优先于信息。

---

## 5.2 卡片最小结构【已冻结】

每条后续认知卡片默认只要求：

```text
形成时间（必须）
认知正文 / signal（必须）
```

可以附带极轻量的上下文入口，但默认不强制显示“类型”。

明确禁止把每条认知强制分类成：

```text
新增理解
修正
否认
补充
```

原因：

> **一次真实表达可能同时具有修正、补充、否认和新增理解等多重含义。**

交互来源仍可在底层记录 `interaction_kind`，但不要求 UI 把它变成互斥类型标签。

---

## 5.3 标签【第一版不作为卡片默认字段】

后续认知卡片第一版不要求用户或 AI 为每条认知建立人工分类标签。

原因：

- 当前功能目标是保留和使用认知变化，不是建立分类学；
- 强制标签会增加表达摩擦；
- 未来若知识整理、搜索或项目视图证明需要，再作为派生能力增加。

因此当前卡片不默认展示标签区。

---

## 5.4 来源入口【按需出现】

“来源”不是要求用户给每条认知手工分类。

它表示：

> 这条当前认知是在什么上下文中形成、指向了什么对象、从哪里一路穿透到这里。

只有当存在有意义的来源关系时，卡片才显示轻量入口，例如：

```text
来自：知识卡 K17 → 项目叙事 → 当前个人叙事
```

或：

```text
查看触发上下文
```

它用于解释因果与溯源，不用于把认知归档进文件夹。

如果认知就是用户直接在当前页面自由追加，也可以不显示来源入口。

---

## 5.5 操作菜单【极简】

卡片操作菜单只保留真正属于“这条认知记录自身”的动作。

第一版建议：

```text
查看形成上下文（若存在）
复制
```

对于刚刚输入、尚未提交的编辑器草稿，可以正常撤销 / 修改；

对于已经提交并成为历史认知的卡片，不提供“直接覆盖旧记录”的普通编辑动作。

如果用户后来认为它表达不准确，应新增一条当前认知，而不是修改过去记录。

删除、隐藏、归档等语义当前不冻结，实施 AI 不得自行加入。

---

# 6. 侧边栏形态

## 6.1 左中右压缩为上中下【已冻结】

侧边栏不是重新设计一套业务，而是把完整形态压缩成纵向信息流：

```text
顶部：日期选择
↓
中部：当日个人叙事草稿 / 正式个人叙事
↓
底部：后续认知追加
```

即：

```text
完整形态        侧边栏

左：日期     →   上：日期
中：叙事     →   中：叙事
右：追加     →   下：追加
```

---

## 6.2 侧边栏的叙事区【已冻结】

侧边栏主要服务快速阅读与调用。

如果当天仍是 AI 草稿：

- 可以展示草稿摘要 / 关键段落；
- 可以提示“待审阅”；
- 可以提供进入完整形态继续审阅的入口；
- 不要求在窄栏里复刻完整长文编辑器。

如果当天已经成为正式个人叙事：

- 展示正文摘要或当前阅读位置；
- 显示已审阅轻量印记；
- 允许快速查看相关后续理解。

---

## 6.3 侧边栏的后续认知区【已冻结】

底部按时间排列后续认知。

在上下文足够清楚时，用户可以直接追加一条当前理解。

如果需要：

```text
阅读完整历史
查看大量来源
长文本编辑
复杂事实核对
```

则跳转完整形态。

因此侧边栏和完整形态共享同一认知 Action；差别只是承载容量与交互密度。

---

# 7. 悬浮球 / 极简常驻形态

## 7.1 只显示两类信息【已冻结】

第一版悬浮球不承担叙事内容展示。

只显示：

```text
1. 今天已经收集到多少条证据 / 事实材料
2. 今天的个人叙事是否已经完成审阅
```

其他信息默认不进入悬浮球。

---

## 7.2 证据数量【已冻结】

悬浮球可以使用一个极小数字或极简计数视觉：

```text
12
```

表示今天已经收集到 12 条当前定义下的事实 / 证据材料。

计数的精确定义——什么粒度算“一条证据”——仍需由事实采集规范进一步冻结；UI 不应在定义前自行猜测。

---

## 7.3 叙事审阅图标【已冻结】

悬浮球使用一个极简“书写 / 编辑”图标表示当天叙事审阅状态。

```text
白色书写图标
→ 今天仍有待审阅个人叙事草稿

绿色书写图标
→ 今天的个人叙事已经审阅完成
```

它只是状态提示，不应闪烁、跳动或制造持续警报感。

晚间可以根据用户设置进行一次轻量提醒，但提醒策略、时间与频率不在本文冻结。

---

# 8. 关键状态模型

第一版至少存在以下业务状态：

```text
某日叙事状态
│
├─ no_material
│  → 当前还不足以形成草稿
│
├─ source_fault
│  → 理论上应有事实 / 来源，但链路缺失或不可读取
│
├─ draft_ready
│  → AI 个人叙事草稿已经生成，待用户审阅
│
└─ narrative_final
   → 用户已经完成审阅，正式个人叙事成立
```

派生产物与之正交：

```text
knowledge_card_exists
project_narrative_or_link_exists
```

后续认知数量也与叙事状态正交，不作为日历默认状态色：

```text
later_cognition_count = N
```

这避免把所有信息压进一个复杂状态枚举。

# 9. 行为验收

## 9.1 草稿到正式叙事

```text
AI 生成草稿
↓
日期出现待审阅提示
↓
用户直接编辑正文
↓
点击完成审阅
↓
正式个人叙事生成
↓
日期待审阅提示消失
↓
正文转展示态并出现轻量已审阅印记
```

通过条件：后续不能再用普通正文编辑器静默覆盖这份正式叙事。

---

## 9.2 后续理解不改过去

```text
打开 1 月正式个人叙事
↓
8 月新增一条当前理解
↓
右侧出现 8 月时间戳卡片
↓
1 月正文逐字不变
```

同时该认知属于 8 月当天材料，可参与 8 月项目 / 个人叙事编制。

---

## 9.3 日历只提示值得注意的信息

有原叙事、有 5 条后续理解但没有待办：

```text
不得因为这些事实给日期画一堆状态点
```

有未审阅草稿：

```text
必须有待处理提示
```

来源事实链故障：

```text
必须有区别于普通待审阅的故障提示
```

有知识卡 / 项目关联：

```text
允许出现微型派生产物图标
```

---

## 9.4 三 Surface 同一事实

同一天：

```text
完整形态显示 draft_ready
侧边栏也必须显示待审阅
悬浮球书写图标必须为待审阅状态
```

完成审阅后：

```text
三处基于同一业务状态同步变化
```

禁止三个 Surface 自己维护三份审核状态。

---

# 10. 当前仍待讨论的 UI 细节

以下不影响当前业务模型成立，可继续通过 UI 原型逐步确定：

1. 待审阅日期细圈最终使用红、橙还是其他低压暖色；
2. `source_fault` 感叹号角标的精确视觉与是否带轻底色；
3. “已审阅印章”的图形、文字、位置和透明度；
4. 主叙事正文是否采用纯文章式排版，还是保留少量块级编辑痕迹；
