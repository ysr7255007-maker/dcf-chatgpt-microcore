# DCF 功能包络与施工控制规范

日期：2026-08-06  
状态：当前施工控制专项规范  
适用范围：DCF 新原生实现的功能定义、能力依赖、最小功能通路验证、施工调度、验收、分支与失败责任边界。

> 本规范只改变**施工控制方式**，不重新定义 DCF 的六层世界、事实所有权、个人叙事、SQLite 锚定认知世界、查询诱导语义场、约束求解或行动世界的业务语义。

---

# 0. 与总规范的权威关系

`docs/spec/2026-08-04-DCF-当前实施规范.md` 继续是 DCF 当前最高层总体架构权威。

本规范是更具体的施工控制专项规范。

它明确替代总规范中以下旧施工控制语义：

```text
第 19 节：P0 → P9 是“当前真实施工顺序”
第 20 节：G0 → G9 是所有功能必须按阶段推进的统一施工流程
```

P0～P9、G0～G9 的历史内容继续保留，用于：

```text
产品成熟度理解
能力覆盖检查
历史施工推演
需求视图
```

但从本规范生效起：

> **它们不再拥有施工调度权。**

当前真实施工控制由本规范定义的：

> **功能包络（Capability Envelope）+ 能力有向无环图（Capability DAG）**

承担。

若只涉及施工顺序、功能施工资格、依赖解锁、通路验证与执行层权限，本规范优先于总规范旧第 19～20 节。

---

# 1. 施工的唯一正式单位：功能包络

DCF 新实现的正式施工单位是：

> **功能包络（Capability Envelope）**

一个功能包络不是：

```text
目录
模块名
类
函数
开发任务
阶段
进度百分比
```

它是：

> **一个能够独立产生有价值输出、能够由下游独立消费、并能够独立机器验收的能力边界。**

从功能包络外部看，它必须像：

> **一台可以单独验收的小机器。**

施工任务可以变化、拆分、失败、重做；功能包络的契约不能因为施工困难而被执行层偷偷改变。

---

# 2. 功能包络在暴露给执行层之前必须已经设计完成

设计层暴露一个正式功能包络时，至少必须冻结：

```text
功能标识与版本
功能定义
输入格式
输入契约
输出格式
输出契约
错误格式
错误契约
允许状态变化
禁止状态变化
功能需求
质量 / 性能要求
真实能力依赖
最小功能通路验证
完整验收步骤
PASS / FAIL 条件
验收证据格式
```

禁止把以下设计责任留给执行层：

```text
输入字段应该叫什么
输出应该返回什么
错误码应该有哪些
性能多快才算够
是否应该增加一个上游能力
是否应该增加 Adapter
是否应该降低下游要求
某个功能是否应该被拆成两个能力
```

这些如果尚未决定：

```text
功能包络 = DESIGN_NOT_CLOSED
```

不得作为正式施工任务派发。

---

# 3. 输入 / 输出必须成为机器契约

正式功能包络禁止只写：

```text
输入：正式正文
输出：不可变修订
```

必须明确到执行者不需要猜测：

```text
数据格式
编码
字段名
字段类型
必填 / 可选
允许值
禁止额外字段与否
长度 / 数量边界
时间格式
身份格式
失败输入的错误语义
成功输出的关系不变量
```

目标是：

> **另一个验收 Agent 不需要理解作者意图，只依据契约和输出就能得到确定 PASS / FAIL。**

当前功能包络元格式仍在通过“稳定认知对象 + 不可变修订”样板收紧；在元格式正式冻结前，不得批量制造模糊功能包络。

---

# 4. 能力 DAG

所有正式功能包络组成：

> **能力有向无环图（Capability DAG）**

依赖边表示：

```text
上游已经承诺并验收的某项输出能力
↓
成为下游正式能力成立所需的输入能力
```

依赖必须尽量绑定到具体可消费输出，而不是模糊模块名。

错误：

```text
个人叙事依赖 SQLite
```

更准确：

```text
正式个人叙事提交
依赖：
- 正式认知对象写入
- 不可变修订编号
- 原子提交保证
```

如果上游提供五项能力而下游只消费两项，不相关的另外三项不得人为阻塞下游。

---

# 5. 不存在全局“基础设施完成”门

工程基础设施可以是一个高扇出的矩形根节点，因为基础设施天然意味着被大量能力依赖。

但它不能成为：

> **整个项目必须完整做完以后才能施工业务的阶段门。**

正确规则：

```text
某功能需要的真实依赖已经成立
↓
该功能即可进入正式施工资格判断
```

如果个人叙事只需要：

```text
现实输入能力
AI 调用能力
正式认知提交能力
审核 Surface 能力
```

则这些依赖成立以后即可施工。

尚未完成的 Job / Worker、LKG、高级执行器等，如果不是它的真实依赖，不得阻塞它。

基础设施本身必须保持：

```text
低复杂度
低耦合
低业务语义
稳定输出
成熟构件优先
DCF 只定义薄接缝
```

---

# 6. 最小功能通路验证属于下游功能本身

每个正式功能包络 B 必须包含：

> **最小功能通路验证（Minimum Functional Path Validation）**

它属于 B。

它不是：

```text
独立功能节点
A → B 之间的新能力层
完整端到端集成测试
上游成熟组件正确性测试
```

它只做一件事：

> **用符合 B 输入契约的最小输入，只实现 B 最短底层逻辑路径，并产生规定的最小有效输出。**

---

# 7. 通路验证默认不依赖真实上游实现完成

B 的通路验证默认输入使用：

```text
最小合成夹具（Minimal Synthetic Fixture）
或
真实样本切片（Real Sample Slice）
```

因此：

> **只要 B 的输入 / 输出契约已经由设计层冻结，B 的通路验证就应该尽早执行。**

即使：

```text
A 还没有产生真实结果
甚至 A 还没有开始完整实现
```

只要设计已经规定 A 将向 B 提供什么结构，而 B 的输入契约已经冻结，就可以构造最小合法 Fixture 验证 B。

这使项目同时存在两股推进波：

```text
通路验证波
→ 沿已经冻结的契约尽量提前探路

真实能力实现波
→ 沿能力 DAG 的真实依赖逐步解锁
```

目的：

> **尽可能在昂贵完整施工抵达之前暴露设计错误。**

---

# 8. 通路验证的 PASS 不等于功能 PASSED

通路验证 PASS 只证明：

```text
合法最小输入
↓
本功能最短底层逻辑
↓
最小有效输出
```

能够成立。

正式能力 B 成为 `PASSED` 仍必须满足：

```text
B 自己的通路验证已 PASS
+
B 所有必要真实上游能力已 PASSED
+
B 完整实现完成
+
B 全部功能验收通过
+
B 全部质量 / 性能门槛通过
```

因此禁止把：

```text
通路验证成功
```

报告成：

```text
功能完成
```

---

# 9. 通路验证失败的责任边界

使用完全符合 B 输入契约的 Fixture 时，如果 B 最小通路无法产生规定输出：

```text
B = DESIGN_BLOCKED
```

执行层必须：

```text
停止
保留固定输入
保留实际输出 / 错误
记录失败步骤
提供可重复证据
返回设计层
```

执行层禁止自行：

```text
降低 B 要求
修改 B 输入 / 输出契约
增加 Adapter
增加新上游能力
扩大 A 职责
重画能力 DAG
```

因为这属于设计错误，而不是施工任务。

---

# 10. 唯一允许对上游提出修改意见的情况

如果通路验证或后续真实接入使用了 A 的真实输出，并发现：

```text
A 的实际输出
不满足
A 自己已经冻结的输出契约
```

则下游可以提交：

> **上游契约违例报告**

必须包含：

```text
A 的既定契约要求
A 的实际输出
不符合字段 / 行为
固定触发输入
复现步骤
失败证据
```

允许提出的修改意见仅限：

> **让 A 的实现重新满足 A 原本已经承诺的输出契约。**

禁止借此：

```text
给 A 增加新字段
给 A 增加新职责
让 A 替 B 做转换
降低 A 原本质量要求
修改 A 的契约语义
```

这不是下游要求上游迁就自己，而是发现上游并未真正履行已经通过的能力事实。

---

# 11. 正式施工资格

功能 B 只有在以下条件同时满足时才能进入完整施工：

```text
B = DESIGN_CLOSED
B.最小功能通路 = PASS
B 的所有必要真实依赖 = PASSED
```

然后：

```text
B = READY
```

调度器从所有 `READY` 功能中选择可并行节点。

如果两个 READY 功能：

```text
没有真实能力依赖
没有资源冲突
没有写入冲突
```

则允许并行施工。

优先级可以考虑：

```text
解锁杠杆
关键路径
风险消除价值
当前资源匹配
```

但这些只能决定：

> **先做哪个 READY 节点。**

不得人为制造新的依赖边。

---

# 12. 执行层权限

执行 Agent 可以：

```text
实现本功能
选择内部算法
选择符合契约的成熟库
组织内部文件
写本功能测试
修复本功能实现
记录证据
报告阻塞
```

执行 Agent 不可以：

```text
修改功能契约
降低性能 / 质量门槛
修改真实依赖
扩大祖先职责
改变功能语义
通过修改上游降低本节点施工难度
自行把设计错误修成新的架构
```

施工困难本身不是修改设计的理由。

如果实现失败但契约没有矛盾：

> **继续修本节点。**

如果发现契约本身无法成立：

> **DESIGN_BLOCKED，返回设计层。**

---

# 13. 功能包络与版本

已经作为能力事实被消费的功能包络，不允许静默改变契约含义。

如果只修实现，使其重新满足原契约：

```text
仍然是同一能力版本
```

如果改变：

```text
输入语义
输出语义
质量保证
错误语义
```

必须形成显式新版本。

下游依赖应绑定到能力契约 / 版本，而不是某个具体库或代码路径。

上游内部实现替换但契约保持不变时，下游不需要重新设计，只需要必要的兼容性 / 回归验证。

---

# 14. `main`、功能分支与证据

`main` 保存：

> **已经接受的设计事实、完整历史、旧产品 LKG，以及通过正式验收的能力事实。**

新功能默认：

```text
main baseline
↓
独立 branch / worktree
↓
实现
↓
本包络完整验收
↓
证据绑定准确 commit
↓
具备进入 main 的资格
```

推荐分支命名：

```text
feature/<功能编号>-<简短名称>
```

每个 `PASSED` 至少绑定：

```text
功能标识 / 版本
准确 Git commit SHA
验证命令
Fixture / 固定输入
实际输出
环境
全部断言结果
```

AI 自报“已经完成”不构成能力成立证据。

---

# 15. 新原生实现与旧代码

新的原生 DCF 实现默认从：

```text
native/
```

生长。

旧：

```text
chrome-extension/
dcf-chatgpt-microcore.user.js
engine/
packages/desktop-electron/
packages/target-adapter-chrome/
旧控制平面 / Surface / Companion / seed
```

继续保存为：

```text
历史实现
行为证据
旧产品回退
经验来源
可选零件库
```

但不作为新实现结构模板。

复用方向必须是：

```text
新功能包络
↓
旧代码是否满足既定契约
↓
满足 → 复用
不满足 → 不继承
```

禁止：

```text
旧代码已经存在
↓
改变新功能包络来迁就旧代码
```

---

# 16. 当前功能包络元格式状态

当前施工控制原则已经冻结。

但“正式功能包络的机器文件格式”仍在通过第一个确定性样板收紧。

当前样板：

> **稳定认知对象 + 不可变修订**

样板必须证明：

```text
一个没有额外 DCF 上下文的施工 Agent
只读包络 + 声明依赖
即可开始实现

另一个独立验收 Agent
只读包络 + 编译产物
即可确定 PASS / FAIL
```

在这个样板未证明元格式足够严密以前：

> **禁止批量创建大量模糊功能包络。**

---

# 17. 当前施工一句话

> **设计层先冻结功能包络；通路验证用最小合法输入提前证明功能底层逻辑能活；正式实现按真实能力 DAG 解锁；执行层只实现和证明，不重新设计。**
