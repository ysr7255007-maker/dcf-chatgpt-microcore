# DCF 功能包络与施工控制规范

日期：2026-08-06  
最后同步：2026-08-07  
状态：**当前施工控制专项规范**  
适用范围：Capability Registry（能力登记表）、Capability Envelope（能力包络）、Standalone World（独立运行世界）/ Composite World（组合运行世界）验收、Public Facility（公共设施）依赖、Shared Semantic Component（共享语义组件）、Provider Resolution（提供者解析）与施工调度。

> 2026-08-07 已根据 Capability × Bun+Becsy World 组合实验、E0–E5 公共设施消歧实验与 Capability Discovery 收口结果同步。
>
> 本规范不再把 Capability 理解成“内部流水中的输入→输出节点”，不再按独占代码量判断 Capability，也不再把人工维护的 Capability DAG 视为第一事实。

# 1. Capability Discovery 当前已关闭

开放式 Capability Discovery（能力发现）不再是当前施工前置任务。

当前结果：

```text
Capability Registry v1：15 项
现实闭环行动：DISCOVERY_DEFERRED
```

15 项产品身份已经承认；后续施工不再反复讨论“它是不是 Capability”，除非出现新的行为证据足以推翻产品主权判断。

未来新增 Capability 才重新进入 Discovery 门禁。

---

# 2. Capability 判断门禁：产品主权，不是实现厚度

未来新增候选必须优先归类为：

```text
Capability（能力）
Public Facility（公共设施）
Provider / Probe（提供者 / 探针）
Recipe / Profile（配方 / 配置）
Query Strategy（查询策略）
Shared Semantic Component（共享语义组件）
Surface（界面载体）
普通内部实现细节
```

Capability 当前第一判断是产品主权四问：

```text
1. 稳定用户目的是什么？
2. 管理什么对象 / 状态 / 交互关系？
3. 用户执行什么独特行为？
4. 什么叫产品成功？
```

“去 DCF 测试”继续作为辅助门禁：

> **抹掉 DCF 品牌以后，这个用户目的是否仍然是一项可以独立命名、使用和验收的软件能力？**

禁止把它误解成：

> “去掉所有公共设施以后，是否还能自己重造全部底层机制？”

因此：

> **能力独立性 ≠ 实现独立性。**

---

# 3. 原生 / 涌现 Capability 同级

Capability 可以是：

```text
原生能力
→ 直接对应一个完整问题闭环

涌现能力
→ 公共设施、共享语义、配方、查询与交互组合后形成新的稳定产品目的
```

两者施工门槛完全相同。

“公共设施 + 配方 + 界面构成”不能作为降级理由。

同时，单独一个配方或一个 UI 外壳也不能仅靠包装自动升级成 Capability；仍必须通过产品主权与独立验收门禁。

---

# 4. 四刀净化：施工前先剥离不属于 Capability 的责任

关闭 Envelope 前，必须用四刀检查职责所有权：

```text
ECS（实体组件系统）
→ 关系接缝

Becsy World（运行世界）
→ 运行 / 生命周期 / 大量编排接缝

Bun
→ 宿主工程接缝

Public Facility（公共设施）
→ 重复专业工程机制
```

四刀的目的：

> **让 Capability 只拥有自己的产品语义。**

不是：

> “砍完以后剩余独有代码不足，所以取消 Capability。”

若一个 Capability 最终只剩：

```text
独特用户目的
+ 产品状态
+ 语义声明
+ 少量规则 / 配方
+ 专门交互
```

仍然完全合法。

---

# 5. Capability Registry 是产品身份事实，DAG 是派生视图

当前 Registry 第一事实至少包括：

```text
Capability identity
产品定义
产品主权
形成方式说明
独立成功标准
当前 Discovery / Envelope 状态
```

Envelope 再补充：

```text
业务不变量
requires / provides 共享语义
Public Facility requirements
provider / fallback declarations
用户可观察行为
错误 / 失败语义
acceptance
```

由这些事实可以派生：

```text
依赖图
施工可用性图
运行 provider graph
Becsy precedence view
```

如果图与 Capability contracts 冲突：

> **修图，不改事实去迎合图。**

---

# 6. Registry 状态与 Envelope 状态必须分离

进入 Registry 只代表：

> **产品身份已经承认。**

不代表：

```text
设计闭合
组件字段冻结
Provider 完成
Standalone World 通过
Composite World 通过
完整行为验收通过
```

当前建议状态：

```text
REGISTERED
ENVELOPE_NOT_CLOSED
ENVELOPE_CLOSED
PATH_PASS
STANDALONE_PASS
READY_FOR_COMPOSITE
COMPOSITE_PASS
PASSED
DESIGN_BLOCKED
```

Discovery 暂缓：

```text
DISCOVERY_DEFERRED
```

因此：

> **能力被发现，与现在有资格施工，是两回事。**

---

# 7. Capability Envelope：正式施工单位

一个正式 Capability 在交给执行层前必须形成 Capability Envelope。

Envelope 至少冻结：

```text
capability id / version
产品定义与产品主权
用户可观察行为
业务不变量
Shared Semantic Component requires / provides
Public Facility requirements
Standalone provider / fixture 规则
错误与失败语义
允许 / 禁止状态变化
质量 / 性能要求
Minimum Functional Path（最小功能通路）
Standalone World 验收
Composite World 兼容验收
验收证据格式
```

如果这些内容仍需执行 Agent 自己猜：

```text
DESIGN_NOT_CLOSED
```

不得派发正式施工。

---

# 8. Shared Semantic Component 契约优先于输入 / 输出 DTO

旧式：

```text
A.output → B.input
```

当前优先：

```text
Capability A
writes Shared Semantic State X

Capability B
reads Shared Semantic State X
```

正式原则：

> **上游不指定消费者；下游不指定生产者。双方围绕共同理解的世界状态与产物语义发生关系。**

Shared Semantic Component 契约必须明确：

```text
世界状态代表什么
数据形状
谁可以写
谁可以读
何时视为成立
权威来源
是否允许多个 Provider
版本 / 兼容性
```

禁止仅因为字段能赋值就判为兼容。

---

# 9. ECS 负责关系接缝，不负责专业机制

ECS 优先吸收：

```text
路由
订阅 / 回调
一对多 / 多对一分发
状态交接
UI 贡献发现
权限 / 审核结果交接
诊断状态共享
恢复需求发现
```

ECS 禁止被扩张成：

```text
大正文数据库
长期权威历史
AI 引擎
检索引擎
Agent 执行器
网络可靠性层
通用工作流引擎
```

施工判断：

> **ECS 吃“谁等谁、谁通知谁、结果交给谁”；专业设施负责困难的事情本身怎么做。**

---

# 10. World 负责统一运行现实

Capability 正式运行时进入 Composite World。

World 优先负责：

```text
系统生命周期
系统启停
运行身份
组件读写约束
大量执行 precedence（先后约束）
坏组合启动前拒绝
唯一 active provider
ExternalOperation 生命周期
```

Standalone World 只用于证明 Capability 独立成立；正式运行不要求大量孤立 World。

World 禁止取代：

```text
长期权威数据库
历史认知
大文件持久层
```

> **World 管当前运行现实；持久层管长期权威历史。**

---

# 11. Bun-first Host（Bun 优先宿主）施工原则

属于 JavaScript / TypeScript 宿主层的通用工程机制，如果 Bun 已稳定原生提供，Envelope 默认优先直接依赖其能力，不先增加新的包装层。

优先审查：

```text
Bun.spawn
Bun.serve
WebSocket
IPC / PTY
bun:sqlite
bun test
bun build
单文件可执行程序
常规文件 / 定时机制
```

只有出现真实行为 / 兼容 / 性能 / 生命周期证据证明 Bun 不够，才允许新增成熟替代轮子或薄适配层。

Bun 不获得任何上层业务语义。

---

# 12. Standalone World：Capability 的独立证明

每个 Capability 必须拥有 Standalone World 验收。

Standalone World 可以使用：

```text
最小合成 fixture
真实样本切片
standalone fallback provider
mocked Public Facility contract
```

但不能借用另一个业务 Capability 的私有实现。

若依赖某种公开业务语义状态，可以通过 standalone fixture / provider 提供同一正式契约。

必须证明：

```text
Capability 在合法世界状态下能够启动
核心产品行为能够独立发生
输出 / 世界推进有独立用户意义
错误路径可观察
重启 / 重跑不依赖上一轮偶然残留
```

---

# 13. 最小功能通路验证仍保留

每个 Envelope 仍包含 Minimum Functional Path Validation（最小功能通路验证）。

它证明：

> **在最小合法 Shared Semantic / Facility fixture 下，本 Capability 的最短核心行为能够成立。**

它不是：

```text
完整功能 PASSED
完整 Composite World 验收
第三方轮子正确性证明
上游 Capability 端到端测试
```

---

# 14. Standalone PASS 不等于 Composite PASS

Capability 成为正式 `PASSED` 至少需要：

```text
ENVELOPE_CLOSED
+
Minimum Functional Path PASS
+
Standalone World PASS
+
必要 Public Facility contracts 已成立
+
完整功能验收 PASS
+
质量 / 性能门槛 PASS
```

准备进入正式组合时追加：

```text
Composite World provider resolution PASS
+
Shared Semantic compatibility PASS
+
无重复 active authority
+
原 Capability 回归验收 PASS
```

因此：

```text
Standalone PASS
≠
Composite PASS
```

---

# 15. Composite World：组合不默认融合源码

若 Capability A 与 B 在 standalone 形态各自拥有同一 overlap provider：

```text
A Standalone
Provider A → Shared X

B Standalone
Provider B → Shared X → B behavior
```

进入 Composite World：

```text
Provider Resolution
↓
只选择一个 active provider for X
```

源码中的 standalone provider 可以保留，但不得同时运行。

> **重复源码允许；重复运行权威禁止。**

源码物理融合不是默认施工步骤。

---

# 16. Composer 只能机械组合

World Composer 可以：

```text
读取 manifests
读取 Shared Semantic contracts
解析 requires / provides
选择唯一 Provider
拒绝 Provider 冲突
拒绝语义不兼容
选择 Systems / Components defs
```

Composer 禁止：

```text
写业务 mapper
理解正文
补业务字段
修 prompt
判断项目叙事含义
把 Provider 怪癖传播到上层
成为第二套 workflow runtime
```

Composer 核心算法复杂度应与 Capability 数量增长基本解耦。

---

# 17. 外部异步能力一律经过 ExternalOperation

Capability / Facility 需要等待：

```text
AI
ACP Agent
独立 Probe
网络服务
长数据库任务
其他外部 worker
```

时，不得各自建立平行生命周期状态机。

正式接入统一使用 ExternalOperation 世界语义。

至少统一：

```text
stable opId
created / running / requires_action / completed / error / cancelled / orphaned
lease / health
cancel intent
result reference
error reference
```

执行器可以 Provider-specific；核心生命周期不可 Provider-specific。

---

# 18. Provider / Probe 施工边界

新增 Provider 理想施工变化：

```text
新增 manifest / compatibility data
+
新增边界 adapter
+
新增 provider-specific tests
```

禁止要求：

```text
修改多个业务 Capability
修改 Composer 核心算法
新增第二套状态权威
把第三方 schema 扩散进 Shared Semantic Component
```

若每新增 Provider 都必须修改多处核心业务代码：

> **判为公共设施边界泄漏。**

---

# 19. Public Facility 依赖显式，但不得变成全局阶段门

Public Facility 可以是高扇出依赖，但不存在：

> “所有基础设施全部完成，所有 Capability 才能施工。”

某 Capability 只要真实所需 Facility 达到该 Envelope 的要求，就可以施工。

例如 Wiki 可能只需要：

```text
Cognition Data Facility
AI Turn Facility（若行为需要）
交互宿主 / Surface
```

Agent Facility 未完成不得因此阻塞 Wiki。

---

# 20. 第三方轮子与 DCF 契约的关系

Envelope 依赖：

```text
AI Turn contract
```

而不是：

```text
ai@某个永久版本
```

依赖：

```text
Derived Retrieval contract
```

而不是：

```text
LanceDB forever
```

第三方轮子可以 exact pin（精确锁定）当前实验实现，但上层契约不得绑定到具体库。

> **继承机制，不交出世界定义权。**

---

# 21. 执行 Agent 权限

执行 Agent 可以：

```text
实现 Envelope 内部算法
选择已允许的成熟轮子
组织内部文件
编写本 Capability / Provider tests
修复实现
提供行为证据
报告 DESIGN_BLOCKED
```

不可以：

```text
改变 Capability 产品主权
修改 Shared Semantic 语义
扩大 Public Facility 业务职责
为了施工方便新增 Adapter 层
让上游 Capability 替自己完成业务意义
降低 acceptance
通过修改 Composer 修复业务不兼容
```

若设计在合法输入下无法成立：

```text
DESIGN_BLOCKED
+
固定 fixture
+
可重复证据
```

返回设计层。

当前允许进入 Envelope 阶段的 15 项：

```text

多源证据编译
AI 协作审阅编辑器
个人叙事
项目叙事
Wiki
知识卡
语言弹药
AI 工作台
认知数据工作台
AI 任务执行台
约束决策助手
全景沉浸交互
嵌入式交互

```

# 23. 当前下一步

Capability Discovery 已收口，不再重新做开放式候选搜索。

当前正确顺序：

```text
Capability Registry v1
↓
选择一个已登记 Capability
↓
关闭 Capability Envelope
↓
Minimum Functional Path
↓
Standalone World
↓
Composite World
↓
正式实现与验收
```

不要先为了“全局漂亮”重新设计 15 个 Capability 的总 DAG。

最高施工纪律：

> **让已经成立的产品主权、共享世界状态和公共设施契约导出组合关系；不要为了让图漂亮反过来设计 Capability。**
