# DCF 功能包络与施工控制规范

日期：2026-08-06  
最后同步：2026-08-07  
状态：**当前施工控制专项规范**  
适用范围：Capability Discovery、Capability Registry、Capability Envelope、Standalone World / Composite World 验收、Public Facility 依赖、Shared Semantic Component、Provider Resolution 与施工调度。

> 2026-08-07 已根据 Capability × Bun+Becsy World 组合实验与 E0–E5 公共设施消歧实验同步。
>
> 本规范不再把 Capability 理解成“内部流水中的输入→输出节点”，也不再把人工维护的 Capability DAG 视为第一事实。

---

# 0. 权威关系

先读取：

```text
docs/spec/README.md
```

当前最高层增量架构裁决：

```text
docs/spec/2026-08-07-DCF-Capability与公共设施当前规范.md
```

本文只负责：

> **怎样把一个已经发现并设计闭合的 Capability 变成可以独立施工、独立验收、再安全进入 Composite World 的正式施工单位。**

---

# 1. 施工前第一步不是画 DAG，而是 Capability Discovery

正式施工前，先判断一个候选到底是什么。

候选必须优先归类为：

```text
Domain / Interaction Capability
Public Facility
Provider / Probe
Recipe / Profile
Shared Semantic Component
普通内部实现细节
```

禁止把它们全部叫 Capability。

Capability 的第一判断是“去 DCF 测试”：

> **抹掉 DCF 语境以后，它是否仍然是一项普通、完整、有独立用户目的的软件功能？**

若只是：

```text
数据库写入步骤
AI 调用步骤
某个内部状态转换
A 到 B 的 mapper
```

默认不是独立 Capability。

---

# 2. Capability 独立不等于零依赖

Capability 必须在不依赖其他业务 Capability 私有实现的前提下完成自己的业务闭环。

允许依赖已经独立验收的 Public Facility，例如：

```text
AI Turn Facility
Agent Execution Facility
Cognition Data Facility
Evidence Intake Facility
```

因此：

> **独立 = 业务意义独立；不是所有工程机制都复制一份。**

禁止为了满足“独立”而让每个 Capability 重造：

```text
AI Harness
数据库
Agent Runtime
消息队列
Provider 生命周期
```

---

# 3. Capability Registry 是候选事实，DAG 是派生视图

设计层维护的第一事实是：

```text
Capability identity
独立产品定义
业务不变量
requires / provides 语义
Shared Semantic Component contract
Public Facility requirements
provider / fallback declarations
acceptance
```

由这些事实可以派生：

```text
依赖图
施工可用性图
运行 provider graph
Becsy precedence view
```

但人工维护的“Capability DAG”不再拥有第一事实地位。

如果图与 capability contracts 冲突：

> **修图，不改事实去迎合图。**

---

# 4. Capability Envelope：正式施工单位

一个正式 Capability 在交给执行层前必须形成 Capability Envelope。

Envelope 至少冻结：

```text
capability id / version
独立产品定义
用户可观察行为
业务不变量
Shared Semantic Component requires / provides
Public Facility requirements
Standalone provider / fixture 规则
错误与失败语义
允许 / 禁止状态变化
质量 / 性能要求
Standalone World 验收
Composite World 兼容验收
验收证据格式
```

如果这些内容仍需执行 Agent 自己猜：

```text
DESIGN_NOT_CLOSED
```

不得派发正式施工。

---

# 5. Shared Semantic Component 契约优先于“输入/输出 DTO”

旧式功能包络强调：

```text
A.output → B.input
```

当前优先模型是：

```text
Capability A
writes Shared Semantic State X

Capability B
reads Shared Semantic State X
```

Shared Semantic Component 契约必须明确：

```text
世界状态到底代表什么
数据形状
谁可以写
谁可以读
何时视为成立
权威来源
是否允许多个 provider
版本 / 兼容性
```

禁止仅因为字段能赋值就判为兼容。

---

# 6. Standalone World：Capability 的独立证明

每个 Capability 必须拥有 Standalone World 验收。

Standalone World 可以使用：

```text
最小合成 fixture
真实样本切片
standalone fallback provider
mocked Public Facility contract
```

但不能借用另一个业务 Capability 的私有实现。

Standalone World 必须证明：

```text
Capability 在合法世界状态下能够启动
核心行为能够独立发生
输出 / 世界推进有独立用户意义
错误路径可观察
重启 / 重跑不会依赖上一轮偶然残留
```

Standalone World 是证明形态，不是生产要求运行大量孤立 World。

---

# 7. 最小功能通路验证仍保留，但职责改变

每个 Envelope 仍应包含 Minimum Functional Path Validation。

它证明：

> **在最小合法 Shared Semantic / Facility fixture 下，本 Capability 的最短核心行为能够成立。**

它不是：

```text
完整功能 PASSED
完整 Composite World 验收
第三方轮子正确性证明
上游 Capability 端到端测试
```

通路验证可以早于真实 provider 完成，以尽快暴露契约错误。

---

# 8. Standalone PASS 不等于正式组合 PASS

Capability 成为正式 `PASSED` 至少需要：

```text
DESIGN_CLOSED
+
Minimum Functional Path PASS
+
Standalone World PASS
+
必要 Public Facility contracts 已成立
+
完整功能验收 PASS
+
质量 / 性能门槛 PASS
```

当它准备进入某个正式组合，还必须追加：

```text
Composite World provider resolution PASS
+
Shared Semantic compatibility PASS
+
无重复 active authority
+
原 Capability 回归验收 PASS
```

因此：

```text
Standalone PASS
≠
Composite PASS
```

---

# 9. Composite World：组合发生在运行世界，不默认融合源码

若 Capability A 与 B 在 standalone 形态各自拥有同一 overlap 的 provider：

```text
A Standalone
Provider A → Shared X

B Standalone
Provider B → Shared X → B behavior
```

进入 Composite World 时：

```text
Provider Resolution
↓
只选择一个 active provider for X
```

B 的 standalone provider 可以继续保留在源码中，但不得同时运行。

> **重复源码允许；重复运行权威禁止。**

源码物理融合不是默认施工步骤。

---

# 10. Composer 只能机械组合

World Composer 可以：

```text
读取 manifests
读取 Shared Semantic contracts
解析 requires / provides
选择唯一 provider
拒绝 provider 冲突
拒绝语义不兼容
选择 Systems / Components defs
```

Composer 禁止：

```text
写业务 mapper
理解正文
补字段
修 prompt
判断项目叙事含义
把某个 provider 的怪癖传播到上层
成为第二套 workflow runtime
```

第三方具体品牌名原则上不应出现在 Composer 业务判断中。

Composer 核心算法复杂度应与 Capability 数量增长基本解耦。

---

# 11. 外部异步能力一律经过 ExternalOperation

Capability / Facility 需要等待：

```text
AI
ACP Agent
独立 Probe
网络服务
长数据库任务
其他外部 worker
```

时，不得各自建立平行生命周期状态机。

正式接入一律使用 ExternalOperation 世界语义。

至少统一：

```text
stable opId
created / running / requires_action / completed / error / cancelled / orphaned
lease / health
cancel intent
result reference
error reference
```

执行器可以 provider-specific；核心生命周期不可 provider-specific。

---

# 12. Provider / Probe 的施工边界

Provider 是边界适配件，不是新的业务世界。

新增 Provider 理想施工变化：

```text
新增 manifest / compatibility data
+
新增边界 adapter
+
新增 provider-specific tests
```

禁止要求：

```text
修改多个业务 Capability
修改 Composer 核心算法
新增第二套状态权威
把第三方 schema 扩散进 Shared Semantic Component
```

若每新增 Provider 都必须修改多处核心业务代码：

> **判为公共设施边界泄漏。**

---

# 13. Public Facility 依赖必须显式，但不得变成全局阶段门

Public Facility 可以是高扇出依赖。

但不存在：

> “所有基础设施全部做完，业务才允许开始。”

某 Capability 只要其真实所需 Facility 已达到该 Envelope 要求，就可以施工。

例如一个薄 Wiki Capability 可能只需要：

```text
Cognition Data Facility
AI Turn Facility（若其行为需要）
Surface host
```

Agent Facility 未完成不得因此阻塞 Wiki。

---

# 14. 第三方轮子与 DCF 契约的关系

Envelope 依赖：

```text
AI Turn contract
```

而不是：

```text
ai@7.0.55
```

依赖：

```text
Derived Retrieval contract
```

而不是：

```text
LanceDB forever
```

第三方轮子可以 exact pin，用实验确定当前默认实现，但上层契约不得绑定到具体库。

正式换轮子时，上层 Capability 原则上不应变化。

---

# 15. 执行 Agent 权限

执行 Agent 可以：

```text
实现 Envelope 内部算法
选择已允许的成熟轮子
组织内部文件
编写本 Capability / Provider tests
修复实现
提供行为证据
报告 DESIGN_BLOCKED
```

执行 Agent 不可以：

```text
改变 Capability 独立产品定义
修改 Shared Semantic 语义
扩大 Public Facility 业务职责
为了施工方便新增 Adapter 层
让上游 Capability 替自己完成业务意义
降低 acceptance
通过修改 Composer 修复业务不兼容
```

若发现设计在合法输入下无法成立：

```text
DESIGN_BLOCKED
+
固定 fixture
+
可重复证据
```

返回设计层。

---

# 16. 契约违例与上游修改

若真实 provider / facility / capability 输出违反其已经冻结的公开契约，可以提交契约违例报告。

允许要求：

> **让实现恢复原本承诺的契约。**

禁止借机：

```text
扩大它的职责
增加只为当前下游服务的字段
改变公共语义
让旧契约静默变成新契约
```

契约语义真的改变时必须形成显式新版本。

---

# 17. 当前施工状态枚举

建议当前设计/施工状态至少区分：

```text
DISCOVERY
CANDIDATE
DESIGN_NOT_CLOSED
DESIGN_CLOSED
PATH_PASS
STANDALONE_PASS
READY_FOR_COMPOSITE
COMPOSITE_PASS
PASSED
DESIGN_BLOCKED
```

这些是施工状态，不是产品成熟度评分。

---

# 18. 当前下一步

公共设施架构已经通过 E0–E5 消歧，不再需要先构造一张新的“大 DAG”。

当前正确顺序：

```text
重新做 Capability Discovery
↓
形成 Capability Registry 候选
↓
为第一个候选关闭 Envelope
↓
Standalone World
↓
Composite World
↓
正式实现与验收
```

当前 Capability 候选池以：

```text
docs/spec/2026-08-07-DCF-Capability与公共设施当前规范.md
```

为准，但尚未冻结编号与边界。

最高施工纪律：

> **不要为了让图漂亮而设计 Capability；让已经成立的独立功能和共享世界状态自己导出图。**
