# DCF 当前架构与实施规范

日期：2026-08-09  
状态：**当前架构实施权威**

本文只描述 DCF **现在是什么、各层负责什么、实施时必须满足什么**。

本文不记录架构演变过程；为什么形成当前结构，见对应 ADR。

---

# 1. 总体结构

DCF 当前结构分为六个职责面：

```text
Capability（产品能力）
        │
        ▼
Application Semantics（正式业务实现）
        │
        ▼
Executable Semantic Seam（可执行语义接缝）
        │
        ▼
Ordinary Backend Runtime
共享 World / ECS / Scheduler / Provider Resolution
        │
        ▼
Durable State / PostgreSQL

AI 探索、长任务与智能体编排
        │
        ▼
AI Workflow Plane（与普通后台分离）

Capability / State / Action / Evidence
        │
        ▼
Surface Contract
        │
        ▼
Replaceable Surface Runtime
```

核心分工：

> **Capability 定义 DCF 能做什么。**

> **Application 实现 Capability 自己真正负责的业务。**

> **Executable Semantic Seam 定义 Capability 与世界之间可执行、可验证、可组合的边界。**

> **Ordinary Backend Runtime 负责让大量异构、长期活动的普通程序共享运行世界，并吸收等待、调度、I/O、Timer、并发和可共享计算成本。**

> **AI Workflow Plane 专门承载 AI 探索、长期智能体任务与不确定执行流程，不反向统治普通后台。**

> **UI 负责交互投影，不拥有业务正确性。**

# 3. Ordinary Backend：当前目标体质

普通后台不是一个 Workflow Engine，也不是“每个 Capability 一个常驻服务”。

DCF 普通后台会长期同时存在大量异构工作：

```text
文件观察
浏览器状态
Git
输入事件
网络
Timer
解析
索引
缓存
FSM
规则
关联
转换
进程管理
本地 API
设备状态
数据库
搜索
压缩
同步
```

这些能力可以持续活动，但不应因此各自重复支付一整套：

```text
等待成本
线程 / 任务调度成本
Timer
I/O 管理
并发基础设施
重复扫描
重复派生计算
重复状态副本
```

当前 Ordinary Backend 的目标不是“让不用的功能休眠”，而是：

> **大量异构、长期活动的普通程序保持独立业务语义，但其等待、调度、I/O、Timer、并发、基础设施以及可共享计算在物理层被统一复用和吸收。**

理想成本形状：

```text
Cost ≈ 实际世界变化 × 被影响计算
```

而不是：

```text
Cost ≈ Capability 数量 × 时间
```

# 4. ECS / Shared World：普通后台的当前结构要求

普通后台当前要求采用成熟 ECS / data-oriented shared world + scheduler 的结构体质。

最重要的不是“Entity / Component API 很快”，而是：

> **把程序组合问题尽量压缩成数据、状态、关系、影响和查询的组合问题。**

优先结构：

```text
Capability / Provider
      │
      ├─ 声明 facts
      ├─ 声明 state
      ├─ 声明 relations
      ├─ 声明 effects
      └─ 声明 conditions
              ↓
           Shared World
              ↓
     Generic Systems / Resolvers
```

默认避免：

```text
Feature A → call Feature B → call Feature C
```

优先：

```text
A ─┐
B ─┤
C ─┼→ World State → Systems / Resolvers
D ─┘
```

正式原则：

> **功能不调用功能；功能向 World 声明事实、状态和影响，System 根据声明匹配并统一求解。**

这不是要求所有代码都 ECS 化。

SQLite、Solver、AI、压缩引擎、搜索引擎、macOS 原生能力等仍可以是专用实现或薄 Provider；ECS 负责共同活动世界与组合语义。

# 5. 当前 ECS 实现选择仍开放

当前已经硬化的是 ECS / shared-world 运行体质，不是某个库名。

当前成熟候选主要为：

```text
Bevy ECS
Flecs
```

Becsy 保留为 2026-08-07 已验证历史证据，但不再要求成为正式实现。

当前已经确认：

> **成熟 ECS + 一个通用、非业务化的薄 Composition Compiler，理论上可以完整保留旧 Becsy 实验所证明的 Capability 独立、Provider 收敛、低接缝组合与能力涌现性质。**

因此后续 Bevy / Flecs 选型不再重复证明“原则上能不能做到”，只比较：

```text
运行时成熟度
动态组合能力
调度 / 并行
运行 schema / relation 表达力
工程复杂度
长期维护成本
与 DCF 业务模型的贴合度
```

Ordinary Backend 最终语言随 Runtime 选型一起决定，当前不冻结 Go、Rust、C/C++ 等具体语言。

# 6. Executable Semantic Seam：Capability 的正式边界工件

Capability 之间不得分别维护“看起来兼容”的输入和输出 Mock。

如果：

```text
A provides X
B requires X
```

则 A / B 共同引用同一个：

> **Executable Semantic Seam X —— 可执行语义接缝。**

它不是 A 的接口，也不是 B 的接口，而是双方共同承认的那一段世界语义。

Seam 至少包含：

```text
业务语义
数据形状
合法性条件
来源 / 证据要求
生命周期
Provider policy
读写语义
基数 / merge / reduce 规则
错误与拒绝条件
最小真实实践
Probe / 验证表面
```

正式原则：

> **Seam First。先冻结双方共同认识的边界，再让 Capability 各自完成自己的正式功能。**

---

# 7. Seam 不是 Public Facility

不得把“Capability 之间存在接缝”误解为“系统应该新增一个公共能力”。

```text
Capability
→ 用户可感知、可独立成立的产品能力

Public Facility
→ 多 Capability 共同依赖的低业务语义专业设施

Executable Semantic Seam
→ Capability 边界本身的共享语义、最小实践与验证工件
```

Seam 可以被多个 Capability 引用，但它不因此获得产品主权。

禁止为了复用而把正式 Capability 拆碎成大量公共小能力。

---

# 8. Standalone：独立完整通过 Seam 补齐环境

Capability 必须能够独立运行、调试和验收。

但独立完整不等于复制全部上下游业务。

例如：

```text
B requires X
```

当真实上游不存在时，Standalone Environment 由 `Semantic Seam X` 的最小真实实践补齐输入：

```text
[缺失上游]
    ↓
Seam X
    ↓
Capability B
```

当真实下游不存在时：

```text
Capability A
    ↓
Seam X
    ↓
Probe / 验证
```

因此：

> **Capability 独立完整 = 缺失环境可以在契约边界被标准化补齐，而不是每个 Capability 复制整个依赖链。**

---

# 9. Seam 的最小实践必须保真

Standalone 使用的 Seam 不得只是随机 Mock。

必须采用：

> **Minimal Realization —— 保持完整业务语义的最小真实实践。**

允许缩减：

```text
数据数量
运行规模
状态空间
并发量
外部环境
持续时间
```

不允许缩减：

```text
业务语义
关键真实规则
合法性条件
因果方向
证据约束
核心状态变化
```

例如正式能力可能处理十万条记录；最小实践可以只处理 1 条。

但不能把真实 `ActivityMaterial` 降成一个字符串，只为了让测试更容易通过。

正式原则：

> **最小削规模，不削语义。**

---

# 10. Seam 运行模式由拓扑自动推导

同一个 Seam 根据连接状态自然呈现三种主要角色：

```text
缺上游
→ Source
→ 产生满足真实契约的最小输入

两侧都连接
→ Pass-through
→ 透明传递，并按需要验证 / 观测 / 追踪

缺下游
→ Sink / Probe
→ 接收、验证、记录真实输出
```

不要求业务代码人工切换测试模式。

正式原则：

> **模式来自拓扑，而不是来自 Capability 内部的 if test_mode。**

---

# 11. Composite Runtime：允许验证重叠，禁止重复运行权威

Standalone 为独立证明而存在的 Provider、Fixture、Minimal Realization 可以保留在源码和验证工件中。

进入正式 Composite Runtime 时：

```text
真实 Provider 出现
↓
Composition Compiler 解析权威
↓
standalone-only 实现退出
↓
同一个 single-provider 语义只保留一份实际运行权威
```

必须满足：

```text
A 源码不改
B 源码不改
不新增 AB 专用 Adapter / Bridge / Mapper / Controller
重复验证实现可以存在
重复运行权威不允许存在
冲突必须在运行世界创建前拒绝
```

正式原则：

> **允许验证层重复，不允许正式运行层重复权威。**

---

# 12. Composition Compiler：通用编译器，不是业务 Glue

DCF 允许一个薄 Composition Compiler / World Composer。

输入：

```text
Capability manifests
Executable Semantic Seam contracts
Provider policies
目标 Capability / 目标能力集合
```

输出：

```text
唯一 Provider 解析
有效 Systems / Components / Relations
执行依赖 / Schedule constraints
错误组合拒绝
```

它不得：

```text
理解具体业务内容
转换业务字段
持有业务状态
按 Capability pair 写 case-by-case 规则
修复语义不兼容
成为 Workflow Engine
```

架构健康指标：

> **Capability 数量增长时，Compiler 核心算法应基本稳定；增长的主要是声明和契约数据，而不是组合 Glue。**

---

# 13. 执行接缝优先由共享状态关系吸收

Capability 之间默认不建立深层直接调用网。

优先表达：

```text
A provides / writes X
B requires / reads X
```

然后由 Runtime Scheduler 原生推导，或由 Composition Compiler 生成通用 schedule edge。

Becsy 曾经用 read/write entitlement 自动得到 `AUTO_PRECEDENCE_PASS`；正式 Runtime 不要求复制同一个 API，但必须保留同一业务性质：

> **能够从声明式状态依赖形成实际执行秩序，而不是让 Capability 彼此手写控制流。**

writer-writer、特殊事务顺序等仍可显式声明。

---

# 14. Capability DAG 是派生视图

首要事实是：

```text
Capability requires / provides
+
Semantic Seam contracts
+
World reads / writes / relations
```

依赖 DAG 应从这些事实推导，用于：

```text
可视化
诊断
Solver
施工解释
验收报告
```

禁止同时维护第二套与真实声明可能漂移的人工架构图作为运行权威。

---

# 15. Minimal Emergence Proof：能力涌现的最小真实证明

候选能力组合不需要一开始就启动全部真实程序。

如果完整候选链是：

```text
A ─ X1 ─ B ─ X2 ─ C ─ ... ─ X25 ─ Z
```

允许先移除完整 Capability，只组合 Executable Semantic Seams：

```text
X1 ─ X2 ─ X3 ─ ... ─ X25
```

首尾因为缺少真实邻居，自动启用最小真实 Source / Sink；中间接缝依靠各自真实契约与 Minimal Realization 组成一个极小但真实的业务世界。

验证不只问“token 能不能传过去”，而问：

> **从 X1 的真实最小输入出发，X25 的 Probe 能否得到满足最终业务语义的真实最小结果？**

若成立：

```text
MINIMAL_EMERGENCE_PASS
```

这说明：

> **候选组合在最小真实语义规模下已经形成一个新能力。**

它仍不替代完整生产环境验收。

---

# 16. 三层能力组合证明

以后必须区分：

## Level 1 — Constraint / Contract Composition

```text
requires / provides
semantic contract
provider policy
cardinality
lifecycle
reads / writes
```

证明：

> 理论组合闭合。

## Level 2 — Minimal Emergence Proof

运行 Seam-only / Minimal Realization World。

证明：

> 真实业务语义在最小规模下能够组合并产生结果。

## Level 3 — Full Runtime / Behavioral Proof

接回完整 Capability、真实 I/O、数据库、模型、并发和外部环境。

证明：

> 完整现实实现兑现了组合。

禁止低层证据冒充高层证据。

---

# 17. Solver / AI 的架构探索入口

Solver 不需要首先理解完整代码。

它优先面对：

```text
Capability Manifest
+
Semantic Seam Contract
+
Minimal Realization
+
Constraints
```

可搜索：

```text
可闭合能力组合
Provider 冲突
依赖缺口
环与不满足约束
目标输出的最短 / 最小组合
潜在新能力
```

推荐验证漏斗：

```text
大量候选
↓
Constraint Solve
↓
合法候选
↓
Minimal Emergence Proof
↓
真实成立候选
↓
Full Runtime Proof
```

正式原则：

> **影子世界负责便宜探索“什么能成立”；真实世界负责昂贵证明“完整实现真的成立”。**

---

# 18. Public Facility / Provider / Probe 继续成立

既有概念继续有效：

```text
Public Facility
→ 多个 Capability 共同使用的低业务语义专业设施

Provider / Probe
→ 把外部系统、模型、Agent、证据来源接入稳定契约
```

公共设施不得拥有上层 Capability 的产品意义。

Provider / Probe 不得反向定义 Capability。

Executable Semantic Seam 与它们不同：Seam 负责 Capability 边界的共享语义和最小可执行证明。

---

# 19. AI Workflow 与 Ordinary Backend 必须分离

AI 探索、模型调用、Agent 子任务、长时间等待、失败后继续、人工审阅后恢复等流程，和普通后台长期活动不是同一个岗位。

当前正式纪律：

```text
Ordinary Backend
→ Shared World / ECS / Scheduler
→ 处理确定性、长期活动的普通程序世界

AI Workflow Plane
→ 专门处理 AI 探索与跨时间智能体过程
```

不得为了统一技术栈，把普通文件观察、索引、状态传播、Timer、设备状态等全部 Workflow 化。

也不得让 AI Workflow Runtime 成为整个 DCF 的统一运行时。

Conductor 继续作为 AI Workflow 专项方向使用；其职责不得扩张成 Ordinary Backend Runtime。

---

# 20. PostgreSQL 当前地位

PostgreSQL 继续作为 DCF durable state 的重要持久化底座。

但当前尚未冻结：

```text
哪些 ECS Active World 状态必须落 PostgreSQL
哪些是可重建投影
哪些采用专用索引 / 压缩存储
World 与 durable state 的同步边界
```

不得因为采用 PostgreSQL，就强迫所有热状态、索引和专用数据结构退化成关系表。

---

# 21. 三种交互 Capability

当前三种交互 Capability 继续是：

```text
全景沉浸交互
嵌入式交互
环境微交互
```

它们定义的是三种交互空间与注意力带宽，不是三个固定 UI 控件。

常见 Surface 可以是：

```text
全景沉浸交互 → 完整 Workspace / 主页
嵌入式交互   → 侧边栏 / IDE 面板 / 浏览器面板
环境微交互   → 悬浮球 / 菜单栏 / 低注意力入口
```

这些只是实现形态，不是不可修改的架构组成。

# 22. UI 是可替换交互投影

DCF 继续采用：

> **Function Hard, UI Soft —— 功能硬化，界面软化。**

稳定的是：

```text
Capability identity
业务状态
Action / Event
Evidence
Executable Semantic Seam
Surface Contract
```

允许反复修改甚至整体推翻的是：

```text
Shell
Navigation
Sidebar
Panel
Layout
Toolbar
Card
Modal
Canvas
Theme
组件结构
视觉风格
具体交互方式
```

正式要求：

> **UI 层没有不可替换组件。**

# 23. Surface Runtime 当前边界

Godot 当前是高表现力实时 Surface Runtime 的强候选，但仍不拥有业务事实世界。

Web、Godot、SillyTavern 或其他 Surface Runtime 都必须服从同一个 Surface Contract。

Surface 可以负责：

```text
视觉
空间
动画
焦点
镜头
拖拽
局部临时交互状态
```

Core 继续负责：

```text
真实事实
长期状态
证据
当前与历史解释
Capability 行为
AI 结果来源
用户确认形成的业务状态
```

原则：

> **Surface 可以决定世界如何被看见，不能决定世界实际上是什么。**

---

# 24. Capability Surface 热插拔

交互界面不得通过硬编码业务列表认识 Capability。

Surface Host 应通过稳定 Surface Contract 发现可展示、可操作的 Capability。

至少表达：

```text
Capability identity
可读取状态
可执行 Action
适用 Surface
进入 / 挂载信息
```

新增或删除 Capability 时，目标仍然是：

```text
Capability 注册 / 注销
↓
Surface Host 重新发现
↓
对应入口与交互投影出现 / 消失
```

而不是修改 Shell 的业务源码。

---

# 25. 当前施工顺序

正式 Capability 施工默认使用：

```text
1. 明确 Capability 的独立用户行为
2. 明确 requires / provides
3. 识别 Semantic Seam
4. 先冻结最小共享语义契约
5. 实现 Seam 的 Minimal Realization 与 Probe
6. 用 Seam 补齐环境，使 Capability Standalone PASS
7. 实现 Capability 正式业务
8. Composite Runtime 自动解析唯一真实 Provider
9. 不修改已完成 Capability 源码
10. 候选组合先做 Constraint Solve
11. 再做 Minimal Emergence Proof
12. 最后做 Full Runtime / Behavioral Proof
```

如果组合要求新增：

```text
AtoBAdapter
ABCController
CapabilityPairMapper
```

默认视为架构警报。

# 27. 当前实施纪律
