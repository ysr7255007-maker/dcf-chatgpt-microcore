# DCF 当前架构与实施规范

日期：2026-08-08  
状态：**当前架构实施权威**

本文只描述 DCF **现在是什么、各层负责什么、实施时必须满足什么**。

本文不记录架构演变过程；为什么形成当前结构，见对应 ADR。

---

# 1. 总体结构

DCF 当前结构分为五层：

```text
Capability（产品能力）
        │
        ▼
Application / Public Facility（业务实现与公共设施）
        │
        ├─ 普通即时逻辑 → Go
        │
        └─ 跨时间长期过程 → DBOS Workflow
                                  │
                                  ▼
                              PostgreSQL
                           Workflow 持久状态

Capability / State / Action
        │
        ▼
Surface Contract（交互语义边界）
        │
        ▼
Replaceable UI（可替换界面实现）
```

核心分工：

> **Capability 定义 DCF 能做什么。**

> **Go 承载普通程序逻辑。**

> **Workflow 承载需要跨时间继续存在的过程。**

> **PostgreSQL 持久保存 Workflow 所需运行状态。**

> **UI 负责交互投影，不拥有业务正确性。**

---

# 2. Capability Registry 保持不变

当前 Capability Registry v1 仍为 15 项：

```text
1. 证据源采集管理
2. 多源证据编译
3. AI 协作审阅编辑器
4. 个人叙事
5. 项目叙事
6. Wiki
7. 知识卡
8. 语言弹药
9. AI 工作台
10. 认知数据工作台
11. AI 任务执行台
12. 约束决策助手
13. 全景沉浸交互
14. 嵌入式交互
15. 环境微交互
```

`现实闭环行动` 继续保持：

```text
DISCOVERY_DEFERRED
```

本次架构更新不重新进行 Capability Discovery，不改变既有产品主权判断。

---

# 3. Go：当前主实现语言

DCF 当前应用主体采用 Go。

Go 负责：

```text
普通业务逻辑
公共设施实现
Provider / Probe 接入
HTTP / IPC / 文件 / 网络等常规 I/O
并发执行
进程与服务组织
与 DBOS / PostgreSQL 的应用集成
```

普通函数默认就是普通 Go 函数。

禁止因为系统存在 Workflow，就把所有函数、所有 Capability 强制 Workflow 化。

---

# 4. Workflow：长期过程的执行语义

Workflow 用于那些**不能只依赖当前进程活着**的过程。

典型特征：

```text
需要等待模型 / 工具 / 用户 / 定时器
可能持续较长时间
中途进程可能退出或崩溃
需要恢复后继续
存在动态分支、子任务或并行探索
需要明确知道过程执行到哪里
```

这类过程使用 DBOS Workflow。

普通即时计算、格式化、局部转换等不进入 Workflow。

正式原则：

> **Workflow 是执行语义，不是新的 Capability。**

> **Capability 描述用户目的；Workflow 描述长期过程如何继续活着。**

---

# 5. DBOS + PostgreSQL 的职责边界

DBOS 当前负责长期 Workflow 的：

```text
Workflow identity
Step / operation progress
等待与恢复
失败后的继续执行
长期过程的运行位置
```

PostgreSQL 作为 DBOS 的持久化底座，保存 DBOS 正常运行所需要的 Workflow 状态。

当前规范只规定这一职责。

不得因为 DBOS 使用 PostgreSQL，就推导出其他 DCF 数据必须迁移、统一或改变存储实现。

---

# 6. Capability 与 Workflow 的关系

Capability 可以完全不需要 Workflow，也可以包含一个或多个 Workflow。

例如：

```text
即时读取 / 展示 / 简单编辑
→ 普通 Go 路径

AI 长时间探索
→ Workflow

等待用户审阅后继续
→ Workflow

跨多个外部工具完成一段长期任务
→ Workflow
```

因此当前结构不是：

```text
Capability = Workflow
```

而是：

```text
Capability
├─ 普通 Go 行为
└─ 必要时使用 Workflow
```

---

# 7. Public Facility / Provider / Probe 继续成立

既有以下概念继续有效：

```text
Public Facility
→ 多个 Capability 共同使用的低业务语义专业设施

Provider / Probe
→ 把具体外部系统、模型、Agent、证据来源接入稳定契约
```

公共设施不得拥有上层 Capability 的产品意义。

Provider / Probe 不得反向定义 Capability。

本规范不重新划分已有公共设施。

---

# 8. 三种交互 Capability

当前三种交互 Capability 继续是：

```text
全景沉浸交互
嵌入式交互
环境微交互
```

它们定义的是三种交互空间与注意力带宽，不是三个固定 UI 控件。

当前常见 Surface 可以是：

```text
全景沉浸交互 → 完整 Workspace / 主页
嵌入式交互   → 侧边栏 / IDE 面板 / 浏览器面板
环境微交互   → 悬浮球 / 菜单栏 / 低注意力入口
```

这些只是实现形态，不是不可修改的架构组成。

---

# 9. UI 是可替换交互投影

DCF 当前采用：

> **Function Hard, UI Soft —— 功能硬化，界面软化。**

稳定的是：

```text
Capability identity
业务状态
Action / Event
Workflow
持久数据
Surface Contract
```

允许反复修改甚至整体推翻的是：

```text
Shell
Navigation
Sidebar
Panel
Layout
Toolbar
Card
Modal
Canvas
Theme
组件结构
视觉风格
具体交互方式
```

正式要求：

> **UI 层没有不可替换组件。**

不得以“系统 UI”“核心导航”“固定 Panel”等理由，把某段前端实现变成以后不能修改的底层结构。

---

# 10. Capability Surface 热插拔

交互界面不得通过硬编码业务列表认识 Capability。

Surface Host 应通过稳定的 Surface Contract 发现可展示、可操作的 Capability。

至少需要表达：

```text
Capability identity
可读取状态
可执行 Action
适用 Surface
进入 / 挂载信息
```

新增或删除 Capability 时，目标是：

```text
Capability 注册 / 注销
↓
Surface Host 重新发现
↓
对应入口与交互投影出现 / 消失
```

而不是修改沉浸式 Shell 的业务源码。

---

# 11. Shell 与 Panel 本身允许替换

沉浸式 UI 的 Shell、导航、Panel Host 与普通控件都属于前端实现。

允许：

```text
局部 Panel 重写
导航结构重做
布局整体调整
Shell 整体换代
视觉体系整体重做
```

这些变化不得要求：

```text
Capability 重写
Workflow 重写
业务状态迁移
后台功能暂停
```

不要求所有前端代码必须做到零帧 HMR。

允许通过：

```text
panel remount
soft reload
frontend bundle replacement
重新连接后台
```

完成 UI 更新。

---

# 12. UI 与业务状态必须分离

前端临时状态可以存在于 UI 内。

业务正确性所依赖的状态不得只存在于某个 React / Vue / Canvas 组件中。

正式验收原则：

> **删除当前完整前端并重新实现一个最小 UI，不应破坏任何 Capability 的业务成立性。**

新的 UI 只要重新接入稳定契约，就应能够：

```text
发现 Capability
读取状态
执行 Action
观察长期 Workflow 状态
```

---

# 13. 自定义绘制与语义接口

DCF 可以根据交互需要使用：

```text
DOM / 标准 Web 控件
Canvas
WebGL / WebGPU
其他自定义绘制
```

视觉实现可以自由选择。

但如果自定义绘制无法自然提供 Accessibility / AX 语义，必须由 Surface 语义层提供可映射的机器可读信息。

原则：

> **视觉实现可以重做，交互语义不能因此消失。**

---

# 14. 当前实施边界

当前第一阶段只要求实现和验证当前架构本身：

```text
Go 应用骨架
DBOS Workflow 接入
PostgreSQL Workflow 持久化
Capability 与 Workflow 的边界
Surface Contract
Capability Surface 动态发现
可替换 Shell / Panel 边界
```

当前规范**不要求**提前设计未来性能优化结构，也不要求预先定义完整 Effect 分类。

只有当未来真实功能和真实负载提出新的问题时，再针对那个问题单独做架构决策。

---

# 15. 当前实施纪律

1. **Capability Registry v1 保持不变。**
2. **Go 是当前主实现语言。**
3. **普通逻辑默认留在 Go。**
4. **只有需要跨时间存活的过程进入 DBOS Workflow。**
5. **PostgreSQL 当前只因 DBOS Workflow 的持久化需求进入本规范。**
6. **不得由此推导其他数据存储迁移。**
7. **Public Facility / Provider / Probe 继续按既有产品边界使用。**
8. **三种交互 Capability 不绑定固定 UI 控件。**
9. **UI 层没有不可替换组件。**
10. **能力热插拔通过 Surface Contract 实现。**
11. **业务正确性不得依赖具体前端实现。**
12. **UI 可以整体删除重做。**
13. **当前未提出的问题，不提前建设未来优化架构。**
