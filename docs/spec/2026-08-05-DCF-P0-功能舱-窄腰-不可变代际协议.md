# 1. P0 总裁决

P0 采用三个主结构同时吸收功能装载、运行隔离、原生界面、跨运行时通信、更新、回滚与恢复复杂度：

```text
功能舱（Feature Capsule）
→ 一个完整功能怎样作为最小产品增长单位存在

DCF Wire（窄腰协议）
→ Bun、macOS Host、原生功能块怎样通过极少稳定语义通信

不可变代际（Immutable Generation）
→ 一组功能怎样被验证、原子切换、伪热更新与回滚
```

核心目标不是为 G-001～G-008 分别制造八套机制，而是让这三个结构共同吸收它们。

正式原则：

> **功能舱定义“完整功能是什么”；DCF Wire 定义“不同运行世界怎样交流”；不可变代际定义“整个产品怎样安全长出新能力”。**

# 2. 功能舱：DCF 的完整部署与产品增长单元

## 2.1 定义【已冻结】

一个正式 DCF 功能不是一个后端模块，也不是一个页面，而是一个完整功能舱。

概念结构：

```text
功能舱
│
├─ contract
│  └─ 功能身份、版本、能力、依赖、入口、Surface、Action、状态通道
│
├─ Bun Runtime
│  └─ TypeScript / Bun 业务逻辑、World 运行逻辑、确定性功能逻辑
│
├─ Native Runtime
│  └─ Swift / SwiftUI / AppKit / WKWebView / Metal / 第三方原生能力
│
├─ resources
│
├─ migrations
│
└─ tests / acceptance
```

具体扩展名、目录拼写和构建脚本不在本文冻结；实现必须保持上述职责完整。

## 2.2 contract 的职责【已冻结】

contract 只描述跨功能、跨运行时必须共同知道的关系，不描述功能内部 UI 像素结构。

最小必须声明：

```text
feature_id
feature_version
required_dcf_contract_version

provides_capabilities[]
requires_capabilities[]
optional_capabilities[]

bun_entry
native_entry（可选）

surfaces:
  full
  sidebar
  floating
  settings

state_channels[]
actions[]
persistence_schema_version
```

禁止把 contract 演化成万能 JSON UI DSL。

> **contract 规定关系，不规定实现。**

## 2.3 原生实现自由【已冻结】

功能舱内部允许使用任意受信任的 Swift / SwiftUI / AppKit 实现；也允许 WKWebView、BlockNote、Metal 和局部第三方库。

DCF Host 不规定功能内部必须使用什么 UI 组件，不要求所有功能被压缩成 Card / List / Button 等有限词汇。

> **限制关系，不限制能力。**

World 隔离是所有权和依赖约束，不是对功能内部技术选择的限制。

# 3. 原生功能入口与 DCFPluginKit

## 3.1 原生载荷【已冻结】

需要原生 UI / 原生能力的功能舱，第一版使用 macOS 可加载 Bundle 作为 Native Runtime 载荷。

功能舱可以没有 Native Runtime；纯运行功能允许只存在 Bun Runtime。

Native Bundle 不承担长期业务真相，只提供原生 Surface、原生交互和必要的局部能力。

## 3.2 DCFPluginKit【已冻结】

DCF 原生宿主只暴露一套极薄的稳定插件接缝，暂称 `DCFPluginKit`。

它负责：

```text
功能身份确认
Surface factory 注册
状态订阅入口
Action 发送入口
生命周期通知
可用 / 不可用状态
诊断信息
```

宿主不得因为新增功能而新增：

```text
NarrativeReviewHostProtocol
ProjectHostProtocol
KnowledgeHostProtocol
...
```

业务专用接口必须停在功能舱内部或 DCF Wire payload 层。

## 3.3 跨边界类型纪律【已冻结】

插件边界优先使用稳定、低耦合的 Foundation / Objective-C compatible 类型或序列化 `Data`，避免让宿主 ABI 依赖大量功能专用 Swift 类型布局。

边界之外进入功能舱以后可以完全使用现代 Swift 类型系统。

原则：

> **最外层边界尽量稳定、无业务知识；边界以内最大自由。**

# 4. Surface 注册与编排

## 4.1 功能拥有展示能力，宿主拥有展示秩序【已冻结】

功能舱可以提供：

```text
完整形态入口
Dashboard / 首页贡献
侧边栏贡献
悬浮球贡献
设置入口
专用原生交互
```

其中侧边栏、悬浮球允许明确“不提供”。

macOS Host 负责：

```text
当前功能注册表
导航与布局
用户排序和组合
侧边栏启用配置
悬浮球启用配置
上下文编排
功能更新后的重新注册
```

宿主不得硬编码未来功能名单。

## 4.2 Surface Factory【已冻结】

原生功能通过 factory 提供可嵌入的原生展示对象。第一版允许返回 `NSViewController` 级别的宿主入口；其内部可使用 `NSHostingController`、SwiftUI、AppKit、WKWebView 等任意实现。

Surface factory 只定义：

```text
这是哪个功能的哪个 Surface
当前是否可创建
怎样创建
怎样接收 DCFContext
怎样销毁局部 UI 状态
```

不规定功能内部视觉结构。

# 5. DCF Wire：唯一跨运行时窄腰

## 5.1 定义【已冻结】

Bun Core、macOS Host 和原生功能之间不建立大量业务专用 IPC 协议。

所有跨运行时通信统一进入 `DCF Wire`。

消息最小信封：

```text
protocol_version
generation_id
feature_id
kind
request_id（需要请求关联时）
sequence（需要顺序时）
payload
```

第一版 `kind` 保持极少类别：

```text
registry.snapshot
state.snapshot
state.event
action.request
action.result
job.event
health
```

叙事、项目、知识、任务等业务语义不进入 Wire 核心类型枚举，而存在于 `feature_id + payload` 中。

> **DCF Wire 知道通信语义，不知道业务世界。**

## 5.2 DCFContext【已冻结】

原生功能不得直接依赖 Bun、XPC 或某个具体运输实现。

原生功能只取得 `DCFContext`，通过它：

```text
订阅状态
获取当前 snapshot
发送 Action
观察 Job / health
读取当前 generation / feature 状态
```

因此运输层可以替换而不要求修改业务功能。

## 5.3 运输层【首选已冻结，允许行为实验替换】

第一版首选：

```text
macOS Host
↕ XPC / libxpc
DCF Wire transport bridge
↕ Node-API addon
Bun Core
```

原则：

- XPC 是运输层，不是业务协议；
- Bun 原生桥只负责收发 Wire 消息，不理解叙事、项目、World、Surface；
- 首选 Bun Node-API native addon 承载极薄原生桥；
- 不把 Bun FFI 作为 P0 唯一正式前提；
- 若行为实验发现 Node-API + XPC 不满足稳定性，可将运输层替换为 Unix Domain Socket，而 DCF Wire、功能 contract、Surface、World 不得因此变化。

这意味着：

> **运输实现是可替换薄层，DCF Wire 才是长期架构边界。**

# 6. 能力依赖：Capability First

## 6.1 默认依赖能力，不依赖具体功能【已冻结】

功能之间默认通过能力声明建立依赖：

```text
Feature A
requires: dcf.narrative.read

Feature B
provides: dcf.narrative.read
```

Registry 在构造候选代际时解析 provider。

这样功能 A 不需要知道能力当前由哪个具体功能实现。

## 6.2 具体 Feature ID 依赖【例外】

只有当语义上不可替代，例如明确依赖另一个功能自己的内部历史或专属对象时，才允许声明具体 Feature ID 依赖。

默认规则：

> **Capability first；Feature ID second。**

## 6.3 依赖校验【已冻结】

候选代际进入运行前必须检查：

```text
必需 capability 是否存在唯一可接受 provider
版本是否兼容
是否存在循环依赖
native / bun 入口是否完整
Surface 声明是否可满足
migration 是否可执行
```

必需依赖缺失时，该候选代际不得提升为 current。

optional capability 缺失时，功能允许以显式降级状态注册；不得假装能力存在。

# 7. 持久化黑洞：Bun Core 单写者 + SQLite Journal / Projection

## 7.1 唯一长期写者【已冻结】

第一版 DCF 长期事实采用：

> **Bun Core 是 DCF 自有持久世界的唯一逻辑写者。**

```text
Swift Surface
→ Action
→ Bun Core
→ SQLite

Worker / Agent
→ Result
→ Bun Core
→ SQLite

来源适配器
→ Fact
→ Bun Core
→ SQLite
```

功能原生插件不得绕过 Bun Core 建立另一套 DCF 长期事实权威。

局部缓存、纯 UI 瞬态和功能内部可丢弃数据不受此限制。

## 7.2 Journal + Projection【已冻结】

不要求把整个 DCF 实现成纯 Event Sourcing。

第一版采用：

```text
发生过什么
→ append journal

现在是什么
→ current projection
```

需要历史意义的变化，例如：

```text
校准事件
功能配置变化
Job 创建 / 完成 / 失败
generation 切换
功能迁移
```

应保留追加记录。

当前查询状态可维护普通投影表。

同一次逻辑变化必须在同一个 SQLite transaction 内完成需要的 journal 追加与 current projection 更新，避免两套状态漂移。

# 8. World 恢复：活动世界可重建，语义进度按需持久

## 8.1 World 定位【已冻结】

```text
World
→ 当前正在发生什么

SQLite 持久层
→ 长期事实与不可丢的语义进度
```

不持久化整个 Becsy World。

## 8.2 恢复分类【已冻结】

World 状态进入三类：

```text
A. 可从长期事实确定重建
→ 重启后直接重算，不 checkpoint

B. 纯瞬态
→ 重启后允许丢失

C. 无法从长期事实确定重建且丢失会改变业务语义
→ 必须在推进时写入持久语义进度 / receipt
```

每个功能块 contract / 规格必须明确自己有哪些 C 类状态。

## 8.3 World 局部失败【已冻结】

某个 World 创建或恢复失败，默认不得阻塞其他无依赖 World 的恢复。

Registry 将该功能标记为：

```text
unavailable / degraded
+
明确失败原因
```

依赖它的功能再根据 required / optional 关系决定不可用或降级。

# 9. 不可变代际：更新、伪热更新与回滚黑洞

## 9.1 Generation 定义【已冻结】

一次正式运行使用一组完整、不可变的功能版本集合，称为一个 `Generation`。

示意：

```text
Generation 17
├─ feature-a@1
└─ feature-b@3

Generation 18
├─ feature-a@1
├─ feature-b@3
└─ feature-c@1
```

Generation 生成后不得原地修改。

功能更新产生新的 Generation，而不是覆盖当前运行文件。

## 9.2 candidate / current / LKG【已冻结】

复用 DCF 历史上已经形成的候选—当前—最后可信模型：

```text
candidate
→ 尚未提升的完整候选代际

current
→ 当前正式运行代际

LKG
→ 最后经过规定行为验证的可信代际
```

状态推进：

```text
构造 candidate
↓
完整预检
↓
提升 current
↓
实际生存 / 行为验证
↓
提升 LKG
```

current 启动失败或关键 P0 验收失败时允许恢复到 LKG。

## 9.3 候选代际预检【已冻结】

candidate 提升前至少检查：

```text
所有 contract 可解析
功能版本与 DCF contract 兼容
Capability DAG 可解析且无禁止循环
Bun entry 可加载
Native Bundle 可加载 / 签名满足当前部署要求
Surface factory 可注册
持久化 migration 可验证
World 注册可建立
测试 / P0 必要验收通过
```

不得出现：

```text
Bun 已切新版本
Native 仍是旧版本
```

因为 Bun 与 Native 属于同一个 Generation。

## 9.4 原子切换【已冻结】

candidate 完成预检后，current 只通过一个原子代际指针切换完成提升。

旧 Generation 保持完整不变，供回滚和证据追踪。

# 10. 伪热更新完整生命周期

## 10.1 更新语义【已冻结】

DCF 不追求真正的 in-process HMR。

正式更新采用：

> **完整候选代际 + 快速硬重启 + 确定性恢复。**

Native Bundle 不依赖可靠 unload/reload 作为更新前提。

## 10.2 生命周期【已冻结】

```text
1. 检测功能源码 / 构建输入变化
↓
2. 构建新功能舱产物
↓
3. 生成 candidate Generation
↓
4. 执行 contract / dependency / load / migration / acceptance 预检
↓
5. 将不能从长期事实恢复的 C 类语义进度写入持久层
↓
6. 停止接受会跨越代际产生歧义的新本地工作
↓
7. current 原子切换到新 Generation
↓
8. 退出活动 Bun Runtime；需要 Native 更新时退出对应 Surface Host 活动实例
↓
9. launchd 按正式生命周期重新拉起
↓
10. 从 current Generation 扫描全部功能舱
↓
11. 重建 Registry / World / Surface Registry
↓
12. macOS Host / Surface 重新连接 DCF Wire
↓
13. 重建可恢复状态，恢复允许继续的 Job / receipt
↓
14. UI 获得最新 registry + state snapshot
↓
15. 进入行为验证；通过后按规定提升 LKG
```

## 10.3 Job 跨代际【已冻结】

Job 必须知道：

```text
创建它的 generation_id
feature_id
逻辑动作身份
当前执行状态
是否允许跨 generation 继续
```

默认：

- 外部独立执行器中已经真实开始、且结果语义仍兼容的 Job 可以继续；
- 运行在即将退出进程内且没有持久 receipt 的工作不得假装继续；
- 新代际若无法理解旧 Job 结果，必须显式标记需要旧版本处理、迁移或失败，不得猜测。

具体每类 Job 的兼容策略由对应功能规格定义。

## 10.4 UI 瞬态【已冻结】

业务事实不得依赖 UI 瞬态才能恢复。

以下允许作为 best-effort UI 恢复：

```text
当前页面
滚动位置
展开状态
窗口位置 / 尺寸
未提交纯 UI 草稿
```

若某个“草稿”业务上不可丢，则它不再属于纯 UI 瞬态，必须提升为功能持久状态。

# 11. P0 试验功能与验收

## 11.1 试验策略【已冻结原则，具体功能名可调整】

P0 不使用复杂真实认知业务来证明底盘。

必须至少存在三个极简完整功能舱 A、B、C；它们应分别覆盖：

```text
长期状态
World 活动状态
共享公共资源
完整形态
侧边栏
悬浮球可选贡献
Action
重启恢复
```

先运行 A / B，再动态加入 C。

## 11.2 必须通过的行为【已冻结】

```text
A / B 正常运行
↓
增加 C
↓
构造 candidate Generation
↓
预检通过
↓
原子切换 current
↓
硬重启
↓
C World 自动建立
↓
完整形态自动出现 C
↓
侧边栏设置自动出现 C
↓
悬浮球设置按 C 声明自动出现 / 不出现
↓
A / B 不修改代码且长期状态仍正确
```

还必须验证：

- A / B 复用同一公共资源而不共享私有状态；
- 删除 / 更新一个功能生成新 Generation，而不是原地污染旧 Generation；
- candidate 失败不破坏 current；
- current 失败可恢复 LKG；
- macOS Host 重连后取得新的 registry.snapshot 与 state.snapshot；
- 一个 World 恢复失败不拖死无依赖 World；
- 功能依赖缺失时得到明确 unavailable / degraded，而不是运行时随机崩溃；
- Surface 中触发 Action 与其他 Surface 触发同一 Action 进入同一业务语义。

# 12. 对总设计说明书缺口的裁决

| 原缺口 | 本文裁决 | 状态 |
|---|---|---|
| G-001 Swift 原生功能块构建与装载 | 功能舱 + Native Loadable Bundle + DCFPluginKit | 原理已冻结；签名/构建命令留实现验证 |
| G-002 Surface 注册协议 | DCFPluginKit Surface factory + Surface Registry | 已冻结 |
| G-003 World 重建与最小恢复点 | A/B/C 三类恢复状态；只持久 C 类语义进度 | 已冻结 |
| G-004 功能依赖声明与加载顺序 | Capability First + candidate DAG 预检 | 已冻结 |
| G-005 Bun ↔ Swift 状态 / Action | DCF Wire + DCFContext；XPC 为首选运输层 | 已冻结 |
| G-006 持久层最小权威模型 | Bun Core 单写者 + SQLite Journal / Projection | 已冻结 |
| G-007 伪热更新生命周期 | Immutable Generation + current 原子切换 + hard restart + LKG | 已冻结 |
| G-008 P0 试验功能 | 三个极简完整功能舱覆盖全链行为 | 原则已冻结；具体功能内容待实现前选择 |

上述缺口不再作为“由实现 AI 自由选择架构”的空白。

# 13. 仍允许实现阶段选择的局部细节

以下不是架构缺口，只要行为验收满足即可由实现 AI选择：

```text
功能舱最终目录名 / 扩展名
contract 使用 JSON、JSON5、TOML 或等价确定性编码
DCFPluginKit 内部具体 Swift 文件拆分
Node-API addon 的具体 C/C++/Objective-C++ 实现方式
XPC 消息序列化的具体库
SQLite 第一版具体表名
Generation ID 具体编码
candidate / current / LKG 指针的具体文件实现
P0 三个试验功能的具体业务外观
```

但如果某个局部选择会改变：

```text
所有权
跨功能依赖
长期事实权威
代际原子性
Surface 动态注册能力
失败 / 回滚语义
```

则它不再是局部实现细节，必须先回到设计规范裁决。

# 14. P0 一句话总图

```text
                 DCF Feature Capsule
              完整功能的最小增长单位
                         │
       ┌─────────────────┴─────────────────┐
       ▼                                   ▼
```
