# 1. 个人叙事的当前定义

个人叙事不是生活日记，也不是工作日报、项目周报或操作流水。

个人叙事是：

> **一个人在世界中生活、思考、判断、行动并受到现实反馈之后，留下的自我认知具象痕迹。**

它记录的不只是“世界发生了什么”，而是：

```text
我接触了什么
↓
我为什么在意
↓
我怎样理解
↓
我怎样行动
↓
现实怎样回应
↓
我的判断怎样变化
↓
哪些东西最终留在我身上
```

个人叙事首先服务于本人重新理解自己。

用户回看它时，应能重新理清思路、发现误解、看见转折，并可能产生新的关联或灵感。

因此：

> **用户审核不是替 DCF 维护数据库，而是一次真实的自我认知生产。**

个人叙事必须清晰直观，也必须保留未来可能改变理解的关键差异；但本功能块不为任何具体下游功能预先决定“什么是项目材料”“什么是知识”“什么该成为 Wiki”。

---

# 2. 既定总体架构：系统拥有现实，DCF 拥有认知

本功能块不得重新制造 macOS 已经长期维护的现实世界。

当前事实所有权已经裁决为：

```text
文件变化历史
→ macOS FSEvents / .fseventsd 拥有

当前文件索引
→ macOS Spotlight 拥有

前台活动与屏幕活动分段
→ macOS KnowledgeC / CoreDuet + NSWorkspace 拥有

用户最终提交文本
→ macOS IMK + Unified Logging Persist 拥有现实记录

进程 / 文件机器动作收据
→ macOS Endpoint Security / eslogger 提供

进程生命周期
→ launchd + XPC 拥有

认知正文 / 当时理解 / 后来理解 / 用户校准
→ DCF SQLite 锚定认知世界拥有
```

DCF 不复制第二份同义权威。

个人叙事功能块只消费公共事实层已经提纯、带来源锚点的现实增量。

# 3. 既定 macOS 公共现实底座

以下不再作为候选重新讨论，而作为当前正式事实底座继承。

## 3.1 文件现实层

```text
FSEvents + Spotlight
```

负责：

- 从持久 event id 取得文件变化历史；
- 通过 Spotlight / MDQuery / mdls 查询当前文件世界；
- 避免 DCF 自建全盘 watcher、定期全量扫描、重复文件索引。

个人叙事功能块消费提纯后的文件现实，不直接维护自己的文件 watcher。

## 3.2 活动时间骨架

```text
KnowledgeC / CoreDuet + NSWorkspace
```

负责：

- 前台 App 起止分段；
- 屏幕亮灭 / 使用分段；
- 实时 App 生命周期和前台变化；
- 避免 DCF 自建第二套 session detector。

这层只提供活动时间背景，不提供项目、目标、意图或因果解释。

## 3.3 用户表达事实层

```text
IMK + Unified Logging
private-data + Persist=Debug
```

已实测能够提供：

- 最终 `insertText` 明文；
- composition 中间态；
- 语音提交；
- 客户端 bundle id 归因；
- Persist=Debug 后的掉线补读。

因此基础文字事实不依赖键盘监听、AX 文本抓取或 OCR 输入还原。

## 3.4 机器 Effect 收据

```text
Endpoint Security / eslogger NOTIFY 精简管道
```

当前用于：

```text
exec
create
rename
exit
```

它提供独立于 Agent 自报结果的物理现实收据。

DCF 可以基于 pid / ppid / exec 命令行尽力关联现实 Effect，但未知关联必须保持未知。

## 3.5 生命周期

```text
launchd + XPC
```

负责常驻观察壳和相关进程生命周期，不由个人叙事功能块自建 supervisor。

## 3.6 来源专用高语义事实

IDE / Agent 本地数据库、结构化事件流、聊天来源记录等继续允许作为来源专用增强事实源。

它们信息密度高，但不取得公共现实底座身份。

## 3.7 已降级 / 淘汰事实面

不得重新提升为基础现实面：

```text
屏幕 / OCR 全量观察
DCF 自建全盘 watcher / index
DCF 自建 session detector
每个 Agent 一套结果自报事实链
```

AX 保留为来源专用、机会主义的结构化 UI 增益，不承担基础兜底身份。

# 4. DCF 常驻观察壳与个人叙事的关系

当前公共现实结构已经裁决为极薄观察壳：

```text
launchd 托管的 DCF 常驻观察壳
├─ FSEvents stream（游标消费）
├─ eslogger NOTIFY 精简集管道
├─ IMK / Unified Log 明文消费者与游标补读
└─ KnowledgeC 分钟级轮询
```

观察壳负责把系统现实提纯后进入 DCF 持久层。

个人叙事功能块不得：

- 再起一套 FSEvents watcher；
- 再做一套前台 App session detector；
- 再全量消费 Unified Log；
- 再为 Codex / OpenCode / shell 分别维护执行结果观察器。

它只消费公共层已经存在的现实事实。

---

# 5. 第 0 层：机器事实翻译

在开放式 AI 形成个人叙事之前，必须存在确定性的第 0 层。

其职责不是理解人生、项目或价值，而是：

> **把底层事实语言翻译成可直接阅读、可直接审核、同时不增义的初始现实文档。**

数据流：

```text
提纯系统事实
↓
确定性主体 / 对象 / 时间绑定
↓
规则与字典翻译
↓
确定性去噪与归并
↓
第 0 层初始现实文档
```

第 0 层优先使用：

```text
解析器
规则
字典
模板
确定性状态机
原生系统身份
```

不使用开放式 AI 来猜测确定事实。

---

# 6. 第 0 层主体归因硬规则

必须严格区分：

```text
系统观察到状态变化
≠
证明用户主动造成该变化
```

例如事实只证明：

```text
Chrome 当前标签页 URL：A → B
```

第 0 层只能写：

> Google Chrome 当前标签页 URL 从 A 变为 B。

禁止写：

> 用户打开了 B。

同理：

```text
前台应用：Chrome → Codex
```

只能写：

> 前台应用从 Google Chrome 变为 Codex。

禁止写：

> 用户切到 Codex 继续开发 DCF。

只有事实源明确证明主体、动作和对象时，才能自然语言展开对应关系。

第 0 层禁止自行生成：

```text
项目归属
用户目标
行为目的
因果
采纳关系
重要性
长期价值
```

---

# 7. 第 0 层翻译与压缩纪律

允许的确定性处理：

- 统一时间；
- bundle id / process id / native id 映射为稳定可读名称；
- 明确的 parent-child / call-result / file-effect 原生关系闭合；
- composition 中间态合并为可辨认的最终提交过程；
- 重复心跳和纯系统噪声删除；
- 同一次确定操作产生的低层重复事件归并；
- 将外部英文协议术语映射为 DCF 内部稳定中文表达。

禁止：

- 为了顺畅补出事实源没有证明的主语；
- 把时间相邻解释成因果；
- 把路径解释成项目；
- 把前台 App 解释成用户目标；
- 把 Agent 自报成功解释成现实成功；
- 把“没有观察到”解释成“没有发生”。

原则：

> **消除机器噪声，不消除现实差异；允许翻译，不允许增义。**

---

# 8. 第 0 层输出：初始现实文档

第 0 层输出普通、可读、可追溯的初始现实文档。

目的：

1. 给个人叙事 AI 一个比底层事件干净得多的输入；
2. 给用户审核个人叙事时提供回忆锚点；
3. 当叙事出错时区分“事实源错 / 第 0 层翻译错 / AI 理解错”。

文档以时间与已经确定的活动分段为骨架。

允许示意：

```text
2026-08-06

05:12–05:38
前台应用：ChatGPT
文本客户端最终提交：……
……

05:39–06:02
前台应用：Codex
Codex / shell 相关现实 Effect：……
文件变化：……
……
```

它不是日记，也不是个人叙事，只是机器能够证明的现实的人类可读版本。

初始现实文档不是长期认知权威，可以随第 0 层规则升级重新生成。

---

# 9. 个人叙事 AI 的输入与职责

个人叙事 AI 读取：

```text
当前复盘时间范围的初始现实文档
+
必要的来源引用
+
必要的前后连续背景
+
个人叙事写作约束
```

它可以进行开放式综合理解。

目标不是逐条复述现实，而是把现实恢复成一个人可以重新理解的认知轨迹。

个人叙事应优先组织：

```text
当时主要关注什么
↓
为什么值得处理
↓
采用了什么主要思路或操作
↓
现实怎样回应
↓
哪里发生关键转折
↓
判断怎样改变
↓
最后留下了什么
↓
当时 / 当前怎样理解这段经历
```

时间是坐标，不是正文主要结构。

禁止默认生成“早上 / 中午 / 晚上做了什么”的生活日记。

# 10. 个人叙事的“清晰 + 详实”要求

清晰不等于短。

详实不等于保留所有操作。

定义：

> **清晰 = 用户无需重新拼接大量原始上下文，就能理解主要对象、思路和转折。**

> **详实 = 未来可能改变理解和行动的关键差异没有被摘要掉。**

允许压缩：

- 重复操作；
- 无意义等待；
- 工具调用流水；
- 没有后果的小动作；
- 已被后续结果完全吸收的低层细节。

必须尽量保留：

- 当时真正试图解决的问题；
- 主要方案；
- 重要操作结果；
- 失败及失败暴露的东西；
- 成功中间里程碑；
- 判断发生变化的原因；
- 得到的成果、能力、方法或认识；
- 尚未吸收的问题；
- 因已有积累而变得可能的新方向。

这些内容因为它们构成个人认知而保留，不是为了提前服务项目、Wiki 或知识卡。

---

# 11. 既定人物叙事 Surface：日历入口

人物叙事继续沿用既有“人物日历”设计。

日历负责天然时间坐标，不代表每天必须写日记。

允许：

- 某天完全空白；
- 某天只有少量现实；
- 连续几天形成一个叙事段；
- 几周后再补审；
- 只审核重要日期。

核心原则：

> **日历负责导航时间，不制造日记负担。**

日历数据直接来自 SQLite 个人叙事对象 / 修订 / 审核状态查询，不通过扫描 Markdown 文件生成。

# 12. 既定当天 / 叙事段审核页

点击日期或叙事段后，继续沿用既有结构：

```text
Interaction Trajectory
+
Human Narrative Draft
+
来源交互引用
+
用户修改区
```

内部中文语义：

```text
交互轨迹
→ 第 0 层初始现实文档及其可展开现实轨迹

个人叙事草稿
→ 个人叙事 AI 草稿

来源引用
→ 支撑当前现实稿和叙事的原始事实 / 来源锚点

用户修改区
→ 对叙事的真实校准与复盘
```

页面主要动作继续是：

```text
批准
纠正
局部重写
拆分
合并
标记“这段没有什么值得保留”
回看来源
```

人物叙事页不得塞入项目管理、知识卡管理、Wiki 管理、求解器或下游切分操作。

核心原则：

> **人物叙事页面的主要动作是校准，不是管理项目。**

# 13. AI 原稿、用户修正版与审核记录

既定 UI 要求继续保留：

```text
AI 原稿
用户修正版
修改差异
```

但三者的长期语义必须分开。

正式历史认知只由用户确认后的 `personal_narrative revision` 承担。

AI 原稿和本次修改差异保存为独立的**审核记录**，用于回答：

```text
AI 最初怎样理解
用户最终怎样修改
二者哪里发生差异
这次审核最终形成了哪个正式 revision
```

逻辑结构可以是：

```text
审核记录
├─ review_id
├─ object_id
├─ ai_draft
├─ user_final_text
├─ diff
├─ model / prompt_version
├─ created_at / confirmed_at
└─ accepted_revision_id
```

审核记录是可追溯证据，但**不等同于正式个人认知修订**。

这样既保留“AI 曾经理解错在哪里”，又不会把未经用户确认的 AI 原稿冒充成个人历史认知。

---

# 14. “当时理解”与“审核时新理解”必须区分

用户审核时可能发生两类动作。

## 14.1 修正 AI 对当时经历的表达

例如：

> AI 把当时的主要不满写成“效率”，用户修正为“接缝残差”。

这是对当前草稿的校准。

## 14.2 审核过程中产生新的理解

例如：

> 回看以后才意识到几个以前分散的问题实际上属于同一条长期路线。

这个理解形成在审核时，不能静默伪装成“当时已经知道”。

必须以当前时间形成新的正文段、补充认知或新修订中的显式时间差异。

例如：

```text
当时：……

2026-08-06 复盘时进一步意识到：……
```

核心原则：

> **认知永远记录在它产生的时间点；它可以引用过去，但不能回写过去。**

# 15. 正式个人叙事的持久化模型

正式个人叙事属于：

> **DCF 锚定认知世界中的长期认知对象。**

当前权威持久层：SQLite。

逻辑结构继承公共规范：

```text
个人叙事对象
├─ object_id
├─ kind = personal_narrative
├─ current_revision_id
├─ narrative_start_at
├─ narrative_end_at
└─ 生命周期 / 审核状态

个人叙事修订
├─ revision_id
├─ object_id
├─ content
├─ created_at
├─ author_kind = user_confirmed / imported_confirmed
├─ source_refs
└─ content_hash
```

用户第一次批准时产生第一个正式用户确认修订。

以后修改时：

```text
旧 revision 保留
↓
创建新 revision
↓
object.current_revision_id 指向新版本
```

禁止原地覆盖旧正式正文。

# 16. 为什么数据库是权威、Markdown 不是权威

个人叙事后续需要高频支持：

```text
按日期查询
按时间范围查询
修订历史
来源锚点
多种重叠标注
多种切分视图
搜索索引
语义向量
词元级表示
项目 / Wiki / 知识等不同解释
```

如果 Markdown 文件是权威、数据库只是镜像，就会额外制造：

```text
文件 ↔ 数据库
双向同步
冲突检测
文件移动身份问题
外部编辑回流问题
```

因此当前裁决：

> **数据库保存认知对象本身；文件只作为导出、交换、备份阅读格式。**

用户需要时可以从 SQLite 导出：

```text
Markdown
JSON
HTML
其他未来格式
```

导出文件不自动成为新的事实权威。

# 17. 草稿运行态、审核记录与正式认知必须分开

审核中的运行状态允许存在运行数据库中：

```text
当前编辑正文
编辑游标
临时 diff
生成状态
失败状态
待审核状态
```

AI 草稿与最终修改差异在审核完成后可以沉淀为第 13 节定义的审核记录。

只有用户明确确认的正文才产生正式个人叙事 revision。

正确边界：

```text
AI 草稿
↓
用户阅读 / 修改
↓
审核记录保存“AI 原稿 + 差异”
↓
用户确认正文
↓
生成正式 immutable revision
↓
SQLite 事务提交
↓
正式认知成立
```

因此不得出现：

```text
AI 自动生成草稿
↓
直接写入正式个人历史
```

---

# 18. 保存事务与原子性

正式保存必须是单数据库事务。

逻辑步骤：

```text
BEGIN
↓
校验当前草稿完整性
↓
写入新的不可变 revision
↓
写入 / 更新本次审核记录并绑定 accepted_revision_id
↓
更新 object.current_revision_id
↓
更新审核状态 / 时间范围
↓
保存来源引用
↓
COMMIT
```

任何一步失败：

```text
ROLLBACK
```

不得出现：

```text
正文已经成为正式历史
但 current_revision 还指向旧版本
```

或：

```text
日历显示已批准
但正式 revision 并不存在
```

---

# 19. 稳定锚点从正式修订产生

正式 revision 提交后，公共认知能力可以使用：

```text
revision_id
+
start_offset
+
end_offset
```

建立稳定正文锚点。

所有未来：

```text
项目切分
Wiki 切分
知识标注
语言弹药标注
语义检索结果
```

都应指向 revision + span，而不是复制正文后形成第二份材料权威。

这使同一篇个人叙事可以同时拥有多种重叠解释，而正文仍然只有一个正式来源。

---

# 20. 个人叙事与查询诱导语义场的边界

正式 personal_narrative revision 提交以后，公共认知查询系统可以异步建立：

```text
FTS 词法索引
字符三元组索引
稠密语义向量
多向量 / 词元级后期交互表示
不同切分 / 标注视图
```

这些全部属于：

> `docs/spec/2026-08-06-DCF-锚定认知世界与查询求解公共能力规范.md`

不是个人叙事功能块的一部分。

因此正确时序：

```text
个人叙事正式 revision COMMIT
↓
个人叙事功能块 END

公共认知运行时观察到新 revision
↓
异步重建 / 增量建立可重算检索投影
```

即使所有 embedding / FTS / 后期交互模型暂时失效，个人叙事保存仍然必须成功。

---

# 21. 个人叙事不主动生产下游材料

保存后禁止主动：

```text
调用项目叙事
调用 Wiki
生成知识卡
生成语言弹药
运行项目涌现
调用约束求解器
强制生成标准切片
```

下游功能未来可以通过公共认知查询提出自己的问题，例如：

```text
项目叙事
→ “哪些个人叙事片段描述了 DCF 项目的目标、路线转折、成果与开放问题？”

知识卡
→ “过去有哪些材料共同支持某个可迁移原则？”

Wiki
→ “解释某主题需要哪些历史材料？”
```

但个人叙事功能块不需要知道这些未来查询。

核心原则：

> **个人叙事只负责形成高质量认知原件；未来意义由未来查询重新发现。**

---

# 22. 切分不再是个人叙事的公共出口协议

当前明确否决：

```text
个人叙事
↓
唯一标准自包含切分
↓
所有未来功能消费
```

以后任何切分都是：

```text
某个 processor / model / rule
+
某个 revision
↓
一套 annotation_set / retrieval_view
```

允许：

```text
project-view/v1
project-view/v2
wiki-view/v1
knowledge-view/v3
semantic-window/v2
```

并存。

个人叙事功能块本身不设计这些规则。

---

# 23. 完整形态 / 侧边栏 / 悬浮球的既定 Surface 关系

本功能块遵守总实施规范：

```text
功能身份 / 业务事实 / 动作语义只有一份
↓
完整形态 / 侧边栏 / 悬浮球只是同一功能的不同投影
```

不得为不同 Surface 复制第二套个人叙事状态或第二套审核逻辑。

## 23.1 完整形态

承载：

```text
人物日历
交互轨迹
个人叙事草稿
来源引用
AI 原稿 / 用户修正版 / 修改差异
正式审核动作
修订历史查看
```

## 23.2 侧边栏

只贡献适合高频窄空间使用的：

```text
待审核叙事入口
当前待校准叙事摘要
```

不复制完整编辑器和历史管理。

## 23.3 悬浮球

只允许极少量真正值得持续存在的状态或快捷入口。

个人叙事不因为存在未审核内容就默认制造持续红点、数量压力或日记债务。

具体排序、组合、手势由宿主动态 Surface 编排负责。

---

# 24. 诊断边界

普通人物叙事 UI 服务理解和校准。

工程事实进入 Diagnostic。

诊断至少能够追踪：

```text
本轮现实文档使用了哪些公共事实源
各来源游标 / 时间范围
哪些事实缺失或 unknown
第 0 层翻译规则 / 版本
个人叙事模型 / Prompt 版本
review_id
AI 草稿
用户修改
最终 object_id / revision_id
事务提交结果
来源引用
公共索引任务状态（只读诊断，不属于保存成功门禁）
```

错误必须能够区分：

```text
事实源没有观察到
事实提纯 / 第 0 层翻译错误
个人叙事 AI 理解错误
用户后来产生了新的理解
正式 revision 保存故障
公共检索投影生成故障
```

不得把六种问题混成“AI 写得不对”。

# 25. 实施步骤

按现有能力直接实施，不重新进入底层调研或 UI 头脑风暴。

## Step 1 — 复用公共现实底座

接入当前 DCF 持久层已经提纯的：

```text
FSEvents / Spotlight 文件事实
KnowledgeC / NSWorkspace 活动骨架
IMK + ULog 用户表达事实
ES / eslogger Effect 收据
来源专用高语义事实
```

不得复制对应观察机制。

## Step 2 — 实现第 0 层事实翻译

完成：

```text
主体归因纪律
稳定身份映射
重复事件归并
时间 / 活动段组织
来源锚点保留
```

## Step 3 — 接入个人叙事 AI

让 AI 只读取第 0 层现实文档与必要来源背景，生成详细、清晰、保留认知转折的个人叙事草稿。

## Step 4 — 接入既有人物日历与审核 UI

沿用：

```text
日历入口
交互轨迹
个人叙事草稿
来源引用
用户修改区
批准 / 纠正 / 局部重写 / 拆分 / 合并
```

并保留 AI 原稿 / 用户修正版 / 修改差异。

## Step 5 — 实现 SQLite 正式认知模型

至少完成：

```text
personal_narrative object
immutable revision
review record
current_revision pointer
source_refs
calendar status / time range
draft 与正式 revision 分离
```

## Step 6 — 事务提交正式个人叙事

用户确认后一次事务完成：

```text
审核记录
+
正式不可变 revision
+
current_revision 指针
+
来源关系
```

成功后本功能块结束。

## Step 7 — 由公共认知能力异步建立检索投影

此步骤属于公共认知运行时，不属于个人叙事保存事务，也不阻塞个人叙事功能验收。

# 26. 行为验收

## A. macOS 公共能力没有被重复实现

若实现额外创建第二套全盘 watcher、前台 session detector、全量 ULog 同步器或每 Agent 一套结果观察器，判失败。

## B. 第 0 层无增义

只证明“Chrome URL 变化”的现实，不得翻译成“用户打开该页面”。

只证明“前台 App 变化”的现实，不得自动生成项目目的。

## C. 个人叙事不是日记

真实一天材料中包含多次思考与操作时，输出必须重建主要问题、探索、反馈、转折和理解变化，而不是按小时流水罗列。

## D. 关键差异没有被压掉

真实材料中明确存在的重要方案变化、判断转折、失败所得、成功里程碑、能力 / 方法 / 认识变化不得系统性消失。

## E. 审核本身有认知价值

用户无需重新打开大量原始材料，就能够借审核页重新理清主要过程，并有空间直接纠正或补充新理解。

## F. 当时理解与后来理解不混淆

审核时产生的新理解不得静默回写成过去已经具有的认识。

## G. AI 原稿不冒充正式认知

未经用户确认的 AI 草稿只能存在于审核运行态 / 审核记录中，不能直接生成正式 personal_narrative revision。

## H. 正式正文只有一个权威

用户确认后的个人叙事必须以 SQLite 正式 revision 为权威。

不得同时把 Markdown 与 SQLite 声称为两个可写权威。

## I. 修订历史不可覆写

更新个人叙事必须新增 revision；旧 revision 必须仍可读、可锚定。

## J. 日历无需扫描文件系统

人物日历必须能直接通过数据库时间与状态字段查询。

## K. 检索投影失败不影响正式保存

关闭 embedding / FTS / 多向量处理器后，正式 personal_narrative revision 仍必须能够成功提交。

## L. 功能块结束边界正确

正式 revision COMMIT 后，本功能块必须结束。

即使系统完全没有：

```text
项目叙事
Wiki
知识卡
语言弹药
约束求解器
任何切分器
```

个人叙事功能仍必须完整成立。

# 29. 最高原则

> **系统尽量拥有现实，DCF 自己拥有认知。**

> **macOS 已经维护的现实，不由 DCF 再造第二份权威。**

> **第 0 层负责把事实语言翻译成人能读的现实，不替用户解释意义。**

> **个人叙事不是生活日记，而是自我认知的具象体现，是一个人在世界中生活后留下的具体认知痕迹。**

> **个人叙事要清晰直观，也要记述详实；可以压缩操作噪声，不能压断认知链。**

> **用户审核不是数据库维护，而是重新理解自己并继续产生认知的过程。**

> **AI 原稿可以保留为审核证据，但只有用户确认正文才是正式个人认知。**

> **正式个人叙事进入 SQLite 锚定认知世界；数据库保存认知对象本身，Markdown 只作为导出与交换格式。**

> **正文可以产生新修订，但旧修订不可被静默覆写。**

> **个人叙事功能块的终点只有一个：形成用户确认的正式个人叙事修订并事务提交。**

> **保存以后，搜索、切分、项目叙事、Wiki、知识卡、语言弹药和约束求解全部属于公共认知能力或独立功能块。**
