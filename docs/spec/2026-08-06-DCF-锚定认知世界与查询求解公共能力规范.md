# DCF 锚定认知世界、查询诱导语义场与约束求解公共能力规范

日期：2026-08-06  
状态：当前公共认知能力实施规范  
适用范围：DCF 中已经形成的个人叙事、正式文档及其后续认知对象，怎样被长期保存、按未来未知语义重新找到，并在需要确定组合判断时进入约束求解。

> 本规范把此前“锚定的查询诱导语义场”“简洁位置代数”“约束求解器”“多种切分 / 多种标注”等讨论收束成可实施的公共能力。
>
> 核心不是把 DCF 做成一个万能知识图谱，也不是把所有历史关系提前算好；而是保存稳定认知对象和可重算语义坐标，让未来查询临时生成相关关系，再把需要确定判断的部分编译成约束模型交给求解器。

---

# 0. 最高设计结论

DCF 的长期认知底座采用三层分工：

```text
【锚定认知世界】
SQLite 保存正式认知对象、不可变修订、时间、稳定锚点与人工关系
        ↓
【查询诱导语义场】
对同一认知世界建立多套可重算语义表示；每次查询临时计算“当前问题下什么相关”
        ↓
【约束求解】
只有当任务涉及明确变量、条件、冲突、可行性或优化时，才把相关材料编译成约束模型并确定求解
```

三层分别回答：

```text
锚定认知世界
→ “真实保存了什么，它在哪里？”

查询诱导语义场
→ “在这一次问题下，哪些过去材料可能相关？”

约束求解器
→ “在已经明确的条件下，什么组合真的成立？”
```

硬边界：

> **语义场负责发现，不负责保证。**

> **求解器负责保证，不负责发现。**

> **AI 负责把开放自然语言编译成当前问题需要的结构，但不能把猜测偷偷升级成硬约束。**

---

# 1. 为什么不再把“数据库黑洞”作为主问题

此前 storage-kernel 实验针对完整 AI trace 验证过压缩自索引结构：在大原始语料下，它能够同时吸收正文、精确索引、位置映射与恢复路径，形成明显空间、查询与同步接缝优势。

当前 DCF 的上游已经改变：

```text
巨大原始现实
↓
机器事实翻译
↓
个人叙事 AI
↓
用户审核
↓
只把高价值个人叙事和相关正式文档进入长期认知世界
```

因此长期认知库的数据量被需求本身大幅压缩。

新的优化顺序是：

```text
存储规模
→ 已被“只保存高价值认知对象”大幅吸收

查询性能
→ 随数据规模下降，大量精确算法已经足够快

搜索准确度
→ 成为主要值得投入复杂度的方向
```

所以当前架构不再追求“一个物理索引结构同时解决一切”，而是允许为了搜索准确度保留多套冗余、可重算的语义表示。

---

# 2. 锚定认知世界

“锚定认知世界”不是新的 AI 模型，而是 DCF 的正式长期认知数据库。

当前选择：

> **SQLite 作为认知对象与关系的权威持久层。**

选择理由：

- 单用户、单机主写与 DCF 现实相符；
- 事务、时间查询、日历查询、关系查询、全文索引都天然可用；
- 一个文件即可备份和迁移；
- 足以承载个人十年尺度的高价值叙事与文档；
- 可以让所有语义索引都成为可删除投影，而不是第二份事实权威。

SQLite 保存“认知对象本身”；语义模型只保存“未来怎样重新找到它”的机器表示。

---

# 3. 正式认知对象与不可变修订

认知对象使用“稳定对象 + 不可变修订”模型。

逻辑结构：

```text
认知对象
├─ object_id             稳定身份
├─ kind                  personal_narrative / document / ...
├─ current_revision_id   当前正式修订
└─ 生命周期元数据

认知修订
├─ revision_id           不可变身份
├─ object_id
├─ content               正文
├─ created_at
├─ author_kind           AI / user / system / import
├─ source_refs
└─ content_hash
```

原则：

> **正文可以有新版本，但已经形成过的修订不被静默覆盖。**

用户后来修改个人叙事时，形成新的 `revision_id`；旧修订仍然存在。

这使“当时理解”和“后来理解”可以同时存在，也让过去的切分、标注和搜索锚点永远有明确落点。

---

# 4. 稳定文本锚点

所有需要指向正文局部的机器关系，必须落回稳定锚点。

当前逻辑锚点：

```text
revision_id
+
start_offset
+
end_offset
+
span_hash / excerpt_hash（校验）
```

偏移以规范化 UTF-8 正文的字节位置为当前首选实现语义。

锚点只在对应不可变修订内部成立。

如果正文产生新修订：

```text
旧标注
→ 仍然指向旧 revision

新修订
→ 由需要的处理器重新建立新锚点
```

禁止通过“修改正文后强行平移旧 offset”制造伪连续性。

核心原则：

> **语义可以重算，原文位置必须可证明。**

---

# 5. 标注不是正文，也不是唯一分类

DCF 允许同一修订拥有任意多套标注。

逻辑结构：

```text
标注集 annotation_set
├─ set_id
├─ producer_id
├─ producer_version
├─ purpose / namespace
├─ rule_hash / config_hash
└─ created_at

标注 annotation
├─ annotation_id
├─ set_id
├─ revision_id
├─ start_offset
├─ end_offset
├─ kind
├─ payload（可选）
└─ source / confidence（可选）
```

例如同一篇个人叙事可以同时拥有：

```text
project-view/v1
project-view/v2
wiki-view/v1
knowledge-view/v3
ammo-view/v1
semantic-window/v2
human-markup/v1
```

公共层不宣布哪一种切分是“正确切法”。

原则：

> **源材料统一，解释可以并存。**

> **切分是视图，不是本体。**

---

# 6. 查询诱导语义场的工程定义

“查询诱导语义场”不是一个需要永久保存的场对象。

它的工程含义是：

> **每次查询到来时，系统针对一批锚定认知单元临时计算当前问题下的相关度，并返回带真实正文锚点的候选集合。**

形式上：

```text
输入：query q
输入：认知锚点集合 P
输入：一套或多套可重算语义表示 Z

计算：score(q, p_i | Z, 当前查询条件)

输出：
[(revision_id, start, end, score, method, evidence), ...]
```

“场”只是表示：当前查询会让整个材料空间获得一组不同的相关度强弱。

查询结束后，这组相关度默认不进入长期事实层。

---

# 7. 为什么不预存所有语义关系

禁止把未来可能出现的语义维度全部固化为永久关系边：

```text
A 相似 B
A 支持 C
A 反驳 D
A 是某种能力
A 属于某种项目
A 体现某种方法
……
```

原因：

- 材料数量增加时，两两关系潜在接近平方增长；
- 未来查询维度不可预知；
- 新模型和新理解会改变“相关”的定义；
- 永久关系会把当前模型判断伪装成历史事实。

因此长期保存：

```text
认知正文
+
稳定锚点
+
人工 / 明确业务关系
+
可重算语义表示
```

查询时才生成：

```text
“这次问题下，A 与 B / A 与 q 有多相关？”
```

核心原则：

> **材料永久存在；开放语义关系按需生成。**

---

# 8. 语义表示全部属于可重算投影

以下均不得成为认知权威：

```text
全文索引
词法索引
字符三元组索引
稠密语义向量
多向量 / 词元级语义表示
查询扩展缓存
重排结果
模型评分
自动切分
自动标签
```

每套语义表示必须绑定：

```text
representation_set_id
producer / model_id
model_version
config_hash
source_revision_id / source_span
created_at
```

模型升级时允许：

```text
旧表示仍存在
+
新表示并行生成
+
真实查询评估后切换
+
旧表示再删除
```

不允许因为更换语义模型而修改正式个人叙事正文。

---

# 9. 第一阶段语义场：词法召回

词法召回负责字面、术语、名称、编号与原话。

当前基础实现使用 SQLite FTS5，但分成至少两类独立能力：

```text
词法全文检索
→ BM25 / 词语级匹配

字符三元组检索
→ substring / 半截词 / 中英混合 / 型号 / 文件名
```

中文分词器不是架构常量。

可以通过真实查询评估选择：

```text
自定义中文分词
字符三元组
二者组合
```

禁止因为“有语义模型”而删除词法检索；专有词、ID、路径、原话等仍然是稠密语义模型的弱点。

---

# 10. 第二阶段语义场：稠密语义表示

“稠密语义表示”指把文本映射成固定长度语义向量，用于按含义召回。

当前个人认知规模下，首选：

> **精确全量向量比较，而不是近似最近邻索引。**

原因：

```text
个人高价值认知规模较小
↓
精确扫描已经足够快
↓
没有必要为了互联网级规模主动牺牲召回
```

因此初版禁止因为习惯直接引入 HNSW / IVF 等近似搜索结构。

只有真实规模测试证明精确扫描已经无法达到交互要求时，才允许把近似搜索作为可替换加速投影引入。

---

# 11. 第三阶段语义场：后期交互

“后期交互（Late Interaction）”在 DCF 内称为：

> **词元级后期交互。**

它不把整段材料压成唯一平均向量，而为一个材料保留多个细粒度语义表示；查询到来后，查询中的不同语义单位分别寻找材料中响应最强的位置，再组合相关度。

它解决：

```text
一篇叙事同时包含多个主题
整段单向量把细节平均掉
查询关心的只是其中某个局部含义
```

当前把 ColBERT / MaxSim 一类模型视为第一批实验候选，但协议不得绑定具体模型。

数据规模允许时优先做精确后期交互，不先引入近似召回。

是否晋级为正式检索层，只由真实 DCF 查询集上的准确度提升决定。

---

# 12. 第四阶段：联合阅读重排

“交叉编码重排（Cross-Encoder Reranking）”在 DCF 内称为：

> **联合阅读重排。**

它把：

```text
当前问题
+
候选原文
```

放在同一次模型判断中，直接评估当前问题与候选原文的关系。

它是昂贵但高质量的最后判断层。

当前使用方式：

```text
多路召回
↓
候选合并
↓
词元级后期交互（如果启用）
↓
联合阅读重排
↓
返回少量高质量真实锚点
```

联合阅读模型只改变查询排序，不修改历史认知。

---

# 13. 查询条件化评分器属于实验扩展

未来允许实验更强的“查询条件化评分器”：查询不仅生成一个向量，而是生成当前问题专用的评分函数 / 小型网络，再对文档表示打分。

例如 Hypencoder 一类路线可以进入实验。

但当前规范不把它设为 P0 依赖，因为：

- 工程成熟度低于 FTS / 稠密向量 / 后期交互 / 联合阅读；
- 是否对 DCF 真实查询显著优于后期交互仍需数据验证；
- 公共协议已经允许以后无痛加入。

它只能作为新的可重算语义算子，不得改变锚点世界 Schema。

---

# 14. 多路召回不是固定权重公式

首版采用可解释的候选并集 + 排名融合，默认优先使用倒数排名融合（Reciprocal Rank Fusion，DCF 中文名：**倒数排名融合**）。

原因：不同检索器的分数尺度不可直接比较，而排名更稳定。

逻辑流程：

```text
词法 Top-K
+
字符 Top-K
+
稠密语义 Top-K
+
其他视图 Top-K
↓
候选并集
↓
倒数排名融合
↓
后期交互 / 联合阅读重排
```

具体 K、融合常数、是否启用某一检索器，都必须由真实查询评估决定，不在架构层拍脑袋冻结。

---

# 15. 查询结果必须回到真实锚点

任何语义检索最终必须返回：

```text
object_id
revision_id
start_offset
end_offset
score
retrieval_method / representation_set
```

必要时附：

```text
为什么命中
哪些查询词元 / 语义视角产生响应
哪一套检索器贡献候选
```

禁止只返回：

> “系统记得你以前认为 X。”

正确行为是：

> “当前查询认为 `revision R / span S` 高度相关；这是对应原文。”

核心原则：

> **语义负责寻找，锚点负责证明。**

---

# 16. 查询关系默认是临时关系

本次查询发现：

```text
材料 A 与材料 B 可能体现同一种思考模式
```

默认只存在于本次查询结果中。

如果用户或某个正式功能决定把这种理解保存下来，应新增一个带时间和来源的认知 / 标注记录：

```text
2028-xx-xx：当前认为 A 与 B 具有关系 R
```

禁止回写：

```text
2026 的 A 从一开始就“拥有”关系 R
```

这样保持：

> **关系可以晚于材料出现；新理解记录在新理解产生的时间。**

---

# 17. 约束求解公共能力

约束求解不是所有认知任务的必经环节。

只有任务符合以下问题签名时才进入：

```text
存在明确候选对象 / 决策变量
+
存在必须满足的条件
+
存在互斥 / 依赖 / 数值边界 / 逻辑关系
+
需要判断可行、冲突或最优组合
```

典型：

```text
项目涌现
架构选择
资源配置
任务排程
方案兼容性
决策比较
当前原则自洽性检查
```

通常不需要求解器：

```text
普通 Wiki 编写
普通知识卡提取
普通项目叙事编织
普通语义搜索
```

---

# 18. 语义场与求解器之间必须有“约束编译器”

求解器不能直接读取自然语言个人叙事。

中间增加：

> **约束编译器。**

当前由 AI 承担开放语义理解，但输出必须是严格结构化的临时约束包。

输入：

```text
用户当前问题
+
语义场返回的相关原文锚点
+
用户显式提供的条件
```

输出逻辑结构：

```text
实体 / 候选
决策变量
硬约束
软约束
目标函数
来源锚点
不确定项
```

每一条“来自历史材料”的约束都必须携带来源锚点。

---

# 19. 不确定自然语言不得自动升级成硬约束

AI 编译时必须区分：

```text
用户当前明确要求
→ 可以成为硬约束

系统确定事实
→ 可以成为硬约束

历史中用户明确且适用条件一致的约束
→ 可以成为硬约束候选

AI 推断 / 模糊偏好 / 语义相关
→ 只能作为软约束或待确认项
```

禁止：

```text
“这段叙事看起来用户很在意离线”
↓
偷偷编译成
必须离线 = true
```

求解器的确定性只能建立在确定输入之上。

核心纪律：

> **不要让不确定 LLM 做确定的事，也不要把不确定 LLM 的输出伪装成确定约束。**

---

# 20. 求解器接口

公共逻辑接口：

```text
solve(constraint_package)
→
status: satisfiable / unsatisfiable / optimal / unknown
solution
objective_values
violated_soft_constraints
unsat_core（如果引擎支持）
```

初版通用求解器优先选择 SMT（可满足性模理论）类别，默认候选为 Z3。

原因：DCF 当前更常出现：

```text
布尔条件
整数 / 实数边界
蕴含
互斥
依赖
多目标优化
```

未来如果某个功能形成纯排程 / 指派等问题，可通过同一公共接口接入 CP-SAT 等专用求解器；不得因此改动上层认知结构。

---

# 21. 求解结果必须带回来源

求解器输出“方案 X 可行”不够。

最终解释至少能够追踪：

```text
方案使用了哪些候选
每条关键约束来自哪里
哪些是用户当前明确输入
哪些来自确定系统事实
哪些来自历史叙事
哪些只是软偏好
为什么某个方案被淘汰
如果无解，哪组约束构成冲突
```

因此完整路径是：

```text
自然语言问题
↓
查询诱导语义场找料
↓
约束编译器建立临时模型
↓
求解器确定求解
↓
AI 把结果解释回自然语言
↓
每个关键结论仍能回到原始锚点
```

---

# 22. 公共调用形态

DCF 功能块使用公共能力时，只依赖以下语义接口，不依赖具体搜索引擎或求解器实现。

## 22.1 认知查询

```text
认知查询(
  query,
  scope,
  time_range?,
  top_k?,
  requested_views?
)
→ 锚定候选集合
```

## 22.2 约束编译

```text
约束编译(
  problem,
  anchored_candidates,
  explicit_user_constraints
)
→ constraint_package
```

## 22.3 确定求解

```text
确定求解(constraint_package)
→ solution / conflict / optimum
```

功能块可以只使用第一项。

只有真正需要组合确定性的功能才使用后两项。

# 23. 典型功能怎样组合公共能力

## 23.1 项目叙事

```text
查询诱导语义场
→ 找项目演化、价值、成果、失败与转折材料
→ 项目叙事 AI 编织
```

默认不需要求解器。

## 23.2 Wiki

```text
查询诱导语义场
→ 找解释主题所需历史材料
→ Wiki AI 组织
```

规范 / 规则自洽检查时可以可选调用求解器。

## 23.3 知识卡

```text
查询诱导语义场
→ 找多个支持同一可迁移原则的案例
→ AI 归纳
→ 形成知识卡
```

默认不需要求解器。

## 23.4 项目涌现

```text
当前目标 / 缺口
↓
查询诱导语义场
→ 找已有能力、成果、工具、失败经验、未满足需求
↓
约束编译
↓
求解器
→ 哪些组合已经形成闭环 / 还缺哪个硬条件
↓
AI 生成候选项目解释
```

## 23.5 架构选择

```text
需求
↓
语义场找历史原则、失败、已有技术事实
↓
AI 编译硬约束 / 软约束 / 候选构件
↓
求解器排除非法组合并优化残差
↓
AI 回译架构建议
```

# 24. 个人规模是这里的结构优势

DCF 不需要照搬互联网级检索系统为了十亿文档作出的妥协。

当前原则：

```text
准确度优先
>
存储大小优化
>
互联网级吞吐优化
```

因此在数据规模允许时优先：

```text
精确向量扫描
精确多向量后期交互
更宽候选集合
更强联合阅读重排
多套语义表示并存
```

而不是：

```text
过早 ANN
过早量化
过早只留一种 embedding
为了节省几十 MB 删除检索视角
```

核心利用方式：

> **因为只服务一个人的高价值认知，DCF 可以把大型搜索系统为规模牺牲掉的精度重新买回来。**

---

# 25. 搜索准确度成为正式评估资产

必须建立：

> **DCF 真实认知查询集。**

查询必须来自用户真实会问的问题，而不是模型自造 benchmark。

例如：

```text
“之前哪里开始认为项目拥有关系而不拥有材料？”
“什么时候把复杂度吸收升格成架构判断标准？”
“有哪些案例是通过改变问题定义而不是增强技术来消掉复杂度？”
“之前哪个失败后来变成了另一个项目的能力？”
```

每条查询人工标注：

```text
强相关锚点
可接受相关锚点
明显误召回
```

核心指标：

```text
Top-1 命中
Recall@K（前 K 个结果召回率）
MRR（平均倒数排名）
nDCG@K（前 K 个排序质量）
锚点准确率
```

任何新的：

```text
分词器
embedding
切分视图
后期交互模型
融合方法
联合阅读模型
查询扩展策略
```

都必须用同一真实查询集比较后才允许晋级。

---

# 26. 求解器必须拥有独立确定性测试集

求解能力不能用“AI 看起来解释得很好”验收。

必须维护明确输入与预期结果：

```text
可满足案例
不可满足案例
已知最优案例
互斥条件
依赖条件
数值边界
软约束冲突
```

验收至少包括：

```text
相同约束包重复求解结果一致
硬约束绝不被软优化违反
无解案例正确返回无解
可用时能返回最小冲突核心
已知最优案例得到正确目标值
```

AI 只负责把自然语言编译成模型；求解正确性由确定性测试验证。

---

# 27. 端到端行为验收

至少建立四类真实行为：

### A. 开放语义回忆

用户使用一个历史中从未存在过的新描述方式提问，系统仍能找到真正相关的过去叙事，并返回正确原文锚点。

### B. 多义材料

一篇同时包含多个主题的叙事，在不同查询下能够命中不同局部 span，而不是总返回整篇平均意义。

### C. 新项目涌现

系统能从分散的历史能力 / 成果 / 当前需求中找候选，并由求解器明确区分：

```text
已经满足
缺一个条件
存在硬冲突
```

### D. 架构选择

在给定显式硬约束和历史经验后，求解器能够排除违反规则的候选；最终解释中的关键条件都能回到用户当前输入或历史锚点。

---

# 28. 数据更新与失败恢复

正式认知对象写入成功不依赖所有语义投影同时成功。

正确流程：

```text
正式 revision 事务提交
↓
进入“需要建立检索投影”队列
↓
FTS / 稠密表示 / 后期交互表示分别生成
↓
失败可重试
```

如果任何语义模型挂掉：

```text
正式个人叙事仍然存在
词法搜索仍然可用
其他语义表示不受影响
```

禁止把“embedding 写入失败”升级成“个人叙事保存失败”。

---

# 29. 不建立统一永久切分层

本规范明确否决：

```text
个人叙事
↓
唯一标准自包含切分
↓
所有未来功能必须消费它
```

允许：

```text
个人叙事修订
├─ 原段落视图
├─ 滑动语义窗口
├─ project-view/v1
├─ wiki-view/v2
├─ knowledge-view/v3
└─ 任意未来视图
```

不同视图都只是一套可重算标注 / 检索单元。

未来功能可以：

- 直接查询原始个人叙事；
- 只查询自己的视图；
- 同时查询多种视图；
- 完全忽略其他功能产生的切分。

---

# 30. 不建立中央语义本体

公共层禁止提前规定：

```text
所有“能力”有哪些类型
所有“项目关系”有哪些枚举
所有“知识”有哪些类别
所有“价值”有哪些标签
```

这些属于具体功能或当前查询的解释空间。

公共层只保证：

```text
稳定认知对象
不可变修订
稳定锚点
多套可重算标注
多套可重算语义表示
查询时相关度
```

这样未来新增认知维度不需要迁移十年历史 Schema。

# 31. 实施顺序

## Phase 1 — 锚定认知数据库

实现 SQLite：

```text
认知对象
认知修订
来源引用
标注集
标注
```

正式个人叙事迁入该权威模型。

## Phase 2 — 词法查询基线

实现：

```text
FTS5
字符三元组
时间 / kind / revision 过滤
稳定 span 回落
```

建立真实查询集。

## Phase 3 — 稠密语义查询

实现：

```text
可替换 embedding 适配器
精确向量扫描
多路候选融合
```

必须与 Phase 2 基线做真实查询准确度比较。

## Phase 4 — 词元级后期交互

在真实查询集证明多义材料 / 模糊回忆仍有明显残差后，引入 ColBERT / MaxSim 类候选。

只在准确度有实证提升时晋级。

## Phase 5 — 联合阅读重排

对有限候选增加强模型联合阅读，测量 Top-1 / 排序质量提升与成本。

## Phase 6 — 约束编译 + SMT 求解

先选择一个明确功能作为首个真实用例，优先：

```text
架构选择
或
项目涌现
```

实现：

```text
锚定候选 → 约束包 → Z3 / SMT → 可追溯结果
```

禁止一开始同时给所有认知功能加 Solver。

# 34. 最高原则

> **锚定认知世界保存“我真实确认过什么”；语义场计算“这一次什么可能相关”；求解器计算“这些明确条件下什么真的成立”。**

> **不要储存未来所有答案、分类和关系；储存足以让未来重新生成关系的认知原文、锚点和可替换语义表示。**

> **语义负责寻找，锚点负责证明。**

> **开放世界交给查询与 AI，封闭规则交给求解器。**

> **语义模型和切分规则都可以换；正式认知历史不随模型升级重写。**

> **个人规模不是搜索系统的缺点，而是允许 DCF 放弃互联网级近似、把计算预算换成准确度的结构优势。**
