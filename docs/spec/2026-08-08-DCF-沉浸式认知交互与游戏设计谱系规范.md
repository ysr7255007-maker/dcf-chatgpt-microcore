# DCF 沉浸式认知交互与游戏设计谱系规范

日期：2026-08-08  
状态：**当前沉浸式交互专项权威**

本文规定 DCF 的全景沉浸交互应承担什么认知责任、从哪里学习交互、如何判断方向是否成立。

本文不冻结具体引擎、布局、组件、动画、美术风格或页面结构。任何具体 UI 实现继续服从：

> **Function Hard, UI Soft —— 功能硬化，界面软化。**

---

# 1. 核心定义：不是游戏化，而是游戏级认知交互

DCF 不把知识管理软件加上积分、成就、角色或动画称为“游戏化”。

当前正式目标是：

> **把游戏工业已经成熟的高带宽人机交互能力，用于帮助用户理解、调查和操纵自己的真实认知世界。**

剧情、推理、文字与调查类游戏尤其重要，因为它们长期面对与 DCF 高度相似的问题：

```text
人物很多
事件跨时间发生
材料零散
关系复杂
真假并存
用户不可能一次记住全部信息
关键意义会随新证据改变
复杂内容必须逐步进入注意力
```

优秀游戏不能要求玩家先学习内部数据结构后才能理解剧情，因此会主动承担：

```text
注意力调度
渐进揭示
外置记忆
状态反馈
关系表达
矛盾突出
上下文恢复
直接操纵
推理结果表达
复杂度分层
```

DCF 的沉浸式交互采用同样的责任分配：

> **专业能力可以要求系统复杂，但不能要求用户替系统承担理解复杂度。**

---

# 2. 剧本替换测试

全景沉浸交互建立一个长期产品判据：

> **如果把 DCF 底层采集到的真实生活材料，替换成一套优秀剧情 / 推理游戏作者精心设计的完整剧本数据，那么 DCF 上层应当具备把它呈现为一款真正成立的好游戏的能力。**

也可以反过来理解：

> **DCF 像一套优秀剧情 / 推理游戏的认知交互系统，只是剧本不是编剧预先写好，而是来自用户日常生活、项目和工作中真实发生的材料。**

因此以下结果不能通过这一判据：

```text
原料已经具有优秀悬疑 / 推理结构
↓
DCF 只呈现为
搜索框 + Wiki + 时间线 + 关系图 + AI 摘要
```

这说明系统只完成了“信息可访问”，没有完成“帮助人理解与参与”。

剧本替换测试是产品方向判据，不是自动化单元测试，也不要求 DCF 真的成为商业游戏产品。

---

# 3. 现实数据与游戏剧本的关键差异

游戏剧本由作者主动安排：

```text
何时出现证据
何时制造矛盾
哪些人物值得记住
哪些信息暂时隐藏
何时回看旧材料
何时形成转折
```

现实生活没有编剧。真实材料天然包含：

```text
大量普通事件
大量重复
噪声
未完成事件
当时看似无关但后来变重要的材料
只有几周或几个月后才显现的关系
```

因此 DCF 比普通剧情游戏多出一个关键责任：

> **从无导演、无剪辑的真实材料中恢复当前值得被理解和体验的结构。**

当前可把这一职责理解为 Narrative Compiler（叙事编译）：

```text
真实材料
↓
AI 开放理解 + 确定性事实约束
↓
当前值得关注的人 / 项目 / 事件
关系
问题
矛盾
判断
转折
未解决线索
↓
交互投影
```

“叙事编译”不获得篡改现实的权力。

正式边界：

> **可以重新组织意义，不能伪造底层事实。**

> **可以产生新的解释，不能静默改写过去存在过的解释。**

> **所有重要叙事投影必须能够穿透回材料、证据层级和形成时间。**

因此表现可以高度戏剧化，证据纪律必须严格。

---

# 4. DCF 的核心认知动作应先于 UI 控件

沉浸式交互不先从“页面有哪些组件”开始设计。

先识别用户正在进行的认知动作，例如：

```text
观察
调查
追踪
关联
提出假设
质疑
出示证据
比较
反证
验证
裁决
保留异议
改变判断
回看演化
委派调查
接管调查
```

再寻找游戏工业中已经成熟的交互语法。

禁止从内部数据结构直接推导 UI：

```text
数据库有字段
→ UI 就要求用户填写字段

系统有 relation_type
→ 用户必须理解 relation_type

系统内部有多个模块
→ 导航必须暴露同样的模块层级
```

正式原则：

> **用户操作语言应尽量接近用户自己的思考语言，而不是系统内部实现语言。**

例如用户的自然动作可以是：

```text
“这个判断我不信了”
```

系统负责把它落实为证据比较、关系追加、认知变化记录等内部操作；不要求用户先学会内部本体论。

---

# 5. 交互参考的证据优先级

DCF 不自行发明一套封闭的“专业认知软件 UX”。

交互方案按以下证据优先级研究。

## 5.1 第一优先：成熟成品游戏

最高权重来自已经被真实玩家长期使用和验证的游戏。

重点不是模仿美术，而是拆解：

```text
它解决了什么认知困难
玩家此刻知道什么
系统隐藏了什么
何时给反馈
如何外置记忆
如何表达关系
如何让玩家自己完成推理而不是直接给答案
如何让复杂度逐步进入注意力
```

当前特别值得持续研究的谱系包括但不限于：

```text
《逆转裁判》
→ 主张、证词、矛盾、出示证据、认知推进

《弹丸论破》
→ 高密度观点碰撞、强反馈、注意力聚焦

《The Roottrees are Dead》
→ 从零散材料恢复人物与关系

《The Incident at Galley House》
→ 从过去残片重建事件

《The Case of the Golden Idol》
→ 外置推理、人物 / 事件 / 关系拼接

《Return of the Obra Dinn》
→ 碎片化观察、身份与事件重建

《Outer Wilds》
→ 传闻图、空间探索、知识本身推进进程

《Her Story》
→ 用户主动决定查询方向并逐步展开叙事
```

这些名称是交互研究入口，不是要求 DCF 复制其具体表现。

## 5.2 第二优先：设计者复盘与案例研究

包括：

```text
GDC 演讲
Postmortem（项目复盘）
设计师访谈
开发日志
经典案例教程
```

这一层用于解释成熟游戏为什么这样设计、哪些方案曾失败、最后如何修正。

## 5.3 第三优先：游戏设计理论与指南

包括：

```text
经典游戏设计教材
Narrative Design（叙事设计）
Game Feel（游戏手感）
UX / Cognitive Design（认知设计）
Game Accessibility（游戏无障碍）指南
```

理论用于抽象已被现实作品支持的规律，不得反过来压过真实使用证据。

# 6. DCF Interaction Pattern Library

后续应逐步维护 DCF Interaction Pattern Library（DCF 交互模式库）。

模式库按“认知问题”组织，而不是按 UI 控件组织。

每个模式至少记录：

```text
模式名称
要解决的认知问题
成熟游戏来源
核心交互结构
适用 DCF Capability / 场景
用户需要保持的判断权
不得退化成什么
已验证 / 未验证状态
```

例如可以出现：

```text
Contradiction Presentation
矛盾出示

Externalized Deduction
推理外置

Progressive Reveal
渐进揭示

Context Recovery
上下文恢复

Direct Evidence Manipulation
直接证据操纵
```

模式名称不是固定 API；真实使用可以继续改变和合并这些抽象。

---

# 7. 游戏引擎的当前地位

游戏引擎进入 DCF 的研究范围，理由不是“DCF 要做成游戏”，而是：

> **游戏引擎长期承载了软件行业中最复杂、最高反馈密度的人机交互之一。**

Godot 等引擎因此可以作为全景沉浸 Surface 的候选 Interactive Runtime（交互运行时）研究。

但当前尚未做出以下决策：

```text
DCF 全景沉浸交互必须使用 Godot
所有 DCF UI 改用游戏引擎
Godot SceneTree 成为 DCF 事实世界
嵌入式交互和环境微交互也必须使用同一技术
```

正式边界继续是：

```text
DCF Capability / State / Action
        ↓
Surface Contract
        ↓
可替换交互 Runtime
        ↓
用户看到和操作的世界
```

游戏引擎可以拥有视觉、空间、动画和临时交互状态，但不得成为 DCF 业务事实源。

---

# 8. 三种交互 Capability 的关系

三种交互 Capability 保持不变：

```text
全景沉浸交互
嵌入式交互
环境微交互
```

本规范主要提高“全景沉浸交互”的目标上限。

它不要求三种交互共享同一物理技术。

可能的实现形态可以是：

```text
全景沉浸交互
→ 游戏引擎 / 自定义交互 Runtime / Web 等候选

嵌入式交互
→ 浏览器、IDE Panel、Web / Native Panel 等

环境微交互
→ 菜单栏、悬浮入口、系统级低注意力交互等
```

这些都只是候选实现，不在本规范冻结。

---

# 9. 对旧固定 UI 规范的处理

`2026-08-05-DCF-叙事日历与三Surface交互规范.md` 中关于以下内容的业务语义继续有效：

```text
个人叙事草稿
人工审阅
正式个人叙事
历史不可静默覆写
后续认知追加
来源穿透
```

但其中把具体 UI 形态写成“已冻结”的内容，例如：

```text
固定三列布局
固定论坛回复式结构
固定日历视觉
固定 Panel / Sidebar / 悬浮球形态
```

不再具有当前 UI 形态约束力。

这些内容保留为当时的设计记录和候选实现。

当前 UI 形态以：

> **Function Hard, UI Soft + 本规范的游戏级认知交互目标**

为准。

# 10. 当前验收问题

一个全景沉浸交互候选至少应回答：

1. 用户是否主要在理解自己的问题，而不是理解 DCF 怎么操作？
2. 复杂度是否按当前注意力和认知需要逐步进入，而不是一次暴露？
3. 重要关系、矛盾、状态变化是否能被直接感知和操作？
4. 是否能外置用户不值得长期占用工作记忆的信息，而不替用户做掉关键判断？
5. 是否能够从任何重要叙事、关系和判断穿透回真实材料与形成历史？
6. 如果输入换成精心设计的优秀推理剧本，当前交互是否有潜力形成真正成立的游戏体验？
7. 当输入换回真实生活数据时，系统是否仍然只发现意义，而不为了戏剧性制造事实？
8. 删除当前完整 UI 并重做一种完全不同的表现，Capability、认知历史和业务正确性是否仍然成立？

如果第 6 问明显失败，则说明系统还停留在“展示数据”的专业软件范式，而没有达到当前沉浸式交互目标。

---

# 11. 当前施工纪律

1. **先设计认知动作，再设计 UI 控件。**
2. **优先研究成熟游戏如何解决同类认知问题。**
3. **成品真实体验优先于设计理论。**
4. **不模仿皮肤，提取交互语法。**
5. **不把内部本体论转嫁给用户。**
6. **不为了戏剧性篡改事实。**
7. **叙事投影必须可追溯。**
8. **历史认知不得静默覆写。**
9. **游戏引擎只是可替换 Surface Runtime 候选。**
10. **剧本替换测试用于约束产品上限，不用于冻结具体表现。**
