# DCF 沉浸式认知交互与游戏设计谱系规范

日期：2026-08-09  
状态：**当前沉浸式交互专项权威**

本文规定 DCF 的全景沉浸交互应承担什么认知责任、从哪里学习交互、如何判断方向是否成立，并记录 2026-08-09 对“游戏级交互、可编辑叙事、SillyTavern 与 Godot”讨论后的收口。

本文不冻结具体引擎、布局、组件、动画、美术风格或页面结构。任何具体 UI 实现继续服从：

> **Function Hard, UI Soft —— 功能硬化，界面软化。**

---

# 1. 核心定义：不是游戏化，而是游戏级认知交互

DCF 不把知识管理软件加上积分、成就、角色或动画称为“游戏化”。

当前正式目标仍是：

> **把游戏工业已经成熟的高带宽人机交互能力，用于帮助用户理解、调查和操纵自己的真实认知世界。**

剧情、推理、文字与调查类游戏尤其重要，因为它们长期面对与 DCF 高度相似的问题：

```text
人物很多
事件跨时间发生
材料零散
关系复杂
真假并存
用户不可能一次记住全部信息
关键意义会随新证据改变
复杂内容必须逐步进入注意力
```

优秀游戏会主动承担：

```text
注意力调度
渐进揭示
外置记忆
状态反馈
关系表达
矛盾突出
上下文恢复
直接操纵
推理结果表达
复杂度分层
```

正式原则：

> **专业能力可以要求系统复杂，但不能要求用户替系统承担理解复杂度。**

但这一原则不再被解释为：

> “DCF 的每一个 Capability 都必须优先做成游戏。”

当前收口是：

> **游戏工业是交互技术谱系和产品上限来源，不是所有 Capability 的强制外观或强制玩法。**

---

# 2. 剧本替换测试继续成立，但只约束上限

全景沉浸交互继续保留长期产品判据：

> **如果把 DCF 底层采集到的真实生活材料，替换成一套优秀剧情 / 推理游戏作者精心设计的完整剧本数据，那么 DCF 上层应当具备把它呈现为一款真正成立的好游戏的能力。**

该判据用于防止 DCF 在已经拥有高质量内容时仍退化成：

```text
搜索框
+ Wiki
+ 时间线
+ 静态关系图
+ AI 摘要
```

但需要明确：

```text
剧本替换测试
≠ 要求普通日常材料天然好玩
≠ 要求所有现实任务都必须被游戏化
≠ 要求立即解决“如何把平凡生活自动写成好故事”
```

讲述方式、叙事质量、戏剧强度以后仍可替换和优化。

当前只要求：

> **当输入本身足够优秀时，交互层不能成为表现能力的天花板。**

---

# 3. 现实 Canon 与玩家解释权

本轮形成一个更明确的叙事模型：

```text
真实数据 / 真实事件
→ Canon Events（不可修改的剧情节点）

Canon 之间的意义、关系、因果、角色定位、章节组织
→ Interpretation（当前解释，可变化）
```

最简表达：

> **事实节点：硬。节点之间的解释：软。**

例如以下事实一旦真实发生：

```text
8 月 3 日讨论方案 A
8 月 5 日执行实验 B
8 月 7 日放弃 A
8 月 8 日转向 C
```

DCF 不允许后来把 B 改成“从未发生”。

但可以同时存在不同阶段的理解：

```text
当时认为：B 证明 A 失败
后来认为：B 其实验证了 A，真正导致转向的是别的因素
更后来认为：关键并不是 A 对错，而是目标本身发生了变化
```

这些解释不是互相覆盖，而是形成有时间、有来源的认知演化。

正式原则：

> **现实不断写入不可修改的 Canon Events；用户拥有这些事件之间的叙事解释权。**

> **用户可以随时修改当前故事，因此产生新的叙事分支 / 世界线；旧解释继续作为历史认知存在。**

这与 DCF 长期纪律一致：

```text
原始材料可追溯
事实不得伪造
历史认知不得静默覆写
后来理解只能追加为新的解释与变化记录
```

---

# 4. 从原始材料到当前故事的顺序

DCF 不能假定现实问题、关系和故事已经预先知道。

正确顺序是：

```text
原始现实材料
↓
确定性事实约束
↓
AI 提出暂定组织 / 关系 / 意义
↓
用户在实际使用中接受、修改、否定、拆分、合并、重述
↓
形成当前 Reality Model / Narrative Model
↓
新的现实继续进入
↓
当前解释再次变化
```

因此 AI 的作用不是一次性“写出正确故事”。

AI 负责提出当前版本；用户通过真实交互不断校准它。

但必须避免把“纠正 AI”本身误当成核心娱乐机制。

正式判断：

> **用户校准现实模型是正常交互产生的副产品，不是必须被包装成游戏目标的劳动。**

---

# 5. 前台是故事，后台可以是图

本轮明确否定一个容易走偏的方向：

> **不能因为底层存在人物、事件、关系和证据图，就把“画关系图 / 修关系图”直接当成主要游玩界面。**

像《The Roottrees Are Dead》这样的作品，核心乐趣来自：

```text
关系未知
↓
玩家重建关系
↓
正确答案逐步锁定
```

DCF 的情况不同：

```text
大量事实关系已经可以从真实数据中获得
↓
真正开放的是这些事实共同意味着什么
↓
用户主要是在塑造 / 修正当前叙事
```

因此：

> **Roottrees 更适合作为“固定事实 + 玩家认知参与”的数据哲学参考，而不是 DCF 的核心玩法模板。**

当前界面原则可以压缩为：

> **后台可以是图，前台应该是戏。**

底层可以维护：

```text
事件节点
人物节点
项目节点
时间
证据
关系候选
叙事版本
历史解释
```

但用户日常面对的高层交互可以是：

```text
剧情
章节
人物
场景
旁白
回忆
重演
可直接修改的当前解释
```

关系图、时间线、证据板等可以作为辅助 Surface，需要时被掀开，而不是默认把用户关在知识图谱编辑器中。

---

# 6. 可编辑叙事：不是预设分支点，而是随时改故事

传统 Galgame / ADV 往往由作者预先决定：

```text
这里出现选项
→ 玩家选 A / B / C
→ 进入预设分支
```

DCF 不需要预先判断“哪些时刻必须让用户做选择”。

当前更适合的模型是：

> **用户可以在任何时刻修改当前叙事，因此从当前理解处产生新的分支。**

例如系统叙述：

> “实验 D 使这条路线第一次真正遭到怀疑。”

用户可以直接表达：

> “不对，D 并没有让我怀疑它；真正改变判断的是 C 后来的那句话。”

系统随后重新组织：

```text
转折点
人物角色
前后事件权重
伏笔
章节结构
当前解释
```

但不改变底层 Canon。

因此 DCF 的目标不是：

> “把故事最终编正确。”

而是：

> **让当前版本越来越接近用户此刻真正认可的理解，同时完整保留理解是如何变化的。**

---

# 7. 近期叙事交互实验：SillyTavern

SillyTavern 当前具有很强的直接参考和实验价值，因为它已经提供了一组成熟的 AI 叙事干预机制：

```text
Edit
Swipe / alternative reply
Regenerate
Continue
Branch
Checkpoint
Persona
Scenario / Author's Note
World Info / Lorebook
Extension / Event
```

这些机制证明：

> **用户可以一边消费 AI 生成叙事，一边随时编辑、重生成、分支和维护世界上下文，而不必把这种行为体验成数据库标注。**

DCF 与 SillyTavern 的关键差异是：

```text
SillyTavern
→ 虚构故事本身可以被修改

DCF
→ Reality Canon 不可修改
→ Canon 之上的当前解释和叙事可以修改、分支、重演
```

因此当前允许把 SillyTavern 当作**叙事交互实验场 / 活体原型**：

```text
先在现成机制上验证实际体验
↓
识别真正有价值的 Edit / Branch / Lorebook 等语法
↓
再决定是否重做、部分重做，甚至是否需要重做
```

直接嵌入、扩展桥接、同源代理等都只是可能工程路径，当前不冻结。

SillyTavern 不成为 DCF 事实源，也不获得业务主权。

# 8. 游戏引擎与 Godot 的当前地位

游戏引擎进入 DCF 的研究范围，理由已经不再只是“以后可能做成完整游戏”。

本轮形成更准确的判断：

> **即使永远不把 DCF 做成传统游戏，Godot 仍可能适合作为高表现力实时 Surface Runtime。**

Godot 的结构性吸引力主要包括：

```text
Scene / Node 把位置、层级、归属变成显式结构
2D / 3D / UI / 动画处于统一场景与渲染模型
适合无限画布、空间界面、连续状态变化和高度自定义绘制
编辑器中可以直接调整场景与位置关系
独立 Scene 可以单独运行和快速验证
开发期不要求先正式部署整个 DCF
GDScript / Scene 文本结构适合 AI 高频修改
开放源码，可从脚本、插件、GDExtension 一直下钻到引擎源码
```

特别针对当前协作方式，Godot 的价值在于：

```text
用户描述画面 / 空间 / 动态意图
↓
AI 快速修改 Scene / GDScript
↓
编辑器预览 / Run Current Scene
↓
用户直接视觉验收
↓
继续修改
```

这使“视觉样片”可以成为高频设计单位，而不要求先把 UI 接进正式系统。

但当前仍然**没有决定**：

```text
DCF 正式采用 Godot
DCF 所有 UI 改用 Godot
全景沉浸交互必须使用 Godot
Godot SceneTree 成为 DCF 事实世界
嵌入式交互和环境微交互必须使用同一技术
```

当前结论是：

> **不绑定 Godot，但架构上不关闭 Godot；真正开始做高表现力 Surface 时，把它作为强候选进入运行验证。**

# 9. Surface Runtime 与 DCF Core 的边界

无论未来 Surface 使用 Web、Godot、SillyTavern 或其他 Runtime，业务边界保持不变：

```text
DCF Capability / State / Action
        ↓
Surface Contract
        ↓
可替换交互 Runtime
        ↓
用户看到和操作的世界
```

Surface 可以拥有：

```text
镜头位置
展开 / 收起
动画进度
hover / focus
缩放
临时拖拽状态
视觉选择状态
```

DCF Core 继续拥有：

```text
真实事实
Evidence
当前解释
历史解释
项目 / 人物 / 事件业务关系
Workflow 状态
AI 产物及来源
用户确认后形成的长期状态
```

最简原则：

> **Surface 可以记住“用户现在怎么看”，不能决定“世界实际上是什么”。**

如果未来 Godot 进入真实运行验证，优先保持一条薄 Surface Adapter / Contract 接缝；具体采用 HTTP、WebSocket、IPC、原生扩展或其他传输方式，当前不冻结。

---

# 10. 三种交互 Capability 的关系

三种交互 Capability 保持不变：

```text
全景沉浸交互
嵌入式交互
环境微交互
```

它们代表三种交互空间与注意力带宽，而不是三个固定控件，也不要求共享同一 Runtime。

当前可能实现形态仍然可以是：

```text
全景沉浸交互
→ Godot / Web / 自定义 Runtime / 其他高表现力 Surface

嵌入式交互
→ 浏览器 / IDE Panel / Web / Native Panel 等

环境微交互
→ 菜单栏 / 悬浮入口 / 系统级低注意力交互等
```

本轮进一步明确：

> **其余 Capability 不再承担“优先游戏化”的额外要求。**

它们只需要在自身功能定稿时选择最合适的交互方式，并保持与 Replaceable Surface 原则兼容。

---

# 11. 交互参考的证据优先级

DCF 继续优先从真实成熟产品学习，不自行发明封闭的“专业认知软件 UX”。

证据优先级：

```text
成熟成品游戏 / 成熟 AI 叙事产品的真实体验
↓
GDC / Postmortem / 设计师复盘 / 开发日志
↓
游戏设计、叙事设计、认知设计、无障碍等理论
```

当前值得保留的参考入口包括：

```text
《逆转裁判》
→ 主张、证词、矛盾、出示证据、认知推进

《弹丸论破》
→ 高密度观点碰撞、强反馈、注意力聚焦

《The Roottrees Are Dead》
→ 固定事实、人物与关系、认知参与；不直接复制其“重建未知关系”核心玩法

《The Case of the Golden Idol》 / 《Return of the Obra Dinn》
→ 外置推理、碎片观察、身份与事件重建

《Outer Wilds》
→ 知识本身推进进程、上下文恢复

《Her Story》
→ 用户主动决定查询方向并逐步展开叙事

SillyTavern
→ 可编辑、可分支、可重生成的 AI 叙事交互
```

这些名称是研究入口，不是 UI 模板清单。

# 12. 对旧固定 UI 规范的处理

`2026-08-05-DCF-叙事日历与三Surface交互规范.md` 中以下业务语义继续有效：

```text
个人叙事草稿
人工审阅
正式个人叙事
历史不可静默覆写
后续认知追加
来源穿透
```

但其中把具体 UI 形态写成“已冻结”的内容，例如：

```text
固定三列布局
固定论坛回复式结构
固定日历视觉
固定 Panel / Sidebar / 悬浮球形态
```

不再具有当前 UI 形态约束力。

当前 UI 形态以：

> **Function Hard, UI Soft + 游戏级认知交互上限 + 当前 Capability 自身需要**

为准。

# 13. 当前验收问题

一个全景沉浸交互或叙事交互候选至少应回答：

1. 用户是否主要在理解自己的问题，而不是理解 DCF 怎么操作？
2. 复杂度是否按当前注意力和认知需要逐步进入，而不是一次暴露？
3. 重要关系、矛盾、状态变化是否能被直接感知和操作？
4. 是否能外置不值得长期占用工作记忆的信息，而不替用户做掉关键判断？
5. 是否能够从重要叙事、关系和判断穿透回真实材料与形成历史？
6. Reality Canon 是否始终不可被叙事表现篡改？
7. 用户是否可以自然改变当前解释，而不需要学习内部本体论？
8. 旧解释是否继续作为历史认知存在，而不是被新版本覆盖？
9. 如果输入换成精心设计的优秀剧本，当前交互是否有潜力形成真正成立的游戏体验？
10. 删除当前完整 UI 并重做一种完全不同的表现，Capability、认知历史和业务正确性是否仍然成立？

---

# 14. 当前施工纪律

1. **Capability Registry v1 不因本轮讨论变化。**
2. **游戏级交互约束产品上限，不要求所有 Capability 游戏化。**
3. **事实节点硬，解释软。**
4. **用户可以随时改变当前故事，旧解释不得静默覆写。**
5. **前台优先让用户面对故事和意义，后台图结构不得直接转嫁为用户劳动。**
6. **纠正 AI 不是必须被包装成娱乐的核心玩法。**
7. **SillyTavern 可以作为近期叙事交互实验场，但不成为事实源。**
8. **Godot 是高表现力 Surface 的强候选，不是当前既定技术选型。**
9. **游戏引擎可以拥有视觉、空间、动画和临时交互状态，不得拥有 DCF 业务事实。**
10. **Surface Runtime 必须继续服从 Surface Contract 与 Replaceable UI。**
11. **剧本替换测试继续成立，但不要求立即解决普通日常材料的戏剧性。**
12. **下一阶段停止继续泛化交互形态，回到 15 个 Capability 逐项定稿。**
