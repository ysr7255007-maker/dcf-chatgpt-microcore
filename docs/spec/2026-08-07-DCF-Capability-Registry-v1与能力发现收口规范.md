# 1. Capability 的新判断标准：产品主权

过去的“去 DCF 测试”仍然有价值，但不能再被误解成：

> “剥掉公共设施、配方、界面以后，还剩多少独有代码？”

这会错误否定由已有基础构件组合后涌现出的真实产品。

当前正式判断改为：

> **一个候选是否形成了稳定、可命名、可进入、可操作、可独立验收的用户目的，并能够独立拥有自己的产品语义。**

这里的“产品主权”至少要求能够独立回答四个问题：

```text
1. 我服务什么稳定用户目的？
2. 我管理什么对象 / 状态 / 交互关系？
3. 用户在我这里执行什么独特行为？
4. 什么叫我做成功了？
```

如果四问能够独立成立，即使实现主要由：

```text
公共设施
+ Shared Semantic Component（共享语义组件）
+ Recipe / Profile（配方 / 配置）
+ Query Strategy（查询策略）
+ Surface（界面载体）
```

组合而成，它仍然可以是一等 Capability。

因此：

> **能力独立性 ≠ 实现独立性。**

> **代码量、独占算法数量、底层机制数量，不是 Capability 身份门禁。**

# 2. 原生能力与涌现能力地位相同

Capability 可以有两种形成方式。

## 2.1 原生能力

自身直接对应一个稳定、完整的软件问题或交互闭环，例如：

```text
证据源采集管理
多源证据编译
AI 协作审阅编辑器
约束决策助手
```

## 2.2 涌现能力

多个基础构件组合以后，形成新的稳定用户目的、交互节奏和产品身份，例如：

```text
个人叙事
项目叙事
Wiki
知识卡
语言弹药
各种第一方工作台
```

涌现能力不是“低一级能力”。

运行时：

```text
原生 Capability
=
涌现 Capability
```

二者都必须拥有稳定产品主权、自己的公开语义和独立验收。

`形成方式：原生 / 涌现` 只用于解释“为什么这个产品被单独承认”，不改变它在 World 中的地位。

# 3. 两条新的独立性证据

## 3.1 跨 Capability 保持同一身份，是独立化证据

一种业务对象若可以同时由多个 Capability 产生、消费或引用，并且跨越这些场景后仍然保持相同产品身份，它不应被永久挂在某个“父能力”下面。

例如：

```text
个人叙事 ─┐
项目叙事 ─┼→ 知识卡 / Wiki
AI 任务执行 ─┤
研究能力 ─┘
```

如果项目叙事消失，知识卡仍然成立；如果 AI 任务执行台消失，Wiki 仍然成立。

因此：

> **被多个能力共同使用但仍保持稳定业务身份，本身就是强 Capability 独立性证据。**

这也是本轮继续保留 Wiki 与知识卡独立 Capability 身份的重要理由。

---

## 3.2 高频交互可以产生产品重力

一个对象即使底层数据形态与其他产品相似，只要长期形成：

```text
高频进入
高频搜索
高频调用
高频修改
独立的信息组织
独立的操作节奏
独立的注意力入口
```

就可能形成新的稳定产品中心。

语言弹药是当前典型例子。

它的独立性不来自“文本格式特殊”，而来自：

> **用户会频繁收集、整理、寻找、调用和复用语言构件。**

因此正式原则：

> **交互语义也是业务语义；足够稳定的使用频率与交互模式可以形成独立 Capability。**

# 4. 四刀法：净化 Capability，不消灭 Capability

后续新增或定型 Capability 时，继续使用四刀审查，但目标不是问“砍完还剩多少代码”，而是问：

> **哪些责任不应该由这个 Capability 自己承担？**

四刀如下：

```text
ECS（实体组件系统）
→ 切掉关系接缝

Becsy World（运行世界）
→ 切掉运行、生命周期与大量编排接缝

Bun（一体化 JavaScript / TypeScript 运行时）
→ 切掉宿主工程接缝

Public Facility（公共设施）
→ 切掉多个能力重复支付的专业工程机制
```

四刀以后，Capability 可以变得非常薄：

```text
独特用户目的
+ 产品状态
+ 业务语义声明
+ 少量规则 / 配方
+ 专门交互
```

这不是能力被削弱，而是：

> **底层高度复用，上层产品仍然丰富。**

# 5. ECS 切线：关系复杂度黑洞

ECS 的主要价值不是“把数据放进组件”，而是吸收：

```text
谁通知谁
谁订阅谁
谁把结果交给谁
一对多 / 多对一分发
状态交接
部分等待关系
UI 贡献发现
权限 / 审核请求交接
诊断状态共享
恢复需求发现
现实验收材料交接
```

正式组合语法：

```text
Capability A
把 World 推进成某种公共语义状态
↓
Capability B
声明自己理解并需要这种状态
```

而不是：

```text
A 调 B
A 给 B 发专用消息
B 注册 A 的回调
```

核心原则：

> **上游不指定消费者；下游不指定生产者。双方围绕共同理解的世界状态和产物语义发生关系。**

> **关系不是“谁订阅谁”，而是“谁认识同一种现实”。**

ECS 的红线：

> **ECS 吃掉“谁等谁、谁通知谁、结果交给谁”；专业设施继续负责困难的事情本身到底怎么做。**

因此 ECS 不取代：

```text
大型正文 / 原件持久存储
数据库权威
证据采集可靠性
网络并发 / 限流
AI 推理
全文 / 向量检索
求解器
Agent 真实执行
大型数据传输
具体恢复算法
```

---

# 6. World 切线：运行复杂度黑洞

Becsy 不只是 ECS；World 是所有 Capability 共同参与的统一运行现实。

当前正式理解：

> **DCF 不是很多 Capability 各自运行以后再彼此协调；DCF 是一个 World，不同 Capability 是共同参与并推进这个 World 的系统。**

World 优先吸收：

```text
系统生命周期
系统启停
运行身份
组件读写约束
大量执行先后关系
坏组合启动前拒绝
统一外部操作生命周期
能力组合后的运行权威选择
```

Becsy 可以根据组件访问关系派生执行 precedence（先后约束）；Capability DAG 继续只是派生视图，不是人工第一事实。

正式公式补充为：

> **Capability 不主要通过彼此调用构成系统；它们通过声明自己理解哪些世界状态、并能把世界推进成哪些新状态，在同一个 World 中自然组合。**

World 的红线：

```text
World
≠ 长期权威数据库
≠ 大文件存储
≠ 历史认知本身
```

World 主要拥有：

> **现在正在发生什么、什么可以运行、谁拥有当前运行权威。**

长期持久层拥有：

> **历史上确实发生过什么、正式认知曾经是什么。**

---

# 7. Bun 切线：宿主工程复杂度黑洞

Bun 的角色不是定义 DCF 业务，而是尽可能吸收 JavaScript / TypeScript 宿主层已经有成熟原生能力解决的工程问题。

当前 Bun-first Host（Bun 优先宿主）原则：

> **属于宿主层的通用工程机制，如果 Bun 已稳定原生提供，默认先证明为什么不能直接使用 Bun，而不是默认再增加一层依赖。**

优先审查 Bun 是否已经提供：

```text
子进程 / Bun.spawn
HTTP / Bun.serve
WebSocket
IPC / PTY
SQLite 驱动
测试
构建
单文件可执行程序
常规文件与计时机制
```

DCF 自己应拥有：

```text
领域状态
业务语义
公共契约
验收规则
```

而不是重复拥有：

```text
ProcessManager
HTTP 框架层
WebSocket 基础层
通用 SQLite 驱动层
独立测试运行器
重复打包 / 启动脚本体系
```

Bun 只是宿主运行时，不获得 DCF 世界定义权。

# 8. Capability Registry v1

本节冻结 Capability 身份和产品主权；每项最终 Shared Semantic Component、Provider、错误语义和完整行为验收仍由 Capability Envelope 关闭。

## 8.1 证据源采集管理

形成方式：**原生能力**。

用户目的：

> **决定 DCF 观察现实的哪些窗口，以及每个窗口怎样可靠观察。**

拥有：

```text
来源发现 / 注册 / 配置
权限
启停
事件 / 轮询 / 定时 / 手动 / 按需采集
新鲜度
并发 / 限流 / 重试
游标 / 检查点
缓冲 / 背压
去重
健康 / 恢复
每个来源自己的公共证据输出语义
```

不拥有：

```text
下游消费者列表
证据业务意义解释
个人 / 项目叙事
AI 开放理解
```

产品成功：用户能可靠管理各种现实来源，并稳定看到来源健康与原始证据进入 DCF。

---

## 8.2 多源证据编译

形成方式：**原生能力**。

用户目的：

> **把已经进入 DCF 的证据按显式、可重放、确定性规则加工成不同用途的可追溯材料与产物。**

拥有：

```text
选择
分组
直通
规范化
翻译 / 替换
去噪
排序
确定性关系闭合
拆分 / 合并
输出形式
输出时机
来源映射
```

不拥有来源采集与开放语义理解。

产品成功：同一批来源证据可以稳定生成一个或多个用途明确、可回源的产物。

---

## 8.3 AI 协作审阅编辑器

形成方式：**原生交互能力**。

用户目的：

> **让人与 AI 围绕一个待审阅对象进行可追踪、可局部控制、可反复修订的共同编辑。**

典型闭环：

```text
材料
→ AI 草稿
→ 人类批注 / 局部编辑
→ AI 定向修订
→ diff
→ 接受 / 拒绝 / 再审
→ 正式版本
```

它不认识“个人叙事 / 项目叙事 / Wiki”这些业务品牌；业务 Capability 通过共享“待审阅”语义与它组合。

---

## 8.4 个人叙事

形成方式：**涌现能力**。

用户目的：

> **形成、回看和校准关于自己的长期理解，并保留不同时间点认知变化的连续历史。**

它拥有个人叙事的选择、解释、阶段、修订与回看语义。

它不拥有采集器、通用 AI 协议、数据库引擎或通用审阅器。

核心不变量：

> **后来理解只能追加，不能静默覆写过去的理解。**

---

## 8.5 项目叙事

形成方式：**涌现能力**。

用户目的：

> **让一个长期项目形成可追溯的自我理解：需求怎样变化、阶段怎样形成、决策怎样演化、版本与分支怎样关联。**

项目叙事不只是展示层；它允许 AI 主动理解、查询、递归取证与长期认知演化。

---

## 8.6 Wiki

形成方式：**涌现能力**。

用户目的：

> **维护可导航、持续演化、可跨来源与跨项目复用的长期知识空间。**

Wiki 可以是项目叙事、个人叙事、AI 任务执行与未来其他能力的附属产物来源 / 去向，但这些关系不取消它自己的产品身份。

跨 Capability 仍保持相同 Wiki 身份，是其独立性证据。

---

## 8.7 知识卡

形成方式：**涌现能力**。

用户目的：

> **捕获、形成、组织和复用小型、自包含、可引用的知识单元。**

它可以由多个 Capability 产生，也可以被多个 Capability 引用；不归属于任何单一“父产品”。

Wiki 与知识卡当前均保留独立 Capability；二者是否未来发生产品合并，只能由真实交互行为证据决定，不能因底层数据结构相似而提前合并。

---

## 8.8 语言弹药

形成方式：**高频交互驱动的涌现能力**。

用户目的：

> **高频收集、整理、寻找、修改并立即调用可复用的语言构件。**

产品主权主要来自：

```text
高频入口
高频搜索
最近使用
收藏 / 分类
快速复制 / 插入 / 调用
面向使用而不是面向阅读的组织方式
```

它可以复用认知存储与查询，但其高频交互节奏足以形成独立产品重力。

---

## 8.9 AI 工作台

形成方式：**工作台型涌现能力**。

用户目的：

> **直接实验、比较、调试和复现 AI 模型 / Provider / 工具调用行为。**

它通过正式 AI Turn Facility（AI 单轮调用公共设施）运行，不走测试后门。

产品成功：用户能够用真实正式路径观察模型、工具、结构化输出、费用 / usage、trace 与失败。

---

## 8.10 认知数据工作台

形成方式：**工作台型涌现能力**。

用户目的：

> **直接观察、查询、比较、诊断和维护自己的长期认知世界。**

它通过 Cognition Data Facility（认知数据公共设施）访问对象、修订、关系、锚点、查询与派生状态；禁止绕过公共契约直接把 SQLite 私有结构变成产品 API。

---

## 8.11 AI 任务执行台

形成方式：**工作台型 / 任务型涌现能力**。

用户目的：

> **委派、观察、控制并理解一个真实工作区中的长期 AI 工程任务。**

拥有用户可见的：

```text
目标
工作区
任务提交
进度 / 活动
权限请求
暂停 / 继续 / 取消
工件
文件变化
提交 / 测试
结果与诊断
```

底层 Agent 协议、session 可靠性与 Provider 接入归 Agent Execution Facility。

---

## 8.12 约束决策助手

形成方式：**原生问题能力**。

用户目的：

> **把开放、自然语言的选择问题转成闭合约束，并用确定性求解得到可验证的可行、冲突或最优结果。**

基本闭环：

```text
开放问题 / 历史材料
→ AI 编译约束
→ 求解器
→ 确定结果
→ 回到用户判断
```

AI 负责理解与编译开放问题；求解器负责闭合世界中的确定保证。

---

## 8.13 全景沉浸交互

形成方式：**原生交互能力**。

旧 Surface 名称：`能力主页`。

用户目的：

> **当用户主动把主要注意力交给 DCF 时，自动发现、归纳整个能力世界，并提供最高带宽的完整理解与操作空间。**

它主动：

```text
发现 Capability
收集公开状态 / 健康 / 产物 / 可执行动作
分类 / 归纳 / 组织
形成统一“能力交互投影”
提供浏览 / 搜索 / 进入 / 配置 / 管理 / 操作 / 诊断
```

它的公共产物不是“主页 DOM”，而是可被其他交互能力消费的：

> **能力交互投影。**

主页只是当前最自然的 Surface 实现。

---

## 8.14 嵌入式交互

形成方式：**原生交互能力**。

旧 Surface 名称：`上下文侧边栏`。

用户目的：

> **不要求用户离开当前宿主环境，把 DCF 的一部分信息与操作能力嵌入其他工作空间，与原工作并存。**

它优先消费“能力交互投影”，再按：

```text
用户固定配置
手动钉住
当前任务
当前项目
上下文匹配
其他筛选策略
```

选择需要的部分。

“上下文相关”只是可选筛选策略，不是 Capability 定义。

侧边栏、IDE 面板、浏览器面板、浮动嵌入区等都只是 Surface。

---

## 8.15 环境微交互

形成方式：**原生交互能力**。

旧 Surface 名称：`环境悬浮球`。

用户目的：

> **让 DCF 在不占据工作空间的情况下长期存在于环境中，用极小信息量和极短操作路径承载最重要的状态与动作。**

它优先消费“能力交互投影”，执行强压缩：

```text
重要度筛选
紧迫性筛选
是否需要用户介入
能否压缩成微信号
允许的极短操作
```

典型输出可以只是：

```text
状态点
图标变化
数字角标
极短文字
```

典型操作：

```text
允许 / 拒绝
暂停 / 继续
打开
忽略
```

悬浮球、菜单栏图标等都只是 Surface。

---

# 9. 三种交互能力形成稳定交互生态位

三者不是三个偶然 UI，而是 DCF 与用户之间三种稳定交互方式：

| Capability | DCF 占用的交互空间 | 信息 / 操作带宽 | 用户注意力 |
| --- | --- | --- | --- |
| 全景沉浸交互 | 主要 / 完整空间 | 最高 | 主动、高 |
| 嵌入式交互 | 与其他工作空间并存 | 中等 | 部分 |
| 环境微交互 | 不占工作空间，只存在于环境 | 极低但关键 | 边缘 |

可以理解为：

```text
完整注意力
↓
全景沉浸交互
↓
部分注意力
↓
嵌入式交互
↓
边缘注意力
↓
环境微交互
```

随着用户愿意支付的注意力下降：

> **信息压缩率提高，操作数量减少，但留下的动作更强调当前重要性。**

业务 Capability 不应分别为主页、侧边栏、悬浮球设计三套专用 API。

优先方式：

```text
业务 Capability
声明“当前有哪些值得用户知道和操作的业务语义”
↓
全景沉浸交互
形成统一能力交互投影
↓
嵌入式交互 / 环境微交互
按自己的交互带宽进行选择、压缩和操作暴露
```

这样不仅吸收展示注册接缝，也吸收操作入口的重复适配。

---

# 10. 暂缓候选：现实闭环行动

现实闭环行动是当前讨论最少、但潜在边界最广的候选。

已知它会同时触及：

```text
执行者选择
权限
风险
副作用
现实观察
效果定义
现实验收
失败语义
部分成功
回滚 / 补偿
人工介入
因果归属
多步长任务
```

当前已有 E5 只冻结一个长期不变量：

> **Agent 执行状态 ≠ 现实成立。Agent 负责劳动；现实负责验收。**

但这不足以关闭“现实闭环行动”完整 Capability 边界。

因此当前状态正式记录为：

```text
DISCOVERY_DEFERRED
```

含义：

```text
保留问题方向
不否定未来 Capability 身份
不冻结当前名称
不冻结完整产品边界
不冻结 Reality Verifier 是否独立 Public Facility
不进入当前 Envelope / 施工队列
```

未来只有出现足够真实行动需求与行为证据时才重新打开 Discovery。

---

# 11. Capability Discovery 正式关闭

当前开放式 Discovery 关闭，不再以“还能不能想到新能力”为下一阶段任务。

未来新增 Capability 必须出现新的真实产品目的，并重新通过门禁：

```text
稳定用户目的
产品主权四问
独立验收
与已有 Capability 的身份差异
四刀净化后的职责边界
```

新增 Recipe、Query Strategy、Provider、Shared Semantic Component 或 Surface，不得自动升级为新 Capability。

同时：

> **可以由已有能力组合出来，也不得自动降级为“不是 Capability”。**

最终判断仍是产品主权。

---

# 12. Registry 状态与 Envelope 状态必须分离

进入 Capability Registry v1 只代表：

> **产品身份已经被承认。**

不代表：

```text
最终设计已关闭
组件字段已冻结
Provider 已实现
Standalone World 已通过
Composite World 已通过
完整功能已验收
```

后续状态至少区分：

```text
REGISTERED
ENVELOPE_NOT_CLOSED
ENVELOPE_CLOSED
STANDALONE_PASS
READY_FOR_COMPOSITE
COMPOSITE_PASS
PASSED
```

暂缓 Discovery 使用：

```text
DISCOVERY_DEFERRED
```

因此：

> **能力已经被发现，与我们现在有资格施工它，是两回事。**

---

# 13. 下一阶段：逐项关闭 Capability Envelope

Capability Discovery 收口后，正确顺序改为：

```text
Capability Registry v1
↓
选择一个已登记 Capability
↓
关闭 Capability Envelope
↓
冻结需要 / 提供的共享语义
↓
冻结 Public Facility 依赖与 Provider / fallback 规则
↓
冻结用户可观察行为与失败语义
↓
Standalone World 验收
↓
Composite World 兼容验收
↓
正式施工与行为验收
```

不再重新画一张人工 Capability DAG 决定施工关系。

Composer（组合器）与 Becsy World 应从各 Capability 的真实声明中派生：

```text
谁能提供什么
谁需要什么
哪些 provider 缺失
哪些语义不兼容
哪里有重复运行权威
自然形成的能力关系图
```

---

# 14. 当前最高层公式

本轮收口后，DCF 当前架构可以压缩为：

> **Capability = 用户目的与产品主权。**

> **Public Facility = 被多个 Capability 重复支付的专业工程机制。**

> **ECS = 共享语义与关系接缝吸收结构。**

> **World = 统一运行现实与运行接缝吸收结构。**

> **Bun = 宿主工程接缝吸收结构。**

> **原生能力与涌现能力运行地位相同。**

> **四刀用于净化 Capability，不用于按实现厚度否定产品。**

> **功能空间可以持续增长，但公共机制数量、运行权威数量与接缝复杂度不应随功能数量同比增长。**
